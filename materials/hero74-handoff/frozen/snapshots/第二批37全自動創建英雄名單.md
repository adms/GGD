## 1. 本批目標與範圍

由較高能力的模型產生完整英雄參考成品，逐名至少完整審查一遍，再以 script 檢查合法性及現有工具能覆蓋的行為，供基底 12B 與微調 12B 在相同條件下比較。

一筆正式資料應包含：生成需求、英雄設定、PASSIVE／Q／W／E／R／EX 六槽、技能與機制模板、特效模板與必要資產綁定、可交付設定、驗收要求及實際測試證據。不能把六個孤立技能或一份可解析 JSON 當成完整英雄。

本批的核心特色由使用者指定：

> 技能設計要有連動組合、符合定位；整體主題以惡搞好玩、不嚴肅為主要特色。

- 本批用途是**驗證集**，不是自動加入訓練集的增補資料。題目、參考答案與衍生技能樣本均依此管理。
- 原先討論 20 名，使用者現提出 37 項。本文件完整保留 37 項；最終凍結全部 37 名或選取其中 20 名，尚未定案，不自行刪減或分配到訓練集。
- 依這次使用者名單選角，不再以「近六年動畫」排除舊作品、漫畫或都市傳說。
- 本文件只整理名單、設計方向及審查點；**未生成正式六槽設定、未執行英雄編譯或上場測試、未啟動訓練、未改動編輯器或遊戲**。
- 小模型負責文字與結構化英雄生成，不負責圖片生成、美術細修或視覺驗證。特效優先採既有模板與正確事件綁定。
- 語意正確性優先順序：英雄身分與核心特色 → 技能機制及連動 → 定位與可玩性 → 特效表現。惡搞趣味貫穿設計，但不能掩蓋機制錯誤。

## 2. 狀態與假設

- **使用者點名**：使用者明確提出人物，但採用時期、能力版本與六槽仍需另行鎖定。
- **主角提案**：使用者只提供作品或簡稱，以下人物是本次討論的預設提議，並非逐名獲得使用者確認。
- **搭檔提案**：使用者點名兩個人物；把兩者製成一名英雄是設計提案，尚未完成控制方式與計數確認。
- **待選**：沒有足夠資訊決定可操作主體，不補造為已確認人物。

所有定位、惡搞標語、技能循環均為 **GGD 改編提案**，不是原作招式名稱或引擎支援聲明。人物名的繁中譯法與別名應在來源審查時固定。

## 5. 每名完整英雄的交付與審查清單

### 5.1 題目與來源先鎖定

- [ ] 作品、人物、譯名／別名、採用時期與能力版本明確。
- [ ] 原作核心特色、使用者不可改需求、可接受的創編與降級分開記錄。
- [ ] 題目足以讓模型知道需要完成什麼，不要求它猜中未提供的私有設定。
- [ ] 先定關鍵驗收條件，再生成教師成品；不只依生成答案反向寫測試。
- [ ] 檢查與全角色清單、實際訓練檔、舊測試與其他支線成品的身分／內容重疊；清單沒列不等於沒有資料污染。
- [ ] 第 23 與第 35 項若同出 MAGI 世界，記錄共享設定；不同人物不能混併成同一身分，同一人物不同版本也不能假裝獨立盲測。

### 5.2 英雄設定完整

- [ ] 出身、背景、屬性、成長、定位、普攻、資源及必要數值完整。
- [ ] 固定公式與合法預設交給 script；需要設計判斷的內容由模型產生並審查。
- [ ] PASSIVE／Q／W／E／R／EX 全部有必要設定，不以空模板或未交代的預設值湊齊。
- [ ] 技能名稱、描述、目標、實際效果、模板及參數一致。
- [ ] 機制模板、特效模板、動作與模型等引用存在且版本匹配。

### 5.3 六槽連動、定位與趣味

- [ ] 一句話能說明英雄核心玩法，每槽能解釋它在核心玩法中的用途。
- [ ] 至少一個完整主循環及兩種情境組合，例如進攻／撤退、爆發／救援。
- [ ] 連動至少包含可驗證的條件或狀態差異，而不是「依序施放傷害更高」的泛泛說明。
- [ ] 主連招外仍有合理操作選擇，不強迫只有唯一按鍵順序。
- [ ] 被動、主動與 EX 各有職責；EX 不吞掉其他槽的所有機制。
- [ ] 代價、反制、失敗與恢復節奏成立；不能所有能力同時無代價常駐。
- [ ] 笑點至少落在一個可感受到的玩法或事件中，而非僅技能名稱搞笑。
- [ ] 原作人物本質仍可辨認，不因惡搞抹掉核心人格、能力或定位。
- [ ] 搞笑不等於亂數失控、不公平或破壞隊友遊戲體驗。

### 5.4 模型完整審查至少一次

- [ ] 逐名閱讀全部需求、背景、六槽描述與結構化設定，不能只查標題。
- [ ] 核對主角身分、同名人物、形態與時期；特別注意第 21、23、27、32、35、36、37 項。
- [ ] 逐一核對敵／友／自身／地點目標，護盾、治療、傷害、控制與資源產消。
- [ ] 沿著兩條連招追蹤狀態，確認前置條件可達成、消耗一致、退出方式存在。
- [ ] 區分原作設定、GGD 平衡改編及純笑點；未查證能力不當作已知事實。
- [ ] 寫出審查者／模型、版本、日期、發現問題與處置；不能只填「看過」。
- [ ] 有修訂則重跑受影響的審查與 script；新版本不得沿用舊版通過證據。

### 5.5 Script 與行為測試

- [ ] JSON 可解析、schema、必填、列舉、數值範圍、ID 唯一性、引用完整性通過。
- [ ] JSON 包裝與正規化流程固定；只能做允許的格式處理，不暗中補寫缺失機制或更換目標。
- [ ] 模板與能力在本次凍結的版本內，編譯後有效值與設計一致。
- [ ] 正向案例：前置完成後確實出現預期效果。
- [ ] 反向案例：前置未完成、無效目標、資源不足時不誤觸發。
- [ ] 邊界案例：打斷、過期、死亡、重複命中、換形態、撤除召喚物後正確清理。
- [ ] 跨槽案例：兩條指定組合的狀態轉移、消耗與最終結果可重現。
- [ ] 隨機英雄固定種子，並檢查多組種子與效果上限；不挑有利一次當結論。
- [ ] 保存原始輸入、輸出、執行命令、檢查器版本、時間與失敗訊息。

### 5.6 素材、匯入與上場證據

- [ ] 素材存在、可解析、已標準化、可用於此用途分開記錄；不是有模型檔就算角色完成。
- [ ] 代理模型、缺少專屬動作及待製素材明確標示，不冒充專屬素材驗收完成。
- [ ] 必要圖示、模型、動作、特效事件與資源包依賴無斷鏈。
- [ ] 施放／命中／持續／結束特效與機制事件一致；不要求小模型微調美術。
- [ ] 儲存重載、編譯、封裝／ZIP 往返、編輯器匯入各有結果。
- [ ] 要宣稱「可上場」，需另有選角與實際對局／行為驗收證據。
- [ ] 未跑的層級標示未驗證；格式合法、編譯通過與完整遊戲成功分開報告。

## 6. 驗證集使用與評分規則

1. 每名英雄分開保存：模型可見題目、允許使用的能力／模板目錄、不可見教師成品、不可見評分答案及原始證據。
2. 模型可見哪些規則或檢查器必須事先固定；基底 12B 與微調 12B 使用相同資訊、工具、輸出預算及重試／修復預算。
3. 正式比較過程不由較高能力模型逐英雄補答案；教師生成與事前審查屬資料準備，不算 12B 自動完成的一部分。
4. 主要結果按完整英雄統計：零人工補填、需求完整、機制正確、必要設定與引用完整、達成所宣稱的執行層級。
5. 同時報告六槽正確率、需求覆蓋、連動、定位、趣味與格式結果。趣味高分不能抵銷錯目標、錯機制或不合法成品。
6. 合理等效答案可通過，不以逐字複製教師答案為唯一準則；允許的等效與創編範圍在凍結前寫清楚。
7. 能力不足的正確拒絕／缺口回報另計，不算成功創建；格式修復成功也不自動等於語意正確。
8. 正式凍結前可以整理不合格題目並記錄原因；凍結後不能刪除模型失敗的難例以提高通過率。
9. 若拿這批結果調 checkpoint、提示詞或訓練資料，這批應標為開發驗證，不再宣稱是未接觸的最終盲測。
10. 同一英雄的六槽、變形、改寫需求、完整答案及衍生題不可跨訓練／盲測分區；本批目前不授權自動轉入訓練集。

## 7. 能力缺口處理

發現「描述想做的機制」與「引擎真正能執行的機制」不一致時：

- 記錄英雄編號、需求、最小重現、預期／實際行為、所用能力與版本、受影響的測試。
- 區分資料／教師錯誤、檢查器錯誤與引擎能力缺口，不混稱模型生成失敗。
- 若需向 main 回饋，先讀取目標專案當下的開票守則，再依規則建立可驗收問題；本文件不代表已開票。
- 不在本名單整理工作中自行修改引擎；不暗中把友軍保護改成自身護盾、把回溯改成回血、把資源機制改成追加傷害。
- 可以提出明示的替代設計，但需確認仍符合需求並取得必要同意，不能把降級版本標成原需求已完成。
