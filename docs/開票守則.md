# 開票守則（Ticket Authoring Standard）

> 這是一套可以直接抄走的開票（issue authoring）規格：**五件必填、內文六節＋三節建議、
> 三層自動化、六條進階心得，以及一頁可複製的模板全文**。
> 它不是理論 —— 來自一個真實專案在同一天回補 150+ 張票、寫出 scaffold 與 lint 的實戰。
> 正文只用任何軟體專案都懂的語言；原專案的實例放在「📦 案例」框裡當佐證，可以整框跳過。

---

## 一、為什麼要有開票規格

### 1.1 沒有證據標準的「做完」，會變成謊話

一張票最危險的字是「done / 做完 / 已修」。如果票上沒有寫下**什麼證據算做完**，
這個詞會自動退化成「**我的工作鏈完成了**」（commit 了、測試綠了）——
而不是「**使用者可觀測的結果被證明了**」。兩者的差距，就是回報者與使用者之間的謊言：
回報的人不覺得自己在說謊，使用者卻拿不到任何東西。

> 📦 **案例**：原專案有一支畫面特效，事件鏈全部接通、四條相關測試全綠、
> release note 寫了「已修」—— 而玩家畫面上是 **0 個亮像素**。四條測試全部驗在
> 中間節點（事件有送、資料有到），沒有一條驗在終點（畫面有亮）。
> 根因之一：**票上從來沒有寫「驗收 = 使用者看得到」**，於是每個人都用自己方便的
> 定義宣告完成。

驗收標準（acceptance criteria）就是把「做完」從一個形容詞變成一張檢查表。
這是整套規格存在的第一個理由。

### 1.2 票是專案唯一可靠的長期記憶

- 對人類團隊：人會換手、離職、放假；三個月後接手的人**只讀得到票的內文**。
- 對 AI 協作：對話 context 會斷；下一輪讀得到的也只有票。

「為什麼選這條路」「哪些前提查證過」如果只存在當時的討論或某人腦中，等於不存在。
所以票不只記「要做什麼」，還要記**思考策略**（為什麼這樣解）與**解決模板**（套哪個
驗證過的形狀）—— 這兩件是傳統 issue 模板最常漏掉、事後最貴的部分。

### 1.3 規格必須配自動化，否則只是散文

「開票要記得寫驗收標準」這種話寫進 CONTRIBUTING 之後，沒有人會在開票的當下重讀它。
**判準（要記得……）會失效；閘（會警告、會變紅的程式）不會。**
所以本守則的每一條都配一個 script 形狀（§四）：產生半（scaffold）把遵守的成本壓到
接近零，檢查半（lint）讓違反的時候有東西出聲。

## 二、五件必填

| # | 件 | 住哪 | 一句話理由 |
|---|---|---|---|
| ① | 優先級 tag | ⭐ **標題** | 排序的人掃的是標題列表 |
| ② | 類型 tag | ⭐ **標題** | 一眼分「壞了要修」與「新東西」；`[breaking change]` 是部署節奏訊號 |
| ③ | 驗收標準（acceptance criteria） | 內文 | 「做完」需要證據標準（§1.1） |
| ④ | [思考策略]（thinking strategy） | 內文 | 讓下一個讀者不必重新推導「為什麼這條路」 |
| ⑤ | [解決模板]（solution template） | 內文 | 抄驗證過的形狀，不逐張重新發明 |

### ① 優先級 tag —— 放在標題，「不急」也要明說

`[緊急]` / `[重要]` / `[優先]` / `[一般]`（或你們慣用的 P0–P3）。兩條鐵則：

- **一定在標題**。負責排序的人（PM、tech lead、on-call）掃的是票的**標題列表**；
  tag 寫在內文等於沒有 —— 他要逐張點開才知道哪張先做。
- **都不是也要明說 `[一般]`，⛔ 不是省略**。省略的票讀起來是「還沒分類」，
  與「分類過了、不急」無法區分 —— 而這兩者該有完全不同的處理。

```
✅ [緊急][fix] 結帳 API 回 500，所有付款被擋
❌ 結帳有點問題          ← 要不要現在處理？點進去才知道 = 排序成本轉嫁給每個讀的人
```

### ② 類型 tag —— 也放在標題

`[breaking change]` / `[fix]` / `[improve]` / `[feature]`
（依專案慣例也收 `refactor` / `perf` / `docs` / `test` / `chore` / `infra`）。

為什麼值得占標題的字數：

- **[fix] vs [feature]** 是完全不同的心智模式 —— 前者有一個「曾經對過的行為」可以釘迴歸，
  後者沒有。讀票的人第一眼就該知道自己在讀哪一種。
- **[breaking change] 是部署節奏的訊號**，不是描述：它意味著不能熱更新、可能要資料遷移、
  要公告、回滾路徑要先想好。這個訊號藏在內文，就會在部署的當下被漏掉。

```
✅ [重要][breaking change] 使用者 ID 由 int 改為 UUID
❌ （票的內文最後一行）「順帶一提，這會改到 DB schema」   ← 部署的人不會讀到那行
```

### ③ 驗收標準 —— 寫「使用者可觀測的終點」，不是內部鏈路

好的驗收標準有一個判別法：**一個沒參與開發的人，照著它做一遍，能得到「過／不過」。**

```
✅ 匯出鈕按下後 3 秒內下載到 CSV，列數等於畫面上的筆數；資料為空時顯示提示而非空檔
❌ 匯出功能正常運作        ← 什麼叫正常？誰驗？怎麼驗？
❌ export() 回傳正確結果    ← 這是中間節點；函式對了、按鈕沒接上，使用者照樣拿不到
```

⚠️ 最常見的走樣是把驗收寫在**方便驗的地方**（單元測試綠）而不是**該驗的地方**
（使用者看得到）。§1.1 的案例就是這樣死的：四條「方便驗」全綠，終點零像素。

### ④ [思考策略] —— 這張票用哪種思考方式解

一行，寫這張票打算用的**思考形狀**。價值在於：接手的人（或三個月後的自己）不必從頭
推導「為什麼是這條路」，而且策略本身可以預測失敗模式（§五-③）。

策略目錄其實很小（§五-①）。以下是通用化的常見八種，任何專案都用得上：

| 策略 | 一句話 |
|---|---|
| 盤點→按解鎖數排序 | 先數每個缺口擋住幾件事，先做解鎖最多的機制，⛔ 不逐件實作 |
| 量到再說 | 先量測拿到數字，再決定動不動手；猜測不進票 |
| 五層根因 | 缺陷本身→守衛為何沒抓→為何回報做完→防線的洞→為何前兩者長得一樣 |
| 兩個名詞的關係 | 故障常在 A 與 B 的**配對**上；分別驗 A、驗 B 各自都綠，抓不到 |
| 閘不是判準 | 把「要記得檢查」換成一個會變紅的自動檢查 |
| 使用者看得到才算做完 | 驗收綁定終端證據，不綁中間節點 |
| 單一事實來源 | 同一個值不可以有第二個住處；有就會漂 |
| 先上線後否決 | 自己選一個預設值＋留回滾開關，不把工作卡在等裁決上 |

```
✅ [思考策略] 量到再說 —— 先在 staging 錄 1 小時 p99，再決定要不要動連線池
❌ [思考策略] 仔細分析     ← 零資訊量；佔位符跟沒寫一樣（lint 驗不出來，人要驗）
```

### ⑤ [解決模板] —— 套哪個驗證過的形狀

一行，寫這張票打算套的**解法形狀**＋它的前例（§五-②）。核心信念：
**第 N 次解同型問題時，抄第 1 次驗證過的形狀，比發明新的少踩一輪坑。**

通用化的常見模板：

| 模板 | 適用 |
|---|---|
| 設定欄位＋開關（落齊所有住處） | 任何「之後可能想改」的數值或決策 |
| 宣告式條件葉（condition leaf） | 「當 X 時額外 Y」這一族需求 —— 一個機制解一族，⛔ 不是一族 if |
| 產生器＋`--check` 閘 | 任何從單一來源推導的文件/程式碼；`--check` 逐位元組比對，過期就紅 |
| 承重守衛＋突變驗證 | 核心行為：把實作關鍵行改壞→測試要紅→改回來 |
| N 同型 = K 模板＋一張參數表 | 一批同構的項目；逐項手刻是 O(N)，模板化是 O(K) |
| 分層 HITL 審查漏斗 | 機器判不了的語意題（視覺/音訊/文案）：機器先篩，人批次終審 |
| 門面（facade）＋閘拆檔 | 大檔拆分：`export * from` 保住既有 import，新檔忘掛要有東西紅 |

```
✅ [解決模板] 產生器+--check 閘 —— 前例：#389 的 api-reference 產生器（tools/spec-gen/）
❌ 每張票貼同一句樣板     ← lint 只驗「有沒有」；樣板化會讓這一格失去存在的意義
```

## 三、內文六節模板＋三節建議

五件必填回答「這張票及不及格」；六節模板回答「內文長什麼樣」。

### 六節（必填）

**1. Objective** —— 這張票存在的目的，一句。判準：**說「不做會怎樣」，不是複述標題。**

```
✅ 使用者匯出 >10k 列時瀏覽器凍結 8 秒，客服一週收 5 件
❌ 實作匯出優化           ← 和標題一模一樣，零新資訊
```

**2. Scope** —— 包含什麼。與 Non-goals（下方）成對。

**3. Files / modules likely affected** —— ⭐ 必須**實查**（grep / ls / 開檔看過），
⛔ 不可憑標題猜。理由有兩層：

- 寫票的人被迫先看過現場 ⇒ **錯誤的前提在開票當下就現形**，不是在實作到一半時。
- 它是併行化的燃料（§五-④）：兩張票能不能同時做，就從這節算出來。

> 📦 **案例**：一批 47 張票做規格回補時逐張實查，**3 張的前提與票文不符** ——
> 一張把測試檔的目錄寫錯層；一張宣稱模組「零引用」而管線其實已經半建好；
> 一張要新增的開關其實已經存在（差點造出第二個會漂移的住處）。
> 三張都是「開票時憑印象寫」的產物，實作者若照票動工就直接踩進去。

**4. Implementation constraints** —— 這張票適用的**專案守則子集**
（例：協定欄位 append-only、產生器產物不可手改、設定值必須同時落所有住處、
決定論要求禁用 `Date.now()`……）。理由：守則全集很長，實作者不會在動工前重讀一遍；
**票攜帶適用的那幾條**，違反成本最高的知識就出現在離手最近的地方。

**5. Acceptance criteria** ——（＝五件裡的③，見 §二）。

**6. Test / verification criteria** —— 與驗收**不是同一件事**：
驗收是「什麼算做完」（契約），這一節是「**怎麼證明**」（證據計畫）——
哪支測試檔、突變哪一行、量什麼數字、畫面類的功能要什麼截圖／像素證據。
把證據計畫寫在開票時而不是收尾時，就不會出現「做完了才發現沒辦法驗」。

### 三節（建議 —— lint 只警告，不擋）

**7. Dependencies** —— 依賴哪張票／哪個機制；**沒有就寫「無」**。
明說的「無」與省略不同：前者是查過的結論，後者可能只是忘了。

**8. Non-goals** —— 明確不做什麼。三週後的讀者分不出「忘了做」與「刻意不做」——
這一節就是分辨器，也是最便宜的 scope creep 煞車。

**9. Known risks** —— 至少一條；真的沒有就寫「低」。
強迫欄位的價值在**強迫思考**：寫不出任何風險的人，多半是還沒想。

### 為什麼這三節不硬擋

被硬擋的欄位會被塞垃圾應付；建議欄位缺了只警告，讓作者自己決定。
**開票的門檻高到讓人「算了不開」，比一張缺欄的票更糟** —— 這條原則同時決定了
§四第二層「警告不擋」的設計。

## 四、三層自動化

原則：**規格只有在「遵守比不遵守便宜」時才會被遵守。** 三層各管一個時機：

### 第一層：開票 scaffold（產生半）

一個指令長出帶齊全部欄位的票。這一層**可以硬擋**（標題缺 tag 就拒絕產生）——
因為它是在幫忙，不是在攔路；被它擋下的人損失的只是重打一次標題。

```bash
# scripts/ticket-new.sh "[重要][fix] 標題" [--dry]
echo "$TITLE" | grep -qE '\[(緊急|重要|優先|一般)\]'   || { echo "⛔ 標題缺優先級 tag"; exit 1; }
echo "$TITLE" | grep -qiE '\[(breaking change|fix|improve|feature|…)\]' \
                                                        || { echo "⛔ 標題缺類型 tag"; exit 1; }
# → 產出 §六 的完整模板到暫存檔；--dry 停在草稿，否則直接建票
```

⚠️ scaffold 開出的票帶著佔位符（`<這張票存在的目的>`）——
開完要**立刻填實**，並用第三層的 lint 驗。帶著佔位符的票會通過「欄位在不在」
的檢查，所以 scaffold 的最後一行永遠要提醒這件事。

### 第二層：建立當下的警告（hook）

攔「建票」的那個動作（CLI hook、CI on issue、或 GitHub Issue Forms），
缺件逐項列出 —— **警告，⛔ 不擋（exit 0）**。

為什麼不擋：一張缺欄的票，仍然比「算了不開」好。會擋人的開票閘，
實際效果是**更少的票**，而沒被記錄的工作是最貴的工作。
警告的價值在於它出現在**還記得細節的當下** —— 這時補一行的成本最低。

### 第三層：事後 lint（檢查半）

```bash
scripts/ticket-lint.sh 669 670 …        # 逐張驗（讀 issue tracker）
scripts/ticket-lint.sh --recent 3       # 驗最近 3 天開的 open 票
scripts/ticket-lint.sh --body-file 草稿  # 開票之前先驗草稿（不碰網路）
# 離開碼：0 = 全過 · 1 = 有缺（逐張列出缺什麼）
```

兩個容易做錯的細節：

- **離線時 fail-open，但要出聲**：網路不通不可以擋人，但必須明說
  「這幾張**沒有被驗**」再跳過 —— **安靜的跳過與全過長得一模一樣**，
  而長得一樣的兩種結果必然被混用。
- lint 自己也分三層，由淺入深：

| 層 | 問什麼 | 例 |
|---|---|---|
| 1. 欄位在不在 | 格式檢查 | 標題有沒有 tag、內文有沒有六節 |
| 2. 是不是佔位符 | 內容檢查 | `<這張票存在的目的>` 還在 = 沒填 |
| 3. 前提還成不成立 | 事實回驗 | 票裡可 grep 的宣告（路徑、「零引用」）定期重查（§五-⑤） |

### 導入既有專案：回補要設截止線，而且 append-only

- 只回補 **open 票＋近期的票**；太舊的**明說不補**（原專案 owner 的裁決是
  「某票號以前的就算了」）。回補的目的是讓活著的票可用，不是考古。
- 回補鐵則三條（150+ 張實戰驗證過）：
  1. **append-only** —— 原文一字不刪不改，規格內容只**追加**在票尾；
  2. **編輯前重抓最新內文** —— ⛔ 不用開工時的快照（併行環境下別人可能改過）；
  3. **冪等標記** —— 追加段落帶一個可辨識的標題，已有者跳過，防重複追加。

## 五、六條進階心得

規格跑起來之後才看得到的東西。每一條都在 150+ 張票的回補中被驗證過。

### ① 策略／模板目錄很小 ⇒ 該是機器可讀的 catalog

實戰統計：**8 種思考策略＋10 種解決模板，蓋掉了 95% 的票。**
一個這麼小的封閉集合，不該散落在各票的自由文字裡（自由文字會漂：同一個策略
出現五種寫法，統計與檢索都失效）。正解：

- 策略與模板收進一份**機器可讀 catalog**（JSON/YAML），每項有 id；
- 票引用 id（自由文字只補「為什麼是它」那一句）；
- lint 升級成驗兩件事：(a) id 存在於 catalog；(b) **該模板宣告的必要欄位**票裡有沒有
  （例：「產生器＋check 閘」模板要求票寫出產物清單與 check 指令；
  「設定開關」模板要求票列出所有住處）。
- 新策略要進 catalog 才能被引用 —— 於是「發明一個新策略」本身自動成為一次 review。

### ② 解決模板最值錢的欄位是「前例路徑」（precedent path）

模板名只是名詞；**帶著前例路徑的模板才是可執行的知識**。
catalog 每一項都該記：第一次驗證這個形狀的票號／commit／檔案路徑。

抄一個驗過的形狀，意味著前例已經替你踩過該形狀的坑（邊界條件、與其他機制的相容、
測試怎麼寫）；發明新形狀則要把整輪坑重踩一遍。回補 150+ 張票時，footer 寫得最快、
事後被證明最準的票，全部是「指著前例抄」的那些。

### ③ 思考策略可以預測失敗模式 ⇒ 每個策略帶「已知坑」清單

同一個策略的死法高度重複。例：「使用者看得到才算做完」這個策略，
最常死在**量尺本身壞掉** —— headless 測試環境根本畫不出像素、截圖計數器讀到
上一幀的緩衝，於是「量到 0」既可能是功能壞了、也可能是量尺壞了，兩種結論相反。
所以這個策略的已知坑第一條永遠是：**先校準量尺 —— 先量一個已知亮的 control，
量不到就宣告這把尺的一切結論作廢。**

落地：catalog 裡每個策略附 known-pitfalls 清單；scaffold 在票引用該策略時，
把坑清單自動帶進票的 Known risks 節。開票的人不必記得所有坑 —— 坑跟著策略走。

### ④ Files affected 是併行化燃料

兩張票的 Files 集合不相交 ⇒ 可以同時做。這讓 **lane 柵欄（工作分配的互斥範圍）
可以從票上直接算出來**，不必人腦排程。兩個前提：

- 柵欄要**檔案級**，⛔ 不是目錄級 —— 原專案曾因「四張票都動同一個目錄」而把它們
  串行，實查後發現動的是不同檔案，白白慢了三倍。
- 這一切只在 Files 節是**實查**的才成立 —— 從猜的清單算出來的柵欄是假柵欄，
  兩條 lane 會在沒人預期的檔案上相撞。

### ⑤ 票的前提會腐爛 ⇒ lint 第三層：可 grep 的事實定期回驗

票開的當下，「X 檔在 Y 目錄」「模組 Z 零引用」「設定 W 不存在」都是真的；
一次重構之後它們翻轉，而**沒有任何訊號** —— 票不會自己變紅。

> 📦 **案例**：#348 開票 3 天後前提翻轉，無聲；實作者是踩進去之後才發現的。
> 另一批 47 張回補時逐張實查，3 張的前提已錯（§三第 3 節的案例）。

對策：票裡的事實宣告盡量寫成**機器可回驗**的形狀（完整路徑、grep pattern、數字），
讓 lint `--recent` 順手重驗；翻轉了就在票上留言標記「前提已變」，
而不是等下一個實作者用半天工時發現。

### ⑥ 類型 tag 路由驗證預算

tag 不只是分類 —— 它應該**決定這張票要花多少、花哪種驗證成本**：

| tag | 驗證預算 |
|---|---|
| `[fix]` | 迴歸測試（把那個缺陷釘住）＋一次突變驗證（把修的那行改壞→測試要紅） |
| `[feature]` 且有畫面 | **使用者可觀測證據**（截圖／像素／E2E）；⛔ 單元測試綠不算做完 |
| `[breaking change]` | 票上必須有**部署節奏聲明**：能不能熱更、要不要遷移、回滾路徑是什麼 |
| `[docs]` / `[chore]` | 一條薄守衛或零測試 —— 驗證預算要有上限，過度測試是真實成本 |

落地兩處：scaffold 按 tag 產不同的 Test / verification 骨架；
lint 按 tag 驗不同的必要欄（`[breaking change]` 缺部署聲明 ⇒ 缺件）。

## 六、一頁可抄走的模板全文

標題格式：`[優先級][類型] 一句話標題（含使用者可感的範圍）`

- 優先級：`[緊急]`（現在就處理）· `[重要]`（這一輪）· `[優先]`（排進近期）·
  `[一般]`（明說的不急 —— ⛔ 不可省略）
- 類型：`[breaking change]` · `[fix]` · `[improve]` · `[feature]` ·
  `[refactor]` · `[perf]` · `[docs]` · `[test]` · `[chore]` · `[infra]`

```markdown
## Objective
<這張票存在的目的，一句 —— 說「不做會怎樣」，不是複述標題>

## Scope
<包含什麼>

## Non-goals
<明確不做什麼 —— 防三週後分不出「忘了」與「刻意」>

## Files / modules likely affected
<實查過的路徑清單（grep/ls），⛔ 不憑標題猜>

## Dependencies
<依賴哪張票／哪個機制；沒有寫「無」>

## Implementation constraints
<適用的專案守則子集：協定相容性／決定論要求／產生檔不可手改／設定落齊所有住處…>

## Known risks
<至少一條；真的沒有寫「低」>

## Acceptance criteria（驗收標準）
<可檢查的完成條件 —— 使用者可觀測的終點；沒參與開發的人照做能得到「過／不過」>

## Test / verification criteria
<怎麼證明：哪支測試 · 突變哪一行 · 量什麼數字；畫面類要附截圖／像素證據>

---
[思考策略] <catalog id ＋ 一句為什麼是它；已知坑清單隨策略帶入 Known risks>
[解決模板] <catalog id ＋ 前例路徑（第一次驗證這個形狀的票號／commit／檔案）>
```
