## 4. 量測基礎

### 4.1 戰力法則是**三層**，只有一支函式可以算

```
stat(L) = baseStats + attr(L)·coefficient + growth·(L−1)
```

⛔ 只讀 `doc.baseStats` 會製造「魔抗只有 4 種相異值、AP 全是 0」的錯覺。
⭐ **唯一**可以算屬性的是 `championStatBase(def, stat, level, env)`（`packages/shared/src/sim/stats/attributes.ts:350`）。
複驗者從 `content/bundle.json` 重算 16 項 × 2 軸 × 74 位 × (卡面+實際) = **2,368 組值**，**mismatch = 0** —— 工具確實在呼叫出貨函式，沒有第二份公式。

| 軸 | 定義 |
|---|---|
| **初始** | `championStatBase(def, stat, 1, ENV)` |
| **每級成長** | `championStatBase(def, stat, 2) − championStatBase(def, stat, 1)` |

⚠️ 成長軸**不可以**只讀 `doc.growth` —— 三圍係數也隨等級長。實測：**73/74 位的 `ap` 成長非零**，而 119 份文件的 `growth.ap` **全部是 0**。
⚠️ 兩軸**各自**跑自己的 Jenks，⛔ 不共用界線（量綱差 15–30 倍，共用會塌成一格）。

> 🔴 **這個定義對攻速是不完整的 —— 見 §5.2 與 §8.1。** `as` 是 `ATTR_STAT_SOURCE` 裡**唯一的乘算列**，對等級是**二次式**，所以 `base(2)−base(1)` 只是 L1→L2 那一級的增量。

### 4.2 卡面值 ≠ 玩家吃到的值（`finalizeStat` 四道關卡）

順序已逐行核對 `packages/shared/src/sim/baseBonus.ts:228-245`：
**①環境倍率鏈 → ②體型倍率 `rangeScale`（只有攻擊距離）→ ③基礎加成（`+`，在倍率之後）→ ④clamp**

| 項目 | 倍率鏈 | 額外 |
|---|---|---|
| 攻擊距離 | `attackRange` ×0.6 | **再 × 體型倍率**（斷點 `1→1.0 / 2→1.2 / 3→1.3`，線性內插、兩端夾住）|
| 生命 | `maxHealth` ×4.0 | **+650**（倍率之後）|
| 魔抗 | `defense` ×1.0 × `magicResistMult` ×0.2 | — |
| 魔力回復 | ×**16** | ⚠️ 全 repo 最大的倍率 |
| 移動速度 | 近戰 ×0.8 ／ 遠程 ×0.6 | — |
| 攻速 / 防禦 / AD / AP / 魔力上限 / 生命回復 / 暴擊 | ×1.0（中性）| — |

手算佐證（三位英雄 × 7 項屬性，21 組卡面 + 21 組實際全部逐位相符）：
`godie-hjai` 生命 518 → 2722（×4 再 +650；若 +650 在倍率之前會是 3122，不是這個數）、魔抗 44.2 → 8.84、移速 5.6 → 3.36（遠程 ×0.6）、射程 8.2 → 4.92。
`rangeScale` 沒有洩漏到別的屬性：`godie-e00r` 初號機（bodyScale 1.55 → ×1.11）射程帶了 1.11，同一位的生命/魔抗/移速都沒有。

⚠️ **成長軸的實際值是「兩端各自過完四道關卡再相減」**，不是「成長 × 倍率」—— 撞到 clamp 的人成長會是 0，那才是玩家真的體感。

### 4.3 界線用 Jenks 自然斷點；三種去重模式在 **11/26 條軸**上分歧

⛔ **不用等分位**：射程有 62%（46/74）的英雄並列在 1.6，等分位的前三個切點會全部是 1.6。

Jenks 本身可信：複驗者用 Python 重寫同一支 DP，對 400 組隨機小輸入（n=6–11、k=3/4/5）做**窮舉**比對，**最大超額 = 0**；
再從 `population.rows` + `stats.*.values` 重建成員資格重跑，**16 屬性 × 2 軸 × 3 模式 = 96 組，breaks / bandCounts / n 全部逐值相符**。
另外三種可能造成錯位的形態（切點值不存在於資料中 / 切點重複造成空帶 / `round(cut,4)` 改動切點）**各 0 筆**。

> ⚠️ **一個載重的事實是錯的（我自己重量的）**：計畫書第 4.2 節、`statTiers.ts:142-143` 的註解、以及交辦簡報都寫
> 「**21 位變身態裡有 17 位的數值與本體逐位元相同**」—— 這正是預設用 `reachable-dedup` 的唯一理由。
> **在 26 個非退化軸格上與本體全同的變身態只有 1 位**（`godie-e00l` 亞瑟王-Saber）。
> 真正的數字是「中位數的變身態在 26 格裡有 **23 格**與本體同值」（最少 13，最多 26）。
> ⭐ **機制（逐屬性去重）是對的**（逐軸丟掉 9–21 位，中位 19），**但那句證據是假的**，別再引用它。

⚠️ **速度的上半段幾乎完全由變身態撐著**（as@初始極大 3/3、as@成長極大 10 位裡 9 位、ms@初始極大 2/2 都是變身態）。
→ **D5 實際上是在問：你要調的是「玩家在選人畫面看到的分布」還是「場上真的會出現的分布」？**

### 5.2 速度（攻擊速度 `as` · 移動速度 `ms`）—— **D3 就在這裡**

#### 🔴 D3：攻速天花板 4.0 —— 原分析用錯公式，結論反轉

`as` 是 `ATTR_STAT_SOURCE` 裡**唯一的乘算列**（`attributes.ts:75-84` 有整段標題「WHY ATTACK SPEED IS THE ONE MULTIPLICATIVE ROW」）：

```
as(L) = (baseStats.as + growth.as·(L−1)) × (1 + 0.02·agi(L))     ← 對 L 是二次式
```

| | **原報告（線性外推）** | **修正後（出貨公式）** |
|---|---|---|
| 第一位撞到 4.0 的等級 | L≈44.1（悟空）| **L = 32**（禮奈 `e00n`／悟空 `o00x`／皮卡丘 `o02l`／拳四郎 `u00l` 四位同時）|
| L≤49（滿 10 回合，`grantLevels` 累計 49）撞頂人數 | **7 位** | **62 / 74（84%）** |
| L=18 全場最高攻速 | 2.26 | **2.513** |
| L=25 全場最高攻速 | 2.73 | **3.236** |

**兩位複驗者各自獨立算出同一組修正值，而且都能用線性外推逐位複製出原報告的數字** —— 分歧點確定就在 `mode`（add vs mul）。

⭐ **仍然站得住的結論**：在你說的實打 5–6 回合（L≈18–25）內**沒有人碰到天花板**。
⛔ **被推翻的是那個論證**：L=25 已經到 4.0 的 **81%**（不是 68%），餘裕沒有原報告說的那麼大。
⛔ **原建議「把極大格的目標卡面值往 4 拉」現在是危險的** —— 撞頂只會更早更多。

**逐位檢查：74/74 全部合規，卡面最高 1.1667**（妙蛙花變身），離 4.0 差 3.43 倍。所以「卡面不可 >4」這條硬規則目前無人違反。

> 🔴 **根因是一行說謊的註解（第三守則）**：`attributes.ts:377-380` 的 `championStatGrowth` 檔頭寫
> 「Every row of the model is linear in level … so the exact increment is simply base(2) − base(1)」——
> **對乘算列是假的**（linear × linear = 二次）。那行註解替線性外推作證。建議開 issue（§9.3）。

#### ⚠️ 連帶：`as@成長` 這一格是**等級 1 的快照**，不是英雄身分

`base(2)−base(1)` 對乘算列只描述 L1→L2。實測 **73/74 位**的每級增量不是常數，L9→L10 的增量比 L1→L2 大 **24–32%**（皮卡丘 0.05736 → 0.07592）。

⭐ **其餘 15 項屬性完全不受影響**（每級增量相對偏差 **0.000%**）—— 這是**一格的問題，不是全表的問題**。

#### ⭐ D9：魔力回復的分帶目前**沒有意義**，要先動倍率

## 6. ⭐ 極大但沒有補償 —— 交付物③

### 6.1 🔴 現行判準**必須換掉**（D6）

你的原則：「極大是少數並且有明顯缺陷作為補償機制」。
現行判準是「任一屬性落在極大 → 檢查他有沒有任何一項落在極小」。**它在初始軸上恆為真。**

**證據**：`docs/hero-stat-tiers.json` 的 `outliers.extremeWithoutCompensation` 有 64 筆，其中
