## 零、先講一件會讓討論卡住的事

**我們已經在量 ping 和抖動，但沒有人看得到。**

`apps/client/src/net/ConnectionStats.ts` 從輸入 ack 的往返時間算 RTT
（`IntentSender` 給每個 seq 蓋送出時間，權威席位的 `lastAckSeq` 追上時量 `now − sentAt`），
用連續封包間隔的平均絕對偏差算抖動，還有一個現成的分級器：

| 等級 | 條件 |
|---|---|
| `good` | ping ≤ 60 ms **且** 抖動 ≤ 15 ms |
| `poor` | ping > 140 ms **或** 抖動 > 45 ms **或** 封包間隔 > 500 ms |
| `fair` | 中間 |

`grep -rl ConnectionStats apps/client/src/ui` → **零個檔案**。

所以現在沒有任何人（包括回報「太延遲」的玩家、包括我）知道他實際的 ping 是 40 還是 200。
**這會讓底下所有討論變成猜測**，因為 40 ms 和 200 ms 要做的事完全不同。

→ **第 0 步，做任何優化之前：把這個數字顯示出來。** 一個角落的小晶片（`98 ms · 抖動 6 ms`）
就夠了。這是零風險、半天的工作，而且它會直接告訴我們下面哪一節才是真正的瓶頸。

（附記：這是本專案標準失敗模式的第七個實例 —— 東西做好了、數字算對了、玩家看不到。
前六個：#93 煙火在地板下、#247 跳躍 77% 在畫面外、蒼月潮連段永遠算不到、
大廳公告沒有客戶端讀者、#259 語音距離模型算完就丟、#131 特效殘留。）

## 一、現在的網路架構（實際讀出來的）

```
玩家按鍵
   │
   ├─→ ① LocalPrediction（本地預測）─────────→ 立即看到  ⟵ 只涵蓋「移動」
   │
   └─→ ② room.send(INPUT) ──網路──→ 伺服器
                                      │
                                 ③ 下一個 tick 處理（30 Hz，最多等 33 ms）
                                      │
                                 ④ 廣播快照（30 Hz，與 tick 對齊）
                                      │
                              ──網路──→ 客戶端
                                      │
                                 ⑤ 插值緩衝延遲 66 ms
                                      │
                                 ⑥ 畫面
```

### 已經做對的事（不要動）

| 常數 | 值 | 為什麼是這個值 |
|---|---|---|
| `TICK_HZ` | 30 | 權威模擬步進 |
| `SNAPSHOT_HZ` | **30** | **每一個權威 tick 都廣播**。曾經是 Colyseus 預設的 20 Hz（而且是無聲的 —— `MatchRoom` 根本沒指派 `patchRate`），已修 |
| `INTERP_DELAY_MS` | **66** | 以「快照間隔」為單位訂的，不是拍腦袋的毫秒：66 / 33.33 = **1.98 個間隔**。緩衝區**從不外插**，跑過最新樣本就凍結，所以需要兩個間隔的墊子讓「一個封包遲到」不被看見。原本 100 ms（2.00 個間隔），縮到 66 是在**不減少墊子**的前提下省下 34 ms |

`LocalPrediction` 的品質也是好的：它用**同一份** shared `orderSystem` + `movementSystem` 跑一個只有本地英雄的迷你 SimWorld，
所以預測與權威**位元相同**；對帳時吸收誤差成一個以 ~100 ms 半衰期指數衰減的偏移，所以修正不會「彈跳」；
朝向刻意不插值（瞄準零延遲）。

### ⚠️ 問題的核心：預測**只涵蓋移動**

`LocalPrediction` 的檔頭寫得很清楚：`orderSystem` + `movementSystem`。就這兩個。

**沒有被預測的：**

| 動作 | 你按下去到看見反應 |
|---|---|
| 移動 | **0 ms**（預測） |
| **施放技能 Q/W/E/R/EX** | RTT + 最多 33 ms（tick 量化） |
| **普通攻擊** | 同上 |
| 命中、傷害數字、擊退 | 同上 |
| 別人的一切 | RTT + 33 ms + **66 ms 插值** |

也就是說：**走路很跟手，打架很鈍。** 而玩家對「延遲」的感受幾乎全部來自後者 ——
沒有人會抱怨走路，大家抱怨的是「我按了 Q，過一下才放」。

`ui/castFeedback.ts` 已經做了「**先預測、後修正**」——但它預測的是**拒絕理由**
（冷卻中／魔力不足／未學習），不是技能本身。按下去會立刻告訴你「為什麼不行」，
但**可以放的時候，畫面還是要等一趟往返才動**。這個不對稱很值得注意：
失敗的回饋是即時的，成功的回饋是延遲的。

## 二、延遲預算（把每一項拆開）

假設玩家在台灣、伺服器在 GCP `34.81.104.163`（asia-east1，台灣）：

| 來源 | 毫秒 | 性質 |
|---|---|---|
| 網路 RTT | **?**（未量測，見第零節） | 物理 + 路由 |
| tick 量化（輸入等下一個 tick） | 0–33，平均 **17** | 可縮，代價是 CPU |
| 伺服器處理 | < 1 | 忽略 |
| 快照對齊 | 0（快照率＝tick 率，已對齊） | 已優化 |
| **插值緩衝**（只影響**別人**） | **66** | 抗抖動，**不該無腦砍** |
| 畫面呈現 | 8–16 | 顯示器 |

**你自己的技能** ≈ RTT + 17 + 12 ≈ **RTT + 30 ms**
**別人的動作** ≈ RTT + 17 + 66 + 12 ≈ **RTT + 95 ms**

所以如果 RTT 是 30 ms（同城光纖），技能延遲約 60 ms —— 這在 MOBA 裡是**可以接受**的。
如果 RTT 是 150 ms（跨海、行動網路、Wi-Fi 干擾），技能延遲 180 ms —— **明顯鈍**。

⇒ **在量到真實 RTT 之前，我沒辦法告訴你該修哪一段。** 這就是第零節為什麼排第一。

## 三、vs all bot 的優化 —— 這一邊有一個「消滅延遲」的解，不是「減少」

### 現況：對 bot 也要繞一圈伺服器

大廳的「⚔️ 一鍵開打」走的是 `platform` → `gamelink` → game server 開房，
所以**一場只有你和 11 隻 bot 的對戰，每一次按鍵都在跨網路來回**。

（`RoomConnection.ts:233` 的 offline flow 直接 CREATE 房間，但那仍然是一個 Colyseus 房 ——
在本機開發時它在 localhost，遠端玩家連上 ggd.adms.ai 時它在雲端。）

### 方案 A ⭐：對 bot 時把模擬跑在瀏覽器裡

**這是本題最大的一塊，而且我們的架構天生就支援。**

`packages/shared` 是**決定性模擬**（30 Hz、禁用 `Math.random` / `Date.now` / 三角函數），
客戶端已經在跑它了 —— `LocalPrediction` 就是一個迷你 SimWorld。
把「迷你」換成「完整」，bot 對戰就完全不需要伺服器：

| 項目 | 現在 | 方案 A |
|---|---|---|
| 技能延遲 | RTT + 30 ms | **0** |
| 移動延遲 | 0（預測） | 0 |
| 別人（bot）的動作 | RTT + 95 ms | **0**（同一個模擬） |
| 頻寬 | 30 Hz × 12 個實體 | **0** |
| 伺服器負載 | 每場一個房 | **0** |

**要處理的三件事：**

1. **結算怎麼記帳。** 現在是 MatchRoom POST 結果回 platform。
   本機跑的話要改成「客戶端提交結果」——那可以偽造。
   對家人私服來說可接受嗎？我的建議是：**接受，但留下 replay**。
   #175 已經有「記錄 seed + 輸入，任何一場都能重播」的機制，
   而模擬是決定性的，所以伺服器可以**離線**重跑那筆 replay 驗證分數，
   不需要即時。作弊會被抓到，只是晚幾秒。
2. **CPU。** 12 個實體 + 30 隻小怪的完整模擬跑在瀏覽器主執行緒上，
   跟渲染搶時間。要量。真的太重就丟進 Web Worker（模擬是純 TS、沒有 DOM，很適合）。
3. **程式碼路徑會分岔。** 「本機模擬」和「遠端房間」兩條路，
   容易變成其中一條悄悄壞掉沒人發現（本專案的老毛病）。
   →**同一個 `SimWorld` 介面，只換傳輸層**，並且寫一條測試比對兩條路徑的結果位元相同。

**規模**：M～L。**收益**：對 bot 的延遲**歸零**，而且家人多半就是在打 bot。

### 方案 B（如果 A 太大）：對 bot 時把插值延遲關掉

bot 的動作是伺服器算的，但**沒有抖動來源**（沒有第二個人的網路）。
不過封包還是要跨網路，所以 66 ms 的墊子還是有用 —— 收益有限，不建議單獨做。

## 四、vs 玩家的優化 —— 這一邊只能「減少」，不能消滅

### 方案 C ⭐：把預測擴大到技能（樂觀施法）

**這是 vs 玩家這一側收益最大的一項。**

按下 Q 的當下，客戶端就：
- 播放前搖動畫
- 畫出地面預告圈
- 開始冷卻轉圈
- 播放施法音

然後伺服器的權威結果回來時：
- **一致** → 什麼都不用做（99% 的情況）
- **被拒絕** → 回捲：停動畫、退冷卻、播失敗音。`castFeedback` 已經有這條路了，只是現在沒有動畫要回捲

**為什麼這比縮短 RTT 值錢**：人對「按下去沒反應」的敏感度遠高於「畫面比伺服器早 50 ms」。
格鬥遊戲和 MOBA 都是這樣做的。

**風險**：回捲會被看見。所以只預測**視覺**，**絕不預測傷害**
（owner 已經裁定「投射物命中時才算傷害」，那條規則正好保護這件事）。
預測動畫、不預測結果。

**規模**：M。**要小心的**：`SIM_CAPABILITIES` 那些原語（leap / 抓取）不可以被預測 ——
位移類的錯誤預測會把角色放到錯的地方，比慢一點糟得多。

### 方案 D：插值延遲改成自適應

66 ms 是為「兩個快照間隔的墊子」訂的，對抗的是**抖動**。
`ConnectionStats` 已經在量抖動了。所以：

- 抖動 ≤ 8 ms（穩定有線）→ 1.5 個間隔 = **50 ms**（省 16 ms）
- 抖動 15–45 ms → 維持 66 ms
- 抖動 > 45 ms → 放大到 3 個間隔 = **100 ms**（寧可慢也不要凍結跳動）

**注意**：這一項要**很小心**。緩衝區從不外插，墊子不夠就會凍結，
而**凍結比延遲更難看**。要有實測的抖動分布才能調，不能憑感覺。
→ 這一項的前置是第零節。

**規模**：S。**收益**：好連線省 16 ms，壞連線**變得更能玩**（這其實才是重點）。

### 方案 E：tick 量化的一半

輸入平均等 17 ms 才被處理。提高 tick 率到 60 Hz 可以砍成 8 ms ——
但**伺服器 CPU 加倍**，而且 30 Hz 是整個模擬的決定性基礎（改它要重測所有時序）。
**不建議**。8 ms 買不到有感的改善，代價卻很大。

### 方案 F：伺服器端的延遲補償（rewind）

伺服器收到「我在 T 時刻打了他」時，把世界回捲到 T 再判定命中。
這是 FPS 的標準做法，能讓高 ping 玩家的攻擊「照他看到的算」。

**但對這個遊戲我不建議現在做**：
- 它會讓「我明明閃開了還是被打到」變成常態 —— 那比延遲更讓人生氣
- owner 已經裁定「投射物命中時才看實際情況計算傷害（例如對方看到飛過來前開了防禦提升）」，
  **rewind 與這條裁定直接衝突**
- 複雜度高，而且會動到決定性模擬的核心

### 方案 G：連線品質的呈現與降級

- 顯示 ping / 抖動晶片（＝第零節）
- `poor` 時給玩家一個**明說**的提示，而不是讓他以為遊戲很爛
- `poor` 時自動加大插值墊子（方案 D 的另一半）

**規模**：S。**收益**：期待管理。一個知道自己 180 ms 的玩家，跟一個以為遊戲很鈍的玩家，
體驗完全不同。

## 五、建議的順序

| 順序 | 項目 | 規模 | 為什麼是這個順序 |
|---|---|---|---|
| **0** | **顯示 ping / 抖動**（方案 G 的一半） | S | **沒有這個，底下每一項都是猜的。** 而且它會直接回答「遠端玩家到底是 40 ms 還是 200 ms」 |
| 1 | **樂觀施法**（方案 C） | M | vs 玩家那側收益最大，而且**同時改善 vs bot**（在方案 A 完成前的過渡） |
| 2 | **bot 對戰跑本機模擬**（方案 A） | M–L | 家人多半在打 bot，這一項讓那個情境的延遲**歸零** |
| 3 | 自適應插值 + 降級提示（方案 D + G 的另一半） | S | 要有第 0 步的實測資料才能調 |
| — | 提高 tick 率（E）、rewind（F） | — | **不建議**。E 代價不成比例；F 與 owner 的傷害結算裁定衝突 |

## 六、要 owner 拍板的三件事

1. **bot 對戰跑在瀏覽器，結算改成「客戶端提交 + 伺服器離線用 replay 驗證」，可以接受嗎？**
   這是方案 A 唯一的取捨。私服家人局我認為可以，但這是信任模型的決定，該由你下。

2. **樂觀施法的回捲會被看見（大約 1% 的情況：冷卻剛好、魔力剛好、被打斷）。**
   「偶爾看到動畫被收回」換「每一次施法都即時」，這筆交易你要嗎？
   （我認為要，但這是手感偏好。）

3. **遠端玩家的實際 ping 是多少？** 這是第 0 步要答的問題，但如果你手上已經有感覺
   （例如「用手機 4G 特別慢，接 Wi-Fi 就還好」），先講，可以省掉一輪。
