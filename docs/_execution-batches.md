## 這份檔案的使用規則

1. **相依 = 同批，沒有例外。** 兩件事碰同一份檔案，或一件需要另一件的 schema／資料，就是同一批。跨批只允許一種關係：**前批的產出被後批消費**。
2. **Lane 是檔案領域，不是主題。** 每個 lane 標明它**獨佔哪些路徑**，lane 之間不共用任何一個檔案。批內若有先後（例如 B 要等 A 的常數），會在描述裡寫明。
3. **排序依據是「玩家按下去會不會覺得被騙」**。唯一的例外是**衛生工作解鎖整個叢集**時（單一寫者、產生器、活頁報表），那種會被提到最前面。
4. **規模**：S ≤ 半天 · M ≈ 1–2 天 · L ≈ 3–5 天 · XL = 自成一波。
5. 每批收工，回寫 `docs/_requirements-audit-gaps.md`、三張活頁、以及本檔的〈附錄：已驗證完成〉。

**沒有價格 = 免費，兩邊都是**：client `lockStateOf` 看到 `price === undefined` 回 `"free"`；server `wallet.OwnsChampion` 看到 `!priced` 直接回 `true`。後果有兩個，第二個比第一個嚴重：

1. 換進來的 10 個本體完全跳過 300 水晶解鎖 → 免費英雄 **12 → 19**、水晶去化池 **38 → 31**。
2. `FreeChampions()` 用 `price == 0` 種新帳號的 `OwnedChampions`，所以**每一個新註冊的帳號都還在被贈送 `godie-h020` / `godie-o00x` / `godie-u01u`** —— 三個現在根本選不到的 id。大廳商店也照樣為這 10 個孤兒各畫一列死掉的商品。

**修法：形狀原封不動。** 每個換進來的本體**繼承它取代的變身態的價位**，10 個舊 id 移除。前 / 壞掉 / 修好 = `12 免費 · 38 付費` → `19 · 31` → `12 · 38`，價格一律 300。owner 已明講藍水晶不動（「藍水晶本來就是獎勵 有人抱怨我們再來改」），所以移動的只有 id，不是數字。副作用：免費那 3 格從變身態換成本體，所以現在免費的是莉娜因巴斯 / 悟空 / 索隆本人。

**守衛（這比修本身重要）**：`TestStarterRosterMatchesChampionPrices`（Go，`whitelist-store-prices`）＋ game-server 的 `curationVsContentModel.test.ts` 鏡像檢查。兩個方向都驗，而且**失敗訊息直接列出漂掉的 id**，不是只報數量。連 `12 / 38` 的形狀也一起釘住，下一個動名冊的人會被逼著明講他要改經濟。

### 最愛（favourites）：選擇「讀取時過濾」而不是資料遷移

`ToggleFavourite` 本來就擋不存在的英雄，所以**寫不進**壞資料；壞掉的方式是名冊在合法的 pin 底下被換走。改在 `overlayMeta` → `liveFavourites` 過濾（`apps/platform/internal/wallet/meta.go`）。

選它不選遷移的理由：遷移要**永久刪掉**耐久紀錄裡的那筆，而英雄是會回來的（白名單可編輯、#119 之後變身態也可能重新可選）；過濾是冪等的、不需要遷移步驟、不會弄丟一筆之後會再度合法的 pin，而且掛在所有介面都會經過的那一條讀取路徑上。空 catalog（平台沒掛 content 也會開機）**不當成證據**，原樣放行，否則一個設定錯誤就會清空所有人的置頂。測試：`TestFavouritesDropChampionsTheCatalogLost`。

## 三個結構性發現（2026-07-26，來自 #247 / 抓取系普查）

這三個都不是「某支技能修好了」，而是「我們一直用錯了一把尺」。

### 1. 垂直軸一直用錯尺 —— 一直有兩把

#247 用平面匯入尺 `GGD_PER_WC3 = 11/600` 去換算 `SetUnitFlyHeightBJ` 的振幅。但**平面尺是由場地幾何決定的**（763 → 14.00u，正確）；**垂直尺是由鏡頭決定的**，而 GGD 的鏡頭不是 WC3 的（WC3 約 30° / 1650u / ~70° fov；GGD 68° / 10u / 0.8 rad）。

解「離鏡頭目標多高還留在視錐內」：WC3 約 950 單位頂空，GGD 只有 5.51u → **每 1 GGD 單位 ≈ 172 WC3 單位，不是 54.5**。平面尺把每條弧在畫面上放大了約 3.2 倍，蒼月潮 77% 的飛行時間在畫面外。

新增 `GGD_APEX_PER_WC3 = 1/250` 與獨立的 `wc3h` 單位。階層完全保留（1000>600>400>300>250 → 4.00>2.40>1.60>1.20>1.00），而且查證到 A0RZ（A=1000）**在 WC3 自己的頂空之外**，也就是那條弧在原作裡本來就會探出畫面——`1/250` 就是選來讓剛好只有那一條也還是會探出去。

**刻意不加執行期 clamp 或 zod `.max()`**：靜默夾限才是忠實匯入規則真正禁止的東西；紅色測試才是「知情地抬高守衛」的機制。

### 2. 地圖本來就有共用的位移引擎

`Set_Move_Value(unit, Distance, Angle)`，`war3map.j:4785`，區段標題「**共同擊退觸發**」。`Move_Func`（j:4745-4783）0.04 秒週期、每 tick 走 50 wc3；**實際位移 < 10 wc3 就判定撞牆**——彈回、生 ThunderClap、砸掉 150 內可破壞物、中止。

散落在各技能裡的碰撞判定（大熊 `>8` j:51210、Berserker `>=5` j:52127、皇者 `>8` j:54373）**是這個函式的複製變體，門檻不同是抄寫失誤而不是設計**。

意義：抓取系的拋出階段**要移植這個原語，不要自己發明**；`collisionEps` 統一成引擎自己的 10 wc3。而且原作分層很清楚——**地面走 `Set_Move_Value`、空中走 `SetUnitFlyHeightBJ`，沒有任何抓取 trigger 自己寫位移數學**。這也要重新檢視 `SIM_CAPABILITIES.knockback` 那條「刻意不提供」。

### 3. 施法時算死 vs 落地才算 —— 一整類的時序錯誤

蒼月潮的連段加成實作了、測試綠了、**在真實遊戲裡永遠不會生效**。

JASS 在 `Trig_Jump_Start_Actions`（j:34211-34216）就把 `+5×敏捷` 加進 `udg_MoonDamage`，41 tick 的弧線跑完後落地發的是**早就凍結的數字**。所以 1 秒的連段視窗在飛行途中過期，在 WC3 裡無所謂。

GGD 反過來，`comboBonus` 在**傷害套用當下**才解算，而那是在**落地**——飛行 1.435 秒 > 視窗 1.00 秒，**任何時序都算不到**。

之前的測試會過，是因為它**在隔離環境測效果，沒有真的飛完整條弧**。這是「完成宣告要問這條觸發在正常一場遊戲裡真的會發生嗎」的又一次。要當成一個**類別**掃：任何施法與結算之間有時間差的效果（跳躍、飛彈、延遲 AoE、引導），只要它的傷害項是條件式的，都可能有同一個病。

## 傷害結算時機：一條標準規則（owner 2026-07-26）

**關於「施法這個動作」的條件 → 施法當下判定。**
**傷害的量值與減免 → 命中當下計算。**

owner 的原話：「通常攻擊與技能都是命中時才看實際情況計算傷害（例如對方看到飛過來前開了防禦提升等）」。

兩者不衝突，因為它們問的是不同的問題：

| | 何時 | 依據 |
|---|---|---|
| 蒼月潮 07-03 的連段視窗 | **施法當下** | 條件是「在者、皆、陣發動後 1 秒內**施展**」——問的是按鍵那一刻。飛行 1.435 秒 > 視窗 1.00 秒，在命中時問永遠是「否」，所以那是 bug（已修，`bakeCastTimeConditionals`） |
| AD/AP 係數、目標的護甲/魔抗/護盾 | **命中當下** | 攻守雙方在飛行途中做的事都應該算數 |

### 這代表 9 條技能刻意不忠於 JASS

原作在施法時就用 `GetHeroStatBJ` 把係數讀死，GGD 讓它到命中才讀，所以施法者在飛行途中被削弱時，投射物會跟著變弱。**這是 owner 知情的選擇，不是遺漏。**

受影響：`godie-hapm.w`、`godie-hart.w`、`godie-u00n.r`、`godie-u00o.r`（onLand）；`godie-u00n.e`、`godie-u010.e`、`sela.q`、`thorne.e`、`augments/storm-arrow`（onHit）。

**下一輪「JASS 為準」的稽核不要把這 9 條當成 bug 修回去。** 已登記在 `docs/todo/abilities.md` 的 `jass-247-14`。
