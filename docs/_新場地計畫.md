## 🥇 這份計畫在防的那件事

owner 2026-08-14 逐字：

```
If a map looks impressive but is difficult to memorize, simplify it.
If removing a room does not harm gameplay, remove the room.
If verticality can be background scenery, make it background scenery.
The player should fight other players, not the map.
```

⚠️ 他點名這是 AI 的通病：**「你說『無限城』，它就真的給你做一座無限城；
你說『納薩力克』，它可能給你做七層地下城。」**

我們要的是 **「24×18 格的小型 GGD 競技場，只是**看起來**像無限城」**。
巨大感一律用**不可進入的背景**（無數樓梯、倒掛建築、深淵）偽造。

⭐ 而且核心交付物**不是一張地圖，是一台機器** —— 七張圖只是套四個 template 之一。

## 🚦 要 owner 決定的五件事

只列**不同答案會改變工作量**的。其餘照守則我自己決定。

### Q1 ⭐ 最大的分岔：一張 anime map 是「一個對戰分區」還是「整場共用一張」？

今天一張場地跑 **2 個對戰分區**，同時兩場互不可見的 3v3（4 隊 → zone 0 與 zone 1）。

| 選項 | 後果 |
|---|---|
| **一張圖 = 一個對戰分區** | 一回合需要兩份（或兩張圖）。既有模型不動。 |
| **整場共用一張圖** | `PairedDuels` 配對、#67「小地圖只顯示自己那區」、以及「zone＝隔離分區」**整個模型都要重做** |

⚠️ **工作量差 2–3 倍**，而且它決定風險 7.8 那個 crash 會不會發生。

### Q2 方形地圖上的火圈／殭屍波／治療花怎麼辦？

三者今天都吃「圓形分區半徑」。

- **(a)** 用內接圓 —— 零改動，但火圈會咬到牆外死角
- **(b)** 這張圖**關掉**火圈與殭屍波，改用 6–10 個互動點當節奏來源
- **(c)** 做矩形收縮的火圈 —— 新機制

⭐ **建議 (b) 當預設、(a) 當後備，做成一格後台開關**（第〇·六守則：不能停就做成開關，
高層級預設 on）。

### Q3 ⭐ `tileSize` 是多少？（1 格 = 幾個世界單位）

| tileSize | 24×18 換算 | 後果 |
|---:|---|---|
| **2** | 48×36 世界單位 | 跟今天的對戰場同尺度 → **全部 90 支技能的射程與 AoE 級距都不用重算**，橫越時間剛好 12–20 秒 |
| 3–4 | 72×54 ～ 96×72 | `aoeTiers` 的 6.0/8.0、火圈的 Zod 上界、**每一支技能的射程**都要重新校準 |

⚠️ **這一格數字決定要不要重調全部 90 支技能。⭐ 建議 2。**

### Q4 牆要不要擋投射物與視野？

今天 `ProjectileSystem.ts:135-137` **完全不看 obstacles**，也沒有視野系統；
`rayVsSegment`（`intersect.ts:112`）原語寫好了但**零生產呼叫者**。

有瓶頸卻不擋彈，躲在牆後照樣被打，玩起來會怪；但擋彈是**靈魂層大改**，
會影響全部投射型技能的手感與所有既有錄影。

⭐ **建議先不做，Phase 3 的 graybox 實測之後再決定。**

### Q5 owner 想微調一堵牆時，改哪裡？

本設計主張：改 `content/maps/map.*.json` → 跑 `pnpm map:gen`。
⛔ 後台**不提供**地圖幾何的覆蓋層編輯 —— 因為後台存檔**不會**觸發產生器，
override 的 MapConfig 會與線上實際載入的 `arena@1` **靜默分岔**，
那正是記憶 `ggd-admin-override-shadows-content` 的最壞版本。
後台只給**規格數字頁**（可調）與**驗證器報告頁**（唯讀）。

⚠️ 若 owner 期待「在後台拖一堵牆就生效」，那要把產生器搬進 content-api 當線上服務 ——
另一個量級，而且會把 `--check` 這個閘打掉。**請確認前者可以接受。**

## 一、好消息：牆早就有了

最大的意外是**靜態碰撞不是新能力**。

### ✅ 已經存在（比預期多）

| 能力 | 位置 | 備註 |
|---|---|---|
| 障礙物（圓 + 線段） | `sim/world/ArenaDef.ts:9-22` | `arena.castle` 每個分區真的有 2 條線段在出貨 |
| 撞牆滑行 collide-and-slide | `sim/collision/resolve.ts:69-90` | 整步 → relax → 取切向 → relax |
| 落點合法化 | `movement/leap.ts:157` → `relaxBody` | leap 與 blink **共用一條規則**（`blink.ts:26-31` 明文禁止第二份） |
| doc→sim 幾何投影 | `arenaDefFromDoc()` | **伺服器與客戶端共用同一支** —— 幾何一致性的唯一保證 |
| 幾何**不上線** | `ArenaDef.ts:141-152` | 只送 `mapId` 字串，客戶端自己重建 ⇒ **新幾何的 wire 成本 = 0** |
| 每回合換圖 | `pickRoundArena` + `arenaSelect.ts` | 用獨立 `hash32`，**刻意不動 `world.rng`**（task #145） |
| 產生器工程慣例 | `tools/skill-remake/`、`tools/voxel-gen/` | 四段式（表 → `--check` → 產物橫幅 → spawnSync 讀 `r.status`）已是成熟樣板 |
| 編輯器 3D 預覽 | `apps/editor/src/preview3d/ArenaPanel.tsx` | 已會畫分區圓盤、紅色障礙物、spawn 標記 |

### ❌ 必須新建（誠實清單）

| 缺什麼 | 現況真相 | 成本 |
|---|---|---|
| **導航圖** | **完全不存在**。全 repo 掃 `navmesh/pathfind/flowfield/astar/waypoint` **零命中** | 大 —— 見下方烘焙式 next-hop |
| **繞過牆走** | `avoid.ts:57` 明確 `if (ob.kind !== "circle") continue;` **跳過線段**。垂直撞牆時切向為 0 → **原地卡死** | 中，關鍵風險點 |
| 矩形邊界 | `boundaryRadius` 是圓、`clampToBoundary` 是徑向。24×18 **沒有型別可表達** | 中，會擴散到 5 個衍生系統 |
| 盒狀（有厚度）障礙物 | 只有零厚度線段 | 小（一個 union 成員 + 7 個消費點） |
| 命名區域 | 不存在任何「命名區域」型別 | 小（烘焙 tile grid + O(1) 查表） |
| 互動點 | 不存在通用機制。花／復活圈／守衛塔各自硬寫 | 中 |
| 可開關的幾何（gate） | 不存在 | 中 |
| 靜態 broad phase | obstacles **不在** `SpatialHash` 裡（`SimWorld.ts:539` 只塞 transform） | 小～中，見 7.4 —— 合併之後**未必需要** |

### ⛔ 一句話結論

> **牆本身不是新能力，「繞過牆走」才是。**

今天撞到牆會沿牆滑，但**走不到牆的另一側** —— 而 CENTRAL_RING 本質上就是一張
「必須繞牆走」的圖。目前對「卡牆」的對策不是路徑規劃，是**搶方向盤**：
`OrderSystem.ts:77-107 updateWalkStall` 卡滿 30 tick 後自動接敵接管（GH#216）。
註解記錄的實測：一次右鍵撞 r1.8 柱子讓 Saber `|v|=0.00` 持續 **2,240 tick**。

### ⭐ 而且尺度剛好

今天對戰分區半徑 24（直徑 48）、`BASE_MOVE_SPEED = 6` → 橫越 8 秒。
若 `tileSize = 2`，24×18 = **48×36 世界單位**，加上必須繞行，實際路徑 72–120 單位
→ **12–20 秒完全落在 owner 的規格內**。

⇒ 小地圖規格**不需要重算任何技能射程或 AoE 級距**。（這就是 Q3。）

## 二、術語衝突 —— 最容易釀成災難的一項

owner 說的「4–6 個 zone」與 codebase 的 `zone` 是**相反的東西**。

| 詞 | codebase 裡的意思 | owner 規格裡的意思 |
|---|---|---|
| `zone` | **一場獨立的 3v3 對戰實例**。它是**隔離分區**：zone 0 的單位對 zone 1 看不到、打不到、治不到、仇恨不到、復活不到。每一個空間查詢都在 filter 它（`GuardianSystem.ts:437`、`FlowerSystem.ts:54`、`MobSystem.ts:185`、`revive.ts:149`）。而且它**走 wire**（`EntityState.zone: uint8`） | 同一張地圖裡的 **4–6 個命名區域**（琵琶廳／紙走廊／中庭／倒置房／月台） |

### ⛔ 如果搞混，會同時發生五件事，而且一條測試都不會紅

1. `pairTeams` 只用 index 0/1（`PairedDuels.ts:135-139`）→ 區域 2–5 **永遠不會有人打架**
2. `activeZones()`（`MatchController.ts:1920`）會武裝 **5 座守衛塔、5 條花排程、5 條殭屍流**
3. `maxAlivePerZone`（第 10 回合前 15→50）**直接 ×5**
4. #67 的小地圖只畫玩家所在那一格 → 玩家**只看得到 1/5 張圖**
5. 火圈變成 **5 個同心圓**（`fireRing.ts:1152` 逐 zone）

### ⭐ 建議命名（寫進 schema 註解與後台標籤）

| 層 | 識別字 | 中文 | 說明 |
|---|---|---|---|
| 作者層 | `map@1` | **地圖** | owner 編寫的 MapConfig |
| 引擎層 | `arena@1` | **場地** | 產生器編譯出的碰撞真相，runtime 只認這個 |
| 隔離層 | `zone` / `ZoneDef` | **對戰分區** | ⛔ **不改名** —— 改名要動 wire 與 40+ 檔 |
| 地形層 | `region` / `MapRegion` | **地圖區域** | ⭐ owner 說的那個「zone」，新欄位 `regions[]` |

⛔ 絕對不要叫 `zone` / `subzone` / `area`（`area` 已被 `randomArea` hook 佔用）。
文件與 commit message 一律寫「對戰分區」與「地圖區域」，**不寫單獨的 zone**。

## 四、MapConfig（`map@1`）與規格數字的家

```
map@1
  id, schema, name, template
  template : "CENTRAL_RING" | "CROSS_RING" | "DOUBLE_LOOP" | "ARENA_RING"   ← 封閉 enum，就四個

  grid    : { cols, rows, tileSize }        # 24, 18, 2.0
  origin  : { x, z }                        # tile(0,0) 的世界座標

  gameplay:                                  # 第一層：可站、會擋、會生成
    tiles       : string[]                   # rows 行字串，'.'=地面 '#'=牆 ' '=虛空
    regions     : [{ id, label, role, tiles|rects }]     # 4–6，prefer 5
    spawns      : [{ regionId, side, slot, at, facing }] # facing 取代硬寫的朝向
    chokepoints : [{ id, at, width }]        # 產生器推導、驗證器檢查
    shortcuts   : [{ id, from, to, gateGroup? }]
    interactions: [{ id, kind, at, radius, regionId, params }]   # 6–10

  landmark:                                  # 第二層：動漫辨識物
    props : [{ model, x, z, rotQuarter, scale, blocks }]
                                             # ⛔ blocks 是唯一會影響 gameplay 的一格
  background:                                # 第三層：不可進入、假尺度
    props : [{ model, x, z, rotQuarter, scale }]         # ⛔ 永遠不編譯成 obstacle

  gimmick :                                  # 至多一個
    kind        : "none" | "routeSwap"
    gateGroups  : [{ id, tiles }]
    schedule    : { kind:"periodic", periodTicks, telegraphTicks, configurations }
```

⭐ `tiles` 用**字串陣列**而不是二維數字陣列：一張 24×18 的圖在 PR 裡就是
18 行 24 字，**人眼能直接讀出佈局**。

### 四個模板怎麼「只有四個」

`template` 是封閉 enum，`templates.ts` 匯出四個純函式 `(grid, params) → tiles + regionSkeleton`。

⛔ 判準（第〇·五守則）：**如果我在為 Infinity Castle 寫一個 if，就越線了。**
「無限城」在程式裡**不應該有名字** —— 它只是 `CENTRAL_RING` + 一組參數 + 一張手繪 tiles。

### 規格數字全部住進 `config.map-spec@1`（三個住處）

```
content/config/map-spec.json        ← 出貨值
  grid        : { colsMin:20, colsMax:26, rowsMin:16, rowsMax:20, tileSize* }
  traversal   : { secMin:12, secMax:20, referenceMoveSpeed:6 }
  topology    : { regionsMin:4, regionsMax:6, regionsPreferred:5,
                  deadEndsMax:1, loopsMin:2, chokepointsMin:2, chokepointsMax:3,
                  shortcutsMin:0, shortcutsMax:2 }
  interactions: { countMin:6, countMax:10 }
  gimmick     : { maxPerMap:1 }
  severity    : { deadEnds:"warn", loops:"warn", chokepoints:"warn", ... }

packages/shared/src/content/schema/config.ts   ← Zod + DEFAULT_MAP_SPEC + resolveMapSpec()
apps/admin/src/mapSpec.ts                      ← SHIPPED_MAP_SPEC + 欄位 union + 標籤 + configFromForm
```

⛔ **驗證器與測試一律從 `DEFAULT_MAP_SPEC` 推導，不抄 24 / 18 / 12 / 20。**
（第零守則：出貨數值住進測試＝第四個住處，必過期且用錯誤訊息紅。）

⚠️ 但 `severity` **只能調品味項**（死路數、迴圈數、瓶頸數）。
**連通性不可調**：任何「有區域走不到」「spawn 不可達」「gate 某個組態把圖切斷」，
產生器**一律拒絕輸出**，與 config 無關。那不是品味，那是正確性。

## 五、每一項引擎機制的落點

| 機制 | 落點 | 新舊 | 備註 |
|---|---|---|---|
| 靜態碰撞：**牆** | `ArenaDef.ts:9-22` + `resolve.ts:36-50` + `zObstacle` | **已存在** | 產生器輸出線段就能跑，**零引擎改動** |
| 靜態碰撞：**盒** | 上列各處加 `kind:"box"` + 一個 AABB 原語 | 新 | 7 個消費點。替代案是拆成 4 條線段（0 新點，但物件數 ×4，且身體生在盒內會被推向最近邊 —— 可能還在盒內）。**建議做 box** |
| **矩形邊界** | `ZoneDef` 加 optional `bounds:{kind:"disc"\|"rect"}`，`clampToBoundary` 分支 | 新 | ⭐ 同時把散落五處的「push out + clamp」樣板收成**一個** `placeInBounds()`：`coins.ts:119`、`flowers.ts:120`、`mobs.ts:2401`、`revive.ts:335`、`summons.ts:294`（第零守則⑨：五處做同一件事＝漏了一次抽象） |
| **導航圖** | 烘焙進 `arena@1` 的 `nav:{ nodes, nextHop }`；runtime 只有 `navFollow.ts::nextWaypoint` 查表 | 新 | ⭐ **核心提案**，見下 |
| **繞牆走** | `MovementSystem.ts:202-204` 呼叫點不變，目標從「最終目的地」換成「下一個 waypoint」 | 改 | 這樣 `avoid.ts:57` 跳過線段那一行**可以原封不動保留**（切線只繞柱子，牆由 waypoint 繞開）。改動面極小 |

### ⭐ 三個關鍵設計決定

#### ① 導航：離線烘焙 next-hop 表，runtime 零搜尋

產生器離線跑 APSP，把 next-hop 表烘進 `arena@1`。N ≤ 64 節點 → 64×64 = **4KB／圖**。
runtime 只查表：**零搜尋、零三角函式、零 `**`、零 Map 迭代序問題**。

這是唯一能同時滿足**三個約束**的形狀：purity 閘 · 決定性 · 客戶端預測必須算出一樣的結果。

#### ② 機制做成通用 gate，⛔ 不是無限城的 if

`gateStateAt(doc, absoluteTick)` 的**三個關鍵性質**：

1. 狀態 =（doc, tick）的純函式 → **客戶端用已複寫的 match tick 自己算**，wire 成本 0、**沒有 desync 通道**
2. **絕對 tick**，不用遞減計數器（硬性約束）
3. 「永不困住玩家」是**驗證器的性質**，不是 runtime 程式碼 ——
   每一個 configuration 的圖都必須全連通、所有 spawn 與互動點可達，否則**產生器拒絕輸出**

⭐ 同一個機制順便給了城門、崩塌的橋、可破壞的牆 —— 七張圖的機制**有五個是這個形狀**。

#### ③ 垂直感只能是背景 —— 這不是美術偏好，是引擎的物理事實

⛔ **單位一律畫在 `y=0`，沒有地面高度查詢**（`ArenaGround.ts:19-31`）。
可玩範圍內任何垂直位移都會讓**所有單位浮空或陷地**。

⛔ 而且視線有硬天花板：`SIGHTLINE_HEIGHT_CAP = 2.4`，而**無條件畫的東西**
（沒有內容可以移除的）必須 ≤ **0.42**（`OBSTACLE_MARKER_TOP_Y`）。
graybox 的牆若高於 2.4，就重新武裝了 task #218 拿掉的那個遮擋 bug。

⇒ **graybox 牆在畫面上必須是矮牆條，不是真的牆。**
⭐ owner 寫「verticality is BACKGROUND ONLY」是設計直覺 —— 它剛好也是引擎的物理事實。

## 七、會咬人的風險

### 7.1 schema tag／欄位與 image rebuild —— 2026-08-02 事故的完整重演形狀

`zArenaDef` 與 `zZoneDef` 都是 **`.strict()`**（已複驗）。
任何新欄位、任何新 obstacle union 成員，對**舊映像**都是 hard Zod failure，
而 `content/` 是 live bind-mount、client/server 烘在映像裡。

**後果**：整份內容載入失敗 → fail-open 退回 2 隻骨架英雄 →
**網站看起來完全正常**，唯一破綻是 console 那一行。

⇒ 部署順序**必須是**：先 deploy 帶新 Zod 的映像
（`bash scripts/host-deploy.sh`，⛔ **不能用 `--content-only`**），確認上線，**再**推內容。

💡 診斷招數（幾十秒有答案、不碰正式站）：
```bash
curl -s https://ggd.adms.ai/content/bundle.json -o /private/tmp/prod-bundle.json
```
再用候選 schema 的 `validateDoc(collection, doc)` 逐份跑。

### 7.2 決定性有三條不同的線

- **換圖**：`pickRoundArena` 用獨立 `hash32`，**刻意不動 `world.rng`**（task #145）。
  資料驅動的地圖池必須保留這個性質，否則同 seed 錄影不再逐位元相同。
- **花的位置會抽 `world.rng`**（`flowers.ts:108`）。改變抽取次數會位移之後
  每一次爆擊／閃避／寶玉的骰子 → **舊錄影全毀**。
- **產生器輸出**必須零時間戳、零 `git describe`、零未排序 Map 迭代。
  `tools/capability-export/export.ts:22-30` 與 `tools/legacy-index/build_index.py` 都記錄了
  失敗形態：**一個會浮動的欄位逼你把 `--check` 放寬成模糊比對，而放寬的閘不是閘。**

### 7.3 purity 閘

`packages/shared/src/sim/**` 禁 `Math.random` / `Date.now` / 全部三角函式 /
`Math.pow|exp|log|hypot|cbrt` / `**`；Map 迭代必須排序；到期用絕對 tick。

⭐ 這正是把 `templates/compile/validate/graph` 放在 `packages/shared/src/map/`
（**不在** `src/sim/` 底下）的原因 —— 烘焙時可以自由用 `Math.hypot` 與三角函式
（前例：`content/arenaCollision.ts`）。只有 `sim/map/{regions,gates,navFollow}.ts`
三個 runtime 檔受管，而它們**全部是查表**，天然合規。

### 7.4 效能（實測估算，比想像樂觀）

relax 是 2 pass × 全部 obstacles，每個 body 每 tick 最多 3 個呼叫點 → 約 5 次全掃。

| 情況 | obstacle 數 | 成本 |
|---|---:|---|
| **合併共線牆之後** | 30–60 | 60 body × 60 × 5 = 18,000 次／tick，20 tick/s ≈ **0.1ms 級 → 不需要 broad phase** |
| 不合併（每格一個盒） | 150–200 | ×3–4，開始有感 |

⇒ **`merge.ts` 比 `staticGrid.ts` 重要，先做前者。**
broad phase 列為 Phase 3 的 optional，只有合併後仍 >150 個才做。

### 7.5 ENTITY_FLAG 的 16 顆 bit 已經用光

`ENTITY_FLAG_FREE_BITS` 是**空陣列**。「這個單位在哪個 region」「在不在掩體後」
**沒有 bit 可用**，而且 ⛔ **不可以重用看起來閒置的 bit**
（線上舊客戶端會靜默 desync，沒有任何一處會報錯）。

⇒ 本設計把 region 與 gate 狀態**全部做成可從 (doc, 座標, tick) 推導**的東西，
wire 成本為 0。**這不是省事，是唯一可行的路。**

### 7.6 bundle 新鮮度 + 未追蹤來源（兩個不同的守衛守兩件不同的事）

`shippedBundleIsCurrent` 守「產物最新」，`shippedBundleHasTrackedSources` 守「來源進了 git」。
後者存在是因為 2026-08-02 的第二次事故：**未 commit 的來源檔被烘進了 commit 的 bundle**。

⇒ 產生器最後一段必須**自己**跑 `pnpm content:build`，再跑
`git ls-files --others --exclude-standard content`，有未追蹤檔就非零離開
（比照 `tools/skill-remake/batch1.py::finalize_content()`）。

### 7.7 客戶端／伺服器幾何重複

兩邊都走 `arenaDefFromDoc`，這是**唯一的一致性保證**。
`ArenaDef.ts:141-152` 記錄了不這樣做的具體後果（伺服器碰撞半徑 42、所有玩家看到 24）。

⛔ **任何伺服器端 runtime 改幾何的做法都會重新打開這個洞。**
gate 做成 `(doc, tick)` 純函式，就是為了讓兩邊各自算出同一個答案，而不是一邊算一邊送。

### 7.8 ⚠️ 單一對戰分區的地圖在第 1–9 回合是未定義行為

`pairTeams` 在 4 隊存活時**一定**吐出 zone 0 與 zone 1（`PairedDuels.ts:132-141`），
而 `MatchController.ts:1721` 是 `this.arena.zones[pairing.zone]!`（非空斷言）。
schema 只要求 `zones.min(1)`。

⇒ **一張只有一個對戰分區的 anime map 放進輪替池，第 1–9 回合會解參考 undefined。**
這直接連到 **Q1**。

### 7.9 spawn 數量的 schema↔程式契約缺口

`zZoneDef.spawns` 每側只要求 `.min(1)`，但 `MatchController.ts:1215/1736` 是
`spawns[side]![slot % TEAM_SIZE]!` ⇒ **合法的 doc 可以在 runtime 給出 undefined**。

產生器必須自己保證每側 ≥ 3，而且這應該變成 `zZoneDef` 的 superRefine ——
但依第零守則⑧，**開 issue 給 owner 勾，不當場修**。

### 7.10 兩份重複的內建幾何

`SKELETON_ARENA`（`ArenaDef.ts:247`）與 `ROYALE_ARENA`（`:162-228`）是 TS 裡的第二份地圖，
被 `loader.test.ts:211` 與 `royaleArena.test.ts` 逐欄位釘住。
⛔ **新地圖絕對不要再開第三份 TS 副本。**

### 7.11 靜默 fail-open ×2

`resolveArena`（`arenaSelect.ts:14`）與客戶端 `applyArena`（`GameApp.ts:1125`）
都會**靜默退回骨架**。⛔ **打錯一個 map id，遊戲照常開始，沒有任何一處紅。**

⇒ 新的地圖流程需要一個 fail-loud 的對應物（比照 `/healthz` 的 `content.ok`）。

### 7.12 守衛的斷言形狀（真的踩過）

⛔ 不要寫 `expect(() => execFileSync(...)).not.toThrow("訊息")` ——
vitest 的 `toThrow(string)` 是**子字串比對**，腳本真的非零離開時它**仍然是綠的**
（`legacyIndexFresh.test.ts:33-38` 就這樣出貨過，靠突變才抓到）。

一律 `spawnSync` 讀 `r.status`，而且要先 `expect(existsSync(GEN)).toBe(true)`，
否則守衛是在測空氣。

### 7.13 測試預算

地圖幾何橫跨兩層：

| 層 | 範圍 | 預算 |
|---|---|---|
| **靈魂層** | 碰撞 / 導航 / gate | 深守衛 + **一條承重線的突變** |
| **體驗層** | 產生器 / 驗證器 / 後台頁 / 報告頁 | 測試行數 ≤ 實作行數且 ≤ 80 行，⛔ 不開對抗輪 |

整批 `npx vitest run` ≤ 3 次 · `tsc` 1 次 · 突變**一批一條**
（建議挑「手改產生的 arena → 守衛紅」那一條）。
⛔ 規格數字（24 / 18 / 12 / 20）**不進斷言**。
