## 1. 產品目標與第一版邊界

### 1.1 一句話目標

讓玩家不用寫程式，就能組合既有積木，製作完整英雄、六槽技能與演出；自動保存、預覽、送審，由管理員在同一頁審查並發布，最後在允許社群內容的遊戲中實際選用。

**自動鑄造是起稿與推薦工具，不是另一套編輯器，也不是發布捷徑。** 不用 AI 仍須完成整條流程。

### 1.2 第一版必須交付

- 新建英雄、修改自己的作品、從允許改作的作品建立獨立新作。
- 同一份 `HeroProject` 的快速鑄造、視覺設計與進階調整；六槽為 `PASSIVE／Q／W／E／R／EX`。
- 可操作的效果模板／成品／效果鏈、特效家族與 subtype、角色動作、時間軸與場地預覽。
- 本機自動保存、離線編輯、恢復未完成工作；登入後同步自己的草稿與投稿結果。
- 上傳英雄／技能 icon；模型、特效貼圖與音效先選用可分發、已核准的資產。
- 完整英雄版本投稿、確定性技術檢查、後台一頁審查、核准並發布、退回、拒絕、下架及回復版本。
- 遊戲取得核准版本、對局鎖版、不改變進行中的對局；明確顯示官方／社群來源。
- 桌面程式可安裝、保存資料後更新；不要求玩家使用 Git、終端機、手動搬 JSON 或部署伺服器。

### 1.3 本輪不擴充

不做完整地圖編輯器、地形繪製、任意素材／MDL 匯入平台、任意腳本或 shader、獨立技能／VFX 交易市場、即時多人共同編輯、多級審批、排程發布、排行榜或 GGD 代管 AI 服務。

既有技能／道具編輯與單檔 JSON、部分／完整 ZIP 匯出繼續保留，但不另做一套社群道具發布流程。未支援能力保留為明確的待辦，不把它從長期架構中刪掉。

## 3. 系統分工與主流程

```text
玩家／設計師
  → Editor：草稿 → 積木組合 → 技術檢查／預覽 → 投稿完整版本
  → Main：權限／資產正規化 → 凍結候選 → 獨立重驗
  → 後台：同一候選的文案、差異、機制、連續影格與試玩
  → 管理員：核准並發布／退回／拒絕
  → Main：驗證收據與 CAS → 發布作品版本 → 遊戲新對局鎖版
```

| 角色 | 應負責 | 不應負責 |
|---|---|---|
| Codex Editor | 創作 UI、積木組合配方、推薦、時間軸、鏡頭、autosave、差異與驗收工具 | 為單一英雄新增 runtime if、修改 `owner-knobs.json` 的人工專用欄位、製造低階 renderer 積木 |
| Main | typed primitive、事件與 resolver、schema、compiler 接縫、伺服器驗證、帳號權限、發布與遊戲載入 | 逐招調配色／鏡頭／美術細節，或替 Editor 再做一套鑄造器 |
| Hero Forge 原實作方 | 交付既有共用契約、deterministic planner、提案 adapter、測試與整合說明 | 因落後 Main 就重寫全套；直接覆蓋 Main importer |
| 管理員／Owner | 審查作品品質、設計偏好與公開資格；操作發布／下架 | 手動傳遞兩邊開發訊息、替程式判定 hash／公式／能力是否合法 |

Main／Admin 使用同一套 authoring 契約與可重用的表單、時間軸、診斷及預覽元件。可共用元件或受控預覽入口，不可複製另一套編譯／模擬邏輯。審查畫面預設唯讀；管理員如要改內容，建立新修訂重新審查，不偷偷改被審版本。

## 4. Editor：操作項目與功能模組

### 4.1 單一導引，三種編輯深度

導引順序：**身分與概念 → 出身與屬性 → 六槽技能 → 效果組合 → 演出 → 試玩檢查 → 匯出／投稿**。

快速模式顯示候選與常用選項；視覺模式顯示卡片、連線、場地與時間軸；進階模式展開精確參數、依賴與診斷。切換深度不複製專案、不重新生成已接受內容、不遺失鎖定。

| 畫面／模組 | 玩家能做的事 | 必須看見的回饋 |
|---|---|---|
| 我的作品 | 新建、續編、複製、開啟已發布版、查看投稿結果、從允許的來源改作 | 本機保存／同步／待審／發布分開；版本與來源明確 |
| 英雄基本資料 | 名稱、Owner 原文、肖像、選用模型、角色來源／形態 | 名稱衝突、模型替身標記、資產缺件與可分發性 |
| 出身／屬性 | 選出身、五級距、角色定位、屬性與成長 | 目前公式、預算、推薦原因及實際生效值 |
| 六槽技能卡 | 命名、選施放方式、主動／被動、升級數值、複用配方、調整卡片順序 | 每級耗魔／冷卻／傷害／距離；缺項可定位到欄位 |
| 效果模板庫 | 搜尋能力、篩選家族／事件／施放形狀、比較適用條件 | 支援、未接線、不可用參數及原因；不能只顯示綠 badge |
| 成品與效果鏈 | 模板製成 Product、複製成品、連接多段、條件、目標、時間點 | 每段會影響誰、前後相依、重複觸發與數量／時序圖 |
| VFX／動畫工坊 | 選家族與 subtype、拖拉資產、角色動作、錨點、方向、大小、配色、時間軸 | 角色實際動作、機制事件標記、限制裁切、替身與素材警告 |
| 試玩場 | 放置預設敵我測試單位、調整站位／血魔／狀態、施放、重播、暫停與逐格看 | 命中、傷害、位移、狀態、觸發來源及對應演出；不是只有 JSON |
| 檢查／比較 | 和原版或上次投稿比對，查看錯誤、警告、AI 建議 | 機器失敗、AI advisory、人工未審分欄，嚴重度及修正入口 |
| 匯出／投稿 | 本機 JSON／ZIP、檢查完整英雄快照、送審、撤回待審、查看退回原因 | 本次送出的版本／依賴／肖像；不出現玩家可直接啟用正式內容的按鈕 |
| 設定 | 參考來源 URL／本機資料夾、帳號、AI、備份、更新 | 遠端參考唯讀；本機離線可編；登入憑證與 AI key 分離 |

上述是完成標準，不因已有相同名稱的按鈕就算交付。進階 JSON 檢視只能輔助，不能代替核心 no-code 操作。

### 4.2 五級距、出身與推薦

- 級距只用 **極小／小／中／大／極大**；出身清單、級距數值、平衡公式與預算從 Main 當前共享契約／config 取得，不再手抄一套。
- 先以能力、輸入／輸出型別與目標相容性過濾，再依出身、定位、已選技能的互補性與預算排序；人氣或 AI 只可調整合法候選順序。
- 推薦顯示「為何適合、代價、相衝之處」；換出身不覆寫 manual／locked 欄位，先列差異。
- 新技能 Q／W／E 四級、R 三級；由共用級數規則驗證。PASSIVE／EX 的等級與觸發型別分開，不能用槽位推斷一切。
- 顯示作者值與 resolver 的實際生效值；系統 AP 乘數、粒子上限等不是逐技能常數，不寫死在配方或另造平衡公式。

## 5. 模組化組裝：保留既有成果，而非逐招硬調

### 5.1 四層關係

```text
效果模板定義（受限 typed graph／能力）
  → 效果模板成品 Product（有版本、參數與目標語意）
  → 效果鏈（引用一個或多個 Product 實例，含次序／條件／排程）
  → 英雄技能 authoring → 共用 compiler → runtime JSON
```

效果鏈放的是**成品引用**，不是靠模板名字猜參數。每個實例有穩定識別；同一模板可被組合多次且參數不同，不能用 `templateId` 當唯一實例 key。

既有 Main 模板與產物唯讀；玩家只能在目前契約允許的 authoring 層組合已支援能力。Editor 自訂配方不等於新增 effect kind／hook／任意程式碼。模板成品預設 host-local；明確 Promote 到 shared authoring library 也不等於公開發布。

### 5.2 家族、subtype 與參數矩陣

把已調好的常用結果整理成具語意名稱的配方，例如同家族的水平光束、垂直終結光柱、單發主斬弧、反擊連斬；實際可選項必須來自當前 Main 積木與已驗證 Editor 配方。

先選配方，再展開矩陣微調。不同配色、尺寸或節奏可由參數變體表示，不建立 `type1/type2` 這類沒有語意的 runtime id。保留舊成果的來源、參數、證據與相容性，不重新開始盲調。

接入時必須逐項遵守：

1. 讀 `ggd-bricks.json`、`ggd-type-catalog.json` 及 runtime／presentation 收據；不靠本文中的數量判斷。
2. 模板只選 `expands: true`；照 `wiring` 寫入正確位置，逐格檢查 `fillsVia`。
3. `inertParams`、未接線與未知能力不可偽裝成有效旋鈕；保留可讀原因與受影響項目。
4. 模型、附屬粒子、動作與錨點各自讀支援收據，顯示已設定但未生效的值。
5. 匯出前重驗 target profile、contract index、引用閉包與生效限制；不因本機曾經成功就跳過。

### 5.3 動作與視覺原則

- 主動施放帶合理角色施法／攻擊動作；連段依真實命中、位移、間隔與終結事件安排動作，不只有粒子。
- 一次明確揮砍通常對應一個主斬擊特效；真正極速多段技才使用多個小斬擊，不能把多月牙當所有技能的預設。
- 被動依情境加 on-hit、暴擊、迴避、格擋、護盾等回饋；純屬性或 aura 不偽造主動 cast。
- 機制傷害、次數與時序只由 ability／SimWorld 決定；VFX script 呈現「畫什麼、掛哪裡、何時」，不得發動另一套傷害。
- 相同事件／通道的預設演出與 script 是否替換，必須按 Main 支援契約處理；不能用雙重播放掩蓋缺口。
- 素材檢查依「貼圖 × 材質 × blendMode × 實際畫面」判斷；透明度健康不等於必須改圖，實心背景板則不能放行。
- 顏色、方向、形狀、尺度、物理語意等明顯錯誤優先修；細微美術偏好留下人工調整，不讓 AI 無止境逼近。
- 同一視覺目標第二輪仍不收斂就停止調參，保留比較圖、來源與缺失能力，走現有 PR packet；不得改成逐技能 workaround。

### 5.4 技能說明與標籤

- Owner 原文、對白、幽默、標點與換行保留；不能為節省 token 自動縮寫。機制解析排除 `「……」` 的角色對白，避免把玩笑當效果。
- 標籤、逐級數值、施法距離與有效形狀分開建模；主動／被動以觸發機制定義，不以槽位、是否耗魔或有無冷卻猜測。[輔助] 僅供主動且對我方產生效果的技能使用。
- 文案中的機制、屬性與數值對應交由既有 tokenizer／規則 script 處理；保護專有名詞與詞界，不在 `GLADIARIA` 等字中間切出 `[AD]`，不產生重複標籤。
- 所有有效 `[]` 使用 Main 的全域標籤／七色 palette 契約；缺映射顯示診斷，不各頁自行寫色碼。主標籤同一行，逐級變化融合進相應敘述。
- 補值、標籤修正、推定與來源衝突都保存中文 issue／變更說明。機器只能自動做已明訂的修正；改變玩法的提案必須讓作者看到差異並接受，不直接改 Owner 原文。

## 6. 資料與版本：一份 authoring、一條正式匯入鏈

以下是**應由既有契約承載的語意**，不是新增另一套已定案的 JSON schema 或 API。

| 資料 | 保存內容 | 不應混入 |
|---|---|---|
| `HeroProject` | 已接受設計、六槽、Product／Chain、演出、鎖定、來源與 revision | key、模型檔、原始模型回應、provider-specific metadata、公開資格 |
| 私有草稿紀錄 | 所有者、project reference、同步版本／etag、最後保存與刪除狀態 | 另一份自行演化的英雄格式 |
| 社群作品紀錄 | 伺服器核定 workId、作者、改作來源版本、公開／改作政策 | 客戶端自稱的帳號所有權 |
| 不可變作品版本 | 可重開編輯的已淨化 authoring、完整英雄 package 與依賴 digest | 浮動 `latest` 資產或審查後偷偷更新的內容 |
| 審查與發布紀錄 | 被審快照、target／驗證收據、真人決定、發布 operation、published version pointer | 由 AI 或包內 reviewer 字串取得的核准 |
| 資產物件 | 正規化後 bytes、digest、種類、尺寸、授權／來源 | 本機絕對路徑、憑證、不可分發資產 |

### 6.1 三種版本不能混為一談

- **草稿 revision**：每次接受編輯遞增，用來取消過期驗證與防止覆寫。
- **作品 version**：每次投稿凍結一個完整版本，包含可再編輯來源及 runtime／資產閉包。
- **遊戲 target／對局內容版本**：指向實際 compiler、schema、能力、限制、資產與 runtime 環境。

Forge 既有 `sourceLock.canonicalId/versionId` 是角色原作／設定版本的鎖，不是社群作品的改作來源。社群 lineage 另由作品紀錄綁定確切父版本，不能把兩者塞成一格。

### 6.2 匯出與回讀

- 重用 Main 正式 manifest、hash／JCS、schema registry、validator、operation／store 與 compiler；不得整包移植 Forge 的另一個 `HeroImportStore` 覆蓋 Main。
- Forge 的 `ggd-hero-package@2` 是分支已有方案，**不等於 Main 已接受的格式**。先定向比對，再由 Main 接納相容 representation／adapter；同一對外 importer 管理版本，不平行經營第二套。
- 完整英雄投稿必須包括可再開啟的 authoring，保留成品實例、鎖定、手動欄位、Owner 原文與演出。只有編譯後 ability JSON 不足以還原作者設計；不得用 AI 反推當作 round-trip。
- 投稿版本以完整英雄為單位；傳輸可按 digest 去重／只上傳缺少 blob，但不能把部分包誤當完整快照。
- 本機既有單檔／部分／完整匯出可留在進階工具；是否可匯入由 target contract 決定。社群投稿不提供「覆蓋全站內容」選項。
- 依賴均固定 id＋版本／digest；缺失、未知 schema、不可分發或未支援的依賴一律阻止發布，不悄悄刪欄位降級。

## 7. 投稿、審查、發布的完整流程

### 7.1 玩家新建、更新與改作

1. 新建本機 `HeroProject`；先不用登入或 AI 也可設計、保存、預覽。
2. 編輯自己的已發布作品時，以該不可變版本建立新草稿；舊發布版不被修改。
3. 改作先檢查來源政策，建立新 workId／作者與父版本記錄；不能覆寫原作者或官方內容。
4. 登入後綁定伺服器所有權與草稿同步。離線變更保留，衝突時可比較、另存，不採靜默 last-write-wins。
5. 投稿前顯示完整英雄、六槽、演出、肖像、技術問題與相對上一版差異；玩家確認要送出的 revision。

### 7.2 伺服器接收與快照凍結

1. 驗登入、所有權、改作權限、大小／頻率／待審數量政策；身分從 session 取得，不信包內欄位。
2. 圖片在隔離區驗格式、尺寸／解碼成本與來源，重編成核准格式；Editor 顯示正規化結果。
3. 用**正規化後**資產建立 manifest、依賴 digest 與候選快照，然後凍結。審查後再改圖會產生新版本，不得只沿用核准。
4. 用 Main 正式驗證鏈重算引用、hash、capability、compile 與有界 SimWorld 證據；Editor 成功收據只作比較，不是信任來源。
5. 技術阻擋直接回到玩家可定位欄位的修正清單，不把必敗資料塞給人工審查。
6. 同一作品預設只有一份有效待審候選；重送建立新候選並取代待審關聯，保留舊版歷史。繼續編輯不會改動已送出的候選。

### 7.3 管理員一頁審查

審查對象固定為一個完整作品版本；顯示作者／來源、肖像、六槽說明、前後差異、技術報告、事件 trace、關鍵連續影格與可互動預覽。

主要操作為 **核准並發布／退回修改／拒絕**。退回附欄位／技能問題與理由；拒絕保存決定，不刪證據。管理員可直接跳到問題技能，但第一版不做六槽分別核准、拼出另一個沒被整體審過的英雄。

AI 視覺分析只能作可展開的參考。腳本可以更新 advisory，但不能簽署、更新或偽造真人的核准。

### 7.4 核准並發布：一個按鈕，分離權限與交易

1. 後端核對管理員權限、候選仍有效，將審查決定綁定確切快照與驗證 target。
2. 重驗來源、依賴、compiler／能力／限制與發布 base；漂移時標記 stale，不偷偷重編成不同內容繼續發布。
3. 使用既有 importer／operation 的能力把驗證版本安置到可讀儲存，再以 CAS 更新該作品的發布指標與資格。
4. 網路重送使用同一冪等 operation；崩潰後依操作紀錄恢復。失敗維持上一個已發布版本，畫面清楚標成「已審、發布失敗」並可安全重試。
5. 已發布列表與遊戲 resolver 只讀成功發布的有效版本；`approved`、promotion ledger 存在或 validate 成功都不等於遊戲已可用。
6. 下架阻止新的選用；回復只能指向仍相容且可用的歷史版本。緊急安全封鎖與一般下架分開記錄，既有對局如何終止由 Main 安全政策處理。

**重要：社群英雄不是官方全域內容切換。** 多個作品必須並存，不能每發布一名英雄就覆蓋 `ACTIVE`、把上一名英雄移除。Main 應在既有 object store／operation 上提供作品範圍的安置與發布關聯，保留官方 ACTIVE 的語意；不要再建另一個不相容的英雄 importer。

| 安裝與版本政策 | 現有桌面打包及 Main CI／release | 簽署更新資訊、支援版本與相容性查詢；不以內容 ZIP 更新應用程式 |

## 9. 遊戲端：發布之後要真的能玩

1. 玩家在允許社群內容的房間看見作品名稱、作者、版本、肖像及相容性；官方／社群來源不可混淆。
2. 建房／選角時由伺服器解析已發布版本，固定官方 base＋本局所選英雄版本＋所有資產 digest。客戶端不能指定任意未審包或本機檔案。
3. 同局可同時選到不同社群作品；resolver 檢查 ID／依賴衝突、能力與資源總預算。不能以最後載入者覆蓋前一份。
4. 客戶端取得與房間一致的英雄、技能、演出及資產，驗完整性再開局；缺檔／版本不合就阻止進場並給可理解原因。
5. Main 目前有啟動期全域 registries 與房間內容版本，整合時須提供受控、不可變的房間內容上下文，或等價的版本隔離方案。不可直接熱改全域 registry 影響其他房間。
6. 發布新版本只影響後續解析；進行中的對局不換技能或資產。重連與回放保存該局版本集合，不靠「現在最新版」重建過去。
7. 回放若缺少相容 runtime／資產，明確拒絕或顯示不可播放；不偽稱可以跨所有歷史引擎版本回放。

這部分由 Main 實作 runtime／server 邊界；Editor 提供可重現的兩作品同局案例、已接受 authoring 及視覺驗收，不自行接管遊戲 registries。

## 10. 保存、離線、同步與更新

### 10.1 自動保存

- 每次操作先更新同一份草稿並排入本機持久化；debounce、失焦及關閉前 flush，畫面只在成功落盤後顯示「已保存」。
- 尚未完成、暫時不合法的輸入也要保住；原始表單輸入可暫存在本機編輯狀態，不強迫通過 package schema 才允許保存。
- 本機寫入採原子替換／交易及恢復備份；磁碟滿、權限失敗、意外關閉有明確提示與恢復路徑。
- 遠端參考 URL／資料夾與草稿儲存分離。離線可用已驗快取編輯；投稿／發布需重驗目標，不假稱離線收據仍最新。
- 草稿同步用既有 revision／etag 做 CAS；遇衝突保留兩份可比較資料，提供採本機、採遠端或另存新作，不靜默覆寫。

### 10.2 桌面更新

- 第一版只做單一穩定更新通道，Windows／macOS 共用業務程式；簽章、安裝與更新 adapter 分平台。
- 更新資訊由可信發布來源提供並驗證簽署／完整性；正式更新前先完成保存與相容性檢查，經使用者確認後重啟。
- 更新與草稿 migration 分開，有版本標記與備份。新版讀不懂或舊版降級時保留原資料，提供唯讀／恢復，不破壞性回寫。
- 更新失敗能繼續使用已知良好版本；不支援自動更新的 portable 產物提供經驗證的手動安裝入口，不偽造自動更新成功。
- 不從遠端下載任意 JavaScript／schema 當熱補丁，不把 Editor 二進位或模型塞進英雄包。

### 10.3 資產保存

原始上傳與正規化結果有清楚來源；發布引用正規化 digest。相同 bytes 可去重，但不能因一份投稿取消就刪掉其他作品仍在用的資產。暫存、失敗上傳與孤兒採有界回收；有效版本依保留政策持續可取用。法規／安全刪除可覆蓋一般保留，但要同步標記作品／回放不可用，不能留下假成功的連結。

## 11. Hero Forge 合併前必須解決的接縫

不切換、修改或合併原 `feat/hero-auto-forge` 工作樹。正式開始整合時，先取得該分支 commit／測試／整合清單，在新的 `codex/<主題>` 分支選擇最小整合方式；保留原成果，不因分支較舊就重寫。

| 接縫 | 實際風險 | 整合方式／負責 |
|---|---|---|
| 共用契約 | 三個 UI 深度或 Main 各自造 HeroProject | 保留 `heroForge.ts` 相容入口；以 `heroForge/` 為唯一鑄造核心。契約變更由 Main review |
| 模板推薦 | Forge UI 用宣告 status 篩選，可能選到不能展開／無效欄位 | Editor 接最新 catalog、`expands`／`fillsVia`／inert 與實際表單收據 |
| 重複模板成品 | `templateIds` 唯一、參數按模板 ID 索引，不能完整表達同模板多實例 | 在既有 Product／Chain 契約內對接實例引用及遷移；不新增第二套 graph |
| 主動／被動／逐級值 | 分支把 PASSIVE tuning 全鎖零；不能據此否定被動內建冷卻、範圍或資源效果 | 共用契約分離施放參數與 trigger／effect 參數，按真實機制與等級規則驗證 |
| 演出接線 | 分支 presentation 以 abilityCast 為中心，不能代表 Main 全事件與 VFX script 能力 | Editor 組合最新 actor／event／channel、subtype 與 `vfx-script@1`；缺能力再提 packet |
| 正式封包 | Forge 路徑 allowlist、target receipt 與 Main 不同；可編輯 HeroProject 不能從 compiled 完整還原 | Main 接納完整 authoring representation；Editor 做無損回讀與最新演出／資產閉包 |
| importer／啟用 | 分支同名 validate／apply routes 背後換成獨立 HeroImportStore，會失去 Main 既有語意與安全修補 | Main 主持移入既有正式管線；保留冪等、CAS、完整收據及健康檢查，不整檔覆蓋 |
| 個人匯入與公開發布 | 分支已有 apply 入口，不能直接給社群玩家發布權限 | 開發／管理匯入與玩家投稿分離；公開發布只走管理員審查編排 |
| 所有權與 lineage | projectId／角色 sourceLock 不能證明作品所有權或改作權 | Main 以登入帳號綁 workId、父作品版本與政策；Editor 顯示且不能偽造 |
| AI 私有資料 | 分支 ProjectReceipt 可含 modelId／providerOrigin 等資料 | 設定與私有提案收據移入本機 sidecar；可攜專案與包採明確輸出 allowlist，遷移不丟已接受設計 |

### AI 的交付策略

`off` 是完整可交付路徑；`local` 與 `byok` 保留 provider-neutral service，UI 不直接綁模型或特定 API。玩家接受提案後才建立新 revision；identity、方向、白名單、鎖定、compile／SimWorld／發布全部由確定性程式判定。

分支的 Qwen3-14B Q4_K_M 品質報告尚有 critical case，runtime manifest 為 `released: false`／`LOCAL_AI_E8_GATE_PENDING`。這是既有證據，不是本次重跑 benchmark。**本機 AI 維持關閉，E8 作獨立交付線；不得為等模型而卡住 off 模式的社群流程。**

BYOK 由使用者主動設定，key 留 OS vault／受控 session；不送 GGD 伺服器、不進日誌或包。沒有模型、API 失敗、無網路或額度不足都只令提案不可用，不導致編輯器／投稿失敗，也不自動換另一個付費或遠端 provider。

Gemini 視覺 advisory 與英雄提案是不同任務。兩者可重用設定／取消等基礎能力，但不能互相取得發布權限；未啟用時驗收仍保留機器證據與人工入口。雲端看圖只在明確開啟、限定資料範圍後執行，不把全部 Owner 對白當分析輸入。

## 12. 自動化驗收：證明玩家能做出來，不只 JSON 能過

### 12.1 四層證據

| 層級 | 檢查 | 能證明／不能證明 |
|---|---|---|
| 即時機器檢查 | schema、引用、capability、實際限制、級距／預算與型別 | 能拒絕無效組合；不能替代視覺與設計審查 |
| 確定性機制檢查 | 有界 SimWorld、事件 trace、seed、重編、傷害／位移／狀態斷言 | 證明特定場景機制；不能只靠 screenshot 判斷傷害正確 |
| 視覺與可操作性 | 真 UI 操作、保存重開、時間軸／角色動畫、連續影格與資產 | 證明設計師可操作且有對應演出；AI 意見不等於人工核准 |
| 正式發布檢查 | 伺服器重驗、真人綁版審查、冪等發布、同局載入、回復 | 證明本次版本可用；不宣告未測過的全部英雄／平台已完成 |

### 12.2 重用 42 主題／46 文件驗收資產

保留既有案例、來源追溯、情境、截圖與視覺報告，並按資料目前的 digest／結果重新判定。46 份都要有基本視覺證據與設計師操作路徑，不把「JSON 通過」改名成全數視覺通過。

每一文件獨立 `sourceDigest`，再包含所用模板、資產、renderer、scenario 與檢查器版本等相關依賴。修改一份只作廢受影響證據；跨技能共享狀態或英雄整套變動才加跑 kit／組合場景。共享 renderer／契約真的影響全部時，全部作廢是合理的，不為省時間重用錯誤收據。

影格從事件時間軸選取，覆蓋施放、位移、命中、終結與清理；簡單技能少取，複雜連段可取 2～18 張或拆分檢查片段，不能固定只看兩張就宣告完整。

AI advisory 使用既有批次工具，依額度與 API 限速有界平行、快取及取消，遇服務故障只記錄基礎設施問題，不重新截完所有技能或重試風暴。人工簽核過期與腳本產生的 advisory 過期分開處理，不能互相冒充。

### 12.3 第一個端到端切片的八組必要案例

1. **不用 AI 新建**：由 UI 製作一個完整六槽英雄、上傳 icon、保存關閉重開；不開 JSON 編輯器修漏欄位。
2. **積木可組合**：同模板兩個不同 Product、條件觸發、兩段位移／傷害及對應動作；保存、重編、重播一致。
3. **離線與同步衝突**：未完成表單、異常關閉、離線修改後重連；不丟資料、不覆寫別人的版本。
4. **投稿與改作權限**：更新自己的作品、合法改作、拒絕跨作者同 ID 覆寫、拒絕未授權官方覆寫；原版本不變。
5. **審查綁定**：上傳正規化後才凍結；審查中作者續編／改圖不替換候選，target 漂移不能沿用舊核准。
6. **發布故障恢復**：重按／斷線重送／中途失敗／CAS 衝突；只有一次有效發布，舊版繼續可用，重試不重複套用。
7. **實際進遊戲**：兩名不同社群作品同局、角色動作／特效／icon 正確；發布新版、下架與重連不靜默換掉進行中的版本。
8. **安裝與降級**：Windows／macOS 對應產物可用，更新前保存、版本 migration 可恢復；AI 未安裝或故障仍走完基本流程。

上述是關鍵端到端組，不取代 schema／權限等單元測試，也不是要求每個 PR 把所有平台、英雄、網路故障做笛卡兒積重跑。

## 13. 分批執行與合併順序

| 批次 | 主要工作／分工 | 完成門檻 |
|---|---|---|
| I0：整合基線 | Codex 核對 Main、Forge commit／變更及既有 PR；Main 確認契約與安全入口 | 有逐檔接縫清單、最新基線結果；不合併未確認改動，不重開已有票 |
| I1：單一鑄造核心 | 原 Forge 成果接入 fresh branch；Codex 對接模板／表單，Main review 共用契約 | off 模式可從 UI 建六槽、重複 Product、編輯演出、無損保存回讀 |
| I2：草稿與作品 | Codex 做 autosave／我的作品／改作；Main 補所有權、同步與來源政策 | 關閉恢復、離線及衝突案例過關，Owner 原文與鎖定不被覆寫 |
| I3：完整英雄匯入 | Main 把 Forge 驗證能力接入正式 importer；Codex 補 producer／依賴／回讀 | 同一正式入口接受完整 authoring＋當前 VFX，未支援內容 fail closed |
| I4：投稿審查發布 | Main 做快照／權限／發布編排，Admin 使用共用審閱能力；Codex 接結果 UI | 一個英雄送審、退回重送、核准發布、失敗重試／下架完整可操作 |
| I5：遊戲與同局隔離 | Main 做發布 resolver、房間內容及客戶端取用；Codex 提供情境／視覺證據 | 不同社群英雄同局可玩，與審查版本一致；新版不影響舊局 |
| I6：收斂與交付 | Codex 補 UI／診斷／更新；Main 提供 CI／簽署發布支援；雙方跑範圍驗收 | 八組端到端＋受影響 46 文件證據、平台安裝、未完項均有真實狀態 |
| AI-E8：獨立支線 | 原 Forge 本機 runtime／品質／硬體驗證 | 只有品質、簽署、硬體都符合才開 local；不得假造或延伸舊收據 |

I2 與 I3 可在 I1 契約確定後分別進行；I5 的房間隔離設計可提早確認，但正式啟用依賴 I3／I4。每批切成可獨立驗證的小 PR，避免再把上百 commit 一次丟給 Main。

不要求 Main 重寫已存在的 Forge 業務程式；只由相應擁有者適配必要接縫。Admin／Platform／Game Server 的實際 code ownership 由 Main 確認，不能因本文列出功能就由 Editor 跨界實作。

### PR 與停止迴圈規則

- 開工先 `git status`，保留 dirty 與其他工作樹；每批從當時 `origin/main` 建新的 `codex/<主題>` 分支，不再延長舊 Editor 分支。
- 修改 repo 的 `content/`／`docs/` 前跑 `bash scripts/genguard.sh <path>`；有擁有者就改來源並用 `genrun`，不手改收據／產物。
- 本機先跑受影響的快速測試；push 前按 `AGENTS.md` 一批執行 `pnpm skills:check`、`pnpm editor:accept:release`、`pnpm coord:check`。共用寫檔資源不能盲目平行，使用既有依賴／隔離機制。
- 只更新受影響的產物與證據；不新增另一套 generator 登記、inbox、heartbeat 或狀態檔。
- 開 PR 並附現有 schema 的 packet；CI／Main review 後才合併。不能把 commit、push、測試、人工審查、merge、部署混稱「完成」。
- Main 必要接縫採 claim／question packet；低階 visual brick 才按當前 `brick-request` 閘填真實受阻案例與同一 brickId，不虛構第二支技能湊門檻。
- 同題先查既有 PR 與契約指紋；已解決的缺口不重問。要重開必須有新的依賴變化或可重現反例。
- 已存在的 CI 紅燈先區分基線、測試工具失敗與本次產品回歸；不改門檻騙綠，也不把所有 unrelated 修復攬入本輪。

## 14. 本輪必須給 Main 的關鍵事項

這些是依目前程式與整合目標推導的工作，不是假稱 Owner 已裁決的需求；正式送出前再查最新 Main／既有票，只送仍存在的差異。

1. **完整英雄進同一正式 importer**：接受可再編輯 authoring、六槽與最新演出／資產，沿用 Main 的安全驗證、operation 及收據；確認作品範圍安置不切換全站 ACTIVE。
2. **作品所有權與不可變投稿**：防同 ID 跨作者覆寫；審查固定版本，支援退回重送而不洗掉證據。
3. **發布完成才可選用**：現有 verdict／promotion 接到真實內容安置、發布 pointer 與失敗恢復；列表不能只憑 approved 顯示已上線。
4. **對局內容隔離**：同局多作品、固定 base／版本／資產、客戶端同步與重連；不是直接更新全域 registries。
5. **由 Main 審核的契約微調**：重複 Product 實例、被動 trigger 參數、provider 私有資料隔離及舊專案 migration，按已有型別補接，不做第二套 graph。
6. **既有政策與交付接線**：開關／配額／安全與安裝更新來源由 Main config／CI 提供，Editor 只讀與操作；不重抄各種上限。

**不附帶要求 Main 幫忙逐招調美術、完成 Editor 的家族配方／時間軸，或重造已出貨積木。** Main 的低階缺口另以機器可讀清冊與最小重現證明。

## 15. 預設政策、完成定義與誠實交付

### 15.1 待採用的產品預設

以下是本方案的建議預設，不當成 Owner 已說過的決定。新增政策欄位須由 Main 合併進既有 config，本文不虛構已存在的 config id。

| 政策 | 建議預設／可回頭的操作 |
|---|---|
| 社群開放 | 完成端到端前維持關閉；先以既有 `ui-cues.playerContent.submit/discover` 控制入口，遊戲選用另需後端實際授權，不靠藏按鈕 |
| 改作 | 建議社群作者投稿時可選允許署名改作，並明示授權；官方作品預設禁止，需白名單。未明示權利時不可自動開放 |
| 遊戲選用 | 建議只在房主明確啟用的社群／自訂房間提供，不默默加入官方競技池 |
| 作品版本 | 新房間選最新相容已發布版；進行中房間鎖版，歷史版供稽核／回復而非一堆玩家選項 |
| AI | off 可用且不強迫下載；local 受 E8 閘；BYOK 明確 opt-in，故障不自動切雲端 |
| 退回與重送 | 同作品一份有效待審候選；保留歷史，重新送出才替換待審關聯 |

### 15.2 第一版完成必須同時成立

- 玩家不用 AI、Git 或手寫 JSON，就能做出、保存、重開並投稿完整英雄；常用家族／subtype 不是空選單或死旋鈕。
- 人工及自動鑄造使用同一 HeroProject／共用 service，沒有平行 importer、重複 schema 或不同 UI 各自生成。
- 六槽的機制與演出能在真正事件驅動的場景驗收；已完成舊案例的證據未被丟棄或用代理值冒充。
- 後台可在一頁審完整英雄；發出去的就是被審的那一版，失敗／漂移／重送不越權。
- 至少兩個社群作品可同局使用，版本與資產一致；下架、回復、新版發布不破壞既有對局。
- Windows／macOS 支援範圍有安裝與保存／更新證據；沒有實機證據的平台明列未交付。
- 所有未支援能力、人工未核准、AI E8、外部簽署或發布限制均明確列出，不以整份綠勾隱藏。

每次交付只回報：**本次完成與證據、尚未完成與責任人、當前 PR／CI 狀態、下一個有限步驟**。不再用「積木都完成」代替可操作性、整合、發布及遊戲驗收。
