# 英雄自動鑄造計劃書

- 狀態：提案，待依里程碑實作
- 日期：2026-09-04
- 產品入口：GGD Codex Editor
- 目標產物：可驗證、可重現、可回滾的完整英雄套件

## 1. 決策摘要

「英雄自動鑄造」應完整整合在 GGD Codex Editor。設計師只需提供少量資訊，例如英雄名稱、一句概念與招式名稱；系統即可提出英雄定位、出身、屬性、六個招式、技能機制、視覺／音效方向與測試場景，生成一個可玩的初稿。設計師再透過同一套逐步流程接受建議、切換模板、鎖定欄位、局部重生與手動微調，最後由確定性工具鏈完成編譯、驗證、模擬、封包、上傳與主程式接收。

本設計採「LLM 可選規劃層＋確定性執行層」：LLM 適合把名稱與自然語言概念轉成結構化提案，但不具執行權威；所有數值生成、引用解析、能力檢查、編譯、模擬、封包、驗包、啟用與回滾，都由版本化 Script 與 Schema 決定。未啟用 LLM 時，流程仍可依預設流派與模板完成，只是使用者需要多選幾個結構化選項。

這份文件是產品與工程計劃，不宣稱下列目標功能已經完成。現況已有英雄草稿、技能 Forge、SimWorld 預覽與 Editor package V1 等基礎；完整英雄封包、主程式 staging 驗證、原子啟用、健康檢查與回滾仍需依本計劃實作。

## 2. 產品目標與邊界

### 2.1 目標

1. 所有英雄製作行為均在 Codex Editor 內完成，不要求設計師直接編輯 JSON、JASS、Excel 或檔案目錄。
2. 少量輸入即可產生完整、可玩的英雄初稿，而非只有文字描述或空白表單。
3. 每項自動決策都可查看原因、來源、信心與能力相容性，並可在 Editor 內覆寫。
4. 使用者可逐欄位或逐區塊鎖定、重生、復原及比較差異，不因再次生成而破壞已確認內容。
5. 技能、特效、動畫、圖示、模型、音效與測試場景共享同一個英雄專案與依賴圖。
6. 輸出為自我描述、內容定址、可重現的完整套件；主程式只能在驗證成功後原子啟用。
7. 匯入失敗不污染線上內容；啟用後若健康檢查失敗，可回到上一個已知良好版本。

### 2.2 非目標

- 不讓 LLM 或使用者文字直接產生並執行任意程式碼。
- 不以生成文案取代遊戲端真實編譯、SimWorld、載入與場景測試。
- 不在封包上傳後直接覆寫 `content/` 或逐檔 PUT 成為上線流程。
- 不把「匯入內容」與「加入可選池／發布給玩家」視為同一個權限。
- 不因規則或測試通過，就宣稱 Owner 文案、對話、幽默或換行已人工審核完成。
- 第一階段不追求讓 AI 從零生成可直接商用的模型、動畫或音效；先支援資產選配、引用、替換與能力檢查。

## 3. 設計師體驗

### 3.1 最少輸入

必填：

- 英雄名稱
- 一句英雄概念，例如「會用自己的血灌溉植物的前排法師」
- 招式名稱；可只填已想到的名稱，其餘由系統提案

選填：

- 出身、路線、射程、資源類型與難度
- 禁止出現的機制、題材或資產
- 參考英雄、偏好的技能模板或 VFX 風格
- 目標強度、團隊職責與操作複雜度
- 是否允許使用 LLM；未提供時沿用專案／工作區設定

只輸入名稱時仍可生成，但所有語意推論必須標成「假設」，顯示信心與依據，且不得默默變成已確認需求。

### 3.2 單一導引流程

Editor 提供一個可中斷、可恢復的「英雄鑄造專案」，左側為步驟，中央為編輯器，右側為即時解釋、相依性與問題清單。

1. **概念**：輸入最少資料，選擇自動程度，產生或編輯英雄企劃。
2. **身分與資產**：確認 ID、名稱、Owner 文案、模型、頭像、圖示與主題色。
3. **出身與屬性**：確認出身、路線、攻擊型態、成長曲線、資源、移速與力量預算。
4. **技能組**：依序處理 PASSIVE、Q、W、E、R、EX；每格可用推薦模板、複製既有技能或空白建立。
5. **特效與演出**：設定 VFX Product／Chain、動畫、掛點、圖示、音效與降級方案。
6. **試玩與驗證**：在 SimWorld 與 3D 預覽執行一般及高風險場景，顯示阻擋、警告與人工檢查項目。
7. **封包與交付**：凍結計劃、重建兩次、比較 digest、產生 ZIP、上傳、追蹤驗包與啟用結果。

每一步都能儲存草稿並回到上一步；尚未完成的欄位可留在「待決定」，不以隱藏預設值偽裝完成。

### 3.3 欄位狀態與重生規則

所有可生成欄位都具備下列狀態：

| 狀態 | 意義 | 再次生成時的行為 |
| --- | --- | --- |
| `auto` | 仍由系統管理 | 可依新條件更新 |
| `manual` | 使用者曾修改 | 預設保留，除非使用者明確選擇覆寫 |
| `locked` | 已確認且禁止自動變更 | 永不由重生覆寫 |

區塊操作包含「重生這一區」「保留手動內容後重生」「查看候選方案」「接受建議」「還原」「鎖定」與「解鎖」。每次重生先顯示差異，再由使用者套用；跨區影響必須列出，例如修改射程可能影響技能模板、數值預算、動畫與場景測試。

## 4. 系統架構

```text
Designer
   │
   ▼
Codex Editor Hero Project
   ├─ Wizard / Diff / Locks / Provenance
   ├─ Optional LLM Planner ──► hero-plan.json
   ├─ Recommendation Engine
   ├─ Deterministic Generators
   ├─ Skill Forge + VFX Workbench + Asset Registry
   ├─ Compiler + Validators + SimWorld + 3D Preview
   └─ Package Builder / Upload Client
                         │
                         ▼
Game Importer
   Quarantine → Verify → Recompile → Stage → Test
              → Immutable Candidate → CAS Activate
              → Health Check → Curate/Publish → Rollback
```

### 4.1 薄 UI、共享核心

Editor UI 只負責流程編排與呈現；實際工作由 `packages/shared` 或可由 CLI 呼叫的共享模組完成，確保桌面 Editor、CI 與主程式驗證使用相同邏輯。對應的 Script 介面如下：

| 指令 | 輸入 | 產出 | 必須確定性 |
| --- | --- | --- | --- |
| `hero:plan` | 最少輸入、模板索引、能力快照 | `hero-plan.json` 候選 | LLM 路徑否；純模板路徑是 |
| `hero:generate` | 已接受並凍結的 plan | Champion、六技能、VFX／資產引用草稿 | 是 |
| `hero:validate` | 完整 authoring graph | Schema、引用、預算、能力、Owner 文案報告 | 是 |
| `hero:simulate` | 編譯內容、場景矩陣、seed | trace、截圖索引、場景結果 | 是 |
| `hero:package` | 已通過 gate 的英雄專案 | 可重現 ZIP、manifest、digest | 是 |
| `hero:upload` | ZIP、目標 profile、授權 | operation ID 與收據 | 傳輸非確定；內容不可變 |

UI 不使用另一套隱藏邏輯；每個按鈕都對應共享函式或上述指令，並把版本、參數與輸出收據存回英雄專案。

### 4.2 英雄專案資料模型

建議新增版本化根文件 `ggd-hero-project@1`，至少包含：

- `projectId`、`heroId`、狀態、建立／更新時間與 base revision
- 使用者輸入、禁止項、目標 profile 與能力快照 digest
- `plan`、候選方案、接受狀態、推論假設與 provenance
- Champion authoring root
- PASSIVE／Q／W／E／R／EX 的 Ability authoring references
- Effect Template、Effect Product、VFX、資產與場景 references
- 每個可生成欄位的 `auto | manual | locked` 狀態
- generator、schema、rule、compiler、template index 版本與 seed
- validation、simulation、manual review、package 與 upload receipts

接受計劃後產生凍結的 `hero-plan.json`。若之後修改會影響結果的輸入、模板、規則或能力快照，Editor 必須把計劃標成 stale，要求重新產生或明確沿用舊計劃。

### 4.3 權威與來源保護

內容權威沿用專案規則：Owner 新描述優先於 Editor JSON、JASS runtime、w3x tooltip 與 raw w3x。匯入舊內容時保留來源文字、對話、幽默與換行；自動化只可新增可驗證的數字事實、標籤與中文 Owner issue，不可未經確認重寫作者語氣。

技能描述中的 `「……」` 是對話，不可被機制抽取器或 LLM 當作觸發條件。來源欄位、衍生欄位與使用者修改必須分開記錄；生成器只能寫入允許的衍生區域。

## 5. LLM 使用政策

### 5.1 建議使用的工作

- 從英雄名稱、概念與招式名稱推論候選定位、主題、技能關係及 VFX 方向
- 產生多個結構化方案，說明取捨與缺少資訊
- 將自然語言需求對應到現有 canonical tags、模板與參數
- 找出技能組在語意上的重複、空缺或不一致
- 草擬需要人類確認的文案，不直接覆寫來源 Owner 文案

### 5.2 禁止成為 LLM 權威的工作

- 輸出或執行任意 Script、JASS、shader 或檔案操作
- 宣稱不存在的 runtime capability 可用，或繞過 target profile
- 決定編譯結果、digest、測試是否通過、是否可上線
- 自動啟用、發布、加入可選池或回滾正式內容
- 把低信心推測偽裝成使用者需求

LLM 輸出必須通過嚴格 Schema，僅能引用 capability catalog、canonical tags、模板與合法參數。無法解析、引用不存在、能力不足或版本不相容時 fail closed，回到 Editor 顯示問題。

### 5.3 無 LLM 模式

無 LLM 時，`hero:plan` 使用出身、路線、技能槽、攻擊型態、複雜度、元素與玩法模板的組合產生候選。若使用者只提供名稱而沒有足夠結構，Editor 會要求補選少量選項，不會以隨機猜測補完。後續生成、驗證、模擬與封包能力與 LLM 模式相同。

## 6. 模板推薦與自動生成

### 6.1 推薦排序輸入

推薦引擎以可解釋的規則排序，輸入包含：

- 出身、路線、技能槽與團隊職責
- canonical tags、目標方式、傷害／控制／位移／元素／時間型態
- 目標強度、資源、冷卻、射程、操作與認知複雜度預算
- 技能組已具備與仍缺少的功能
- target profile 的 live／supported／preview-only／unsupported capability
- 模型、動畫、掛點、VFX、音效與授權資產的可用性
- 模板成熟度、測試覆蓋、歷史採用與已知限制

每張推薦卡顯示「為何推薦」「缺少什麼」「會新增哪些依賴」「能力狀態」「預估力量／複雜度」與可替代模板。推薦結果不可只是一個黑箱分數。

### 6.2 六個技能槽

PASSIVE、Q、W、E、R、EX 各自支援三種起點：

1. **推薦模板**：帶入合法參數、預設產品鏈、場景與 VFX 配方。
2. **複製既有技能**：建立新 ID 與來源引用，避免直接修改原技能。
3. **空白建立**：只建立 Schema 合法的最小骨架。

自動生成的技能必須是模板與結構化 authoring composition，不是英雄專屬 runtime script。技能機制只能使用能力目錄已支援的節點；未支援需求列為 blocker 或明確降級，不可偷偷以 preview-only 效果取代正式 gameplay 行為。

### 6.3 預算與自動調整

力量預算是輔助指標，不是平衡真理。系統可依角色定位提出數值範圍與互補性警告，但每次自動調整都需產生 diff、理由、受影響場景與 seed。預設只調整 `auto` 欄位；`manual` 與 `locked` 欄位不動。達不到預算時回報衝突，而不是突破鎖定。

## 7. 特效、動畫與資產

技能 VFX 應重用現有 Effect Template、Effect Product、Chain 與 VFX Workbench。每個 gameplay event 對應可驗證的演出事件，Editor 同時顯示：

- 遊戲效果與視覺／音效事件的對應
- 模型、動畫、掛點、材質、圖示、音效等依賴
- 正式 runtime、Editor preview 與 fallback 的能力差異
- 遺失資產、循環引用、超額尺寸與授權／來源問題
- 關閉華麗特效、低規格或能力不足時的降級結果

資產不可只靠路徑引用；封包 manifest 必須記錄 kind、MIME、byte size、SHA-256、來源、授權註記與消費者。第一階段優先使用既有資產與匯入；未來若加入圖片／音效／模型生成，也只能先進入候選資產區，通過檢查與人工接受後才成為英雄依賴。

## 8. 驗證與試玩

### 8.1 Editor 即時驗證

每次修改執行增量檢查，封包前執行完整 gate：

- Schema、ID、引用閉包、槽位唯一性與 base revision
- target profile capability 與 preview/runtime 差異
- 數值範圍、冷卻、資源、標籤、Owner 文案與本地化完整性
- 資產 digest、格式、大小、掛點、動畫與 fallback
- 編譯兩次的 byte／digest 一致性
- gameplay-to-render trace 與不可觀測的視覺承諾
- 必要人工檢查是否完成；自動化不可替人工簽核

### 8.2 場景矩陣

每名英雄至少產生並執行下列場景，實際清單由技能能力與標籤擴充：

- 單體命中、未命中、冷卻與資源不足
- 範圍技能、邊界、最大目標數與目標死亡
- 位移、碰撞、地形、不可位移與中斷
- 控制、免疫、驅散、重複施放與疊層上限
- 延遲、週期、持續時間、取消、施法者死亡與 reset
- 投射物、命中事件、召喚物、光環與 owner 切換
- PASSIVE／Q／W／E／R／EX 的交互與資源循環
- 模型／動畫／掛點缺失與低規格 VFX fallback
- save／load、全量內容載入與既有英雄回歸

SimWorld trace 是 gameplay 意圖驗證的權威；3D 預覽用於確認渲染事件與資產呈現。兩者不一致時阻擋發布，不能只以預覽看起來正常作為通過依據。

## 9. 完整英雄封包

### 9.1 契約版本

現行 `ggd-editor-package@1` 主要涵蓋 ability／item 與 icon asset，不足以表達 Champion root、完整六技能依賴、模型、材質與音效。英雄鑄造應新增能力協商後的版本化契約，例如 `ggd-editor-package@2` 搭配 `ggd-hero-bundle@1` selection，並保留 V1 匯入相容性；不可在不升版的情況下改變既有欄位語意。

### 9.2 建議內容

```text
manifest.json
authoring/champion/<hero-id>.json
authoring/ability/<hero-id>.<slot>.json
authoring/effect-template/<id>.json
authoring/effect-product/<id>.json
authoring/vfx/<id>.json
compiled/champions/<hero-id>.json
compiled/abilities/<ability-id>.json
assets/models/<sha256>.<ext>
assets/textures/<sha256>.<ext>
assets/icons/<sha256>.<ext>
assets/audio/<sha256>.<ext>
validation/hero.<hero-id>.json
validation/scenario.<scenario-id>.json
reports/owner-text-diff.json
reports/capability-report.json
reports/asset-report.json
reports/manual-review.json
```

manifest 的 selection root 是單一 Champion authoring root，dependency closure 必須涵蓋六技能、模板、產品、VFX、場景與資產。每個 entry 記錄路徑、類型、Schema、SHA-256、大小與依賴；ZIP 採固定排序、固定 metadata 與受控壓縮設定，讓同一凍結輸入產生相同 digest。

`compiled/` 與 `expectedDerived` 只作為比較證據，主程式不得直接信任。主程式需以自己的 compiler 重新產生並比較，再重建 champion／ability mirrors、索引、bundle 與 manifest。

## 10. 主程式接收、拆包與啟用

### 10.1 操作狀態

```text
UPLOADED → QUARANTINED → VERIFIED → STAGED → TESTED
         → CANDIDATE_READY → ACTIVATING → ACTIVE → HEALTHY
                                              └→ ROLLED_BACK
```

失敗狀態需記錄分類，例如 transport、zip safety、schema、reference、capability、compile、digest drift、scenario、activation、health 或 curation，而不是只回傳一個通用錯誤。

### 10.2 安全匯入順序

1. 以串流與大小上限接收 ZIP，建立 operation ID、上傳 digest 與不可變收據。
2. 在隔離區解壓；拒絕 path traversal、symlink、重複／大小寫衝突路徑、zip bomb、超額檔案與不符 magic bytes 的資產。
3. 驗證 package/schema 版本、entry digest、selection、引用閉包、base revision 與 target capability。
4. 使用遊戲端受信任 compiler 編譯兩次，確認結果一致並與套件證據比較。
5. 在 staging 重新建立 derived artifacts，執行必要場景、全量 loader 與衝突檢查。
6. 產生 verified plan，列出 candidate digest、內容差異、警告、人工 gate 與可回滾目標。
7. 寫入不可變 candidate，以 compare-and-swap 更新 ACTIVE 指標，禁止部分檔案可見。
8. 執行健康檢查；失敗時以 CAS 回到上一個已知良好版本並保留完整 audit trail。
9. 內容 ACTIVE 後，另行提交 curation／pickability 操作；它可以由同一個 Editor 流程追蹤，但必須具備不同權限與收據。

主程式不得直接把 ZIP 解壓到正式 `content/`，也不得以套件內的成功報告代替自己的檢查。

## 11. 權限、稽核與失敗處理

- `draft`、`validate`、`upload`、`activate`、`curate`、`rollback` 分別授權；本地生成權不等於正式發布權。
- 每次 LLM 提案保存 provider／model、prompt template、Schema、能力快照、seed 與接受差異；敏感 prompt 或憑證不得進套件。
- 每次 Script 保存版本、輸入 digest、輸出 digest、stdout 摘要與結構化報告。
- Editor 顯示主程式回傳的 operation timeline，允許安全重試；idempotency key 防止重複匯入或重複啟用。
- 網路中斷時先查 operation 狀態，不盲目重送 activate。
- 所有 blocker 都需能定位到步驟、文件、欄位或資產；修正後只重跑受影響與強制 gate。
- 回滾只改 ACTIVE 指標，不刪除 candidate、舊版本或稽核證據。

## 13. 實作里程碑

### H0：契約凍結與測試骨架

交付：Hero Project Schema、Hero Plan Schema、package V2／hero bundle 契約、Champion authoring kind、operation state、權限矩陣、golden fixtures 與 mutation test 清單。

Gate：相同 fixture 在 Editor 與 Content API 通過；未知欄位、未知能力、錯誤 digest、路徑攻擊、依賴遺失與 compiler 版本不合均 fail closed。

### H1：Editor Hero Project 與導引殼層

交付：專案建立／恢復、七步 wizard、最少輸入、`auto/manual/locked`、區塊重生、diff、undo、問題導覽與 provenance UI。

Gate：重新開啟專案不遺失狀態；重生不改 locked，預設不覆寫 manual；跨區依賴能標 stale。

### H2：規劃、推薦與生成

交付：純模板 planner、可選 LLM adapter、推薦排序與原因、六槽技能生成、力量／複雜度預算、版本與 seed 凍結。

Gate：關閉 LLM 仍可完成；非法 LLM 輸出無法進 authoring graph；固定 plan 可重現相同內容；推薦只使用 live capability。

### H3：技能、VFX 與資產整合

交付：Skill Forge writeback、Effect Product／Chain、VFX Workbench、動畫／掛點／圖示／模型／音效 registry、fallback 與資產報告。

Gate：修改 gameplay 事件會使相關演出檢查 stale；缺資產或 unsupported runtime capability 阻擋封包；preview-only 明確標示。

### H4：驗證、試玩與自動調整

交付：完整 validator、場景產生器、高風險矩陣、SimWorld trace、3D render bridge、截圖／事件證據、有限度 autotune。

Gate：每一能力都有 positive、negative 與 mutation test；模擬與渲染事件不一致時 fail；人工檢查未完成不可偽裝通過。

### H5：完整英雄封包

交付：package V2 builder、Champion selection、完整依賴閉包、binary assets、固定 ZIP、兩次重建、Owner／能力／資產／人工報告。

Gate：相同凍結專案輸出相同 digest；變更任一 entry 都被偵測；V1 regression fixtures 保持可讀；超額與惡意 ZIP fixture 被拒絕。

### H6：主程式驗包與 staging

交付：安全上傳、隔離拆包、Schema／hash／reference／capability 驗證、遊戲端雙編譯、compiled compare、derived rebuild、scenario 與 full-loader gate。

Gate：任何失敗都不修改 ACTIVE；可由 operation ID 取得結構化錯誤與完整 audit evidence；重試具冪等性。

### H7：原子啟用、健康檢查、發布與回滾

交付：不可變 candidate、CAS ACTIVE、健康檢查、自動／手動回滾、curation proposal、權限與收據。

Gate：併發啟用只有一個成功；任何時刻玩家只看到完整舊版或完整新版；健康失敗可回復；curation 未授權時內容可 ACTIVE 但不可選用。

### H8：端到端與桌面交付

交付：從三個最少輸入到遊戲可選英雄的 E2E、重啟恢復、離線／網路中斷、Windows clean-checkout smoke、效能與容量基準、設計師操作手冊。

Gate：新使用者可依導引完成；測試涵蓋成功、拒絕、重試、衝突、健康失敗與回滾；產出的證據可由另一台乾淨環境重驗。

- 高風險場景矩陣、事件正確的 3D render bridge 與有限度 autotune

## 15. 主要風險與緩解

| 風險 | 緩解 |
| --- | --- |
| 名稱太少導致 AI 猜測過度 | 標示假設、信心與 provenance；低信心要求補選；支援無 LLM 模式 |
| 自動生成覆寫設計師成果 | `auto/manual/locked`、diff、undo、區塊套用與 stale tracking |
| 預覽與正式玩法不一致 | SimWorld 為 gameplay 權威；事件 trace 連接 3D 預覽；能力不足 fail closed |
| 套件含惡意或過大資產 | 串流上限、隔離拆包、路徑／magic／hash／size 驗證與 allowlist |
| Editor 與主程式 compiler 漂移 | compiler digest、雙編譯、game-side recompile 與 compiled compare |
| 部分上線或併發覆蓋 | immutable candidate、CAS ACTIVE、健康檢查與回滾 |
| 通過規則卻破壞作者文案 | 完整 Owner 文字 diff、來源保護與明確人工 review gate |
| 兩套 Hero Forge 分歧 | shared 核心為唯一規則來源；Admin 只保留過渡入口 |
| 一鍵流程越權發布 | validate／activate／curate 權限與收據分離；UI 可連續但後端不合併授權 |

## 16. 完成定義

以下條件全部成立，才能稱為「英雄自動鑄造完整上線」：

1. 設計師僅以英雄名稱、一句概念與招式名稱，可在 Codex Editor 產生完整英雄初稿。
2. 不使用 LLM 也有可完成的模板流程；使用 LLM 時所有輸出受 Schema、能力與 provenance 約束。
3. 設計師可逐步調整，locked／manual 欄位在重生中受到保護，所有變更可比較與復原。
4. Champion、六技能、機制、VFX、動畫、圖示、模型、音效與測試形成封閉且可追蹤的依賴圖。
5. 固定輸入可重現相同 authoring、compiled 與 package digest。
6. 完整 Owner 文案、對話、幽默與換行已逐項審查；自動規則通過不能取代該審查。
7. 必要場景、全量 loader、能力、資產與安全 gate 全數通過，人工 gate 有具名收據。
8. 主程式在隔離區驗包、重新編譯、重建 derived artifacts，未通過時不改變 ACTIVE。
9. 啟用為原子 CAS，健康失敗可回滾；curation／pickability 另有明確權限與結果。
10. 從 Editor 建立到主程式可選用的成功與失敗 E2E，能在乾淨桌面環境重現。

## 17. 建議立即執行順序

1. 先完成 H0，凍結 Hero Project、Hero Plan 與 package V2 契約，避免 UI、生成器與 importer 各自猜測。
2. 以現有 `heroForge` 純邏輯與 Editor Forge 建立 H1 垂直切片：一名英雄、六槽、既有資產、可儲存與重開。
3. 加入純模板 `hero:plan`，確認無 LLM 的完整路徑，再接可關閉的 LLM adapter。
4. 打通「生成一名英雄 → SimWorld → deterministic ZIP → Content API read-only validate」的第一條 E2E。
5. 在 read-only validate 有足夠拒絕測試與 evidence 後，才實作 apply、curation 與 rollback。

上述順序讓自動化從第一個垂直切片就可驗證，同時保留未來擴充 LLM、資產生成與正式發布的契約空間。
