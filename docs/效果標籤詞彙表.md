>
> 用途有兩個：
> 1. **owner 寫技能/道具/增益卡規格時**用中文方括號標籤（`【暈眩】`、`【焚身】`），

## 0 · 先讀這一段：五層是不同的東西，不能混用

一個常見的誤解是把所有「效果」當成同一層。實際上：

| 層 | 是什麼 | 例 |
|---|---|---|
| **1 · 效果種類** | `EffectDef.kind` —— 原子動作 | `damage` / `dot` / `leap` / `shield` |
| **2 · 狀態軸** | 掛在 `applyStatus` 上的具名欄位 | `stun` / `root` / `moveSpeedMult` |
| **3 · 觸發時機** | `HookDef.on` —— 事件 | `onBasicAttack` / `onKill` |
| **4 · 條件** | `HookDef.condition` —— 才算數的情況 | 血量低於 X%、機率 |
| **5 · 授權格** | 哪一種文件可以宣告哪一種能力 | 卡片只有 `modifiers` 與 `hooks` |

**具體例子**：`【暈眩】` 和 `【焚身】` 看起來是同一種東西，在引擎裡分屬不同層 ——
- `【焚身】` 是**層 1** 的 `dot`（一個效果種類）
- `【暈眩】` 是**層 2** 的 `stun`（`applyStatus` 上的一個布林開關）

所以「給我一個暈眩效果」在引擎裡不存在。正確的寫法是
**「發一個 `applyStatus`，把 `stun` 這一軸打開」**。

## ⛔ 三個結構性的洞 —— 實作編輯器之前必須知道

### ① 引擎完全沒有「解除狀態」的能力

沒有淨化、沒有驅散、沒有 `dispellable` 欄位。
`world.status` 的 `st.effects` 陣列在全 repo 只有兩個會**縮小**它的站點：

1. `packages/shared/src/sim/systems/StatusSystem.ts` —— 到期過濾（整個檔案只有 9 行）
2. `packages/shared/src/sim/effects/revive.ts:367` —— `st.effects = []`，
   **唯一一次真的清空**，但綁死在「把屍體扶起來」的路徑上，內容作者拿不到

其餘全是「加」或「刷新」。`world.dot` 是獨立的 Map，連 revive 那條都碰不到。

**後果**：所有 debuff 都沒有解法。
**owner 2026-08-04 已核准補上淨化／驅散。**

### ② 殭屍身上吃不到 `applyStatus` / `applyBuff` / `grantAttribute`

`packages/shared/src/sim/mobs.ts` 從不建 StatusComp 也不建 StatsComp，所以那三個效果
對整波殭屍**靜默無效，而且沒有任何錯誤訊息**。

有效的四個 —— `taunt` / `knockback` / `invulnerable` / `dot` —— 全都走**自己的 world store**。
**那就是要抄的形狀。**

**後果**：這份表裡一整批標成「✅ 已有」的東西，在第 3 場之後（殭屍波開始）
**對場上大多數敵人是無效的**。編輯器如果不標示這件事，作者會做出一張在殭屍回合半殘的卡。

### ③ 三選一增益卡的授權面比技能窄得多

`zAugmentDef` 只有 `modifiers` 與 `hooks` 兩格。
所以「隱身 5 秒」「格擋 3 秒」「飛行 5 秒」這類卡**今天一張都寫不出來**
—— **不是因為機制不存在**：sim 端的 `syncVisionGrants` / `syncFlightGrants`
讀的是**任何**帶 `expiresAtTick` 的 ModifierSource，缺的純粹是 schema 上的欄位。

## 附錄 A · 硬性技術約束（實作前必讀）

這些不是風格建議，是會讓測試變紅或讓線上壞掉的東西：

- **`packages/shared/src/sim/**` 禁用** `Math.random` / `Date.now` / 三角函式 / `**`（冪運算）。
  守衛：`packages/shared/src/sim/purity.test.ts`。
  到期一律用**絕對 tick**，不是遞減計數器。Map 迭代要先排序。
  → 影響：扇形投射物不能用 `sin`/`cos`；技能加速不能用 `1/(1+h/100)` 的冪形式。
- **Colyseus `defineTypes` 是 APPEND-ONLY** —— 新欄位只能加在最後，加錯回不去。
- **`ENTITY_FLAG` 的位元已經用完。** CLAUDE.md 寫「剩 16384 / 32768 兩格」是**過期的**
  （MOB_ELITE 拿走 32768、INVISIBLE 拿走 16384）。任何要上線的新狀態旗標要先想清楚怎麼傳。
- **30Hz 決定性 sim**，replay 靠重放輸入 —— 任何非決定性的東西會讓錄影對不起來。
- **每一個新欄位要同時落在三個地方**（`CLAUDE.md` 第一守則），缺一個 drift 測試就紅：
  1. `content/config/*.json` — 出貨值
  2. `packages/shared/src/content/schema/config.ts` — Zod schema（**上下界都要**）+ `DEFAULT_*`
  3. `apps/admin/src/*.ts` — `SHIPPED_*` + 欄位 union + 順序 + 標籤 + 分組 + `configFromForm`
  ⚠️ 如果那個欄位也走 Go 平台，`apps/platform/internal/*` 的鏡射**一定要一起改** ——
  key 不在 Go 那份，平台會把它從它服務的每一張表丟掉，後台看不到也改不了。

## 附錄 B · 開發守則摘要

- **第一守則**：所有功能做成後台可調。**寫死才需要理由。**
  尤其是**決策點** —— 如果實作時心裡出現「這裡要選 A 還是 B」，那就是一個後台開關。
- **第二守則**：每個功能要有「改壞就會紅」的守衛，而且要做**突變驗證**
  （把關鍵那行改壞 → 確認紅 → 改回）。
  但**驗機制不驗數字** —— 出貨數值不要寫進斷言，它們已經有三個住處。
- **第三守則**：註解會說謊。看到「已驗證」「measured」「see xxx.test.ts」先確認那個檔案存在。

完整版見 repo 根目錄的 `CLAUDE.md`。

## 附錄 C · 這份文件怎麼維護

它是由 `content/` 與 `packages/shared/src/` 的實際內容盤點出來的，不是手寫的。
**引擎新增一個 kind / 狀態軸 / 觸發事件之後，這份表要一起更新** ——
否則它會變成第三守則點名的那種「自洽地一起錯」的文件。
