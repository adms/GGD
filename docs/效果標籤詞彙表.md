# 第一部 · 詞彙表

## 0 · 先讀這一段：五層是不同的東西，不能混用

一個常見的誤解是把所有「效果」當成同一層。實際上：

| 層 | 是什麼 | 例 |
|---|---|---|
| **1 · 效果種類** | `EffectDef.kind` —— 原子動作 | `damage` / `dot` / `leap` / `shield` |
| **2 · 狀態軸** | 掛在 `applyStatus` 上的具名欄位 | `stun` / `root` / `moveSpeedMult` |
| **3 · 觸發時機** | `HookDef.on` —— 事件 | `onBasicAttack` / `onKill` |
| **4 · 條件** | `HookDef.condition` —— 才算數的情況 | 血量低於 X%、機率 |
| **5 · 授權格** | 哪一種文件可以宣告哪一種能力 | 卡片只有 `modifiers` 與 `hooks` |

**具體例子**：`【暈眩】` 和 `【焚身】` 看起來是同一種東西，在引擎裡分屬不同層 ——
- `【焚身】` 是**層 1** 的 `dot`（一個效果種類）
- `【暈眩】` 是**層 2** 的 `stun`（`applyStatus` 上的一個布林開關）

所以「給我一個暈眩效果」在引擎裡不存在。正確的寫法是
**「發一個 `applyStatus`，把 `stun` 這一軸打開」**。

## ⛔ 三個結構性的洞 —— 實作編輯器之前必須知道

### ① 引擎完全沒有「解除狀態」的能力

沒有淨化、沒有驅散、沒有 `dispellable` 欄位。
`world.status` 的 `st.effects` 陣列在全 repo 只有兩個會**縮小**它的站點：

1. `packages/shared/src/sim/systems/StatusSystem.ts` —— 到期過濾（整個檔案只有 9 行）
2. `packages/shared/src/sim/effects/revive.ts:367` —— `st.effects = []`，
   **唯一一次真的清空**，但綁死在「把屍體扶起來」的路徑上，內容作者拿不到

其餘全是「加」或「刷新」。`world.dot` 是獨立的 Map，連 revive 那條都碰不到。

**後果**：所有 debuff 都沒有解法。
**owner 2026-08-04 已核准補上淨化／驅散。**

### ② 殭屍身上吃不到 `applyStatus` / `applyBuff` / `grantAttribute`

`packages/shared/src/sim/mobs.ts` 從不建 StatusComp 也不建 StatsComp，所以那三個效果
對整波殭屍**靜默無效，而且沒有任何錯誤訊息**。

有效的四個 —— `taunt` / `knockback` / `invulnerable` / `dot` —— 全都走**自己的 world store**。
**那就是要抄的形狀。**

**後果**：這份表裡一整批標成「✅ 已有」的東西，在第 3 場之後（殭屍波開始）
**對場上大多數敵人是無效的**。編輯器如果不標示這件事，作者會做出一張在殭屍回合半殘的卡。

### ③ 三選一增益卡的授權面比技能窄得多

`zAugmentDef` 只有 `modifiers` 與 `hooks` 兩格。
所以「隱身 5 秒」「格擋 3 秒」「飛行 5 秒」這類卡**今天一張都寫不出來**
—— **不是因為機制不存在**：sim 端的 `syncVisionGrants` / `syncFlightGrants`
讀的是**任何**帶 `expiresAtTick` 的 ModifierSource，缺的純粹是 schema 上的欄位。

## 成本形狀

**成本形狀：owner 的 17 張卡名目上引用了 61 個新東西（21 個效果 kind 引用 · 7 個觸發事件 · 7 個 hook 欄位 · 3 個條件 · 18 個屬性 · 5 個加成方式），實際上只有 12 批工作，而且真正的新原語只有 4 個 effect kind、0 條新 Stat、1 個新 ModOp。**三路盤點交叉去重之後，合併率是 O(61) → O(12)。

**最關鍵的發現有五個：**

**① 六（其實是七）個堆層 kind 是同一根。**applyStackingBuff / applyRoundStackingBuff / applyChargeBuff / incrementTargetCounter / resetTargetCounter / addPersistentCounter / refreshDerivedModifier ＝ 既有的 `applyBuff` ＋ 5 格欄位（活多久 · 記在誰帳上 · 加還是扣 · 到頂做什麼 · 讀取量化）。而且 applyBuff **已經答對其中一種**（stackKey/maxStacks），statPipeline **已經在乘 stacks**。**新 kind 數 = 0，砍掉 7 個 handler + 7 張編輯器卡 + 7 套測試。**其中 `refreshDerivedModifier` 與 `resetTargetCounter` **整個消失** —— 前者是計數器的讀取面而讀取面本來就存在，後者是一個布林。

**② 11 個「新屬性」一條都不該進 Stat enum。**abilityHaste / abilityDamage / healingDone / shieldingDone / abilityDisabled / abilitySlots / abilityTags 是同一根 `abilityMods`（騎在 ModifierSource 上、在**四個已經存在而且已經各乘一個全域因子**的讀取點解析）；`conversion` ＝ 已出貨的 `percentOf`、`set` ＝ 已出貨的 `override`（新建它們的唯一產出是兩個同義詞）；`bonusAd` / `asFromBonusMs` ＝ 一格 `basis`（而且有現成的 `attrRatios.basis` 可以照抄）；`adaptiveForce` 騎現成的兩趟管線。實測代價：**每加一條 Stat ＝ 5 個編譯錯誤點 + 1 個只有測試守得住的點 + 後台兩頁各多一個對操作者毫無意義的輸入框 + 玩家面板多一列。**11 條全做成 Stat ＝ 30 處改動 + 22 個空白輸入框；走 abilityMods ＝ **O(30) → O(5)**。

**③ 四個「新事件」是一條佇列。**onMobilityEnd / onHardCCApplied / onEnterCombat / onLevelUp 全部卡在同一件事（發生地點不可以 import effects/hooks，會 close 初始化環），而解法**已經在 repo 裡跑著**（world.pendingStunHooks ＋ ccHookSystem）。泛化一次，4 支 bespoke system 變成 1 支 drain ＋ 5 個一行 push，順手補完 onLevelUp「後台選得到但零發射點」的既有謊言。

## ⚖️ owner 已裁決的三項（2026-08-04）

### 1 · 角色體型 —— ✅ 做，而且比盤點者估的便宜

owner：「**其實不難，因為殭屍王已經是這樣，有預留倍率參數**」

查證下來 owner 是對的，而且盤點者的「可能永遠寫不出來」是**錯的**，有三個理由：

1. **渲染端的機器已經在跑。** `apps/client/src/render/EntityViewRegistry.ts` 的
   `mobModelSizeOverride()` 做的就是 `relativeScale = docScale × sizeMult`，
   而且註解明寫「兩個因子不是一個，刻意的」。擋住英雄的只有開頭一行
   `if (e.kind !== ENTITY_KIND.MOB) return null;`。
2. **線材的做法已經有前例。** 殭屍走 **SLOT REUSE**：`EntityState.mana` 那一格
   在 MOB 身上是體型倍率（`maxMana` 保持 0，所以沒有人會從它畫魔力條）。
   同一個慣例也用在復活圈、金幣、暗夜旗上，`protocol/schema.ts:745` 有完整說明。
   ⚠️ 英雄的 `mana` / `maxMana` / `shield` 都真的在用，**不能照抄這一招** ——
   英雄要的是在 `defineTypes` 最後**追加一格 `float32`**。
   ⚠️ 「append-only」的意思是**只能加在最後**，不是不能加。追加是受認可的路徑，
   只是不可逆 —— 所以要跟其他要上線的欄位**合併成一次追加**，不要各加各的。
3. ⭐ **`bodyScale` 已經是英雄卡上的一個活數值**，而且已經接進
   `config.ts` 的 `attackRangeCurve`（體型越大射程越遠，見 `sim/bodyScale.ts`）。
   **所以體型對英雄早就不只是視覺**，`giant-slayer` 的傷害公式讀它是合理的。

**剩下的實際工作**：把 `bodyScale` 從「開場讀一次的靜態值」變成「跑的時候會變的值」
（＝一條可以被 modifier 改的通道）＋ 一格線材 ＋ 拿掉渲染端那個 `kind` 閘。

建議做成一個開關，預設**只動外觀與射程**（＝今天 `attackRangeCurve` 已經有的行為），

### 批 11（驅散／淨化）
11-1 **拔哪些池** status / dot / buff / shield 四個獨立開關（陣列欄位）。「拔盾」特別強，owner 大概想單獨控制。
11-2 **`dispellable` 的預設值** ⭐ A＝預設 true → 功能一上線，**14 份 status 文件與每一支 DoT 同時變成可拔**，那是一次真的平衡改動／B＝預設 false → 按鈕上線那天視覺上什麼都不做（失敗形態 ②）。**建議 status/dot 預設 true、buff 預設 false**（沒有人預期自己的道具被動可以被敵人剝掉），逐份可覆寫。
11-3 **正面增益能不能被敵人拔**（「驅散」vs「淨化」的分野）→ `polarity` 欄位，⛔ **必須在施加時就寫死，不能靠推導**（一個 ModifierSource 可以同時帶正負 modifier）。
11-4 **只拔一部分時拔誰** newest / oldest / longest / shortest。⛔ **必填或有明確預設** —— 沒有這一格就是靠陣列順序，直接違反 purity 的「Map 迭代要先排序」。
11-5 **免疫擋不擋得住被驅散**（invulnerable.blocksControl 目前只管 stun/root/減速）。**預設不擋**（驅散不是控場）。
11-6 **疊層的燃燒是全拔還是拔一層** → 欄位 `dotStackMode`。

### 批 12（體型）—— 全部住進既有的 `config.body-scale@1`
12-1 **size 影響碰撞半徑 / 受擊判定**（在這個引擎是**同一格**，只有 Transform.radius，沒有第二個 hitbox）。**預設開**，否則 goliath 的 +30% 只是貼圖。⚠️ 但這會改變既有錄影的軌跡（世界狀態問題不是 rng 問題）—— 若要保留舊錄影可比性，**出貨預設關**。
12-2 **size 影響普攻射程** **預設開** —— 曲線已經在 sim/bodyScale.ts（斷點表 1→1.0 / 2→1.2 / 3→1.3，線性內插兩端夾住），這一格只是把它從讀 def.bodyScale 改成讀 live size。
12-3 **size 影響技能距離 / AoE 半徑** **預設關** —— bodyScale.ts 檔頭已經明說今天刻意不連動（combatEnv.abilityRange 被 #136 壓到 0.6，再乘體型會讓那個決定對大體型悄悄失效），並且明說「那是**下一個**決定，應該由 owner 看實戰結果來下」。
12-4 **size 影響模型縮放（視覺）** ⛔ **這一題要 owner 拍板，不要替他選。**A＝EntityState 補一格 append-only float32（**單向門，加錯回不去**）／B＝承認體型只影響數值不影響畫面（卡面說謊，失敗形態 ①/②）／C＝借 growthTier 的兩格門檻位元（**不行 —— 那兩格已經是 #244 黑泥吞噬的，語意被佔用，借過來會讓兩個機制互相污染**）。**建議：若 owner 選 A，把這次所有要上線的欄位合併成一次 defineTypes 追加，不要各加各的。**
12-5 **damageAmp 的曲線形狀** min / max / 滿額差距三個數字（卡面的 8% / 25% / 0.8）**都是欄位不是常數**。方向也是資料 —— 「比我小的打更痛」用同一組欄位就寫得出來。
12-6 **殭屍的第二套體型要不要收斂** 殭屍走 radius × radiusMult（wire 借 MOB 的 mana 欄位），與 ChampionDef.bodyScale 是兩套完全不同的數字。A＝維持兩套／B＝讓 size 原語同時讀兩邊並把 #244 growth tier 也收進來。**預設 A**（B 是獨立的一批工作）。

## 殭屍波的影響


### 逐張點名

**❌ 全殘（所有 hook 都被擋）：3 張**
· **symphony-of-war** —— 三個 hook 全 enemyChampion
· **master-of-duality** —— 兩個 hook 全 enemyChampion
· **cerberus** —— onEnterCombat 若不認殭屍就永不進戰鬥，onBasicAttack 又是 enemyChampion

**⚠️ 半殘（觸發器被擋，效果本身沒問題）：8 張**
· mystic-punch · courage-of-the-colossus · tap-dancer · fan-the-hammer · infernal-conduit · doomsayer · plaguebearer · giant-slayer

**✅ 完全不受影響：6 張**
· dual-wield（hook **沒有** targetFilter）· earthwake（觸發器與目標無關）· dashing / goliath / jeweled-gauntlet / back-to-basics（純 modifier 或只看施法者）

### ⭐ 關鍵發現：11 張裡只有 **1.5 張**真的被結構洞② 擋住

我逐張追了效果掛在誰身上，結論是 **11 張裡有 9 張的效果全部掛在「持有者自己」身上**（縮自己的冷卻、給自己護盾、給自己疊層、給自己加計數器、從自己身上發射箭矢、燃燒走 world.dot），**只有觸發條件在看目標**。而持有者永遠是英雄，永遠有 StatsComp。

所以那 9 張的修法是**批 1 決策點 1-1 的一格欄位**（union 加 `enemy` 成員 + 全域覆寫），不是給殭屍 StatsComp：
mystic-punch · symphony-of-war · courage-of-the-colossus · tap-dancer · fan-the-hammer · infernal-conduit · doomsayer · plaguebearer · master-of-duality

**真正被結構洞② 擋住的只有：**
1. **cerberus（完整的 1 張）** —— 易傷（applyStatus）與目標計數器（applyBuff）都必須掛在**目標**身上。mobs.ts 從不建 StatusComp / StatsComp，兩個 handler 的 `if (!st) continue` / `if (!sc) continue` 都是**靜默**丟掉。就算把 targetFilter 放寬到殭屍，這張卡在殭屍波仍然無效。
2. **giant-slayer（半張）** —— 它要讀目標的體型，而殭屍走**另一套** size（radius × radiusMult，wire 借 MOB 的 mana 欄位），與 ChampionDef.bodyScale 是兩個互不知道對方的數字。這是「兩套體型」的問題，不是 StatsComp 的問題，修法也不同。

### 給 owner 的判斷

**⛔ 不建議把結構洞② 排在前面。**投報比很清楚：

| 做法 | 成本 | 救回幾張 |
|---|---|---|
| 批 1 的一格 `enemy` 語意 + 全域覆寫 | **零額外成本**（本來就在批 1 裡） | **9 張** |
| 給殭屍 StatsComp + StatusComp（結構洞②） | 一區 30 隻 × 多區的 per-entity 元件、snapshot 面變寬、每一條屬性管線的熱迴圈變長、**每一場的效能與平衡都要重測** | **1.5 張** |

而且翻開關本身有平衡後果需要 owner 實打確認（symphony 的 12 層與 master-of-duality 的 20 層在殭屍潮裡會瞬間滿層、cerberus 的 3 充能會常駐刷新）—— **所以那一格不該是單一全域布林，要 per-card 可寫 + 一個全域覆寫給 owner 現場翻。**per-card 住在 `content/`（live bind-mount，改一次不用重建映像），全域覆寫住在後台。

⚠️ **最後一件必須做的事**：無論開關怎麼設，**每一張卡的說明文字都要誠實寫出對殭屍是否生效**。否則玩家在第 9 回合滿場殭屍裡拿著 plaguebearer 一點都不疊，會直接認定卡片壞了 —— 那正是 CLAUDE.md 失敗形態 ②（卡片上寫了，遊戲裡是另一件事）。

# 第三部 · 實作前必讀

## 附錄 A · 硬性技術約束

這些不是風格建議，是會讓測試變紅或讓線上壞掉的東西：

- **`packages/shared/src/sim/**` 禁用** `Math.random` / `Date.now` / 三角函式 / `**`（冪運算）。
  守衛：`packages/shared/src/sim/purity.test.ts`。
  到期一律用**絕對 tick**，不是遞減計數器。Map 迭代要先排序。
  → 影響：扇形投射物不能用 `sin`/`cos`；技能加速不能用 `1/(1+h/100)` 的冪形式。
- **Colyseus `defineTypes` 是 APPEND-ONLY** —— 新欄位只能加在最後，加錯回不去。
- **`ENTITY_FLAG` 的位元已經用完。** CLAUDE.md 寫「剩 16384 / 32768 兩格」是**過期的**
  （MOB_ELITE 拿走 32768、INVISIBLE 拿走 16384）。任何要上線的新狀態旗標要先想清楚怎麼傳。
- **30Hz 決定性 sim**，replay 靠重放輸入 —— 任何非決定性的東西會讓錄影對不起來。
- **每一個新欄位要同時落在三個地方**（`CLAUDE.md` 第一守則），缺一個 drift 測試就紅：
  1. `content/config/*.json` — 出貨值
  2. `packages/shared/src/content/schema/config.ts` — Zod schema（**上下界都要**）+ `DEFAULT_*`
  3. `apps/admin/src/*.ts` — `SHIPPED_*` + 欄位 union + 順序 + 標籤 + 分組 + `configFromForm`
  ⚠️ 如果那個欄位也走 Go 平台，`apps/platform/internal/*` 的鏡射**一定要一起改** ——
  key 不在 Go 那份，平台會把它從它服務的每一張表丟掉，後台看不到也改不了。

## 附錄 B · 開發守則摘要

- **第一守則**：所有功能做成後台可調。**寫死才需要理由。**
  尤其是**決策點** —— 如果實作時心裡出現「這裡要選 A 還是 B」，那就是一個後台開關。
- **第二守則**：每個功能要有「改壞就會紅」的守衛，而且要做**突變驗證**
  （把關鍵那行改壞 → 確認紅 → 改回）。
  但**驗機制不驗數字** —— 出貨數值不要寫進斷言，它們已經有三個住處。
- **第三守則**：註解會說謊。看到「已驗證」「measured」「see xxx.test.ts」先確認那個檔案存在。

完整版見 repo 根目錄的 `CLAUDE.md`。

## 附錄 C · 這份文件怎麼維護

它是由 `content/` 與 `packages/shared/src/` 的實際內容盤點出來的，不是手寫的。
**引擎新增一個 kind / 狀態軸 / 觸發事件之後，這份表要一起更新** ——
否則它會變成第三守則點名的那種「自洽地一起錯」的文件。

同一份內容也發成了 hosted 頁面（有固定 URL，改版原地更新，版本之間的演進本身是資料）。
