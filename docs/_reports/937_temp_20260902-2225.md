### 葉子的形狀（跟同一檔的 `status` / `equipment` 逐字同型）

```jsonc
{ "kind":"recentCast", "subject":"self",   "abilityId":"godie-hpb1.w", "withinSec":1 }  // 這一支
{ "kind":"recentCast", "subject":"target", "slot":"R",                 "withinSec":1 }  // 這一格
```

兩個分支各只帶一格且都 `.strict()` ⇒ `{abilityId, slot}` 一起寫是 **PARSE ERROR**，
⛔ 不會安靜地由求值端替作者決定哪一格贏。

### 三個刻意的決定

1. **⭐ 上界是結構性的，⛔ 不是一格 `maxTrackedCasts` 旋鈕。**
   紀錄是 **per-slot 的最後一次** ⇒ 一個身體最多 `CASTABLE_SLOTS.length` = **6 筆**，
   而那個 6 是**槽位的數目**，⛔ 不是一個挑出來的容量。
   同一格按鈕不可能同時放兩支技能，而連續技窗口問的正是「上一次那一格按下去是何時」——
   環形緩衝多存的那些**沒有任何讀端問得到**。
   ⚠️ 已知取捨：變身換掉同一格的技能後，舊技能的紀錄被覆蓋。紀錄帶著**當時真的施放的**
   `abilityId`，所以「剛剛放的是哪一支」永遠對；掉的是「更早以前用這一格放過別支」——
   而那超過任何一個連續技窗口的長度。

2. **⭐ 絕對 tick，⛔ 沒有遞減計數器**（CLAUDE.md 硬約束）。
   存「第幾 tick 放的」，讀端算 `world.tick - at <= Math.round(withinSec / world.dt)`。
   ⇒ ⛔ 不需要每 tick 走一遍全部的身體；⇒ 窗口長度在**讀的當下**才換算，內容改了⛔ 不必重寫紀錄。

3. **⭐ 快取不進 snapshot**（票文點名要先答的那一題）。
   ⇒ **不進**。今天沒有任何客戶端表面要畫「連續技窗口開著」，而一格沒有讀端的
   snapshot 欄位是失敗形態②的反面（送了但沒人收）＋ 一次不可逆的
   `defineTypes` append。要畫的那一天再開一張票。
