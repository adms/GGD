### ⭐ B 的關鍵設計：**只加新文件，⛔ 永遠不改既有的**

| 覆蓋層裡的文件 | 熱套用？ | 為什麼 |
|---|---|---|
| ⭐ **新增**（這個 id 登錄表裡沒有） | ✅ 套 | ⭐ **沒有任何進行中的對局引用得到它** —— 它五秒前還不存在 |
| ⛔ **修改／刪除**（id 已註冊） | ❌ 扣住並**逐份指名** | 改掉一支**正在被使用**的技能＝對局中途換版 |

實作是「① 整棵合併樹 `registerAll()` → ② 把**每一個開機就在的 id** 原封寫回去」。
⭐ 寫回去的是**開機時那個物件參照**（⛔ 不是一份結構相同的新物件）——
一場正在打的比賽握著的 `ChampionDef` / `AbilityDef` 連 identity 都沒有動過。
⚠️ 為什麼不「只註冊新的那幾份」：`registerAll` 要完整的 `config` 與 `ability-templates`
才展開得對（模板／五級距／卡面文案）—— 只餵新的會讓新英雄拿到**預設級距**，
也就是「商店顯示 6.0、場上打 4.5」那種對不起來的死法。

⭐ **登錄表清單是推導的**（duck-type 掃兩個模組的匯出），⛔ 不是手寫一張表 ——
手寫的話，下一個人加第 17 個登錄表時那個 collection 的**修改**會被靜默熱套用。

### ⭐ fail-loud（票文 Implementation constraints 逐字要求的那一條）

## ⑤ ⛔ 沒做的：Scope C（`contentPool` 社群房）—— 為什麼，與下一步

⭐ **技術上的擋點是「哪些內容算社群內容」今天沒有答案。**

- `contentPool` 這一格本身很便宜（`roomSettings.ts` 加一格 ＋ 三個住處）。
- ⛔ 貴的是**過濾**：要從白名單裡減掉「社群來的」那一批，
  就要有一份「哪些 id 是社群來的」——⭐ 而 `Whitelist` / `Champions` 兩邊都沒有這個維度。
- ⚠️ 一個**看起來會動的半套**是危險的：熱套用時我知道哪幾個 id 是新加的，
  ⛔ 但**重啟之後**那個資訊就沒了（開機那一趟是整棵合併樹，分不出哪一份來自覆蓋層）
  ⇒ 「社群英雄在重啟前只進社群房、重啟後跑進官方房」——
  ⭐ 那正是本 repo 記過的「壞掉跟正常長得一模一樣」。

**⭐ 下一步（建議寫進票的 Scope C）**：讓**發布**那一刻就記下 provenance ——
`submissionPublisher()` 已經知道 `Target.Collection/ID`，
⇒ 讓 platform 多服務一份「社群 id 清單」（與 curation whitelist 同一個形狀、
同一條 Redis 公告），shard 端像 `sharedWhitelistCache` 一樣在**開房那一刻**取快照，
再由 `contentPool` 決定要不要減掉它。
⇒ ⭐ 那樣「哪些是社群內容」**重啟前後是同一個答案**。

⚠️ 另外兩件**沒做**的小事（誠實列出）：
- `ugc.communityRoomOnly`：C 沒做 ⇒ 它會是零消費端的裝飾 ⇒ ⛔ 刻意不加。
- 票文提到的 `x-ggd-operation-id`：⛔ 沒用它 —— ⭐ 冪等鍵用**既有的 digest**
  （`Promoted()` 本來就是拿指紋綁的），⛔ 多一把鑰匙就是多一份會漂的真相。
