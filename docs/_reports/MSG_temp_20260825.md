## 2 · 閘的判準（⭐ 刻意寧可漏報）

1. 只讀**訊息字串** —— `expect(_, 訊息)` 第二參數（含 `const message = [...].join()` 這種同檔常數，
   用 TS AST 解析，⛔ 不是正則猜）、`it/test/describe` 標題、**檔頭** block comment。
2. 只認 `content/{abilities,champions,config}/`。
3. glob／`<id>` 佔位**只在它涵蓋的每一個實檔都是產物**時才算命中。
4. 「是不是產物」只有一個住處：`sync-io.json` 的 `steps[].writes`（⛔ 不抄第二份表）。
5. 擁有者線索（`genguard`／`genrun`／`skills:sync`／`產生器`／`不要手改`／`改來源`）**逐檔**判定。

### ⛔ 誠實：三個已知的漏（寫進檔頭，⛔ 不當成「掃乾淨了」）

| 漏 | 實例 |
|---|---|
| 訊息用 `${n.file}` **動態**印路徑 | **A2 `tierFlatExclusive` 與 A4 `slowLabelMatchesMultiplier` 正是這一種** —— 閘看不到它們，這一批是**手動**補的 |
| `content/{items,augments,status-effects}/` | 混著手編檔與產物，這一版不掃 |
| PENDING 上的檔再加新的誤導訊息 | 只要路徑集合不變就不會紅 |

⇒ ⭐ **A2/A4 是這條閘的誠實邊界**：它抓得到「訊息裡寫死了產物路徑」，
⛔ 抓不到「訊息把路徑算出來再印」。⛔ 我沒有為了讓數字好看而放寬判準。

## 3 · 棘輪怎麼實作的

`tools/parallel-gates/guard-message-pending.json` 的 `pending` 是一張**寫死的檔案清單**，
每列 `{ "product": "<產物路徑>", "owner": "<步驟名>" }`。三個方向都關起來：

| 情況 | 結果 |
|---|---|
| 違規但**不在**表上（＝新增／改動的守衛） | 🔴 紅，逐則印 `檔:行 · 路徑 · 誰的產物` ＋ 建議補的那一句 |
| 在表上但**已經不違規** | 🔴 紅：「已經修好 ⇒ 把這一列刪掉」——⭐ 表只准變短 |
| 在表上、仍違規，但 `product`／`owner` 對不上實測 | 🔴 紅：「這一列過期了」——⛔ 豁免表自己不可以說謊 |

⛔ 沒有「加一列就過」這條路：修法一律是**在那支的訊息裡補一句**，然後刪列。
