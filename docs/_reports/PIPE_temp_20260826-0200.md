## GH#708 —— `deriveCastTimes` 靜默跳過一位英雄

### ⭐ 真因（⛔ 不是票上猜的 `catch { continue }`）

`packages/shared/scripts/deriveCastTimes.ts` 用 **出貨政策** 載入內容：

```ts
const result = await new ContentLoader(new FsContentSource(CONTENT_DIR)).load();   // ⛔ 沒帶 policy
```

`load()` 不帶政策 ⇒ 用 `config.content-load@1` 的出貨值 **`quarantine`**。
`loader.ts` 對一份 schema 壞掉 / id 對不上 / 硬參照斷掉的文件的處理是
**`quarantined.push(...)` ＋ `continue`（或 `store.remove()` cascade）** ——
也就是**把那張英雄卡從 store 拿掉**。於是：

| | |
|---|---|
| 那位英雄 | ⛔ 不在 `Champions.all()` 裡 ⇒ 寫入迴圈**連看都沒看過他** ⇒ 內嵌 `castTimeSec` 不會被寫 |
| 他的 standalone 技能檔 | ✅ 自己是好的 ⇒ 照樣寫對了 |
| 症狀 | 「standalone 有、內嵌沒有」＝ `abilityMirror.test.ts` 紅，而訊息**不指向這支腳本** |
| 數字 | 14/42 → 13/39（少一位、少他改動到的 3 格） |

⭐ 而 `loader.ts` 自己的檔頭就寫著「呼叫端**必須**把非空的 `quarantined` 送到一個看得見的
地方，⛔ 一行 console.warn 不算」—— 這支腳本**把它整個丟掉**。
⭐ 同一個 repo 的另一支產出期寫入端 `buildIndexes.ts:109` **已經**傳了
`{ policy: "fail-closed" }`，理由逐字就是「產出期沒有玩家在等」。⇒ 這支漏了同一行。

**⛔ 排除掉的兩個假說**（都實測過）：
- **EACCES（產物 444）不是靜默的** —— `node` 對 444 檔 `writeFileSync` 擲 `EACCES`（讀 OK），
  而那個 write ⛔ 不在 try 裡 ⇒ 它會**炸掉**，⛔ 不是跳過。
- **`derived.get()` 缺項** —— 現況實測 `noDerived = 0` / `noFile = 0`，而且它會連帶讓
  standalone 也漏寫（與症狀矛盾）。

### 修了什麼（`packages/shared/scripts/deriveCastTimes.ts`）

1. `load({ policy: "fail-closed" })` —— 產出期一律 fail-closed（＝ `buildIndexes.ts` 的規矩）。
2. 防禦層：`result.quarantined` 非空 ⇒ **逐份列出 collection/id/reason/detail 並 exit 1**。
3. 每一個跳過點都留名字：
   - abilities 讀不到 ⇒ 記錄；`ENOENT` 合法（內嵌式技能），**其餘錯誤碼是 fatal**。
   - champions 讀不到 ⇒ **fatal**（註冊表裡的每一位都來自 `content/champions/<id>.json`）。
   - `derived` 沒有那支技能 ⇒ **fatal**，訊息帶 `<英雄>.<槽位> → <技能 id>`。
4. **終端對帳**（⛔ 不是中間節點）：寫完把檔案**讀回來**，逐英雄逐槽位比對
   內嵌 `castTimeSec` 是否等於公式值；並且比對**磁碟索引筆數 vs 註冊表筆數**
   —— ⭐ 後者是關鍵：`Champions.all().length` 自己就是**隔離之後**的數字，
   拿它當分母，「安靜掉一位」永遠是 71/71。任何一項不符 ⇒ 列出來 ＋ **exit 1**。
5. **寫入點自解鎖** `writeProduct()`（`chmodSync(0o644)` 再 write，前例
   `tools/editor-contract/gen_contract_numbers.py:1255`）—— 這支寫的檔有一大半是
   **別支產生器**的產物，`genrun.sh skillremake:json` 只解鎖 skillremake 自己那 126 份。

### 守衛 ＋ 突變

`packages/shared/src/ops/deriveCastTimesFailsLoud.test.ts`（**新檔**，2.4s）——
用**符號連結農場**造一棵內容樹（⛔ 不複製 354MB），把第一位英雄的 `id` 改成 schema
收不下的樣子，真的把腳本跑起來。⭐ 先跑一次**乾淨**的當量尺校準（控制組不綠 ⇒ 結論作廢）。

| 突變 | 結果 |
|---|---|
| 只拿掉 `policy: "fail-closed"` | 仍綠（防禦層 ② 接住）—— 兩層是刻意的 |
| **同時**拿掉 fail-closed ＋ quarantined 報告 | ⛔ **腳本 exit 0 而英雄被安靜丟掉 ⇒ 守衛紅** ✅ |

沙箱實測（`GGD_CONTENT_DIR=/private/tmp/ggd-content-sbx`）：
- 現況 `--write`：`WROTE 0 / 0 (0)`，`對帳：走過 71/71 位英雄 · 不符 0 格`
- 把 `godie-edem` 的 id 改壞：`exit 1`，訊息逐字指名
  `champions/godie-edem: schema validation failed — id: …`

## GH#710 —— `skills:sync` 一次收斂不了

### 量到的（`sync-io.json`，⛔ 不是感覺）

`content:build` 在鏈上第 **11** 支，而**寫 `content/` 且排在它後面**的有 3 支，
它們寫的檔正是 `content:build` 自己會讀的：

| # | 步驟 | 寫 | 被排在它**前面**的幾支讀 |
|---:|---|---|---|
| 28 | `jasscombo:build` | `content/config/combo-strikes.json` | 5（含 `content:build` · `contract:numbers`） |
| 29 | `vfxbind:build` | `content/config/ability-vfx-bindings.json` | 4 |
| 30 | `sfxbind:build` | `content/audio-manifests/ability-sfx-cues.json` | 2 |

（把範圍放寬到「任何寫 `content/` 且有更早的讀者」的話是 **10 支** —— 守衛用的是這個
較寬的定義，因為那才是「一次線性掃鏈不可能收斂」的充分條件。）

### 選了 (b) 跑到不動點 —— 理由

⛔ **不選 (a) 重排拓撲序**，兩個成本都是量到的：
1. `sync-io.json.chain` 是**身分**：`sync.mjs` 閘① 逐字比對它與 `package.json`
   的 `skills:sync`，對不上就**拒跑** ⇒ 動一個字就要重跑 3-pass trace 重量整張圖。
2. `skills:sync` 這個**名字**被 20 幾處逐字引用，其中 `tools/ap-conversion/gen.py`
   還會**印出它的步驟位置表**（那是產生的文件）⇒ 改順序＝一票產物同時過期。

⇒ (b) **一個字都不動那條鏈**。

### 做了什麼

| 檔 | 動作 |
|---|---|
| `tools/parallel-gates/converge.mjs` | **新檔** —— 不動點迴圈：`sync` → `run.mjs skills:check`，綠就停；**上限 3 輪**；⭐ **連兩輪 stale 集合相同 ⇒ 判定震盪提早停**；`sync` 自己紅了 ⇒ 立刻停（⛔ 不當成「還沒收斂」）。未收斂 ⇒ **exit 1 並列出仍 stale 的步驟名**。 |
| `tools/parallel-gates/converge.d.mts` | **新檔** —— 型別門面，讓守衛跑**真的那一支**（⛔ 不在測試裡重抄迴圈） |
| `package.json` | **新增一行** `"sync:converge": "node tools/parallel-gates/converge.mjs"`（⭐ `skills:sync` 的字串**一個位元都沒動** ⇒ 閘① 仍然過） |
| `tools/parallel-gates/ship.mjs` | 序列段的 sync 步驟改走 `sync:converge` |

**🔙 rollback 開關**（owner 常設：自己判斷但要留一鍵回頭）
`GGD_SYNC_CONVERGE=0` ⇒ ship 退回 `skills:sync` 單跑一次；
`node tools/parallel-gates/converge.mjs --rounds 1` ⇒ 同樣的舊行為。
⚠️ 這是 build 工具的旗標，⛔ 不是內容參數 ⇒ **沒有**落三個住處（`content/config` +
Zod + admin）—— 如果主 session 認為它該進後台，那是另一張票。

### 守衛 ＋ 突變

`packages/shared/src/ops/syncConverges.test.ts`（**新檔**，9ms）兩條：
1. **拓撲關係閘**：從 `sync-io.json` 推導「排在自己的讀者後面的寫入端」；
   ⭐ 只要**還有**這種步驟，就要求 ship 的序列段接上 `sync:converge`。
   哪天有人真的把拓撲修好（歸零），這條**自動放行**，⛔ 不必改測試。
2. **迴圈行為**（注入 runner，⛔ 不跑真的 sync）：第二輪綠就停 · 跑滿上限回非零並列出
   stale · 震盪第二輪停 · sync 自己紅立刻停 · 半形/全形括號的 stale 名字都撈得到。

**突變**：把 ship.mjs 的 `SERIAL` 改回寫死 `"skills:sync"` ⇒ **紅**，
訊息逐字列出那 10 支後置寫入端。已還原。

### ⚠️ 誠實：守衛**沒有**真的跑一次 sync

票上寫的是「沙箱樹上跑一次 sync、斷言 check 為 0」。⛔ 我沒有這樣做，兩個理由：
① `skills:sync` 是**全域鎖**，而另一條 lane 正在跑（硬性約束）；
② 一次完整鏈以**分鐘**計，放進 vitest 直接違反第零守則的 5 分鐘規則。
⇒ 拆成「拓撲從量到的 I/O 推導」＋「迴圈用注入 runner 驗」兩半。
⭐ **仍缺的那一半**（主 session 全域鎖時段可做，≈ 兩輪鏈）：
真的改一個會觸發 `vfxbind:build` 的內容檔 → 跑 `pnpm sync:converge` →
斷言它報「第 2 輪達到不動點」而不是「第 1 輪」。
