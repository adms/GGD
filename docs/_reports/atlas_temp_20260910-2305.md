# 貼圖圖集 —— GH#1174 的圖集那一半（2026-09-10）

> owner 2026-09-10（逐字）：「**貼圖圖集跟減面的優化 還是可以做的 是獨立考量**」

## ⭐ 結論：兩顆都過線了，而且**畫面上量不出差別**

| 模型 | 英雄 | draw call | VRAM | 最大貼圖邊長 | 三角面 | 檔案 |
|---|---|---:|---:|---:|---:|---:|
| `ou99.473324` | `b2-aladdin` 阿拉丁 | **8 → 3** | 2.21 → **0.67 MB** | 512 → **256** | 7,970（不變） | 1.57 → 1.38 MB |
| `ou99.458777` | `b2-keyaru` 凱亞爾 | **7 → 2** | 2.17 → **0.67 MB** | 512 → **256** | 7,003（不變） | 2.17 → 1.94 MB |

上限：`HERO_MODEL_BUDGET.meshes = {warn 3, limit 6}`、`texEdge = {warn 256, limit 256}`。
⇒ 兩顆的 draw call 現在都在**警戒線以內**（3 ≤ 3、2 ≤ 3），貼圖邊長的違規也一併消失。

`heroBody` 已翻回 `true`，`heroBodyNote` 已移除。

## ⭐ 最重要的一個發現：這兩顆的 draw call **不是被貼圖大小卡住的**

既有的 texture stage 只會把每一張貼圖**縮小**，⛔ 它一張都不會**減少** ——
而 draw call 數的是「有幾種畫法」。⇒ 7 張不同貼圖不管縮到多小都還是 7 個 draw call。

⭐ 而**兩顆的 14 個 primitive 沒有一個是 tile 的**（逐 primitive 量 UV 範圍，
全部嚴格落在 [0,1] 內，`uvOutside01 = 0`）—— 這是圖集可行的**充分條件**，
而它在做之前是未知的（WC3 貼圖預設 REPEAT，會 tile 的併不了）。

第二個發現：14 個 primitive 裡只有 **1 個**的畫法真的不同
（`473324` 的 `mat5`，68 面，`doubleSided: false`）。其餘 13 個**只差 baseColorTexture** ——
也就是說「每一個 primitive 畫法都不同」這個結論**是貼圖造成的假象**，
⛔ 不是幾何的性質。把貼圖併掉，畫法就一樣了。

## 做了什麼

### ① `tools/model-budget/optimize/atlas_pack.py`（新，圖集 stage 的本體）

判準與 `tools/w3x-import/merge_glb_prims.py` 是**同一條，反過來用**：那一支問
「畫法一不一樣」，這一支**把畫法變成一樣**，然後叫它去併。

**⛔ 什麼不可以進同一張圖集**（都是可執行的判定，⛔ 不是註解）：

| 條件 | 為什麼 | 這兩顆的實際結果 |
|---|---|---|
| UV 超出 [0,1] ⇒ 會 tile | 重映射之後 wrap 會取樣到隔壁格 ⇒ 整片錯位 | 0 個命中（兩顆都沒有 tile 的） |
| render key 不同（alphaMode / doubleSided / emissive / 其他材質欄位） | 那是不同的畫法 | 1 個命中（`473324` 的 `doubleSided:false`）⇒ 它保留自己的材質，⭐ 但貼圖仍指進圖集 |
| 材質帶第二張貼圖（normal / MR / occlusion / emissive） | 版面要一起搬，今天沒做 | 0 個命中 |

**mip 滲色**：每一格內縮 4 texel，邊緣像素**往外擴**填滿那一圈；圖集的 sampler
一律改成 `CLAMP_TO_EDGE`（原本是 `REPEAT`）⇒ 就算有 1e-4 的 UV 溢出也只會夾在自己的擴邊裡。

**版面配置**：每一格從「原生尺寸（夾在 256 內）」出發，塞不下就砍**取樣最浪費**
的那一格（判準 = `格子面積 ÷ 這張貼圖服務的表面積佔比`，表面積是從 POSITION+indices
真的算出來的）。⭐ 砍完再**長回去** —— 貪心的砍法會砍過頭（shelf 排不下 ≠ 面積不夠），
而砍過頭不會有任何東西叫，它只會讓貼圖比需要的更糊。

**圖集張數**：取**還進得了 draw call 預算的最多張**（`--quality` 品質底線 0.45），
⛔ 不是「最少張」—— 少一張圖集省 0.33 MB（額度 4 MB，不缺），代價卻是每一格再糊一倍。

**GC**：丟掉沒有人引用的 material/texture/image/accessor/bufferView 並重打包 buffer。
⛔ 這一步不是潔癖 —— `measureGlb` 的 VRAM 逐張數 `images[]`（⛔ 不管有沒有人用），
不做 GC 的話「圖集省了 VRAM」這句話是假的。

### ② `tools/model-budget/optimize.ts` —— 第三個 stage（`--atlas`）

照 texture / geometry 兩個 stage 的形狀：寫到 `optimized-out/` 獨立樹、hash 側車
（key 含圖集參數）、⛔ 絕不就地覆蓋、採用是獨立的人工步驟。

- 只對**真的超過 draw call 上限**的模型跑（圖集會改變畫面，⛔ 不是「順便做一下」）
- 跑圖集時**關掉 texture stage**：圖集自己就夾在 `--edge` 內，先 512→256 再 256→128
  是**兩次**重取樣 —— 同一個結果，多糊一次
- **兩個方向都驗才採用**：draw call 真的掉到線內 **且** rig 一根骨頭都沒動
- 收尾的 VRAM 一律**量出來的**（規劃階段算不出圖集排成幾張，報估計值就是說謊）

### ③ `tools/model-budget/rig.ts` —— `tris` 這一條逐 stage 不同

減面：面數**必須變少**；圖集：面數**必須一模一樣**。
⛔ 在此之前 `checkRig` 硬寫「面數沒變少就是失敗」⇒ 它會拒絕**每一個**正確的圖集候選。

### ④ ⛔ 一個踩到的坑：python 探針只驗了一半

`execFileSync("python3", ...)` 在這台機器上載不動 Pillow ——
node 跑在 **x64（Rosetta）**下，而 `/usr/local/bin/python3` 是 universal binary
⇒ 它**繼承父行程的架構**：同一條路徑在 shell 裡是 arm64、被 node spawn 出來是 x86_64。
⇒ 加了一個「哪個 python 載得動 Pillow」的探針。

⚠️ ⭐ **而探針第一版自己就犯了本文件記過的錯**：它 `import PIL`（純 python 的
`__init__.py`）⇒ **通過**，而壞掉的是原生的 `_imaging` ⇒ 它放行了一個載不動的 python。
改成 `from PIL import Image; Image.new(...)` 才真的驗到。

## 怎麼重跑

```bash

npx tsx tools/model-budget/optimize.ts <glb…> --role champion --atlas

# 寫到 optimized-out/（⛔ 絕不就地覆蓋；採用是獨立的人工步驟）
npx tsx tools/model-budget/optimize.ts <glb…> --role champion --atlas --apply

# 單獨跑圖集（含逐 primitive 的可否進圖集判定與理由）
python3 tools/model-budget/optimize/atlas_pack.py <glb> [--out X] [--edge 256] [--quality 0.45] [--atlases N]
```
