## ② 公式住在哪？ ⇒ **半個住在設定檔，⛔ 另外半個是寫死的第二個住處**

### 量到的（⛔ 不是推測）

| 誰 | 讀 `apPerAttrPoint` 的方式 | 判定 |
|---|---|---|
| `tools/ap-conversion/apply.py` | `load_knobs()` 讀 `tools/ap-conversion/knobs.json` | ⭐ 對 |
| **`tools/ap-conversion/gen.py`** | **`AP_PER_ATTR_POINT = 0.25` 寫死在模組頂層**（連同 `STEP_PCT` / `ROUNDING` / `MIN_PCT` 四個） | ⛔ **第二個住處** |

⇒ 把 `knobs.json` 的 `apPerAttrPoint` 改成 `0.3`：

* `pnpm apconv:build` 照 **0.3** 換算 → 出貨技能真的變了
* `pnpm apconv:plan` 產出的 `docs/技能AP換算計畫.md` 仍然印「屬性乘數 × **25%**」
* **兩支都 EXIT 0**

⇒ owner 讀到的那份逐支對照表會變成一份**看起來完全正常的謊話**（第〇·四守則量到的
形狀：一個算得出來的數字有第二個住處，⛔ 烘進去的那一份必然過期）。

### 修法（已落地）

`gen.py` 頂層改成從 `knobs.json` 讀，四個常數全部：

```python
KNOBS_PATH = "tools/ap-conversion/knobs.json"
with open(os.path.join(ROOT, KNOBS_PATH), encoding="utf-8") as _f:
    KNOBS = json.load(_f)
AP_PER_ATTR_POINT = KNOBS["apPerAttrPoint"]
STEP_PCT          = KNOBS["stepPct"]
ROUNDING          = KNOBS["rounding"]
MIN_PCT           = KNOBS["minPct"]
```

⇒ 現在**唯一的住處**是 `knobs.json`，而它同時是 owner 要的那份「寫在 JSON 的公式」：
新增 `$formula` 一格，裡面有 owner 兩則原話、機器可讀的 `expr`、中文說明、
九個例子、「只有第 1 條宣稱進係數」的範圍限制、以及「抽取來源是卡面不是 `ratios`」。

```
apPct = max(minPct, round_{rounding}( coeff × apPerAttrPoint × 100 ÷ stepPct ) × stepPct)
```
> AP 百分比 = 「屬性乘數 × 25%」四捨五入到最近的 10%，最低 10%。
> 力量*1→30% · *2→50% · *3→80% · *4→100% · *5→130% · *6→150% · *9→230%

## 守衛（一條，⛔ 不是 58 條）

`tools/ap-conversion/apply.py::audit()`，跑在 **`pnpm apconv:check`** 裡 ——
⭐ 而 `apconv:check` **已經在 `pnpm skills:check`** 中（package.json:95），
所以 ⛔ 不需要動 `package.json`，也不會踩 `skillsSyncCoversGenerators.test.ts`。

它驗的是**「還有誰沒被看過」**，⛔ 不是「這 58 支有沒有被手改」：

> `--check` 的逐位元組比對只看得見 `claims.json` 收進來的那 58 支。一支沒進凍結表
> 的技能，`--check` 對它**永遠是綠的**（它根本不在迴圈裡）。這正是那三件道具能在
> 全綠的情況下帶著 `智慧*9` 出貨的原因。

三條後置條件（任何一條不成立就非零離開）：

1. 出貨的 5 個集合裡不可以有**未換算的屬性額外傷害**（prose 軸 + json 軸）
2. 豁免表每一列都要有 `why` / **`refutedBy`** / `expiresWhen`
   —— ⭐ 一筆沒有 `refutedBy` 的豁免就是一段沒有人能反駁的散文，它會活得比它的理由久
3. **對不到任何東西的豁免 ⇒ 紅**（過期的豁免是一句沒有人會發現的謊）
