# A2 —— 內容樹讀一次進 Redis（TTL 24h）

> owner 2026-08-23 逐字：
> 「**大量重複IO的地方先讀取後合成暫存起來(Redis with lifetime 24HR)
>   不要每次都去大量抓檔案造成 storage 瓶頸與壽命縮短**」

---

## 1. 量到的重複 IO（⛔ 不是假設）

`new ContentLoader(new FsContentSource(content)).load()` 一次 =
**1 份 manifest + 14 份 `_index.json` + 1,712 份文件 = 1,727 次 `readFile`**。

拆開量（2026-08-23，M-series，暖 page cache）：

| 段 | ms |
|---|---:|
| 1,727 次 `readFile` + `JSON.parse` | 168 |
| 1,712 次 Zod `.parse()` | 169 |
| `content/bundle.json` 單檔讀+parse（2.09 MB，⭐ 對照組） | 20 |
| **合計 `load()`**（冷 352 / 暖 210） | **~340** |

⭐ **所以快取要存的是 Zod 之後的東西**，⛔ 不是「檔案內容」——
只快取檔案內容（＝ `bundle.json` 已經在做的事）只省得到上面那一半。

而它被付了很多次：全 repo **116 個檔**打這一行，其中產生器 12 支
（`skill-spec` · `mana-audit` · `skill-tiers` · `card-prose`×2 · `skill-normalize`×2 ·
`ttk-sim`×4 · `buildIndexes`），⇒ 一次 `pnpm skills:sync` 就付十幾次。

## 3. ⭐ 快取鍵：為什麼**不可能**吃到過期的內容

owner 的條件是「鍵含內容雜湊 ⇒ 內容一動鍵就變」。兩個看起來可以但**不行**的候選：

| 候選 | 為什麼不行 |
|---|---|
| **mtime** | 產生器把 config **原樣重寫**（位元組沒變）mtime 也會跳 ⇒ 永遠 miss；反過來 `git checkout` 退回舊版可能讓 mtime 比快取新卻是**別的內容** |
| `manifest.json` 的 `contentVersion` | 它是**產物**。lane 編了 doc 卻還沒 `content:build` ⇒ manifest 沒動 ⇒ **鍵沒變而內容變了** = 08-01／08-02 兩次生產事故的形狀 |

⭐ **用得起的內容雜湊：git 已經算好了。**

```
git ls-files -s -z -- <content 15 個集合> <packages/shared/src>
    → 每一個追蹤檔的 blob SHA-1,⛔ 一個工作樹檔案都不開
git status --porcelain -z --untracked-files=all -- <同上>
    → 工作樹跟 index 不同的那幾份(⭐ 內容真理:stat 變了 git 會**真的讀出來比雜湊**)
    → 那幾份我們自己 sha256 它現在的位元組
```

⇒ 任何一個位元組變了，鍵一定變。**任何**：已 commit / 已 add / 只改工作樹 / 新增未追蹤 / 刪除。

### ⭐ 鍵裡也有**程式碼**

快取存的是 Zod `.parse()` 之後的東西 ⇒ 它是「內容 × schema」的函數。
schema 加一個 `.default()` 而鍵沒變 = 產生器讀到**缺欄位**的內容而且完全看不出來。
⇒ `packages/shared/src`（`*.test.ts` / `.baseline` / `.md` 除外）整棵樹的 blob SHA 也折進去。
⚠️ 範圍必須是整個 `packages/shared/src` ⛔ 不是 `content/schema/` ——
量到 schema 的 import 早就跨出去了（`../../sim/**`、`../../voxel/**`、`../../ids`…）。

### ⭐ 兩個子行程，⛔ 不是四個

量到：**每一個 git 呼叫 ≈ 45 ms，而 `git --version` 也是 43 ms** ——
成本幾乎全是行程啟動，⛔ 與 pathspec 或輸出大小無關。
⇒ 兩組 pathspec **一起問**，回來依前綴分堆：190 ms → **107 ms**。

⚠️ 沒有 git（tarball / 容器）時退回 `read-all`（真的逐份讀出來雜湊）。
慢，但**答案一模一樣** —— 是「同一份資料的另一條讀法」，⛔ 不是別的語意。

## 5. 退回行為（⚠️ fail-open 沒錯，靜默才是缺陷）

| 情況 | 行為 | 有沒有出聲 |
|---|---|---|
| Redis 連不上 | 退檔案層（`mode=redis` 時退到讀內容樹） | ✅ `[content-cache] Redis 連不上（host:port）⇒ 退回…` |

## 8. ⚠️ 唯一量到的差別：`-0` → `0`

快取走 JSON 序列化，而 `JSON.stringify(-0) === "0"`（`content/models/imported.*.json`
的 attachPoints 有這種值）。⭐ 這**不是新的漂移**：

· `content/bundle.json` 裡 `-0` 出現 **0 次** ⇒ **瀏覽器端從第一天起拿到的就是 `0`**
· `hashDoc()` 走 `stableStringify` ⇒ 內容定址層**本來就把兩者當同一份文件**
· 產生器要把值寫回 JSON 時也一律 `JSON.stringify` ⇒ 寫出來一樣是 `0`

⇒ 觀察得到差別的只剩 `Object.is(x, -0)` 與 `1/x === -Infinity`。
⛔ 所以不為它付 replacer/reviver 的代價（hydrate 27 → ~70 ms）。
⭐ 而守衛**只**允許這一個差別：多冒出第二種（少一個鍵、Date 變字串…）就會紅。
