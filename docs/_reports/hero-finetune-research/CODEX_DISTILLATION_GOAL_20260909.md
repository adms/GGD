## 1. 目標與完成單位

用已採用英雄＋37 名社群英雄的既有 Codex 成品，微調 Mac 本機 Gemma 4 12B IT，將 Codex 的領域生成能力轉移至「12B＋自動化 script」。使用者只提供英雄需求／指定版本；系統自行完成來源與可用目錄的取得或整理、生成、欄位填入、編譯、驗證與可上場作品交付，不要求人工補齊設定。

**完成單位是一名完整可上場的英雄，不是分類標籤、模板建議、JSON 草稿或只有預覽動畫的展示。**

完整輸出必須包含：

1. 英雄名稱、身分／採用版本、設定、出身、定位、攻擊類型。
2. 三圍、成長與其他必要屬性；按既有出身／級距／正規化規則計算並自洽，不以模型任意數字繞過規則。
3. PASSIVE／Q／W／E／R／EX 六槽的全部必要設定、名稱／描述、合法模板／產品／組合引用及可執行配置。
4. 傷害／治療／控制／位移／召喚等必要機制，包含友敵、事件、條件、時序、資源與跨槽關係；不能用外觀相似替代必要機制。
5. 既有特效模板選擇及完整有效綁定：施放／命中／持續／結束等必要事件、附件與可用預設參數；依實際 schema 填入，不留給人工完成必填設定。
6. 可用的既有模型、必要動作、圖示與其他上場必需依賴。缺少專屬美術不等於可以留下失效引用；採用已授權、契約相容的素材，不新增圖片／模型生成專案。
7. 英雄與技能資料自動寫入既有編輯器流程，保存後重新讀取一致；必要 refs、鏡像、模板展開與版本契約均有效。
8. 作品可在固定版本的本機／隔離測試環境匯入、選取、進入對局，六槽可依其條件使用；完成必要正向與反例行為測試並保留證據。

沿用「特效細部微調不入訓、視覺驗證不是小模型任務」的邊界，不等於交付缺參數的建議。合法必要值由既有規則／版本預設或來源明示值自動填入；人工後續美術／平衡客製是可選，不是上場前補作業。

## 2. 教師資料：既有成品直接教生成

主要來源為使用者指定的已採用英雄與 37 名英雄，不以「所有 corpus 版本」或巨大素材庫取代主資料。未採用 legacy、還原副本、同名不同版不能自動混入。

每個教師樣本對齊：

- 輸入：需求／原文、身分版本、必要共用規則、可用能力／技能／機制／特效／素材目錄。
- 輸出：同版本已採用的 Codex 最終英雄／單槽配置，包含適用的設定及綁定。
- 出處：教師成品版本、來源／目錄／答案 hash、採用與既有驗證紀錄、已知缺口、任務與分組。

保留完整英雄生成樣本，學六槽一致性及跨槽依賴；有效單槽可以另作輔助，但不得拆掉全部完整英雄上下文。來源三分類及支援／拒絕題只是輔助，不再是主訓練成果。

若原始 prompt 不在，先從既有獨立需求來源按固定契約組裝輸入，標為 reconstructed-input；不得假稱原始 Codex 對話，不從答案反推並塞回 template ID／目標效果，造成答案洩漏。缺少足以配對的需求或合法輸出就排除該任務並回報，不展開新標註工程。

Codex 生成不自動等於正確，但不要求全庫重新取得獨立人工 Gold 才能訓練。優先採用既有接受／驗證證據；已知錯誤、未授權降級、來源與版本混淆直接排除。單槽有問題不否定其他可靠槽；完整英雄正例不得藏有已知必要機制缺失。舊隔離結論只適用其固定版本，不能否定已修復的新版本。

37 名校正版另外已有 555 題來源判讀增補（74 英雄／481 技能），可作輔助候選；它不是 555 個完整英雄，也未全部符合新的切分。不得再遺漏此目錄，或把它與重複版本直接相加。

## 4. 比較對象與評分

三組為：

- T：Codex，在固定新英雄需求與允許資訊／工具下產生的教師參考。
- A：未微調的同一 Gemma 4 12B IT＋共用自動化流程。
- B：同一基底＋本次 LoRA＋完全相同自動化流程。

不指定新的 Codex 型號／effort；記錄實際執行設定，歷史不可得時寫 unknown，不虛構。三組使用同一來源／引擎／目錄版本及輸出契約；A／B 的 prompt、解碼、token 上限、重試政策、工具與評分完全相同。教師與 12B 的工具／推理預算差異單獨揭露，不把不同工作流的收益冒充微調收益。

主要評分依序為：

1. 英雄設定／出身／屬性規則正確。
2. 六槽及必要機制完整、友敵與時序正確、跨槽資源／狀態一致。
3. 技能／機制／特效模板與引用合法；功能等價方案可接受，不以 JSON 逐字相同作唯一標準。
4. 所有必填欄位、特效／模型／動作依賴完整，編輯器填入、保存、重讀與編譯成功。
5. 對局可用與正反行為符合需求，無未授權降級或錯誤放行。
6. 批次端到端成功率、人工介入次數、Codex／A／B 逐例差異、延遲、token、記憶體與失敗類型。

**宣告成功的每名英雄必須零人工補填／補機制，並通過相應必要檢查。** 來源缺少、能力不支援或安全拒絕是失敗／拒絕類別，不計為自動創建成功；未測機制不得自動通過。特效得分不能補償核心機制錯誤。

延續既有完整支援組英雄級成功率至少 95%、危險錯誤接受觀察數 0 的品質目標；同時量化與 Codex 的各項差距，不把 Codex 當保證 100% 的上限或真相。新批數量太少時報實際分子／分母及不確定性，不能以少數成功推論高機率泛化。整體目標未達標就報差距，不因交完報告而宣稱模型已達成目標。

## 5. 自動化與算力邊界

- 12B 負責語意生成／選擇；script 負責規則推導、合法預設、格式、編輯器資料填入、編譯、對局測試、統計與保存。
- 最終 12B 工作流不可依赖 Codex 為每名生成英雄補答案；教師生成及實驗分析屬研究階段，人工介入／LLM 修復若有發生必須單列，不算零人工成果。
- 沿用既有有效工具，新增必要完整輸出契約與資料介接即可；不重新建大型平台，不再做只含 12 筆的技術可行性循環。
- JSON 正規化與 schema／能力／編譯／行為檢查包含在共同流程；不靠修逗號、替換答案、偷偷補技能來美化分數。
- 不更換 12B 基底或重做 4／9／27B 排名。既有 last-two-layer LoRA 是已驗證起點，不是「已證明適合完整長輸出」；完整 token／記憶體預檢後固定正式設定與單輪上限，不自動 sweep。
- Mac-only、單一受保護 GPU worker、雲端 GPU 支出 0。保留接電、RAM、swap、timeout 與停止自己的 worker 的保護。
- 先用實際可用筆數及完整序列長度估算一輪成本，不能承諾沿用 12 筆試驗時間。上一版 4 小時只是未核准提案，不偽稱已取得新的時限承諾；不自動延長或加跑候選。
- 發現資料问题排除並報告；需 Main 修引擎者按開票守則處理，不在本研究自行修遊戲機制。缺既有積木時不能以靜默近似交付。
