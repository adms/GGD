## 1. 要交付什麼

最終目標不變：在 Mac 本機使用 Gemma 4 12B IT，協助全自動建立忠於指定來源版本的英雄設定、六槽技能、必要機制與跨技能關係；特效只推薦既有模板，細節交人工微調。

下一輪要回答的問題是：

> 使用全部既有資料中去重、品質合格、用途相符的訓練樣本，是否比同一個未微調 12B 更會理解來源、判斷機制、選擇合法模板組合，且能改善完整英雄生成，而不增加錯誤接受？

## 2. 工作範圍與禁止事項

## 4. 品質檢查與排除規則

script 為每筆建立：來源檔、來源 hash、版本、原 ID、任務類型、原切分、來源／英雄／家族關係、審查層級、保留／排除理由與目標 hash。

自動檢查：

1. JSON 可讀、必要欄位與任務 schema 正確、原文及目標未漂移。
2. 相同題目／答案與相同來源變體去重；衝突標籤不得以多數決自行修正。
3. 標籤及可接受答案符合既有審查收據。只有 reviewed 欄位或一句自評，不直接視為完整語意證據。
4. 模板／組合答案只能引用該題明示目錄允許的 ID，並核對相關版本與既有能力證據。
5. 缺關鍵原文、來源不明、答案洩漏、錯置友敵／時序、已知壞配方等，直接排除；不補答案。
6. 舊版目錄題若有明確版本及可信答案，可保留為「依提供目錄判斷」的輔助題；不得把舊版隔離／支援結論當作目前引擎事實。沒有版本邊界或證據不足者排除。
7. 視覺待微調、原文未指定的數值，不自動算成機制錯誤；新版已修好的機制也不沿用舊版失敗判斷。
8. 語意無法靠程式判定時，沿用可核對的既有逐筆審查；有爭議則隔離並回報，不在本輪展開重寫／重新標註工程。

第一輪優先使用全部合格的非特效訓練樣本。特效題留在資料清冊與獨立評估，不為了增加筆數加入主訓練；需要下一輪加入時另外記錄假說與比例。

交付數量必須分開列：原始筆數、跨版本唯一筆數、合格筆數、各任務筆數、唯一英雄／來源／家族數、train／dev／regression／fresh-holdout、各排除原因。不能用 466 行代表 466 名英雄，也不能把重複 epoch 算成新增資料。

## 5. 切分與曝光政策

- **先合併去重，再依英雄與來源家族分組。** 同源技能、換皮與近重複改寫不得跨訓練／評估邊界。
- 共用一份能力目錄、相同模板 ID 或一般機制類型，本身不等於同一個樣本。未見英雄測試容許機制類型重疊；「整個機制家族未見」另建外推分組，不能把兩種測試混為一談而排空所有資料。
- 預設希望接近 train 80%／dev 10%／test 10%，但比例是次要目標；不拆家族或破壞既有評估保留來湊比例。
- 既有曾用作驗證、測試或選模的題目與其群組，保守保留為 evaluation-only。若與某筆歷史 train 衝突，排除該 train 候選，不把 test 改標成 train。
- 對其餘可分配群組使用固定 seed、一次性切分；在新推論前凍結，不按模型答對與否移動題目。
- dev 用於是否續跑／選候選；regression 用於固定前後比較。歷史曝光必須明列，即使換成 12B，也不聲稱是本研究全新盲測。
- 真正未曝光的獨立英雄／機制家族留出另存，答案不進 prompt、檢索或訓練。候選固定後才評估，不再用該批調參。
- 沒有 fresh holdout **不阻止合格 train／dev 的初輪訓練**，但阻止最終獨立泛化與 95% 達標宣稱。
- 機制組合外推、同家族未見英雄及歷史回歸分開報告，不把它們混成一個漂亮總分。

## 7. JSON 檢查已是共同流程，不另做一個研究主題

沿用 normalize.mjs 與既有評分器；最近實跑的 JSON 工具測試 31／31 通過。

輸出依序檢查：

1. 明確 final channel、正常停止、大小限制；只可移除完整 Markdown JSON 外框及外側空白。

## 8. Benchmark 與採用規則

每項皆以完整固定題組為分母；JSON 失敗、截斷或拒絕不從分母消失。分類及生成分開，特效不補償機制錯誤。

| 層級 | 主要指標 |
| --- | --- |
| 英雄／來源理解 | 各任務與 supported／contradicted／not-stated 分類表、macro 分數、錯誤支持、必要數字／主體／版本判讀 |
| 機制與模板組合 | 所有必要條件涵蓋、正確模板／組合、錯誤接受、錯誤拒絕、合法降級；單卡與多卡分開 |
| 格式與契約 | 原始 JSON、正規化後 JSON、schema 通過率；不得混作語意能力 |
| 完整英雄生成 | 六槽、設定／原文約束、跨槽資源與狀態、目標友敵、時序、編譯、正向與反例行為 |
| 成本與可復現 | 訓練實際覆蓋筆數／epoch、推論時間、token、記憶體、swap、停止原因、權重重載 |

目前四名完整生成案例只有部分行為覆蓋，保留作回歸診斷，不稱為完整產品 benchmark。只有已有完整來源—答案—行為證據的英雄，才能進完整支援组驗收；其分母在推論前固定。其餘未充分驗證的生成物不自動放行。

第一輪判讀：

- 分別報 A／B 的逐例改善、退步、持平及各任務 macro 差異，不只報一個平均數。
- loss 與訓練內分數只作診斷，不作採用理由。
- 固定配對集上新增危險錯誤接受，則拒絕採用該候選；不可拿其他題改善抵銷。
- 完整英雄沒有改善，只能報輔助能力是否改善，不能報全自動模型完成。
- 小樣本或家族集中時明列證據不足；不以幾題淨增宣稱高機率達到 95%。

最終成品仍要求：完整支援組英雄級通過率至少 95%、危險錯誤接受觀察數 0、每份可執行成品通過相應驗證，並有未参与調參的獨立評估。正確拒絕不是創建成功；零觀察錯誤不等於零風險。未達標就交付未達標結果與原因，目標不能標成功。

## 9. 訓練與時間邊界（本次待核准部分）

第一輪採用已驗證可載入的 LoRA 路徑：

- 從原基底初始化，不接續不合格歷史 adapter。
- 初始設定：最後兩層 q_proj／o_proj、rank 8、scale 8、dropout 0、micro-batch 1、learning rate 2e-5、seed 20260909。
- 只計答案部分的 loss；重新用 Gemma tokenizer 編碼，沿用既有 non-thinking 前綴及停止 token 校驗。
- **使用全部准入 train，預定 1 個完整 epoch。** 不是任取 12 筆，也不是把 24／72 步當成固定訓練規模。
- 事前固定每筆序列與生成上限。過長樣本不能截掉必要原文；先列入排除／容量缺口，報告受影響數量與任務，不能悄悄縮成容易題。
- checkpoint 每 32 個更新及 epoch 結束保存；受保護的中斷保留最後完整 checkpoint 和已處理 ID。強制終止時不宣稱最後一步已保存。
- 預先使用最後完整 epoch 的候選；若時間／資源上限未跑完，明列部分完成，不當作全資料實驗成功。

**本次建議核准：1 個正式候選、總工作時間上限 4 小時。** 分配如下，估算不是已量測承諾：

| 階段 | 上限／交付 |
| --- | --- |
| 既有資料盤點、檢查、去重與凍結 | 45 分鐘；逐筆准入／排除清冊與切分統計 |
| CPU token／資源預檢與 baseline | 45 分鐘；固定設定、容量估算及 baseline 原始結果 |
| 1 epoch LoRA | 90 分鐘；實際覆蓋數、checkpoint、訓練紀錄 |
| 同題候選推論與評分 | 45 分鐘；逐例 before／after、行為反例與成本 |
| 定稿與本地交付 | 15 分鐘；報告、入口、版本及保存狀態 |

不自動增加第二輪候選、再開超參數 sweep 或延長時限。若 CPU 預檢顯示容量／時間明顯超出，先交實際數量及估算，請使用者決定是否延長，不擅自抽掉多數資料。若某階段提早完成，剩餘時間可以移給同一輪必要工作；4 小時總上限不變。

以上是**這次實驗的界線，不是四小時內保證達到全自動 95%**。之後是否延長或第二輪，依結果另審。

## 10. Mac 資源、隔離及例外處理

- 全程最多一個本任務 GPU worker；啟動前核對接電、可用 RAM、swap、磁碟及現行 worker，不只相信舊狀態檔。
- 保留既有監督器的接電／掉電／記憶體／swap 門檻與 timeout，不為了開跑調鬆保護。
- 掉電、記憶體不足、swap 異常或使用者停止時，停止自己的 worker；不終止其他任務。
- 用固定版本的引擎與能力資料，不在其他任務正在修改的 checkout 上混合驗收。
- 全部歷史原檔、權重、失敗與排除資料保留。新的實驗使用獨立版本目錄。
- 發現資料問題：排除並報告。發現引擎問題：隔離受影響案例，依開票守則查重及記錄，不自行修復。
- 沒有合格完整英雄資料，不阻止已有合格輔助資料的試驗；如果連可用輔助 train／dev 都無法成立，交付具體缺口，不重複空跑。
