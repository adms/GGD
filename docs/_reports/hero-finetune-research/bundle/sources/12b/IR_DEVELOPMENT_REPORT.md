# 12B 語意中介格式與 script 組裝：開發實驗

本輪不是訓練收益實驗，也不是完整英雄驗收。測試同一個 Gemma 4 12B IT 8-bit、同四位已曝光的開發英雄，將模型工作從「直接寫引擎模板與效果 JSON」改為「抽取有逐字證據的語意動作，再由 script 組裝」。舊實驗檔、舊評分器與舊分數保留，不修補舊輸出重新宣稱進步。

## 已完成的 CPU 工程

- `semantic-ir.mts`：19 種語意操作；嚴格欄位、六槽、引用與深度限制。涵蓋普攻條件／內置冷卻、持續與逐波傷害、連鎖、連擊、落地傷害、資源、同來源詛咒、互斥分支及非傷害生命代價。不是 49 種引擎效果的完整語言。
- `ir-compiler.mts`：通用、無英雄名字分支的 deterministic lowering；使用現行 `tpl-event-passive`、`tpl-mark-stacks`、`tpl-effect-sequence` 與正式編譯器。完整來源、英雄名字、技能名字由 script 原樣保留。無引擎、原始英雄、ZIP、正式模型或發布設定修改。
- `ir-fixtures.mts`：四份人工讀來源後撰寫的開發 fixture。這是測工具的資料，不是模型答案、盲測或獨立核准 Gold。沒有放進模型提示，也沒有納入正式訓練。
- `ir-compiler-check-v2/`：四英雄、24 槽皆通過現行編譯。阿薩謝爾 E 的近身技能分類仍是明示機制缺口，編譯的是普攻反擊預覽，不能算整隻完成。
- `ir-fixture-probes-v2/`：21/21 個針對性真實模擬探針通過。包含 35% 嚴格邊界、2 秒內置冷卻、立即自療、三跳 DoT、不給施法者無敵、Q／EX 獨立、固定落點進出、每施法一資源、空資源拒絕、同來源／他人／淨化／到期的 EX 分支。這些不是 21 個獨立英雄，也尚未涵蓋所有六槽條件。
- 工具測試：86/86 Node 測試（本輪新增 28），另 7/7 CPU 資源政策測試。tsx 執行測試不等於整個產品 typecheck、建置或遊戲驗收。

## 兩類缺口必須分開

`mechanismGaps` 是尚未表達的必要機制；`tuningNotes` 是平衡、幾何、出身等設計提案。不再因護盾量待微調就判「沒有護盾機制」。但零護盾、零傷害、漏控制、友敵反轉、錯誤扣資源等會改變玩法，仍是錯誤。

允許 null 的未知數值由有界預覽政策填入非零值並另存提案收據，不冒充原文。非 null 的模型值也不因有引用就自動獲得來源核准；仍要逐項審查。原文未明示的傷害型別、數量及距離尤其不能用新預設當標準答案。

## 有保存的失敗與修正

1. `ir-compiler-check-v1/` 只有 1/4 編譯通過：研究組裝器把增益效果誤寫成 `buff`；當前正式 schema 是 `applyBuff`。改正研究工具後才得到 v2 的 4/4。**舊直接輸出 prompt 也包含 `buff` 範例錯字**，故舊基線失敗不能全部歸咎於模型弱；其三份 JSON 本身損坏與其他機制遺漏仍另有原始證據。沒有回改舊 prompt 或分數。
2. `ir-fixture-probes-v1/` 為 19/21。測試直接放大 HealthComp 的 maxHp／hp，正式屬性重算覆回最大值，造成生命比例／治療判斷失真。改為透過正式屬性來源增加 MaxHealth／MaxMana，再使用真實 maxHp 設比例，v2 才達 21/21。這是測試裝置問題，沒有證明引擎回歸，也沒有修改來源答案來讓它通過。

## 模型對照設計

`ir-smoke-v1/manifest.json` 在推論前釘選中介 schema、組裝器、探針、評估器、normalizer 與資料工具 hash；仍然只接受完整 final JSON／整段 fence，不修補、不挖取子字串、不重試。

## 實際模型結果：格式變好，完整創建仍未成功

四份原始輸出皆正常 `stop`，均為整段 JSON fence，無截斷、無重試。移除合法外層 fence 後 **4/4 JSON 有效**；舊直寫引擎 JSON 是 1/4。嚴格 IR 契約仍 **0/4**，因此 **0 份進入模型成品編譯、0 次模型成品行為測試、0 自動接受**。這不是「21 個模型行為測試都成功」；21/21 是人工 fixture 的工具驗證。

共同的 sourceEvidence 標頭問題值得修改**未來輸出責任**：既然來源與槽名由 script 保留，模型不必重抄一次完整槽文。可只輸出機制 evidence 的定位，script 檢查它確實屬於指定槽。不得在本版評分時偷偷剝標頭補成通過。

目前提示也有改進空間：示例把所有主動槽預填 targeted，可能產生複製偏差；這是待驗證的提示假說，不是已證實的因果。下一版應改成中性的欄位契約，或使用互相對照的完整 self／targeted／ground 範例，不讓錯誤默認進入測試。

## 下一步與微調假說

1. 先另立版本修掉冗餘輸出與誤導範例；增加「聲稱依賴卻沒有對應可執行條件」的雙向一致性守衛。本版 validator 已拒絕可執行依賴缺少 relation，反方向尚不足，不能宣稱所有跨槽錯誤都已攔截。
2. 用其餘待審來源整理「改為／不再／只有」的否定與替換、「唯一目標數 vs 命中次數」、「區域重取 vs 單位 DoT」、「內含落地效果 vs 額外立即效果」、「資源宣告 vs 資源消耗」五類正反對照。用來源與真實行為標準判斷，不按模型輸出或舊模板標籤自動給正例。
3. 四位開發英雄的錯誤可用來選擇失敗類型，**不要將這四位答案直接灌回訓練後稱泛化提升**。先以其他已逐筆審查來源建立 train，固定同契約 base／LoRA 的配對開發測試；仍需額外未参与調參的英雄／機制家族作最後證據。
4. 下一個 LoRA 要測這些語意差異，不要主要花在技能名、JSON 括號或 VFX 微調。若契約簡化已足够，保留基底也可以；若仍錯，再以小批本機 LoRA 測是否能改善完整英雄且不新增危險誤接受。
5. 不因 4/4 JSON 就升級模型或資料。現階段正式正向映射訓練核准仍為 0；沒有新的正式訓練、adapter 或發布。

## 安全與採用規則

所有產物維持 `releaseQualified:false`、`automaticallyAccepted:false`。當前 fixture、輸出或 Loss 不會自動進訓練庫。先把模型錯誤、資料歧義、IR 表達限制、編譯器錯誤與測試裝置問題分開，才決定小規模 LoRA 的真實學習目標。

本輪推論沿用單一 GPU 鎖與接電／記憶體／swap／時間保護。119 個監督樣本皆接電、100%，最低可用記憶體約 28.41 GiB；初始既有 swap 17.45 GiB，峰值新增 swap 0。worker 已退出、鎖已釋放；11 份模型／設定檔逐位元 hash 重驗不變。這不表示其他應用沒有使用 GPU。
