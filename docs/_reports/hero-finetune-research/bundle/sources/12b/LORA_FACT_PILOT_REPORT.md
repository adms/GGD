# 12B 第一輪有界 LoRA：判讀有進步，完整英雄未改善

2026-09-08，Asia/Taipei。新版持續目標未完成；本批 GPU worker 已退出，沒有啟用／發布新模型。

## 結論

這次不是只做相容性測試：已真正完成 24 次權重更新、保存四個 checkpoint，並以相同輸入、seed、輸出預算及驗證器，回測 16 位英雄的原文判讀和原本四位英雄的完整生成。

小型 LoRA 能改善輸出格式，且有少數實質語意修正，但目前沒有完整英雄層級的淨收益，不能據此放大全量訓練。保留 adapter 作研究，不取代基底。不能從本輪推論「12B 絕對太弱」或「更多分類資料就能高機率達成全自動」。

- 原本四位完整英雄 dev（沃維克、李星、好運姐、阿薩謝爾）未加入這份訓練。沒有把舊 222 槽映射當正例。

- GPU 單 worker，28 GiB Metal 上限，接電／掉電／可用 RAM／新增 swap／STOP／最長時間監督。未使用雲端 GPU。

## 下一步實驗決策

1. **不擴大這份分類 LoRA、不增加 epoch 追求 loss。** 「分類改善會自然轉移到完整英雄」這個假說，本輪沒有得到整英雄通過率支持。
2. 下一批資料改成少量**完整六槽的原文→機制計畫**，含正確順序、友敵、來源歸屬、跨槽資源與「不能擅自加機制」的對照；每個正例先有相應編譯及正反行為證據。不是重用隔離的222槽配方。
3. 不讓模型反覆生成可由 script 決定的 boilerplate、預設數值或逐字引文；研究較短的機制選擇／來源片段引用契約。契約若改變，先跑新基底，再比較 LoRA，不能把 prompt 改善算成訓練收益。
4. 訓練前固定分開計分的三件事：未見英雄的原文判讀、完整機制計畫、可執行整英雄；不再用第一項替代第三項。
5. 現有四位只作開發回歸，不回灌後假稱泛化。獨立英雄／來源家族與機制家族的最終留出資料仍須建立。≥95%整英雄與零危險錯誤接受門檻維持不變。

這輪排除了「先大量補分類題再長時間訓練就夠」的捷徑，沒有排除經過完整配方資料訓練後改善的可能。下一次 GPU 前，先做可審查的完整目標與短契約 CPU 工作。
