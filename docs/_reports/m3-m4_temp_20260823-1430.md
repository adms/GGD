## 1. M3 模型覆寫 —— 一格狀態換整具身體

### 1.1 資料層（第〇·四／第一守則）

`packages/shared/src/content/schema/config/formVisuals.ts` 的 `zFormVisualEntry` 多一格：

```ts
modelKey: z.string().min(1).max(64).optional(),
```

⚠️ **optional 是承重的**：線上存過的耐久覆蓋層沒有這一格，必填會讓整份
`safeParse` 失敗 ⇒ 整層外觀消失。同一份文件其他格已經是這個理由。

⭐ 它與 `attachModelKey` 是**兩件事**：那一格是**多掛**一份 glb（悟空超三的頭），
這一格是本體**換掉**（拳四郎 barbarian → heropikachu）。

### 1.2 解析層

`packages/shared/src/content/championFormVisuals.ts`：
`FormVisual` 多一格 `readonly modelKey?: string`，`resolveFormVisual` 解析它，
`composeBodyVisual` 帶它（**第一格贏**，與掛件同一條規矩 —— 兩份模型之間沒有中間值）。

**它吃哪幾道閘**：`enabled`（總開關）、`statusStrength === 0`（M1/M3 共用的一鍵
rollback，兩者上面都已經 early-return）。
⛔ **不吃** `attachmentsEnabled` —— 那一格的理由是「低階機器不要多載一份 glb」，
而換身體**不會多**一份，它換的是本來就要載的那一份。

⚠️ 「三樣算完都中性 ⇒ 回 null」那道判斷**也加了 `modelKey === undefined`**。
⛔ 少了它，一格**只**換模型的狀態會在這裡被判成中性 ⇒ schema 收得下、後台畫得
出來、遊戲裡什麼都不發生（第一·五守則點名的形狀）。

### 1.3 兩條算繪路（`apps/client/src/render/views/championBody.ts`）

| 路 | 改了什麼 | 少了它的症狀 |
|---|---|---|
| `modelDocFor` | `deps.resolveModelKey(overrideKey ?? modelKey, seatId)` | 身體根本沒換 |
| `modelOverrideFor` | `ARCHETYPE_BY_MODEL_KEY[visual?.modelKey ?? e.key]` | 身體換了，**卻還戴著上一具的臉**（#226 方塊人外觀） |

⭐ 兩支共用**同一份**解析（新抽的 `visualForSeatForm(seatId, formIndex)`），
所以「多格狀態同時命中的排序」與「狀態取代形態」只有一個住處。
`formVisualFor(e)` 現在是它的一行包裝，行為逐位元不變（`statusFormVisual.test.ts` 全綠）。

### 1.4 ⚠️ 與既有兩條解析路的**優先序**（寫進 schema 註解，因為它是資料層的承諾）

1. **贏過 `e.key`** —— `e.key` 是伺服器每 tick 從
   `Champions.get(championId).modelKey` 重算的（「這個座位選了誰」）；
   這一格說的是「這具身體**現在**穿什麼」，那是更晚的一句話。
2. **贏過裝備造型替換**（`resolveModelKey`）—— ⭐ 落地方式是把它餵成
   `resolveModelKey` 的**輸入**，⛔ 不是加一條 if：造型表查不到這個新的 key ⇒
   原樣回傳 ⇒「變身贏」是自然結果而不是第二條規則。
3. **繞過 `blizzardOverlay.resolve`** —— overlay 的工作是「這個 championId 沒有
   自己的模型時去 w3u 借一具」，而這一格是操作者**明寫**的選擇，
   和裝備造型同一個待遇（`resolved !== modelKey` 那條早退**同時**涵蓋兩者）。

## 2. M4 攻擊型態覆寫 —— 第十二格授予

### 2.1 一格加三處，四個授權面自動全拿

| 住處 | 檔 |
|---|---|
| TS 授予表 | `sim/stats/sourceGrants.ts` —— `SourceGrantFields.attackType` ＋ `sourceGrants()` ＋ `hasSourceGrant()` |
| Zod 授權格 | `content/schema/effects/_shared.ts` —— `SOURCE_GRANT_SHAPE.attackType` |
| 執行期來源 | `sim/stats/modifiers.ts` —— `ModifierSource.attackType` |

⭐ **四個授權面自動拿到**（道具 / 天生技 rank / 增益卡 / `applyBuff`）——
`sim/content/defs.ts` 的註解逐字寫著「下一個授予加進 `SourceGrantFields` 一格，
三個授權面自動全部拿到」，而 `ApplyBuffVariant` 今天已經 `extends SourceGrantFields`
（commit `6b9c8584`）⇒ 第四面（`applyBuff`）也自動拿到。
⛔ 我一行 `applyBuff` 的程式都沒有寫，`variantMirrorsSchema.test.ts` 直接綠。

### 2.2 詞彙**推導**，⛔ 不是第二份字面值

```ts
export type AttackTypeGrant = ChampionDef["attackType"];
```

它的語意就是「蓋掉英雄卡上宣告的那一格」，所以兩邊永遠不可能漂。
（Zod 那一側仍是 `z.enum(["melee","ranged"])` —— 與 `champion@1.attackType`
和 `item@1.requiresAttackType` 一致，repo 既有慣例，⛔ 沒有為它新開一份共用常數：
那要改 `schema/champion.ts`，不在柵欄內。）

### 2.3 兩個消費端，**一支**摺疊

| 消費端 | 那一行 | 只接它的症狀 |
|---|---|---|
| `sim/systems/BasicAttackSystem.ts:277` | `sourceAttackType(sc.sources, world.tick) ?? cdef?.attackType ?? "melee"` | 射得出去但**吃近戰的移速倍率** |
| `sim/stats/statPipeline.ts:150` | `{ attackType: sourceAttackType(...) ?? def.attackType }` | 移速換了但**人還是走過去揮刀** |

⭐ 兩邊共用 `sourceGrants.ts::sourceAttackType()`（最後掛上的贏、跳過已過期的來源
—— 與 `sourcePrimaryAttribute` / `damageTypeOverride` 同一條規矩）。
⛔ 它**不住在** `statPipeline.ts`：`BasicAttackSystem` 根本不經過統計管線，
兩邊各寫一次摺疊就是兩份會漂移的實作（失敗形態⑤）。

### 2.4 ⚠️ **刻意不接**的第三個讀取端

`sim/economy/offerEligibility.ts::championAttackType`（`item@1.requiresAttackType`
的商店推薦過濾）**沒有**跟著改，而那是一個決定，不是遺漏：

- 它回答的是「**這位英雄**該被推薦什麼裝備」，那是選角時定下來的身分；
- 讓一份 6 秒的 buff 去改它，商店可選清單會在變身進出時**整排跳動**；
- 而**已經買下的裝備沒有任何東西會重新檢查**（那份檔頭自己寫著這件事）。

理由逐字寫在 `sourceGrants.ts` 的 `attackType` 註解裡，⛔ 不是只寫在這份報告。

### 2.5 解鎖的 2 對

`godie-n00p` 妖狐 melee→ranged · `godie-o02l` 皮卡 ranged→melee
⚠️ 這 2 對**同時**還缺 M3 ⇒ 兩個機制都在了才動得了它們（這正是它們同一條 lane 的理由）。
