# GH#520 —— 手把五個手感常數落三個住處

日期 2026-08-22 · lane #520 · ⛔ 未 push

## 做了什麼

新增 `config.gamepad@1`（`content/config/gamepad.json`），把
`apps/client/src/input/GamepadInput.ts` 的五個 module-level `export const` 變成
後台調得到的欄位，三個住處一起落。

| 欄位 | 原本的常數 | 消費點 |
|---|---|---|
| `deadzone` | `GAMEPAD_DEADZONE` | `GamepadInput.poll()` → `stickToWorld(..., feel.deadzone)` |
| `moveLead` | `MOVE_LEAD` | `mapGamepadFrame()` 的 `move` order |
| `attackMoveLead` | `ATTACK_MOVE_LEAD` | `mapGamepadFrame()` 的 LT `attackMove` order |
| `basicAttackRange` | `BASIC_ATTACK_RANGE` | `mapGamepadFrame()` 的 RT `nearestEnemy` 搜敵半徑 |
| `longPressMs` | `GAMEPAD_LONG_PRESS_MS` | `GamepadInput.poll()` 的長按 edge |

**出貨值逐字等於原本那五個常數 —— 這一版手感一個位元都沒動。**

三個住處：
1. `content/config/gamepad.json`
2. `packages/shared/src/content/schema/config.ts` —— `zConfigGamepadDoc` +
   `DEFAULT_GAMEPAD_FEEL_POLICY` + `resolveGamepadFeel()` + **`zConfigDoc` union 一行**
3. `apps/admin/src/configForms.ts` 的 `GAMEPAD_SPEC` + `CONFIG_DOC_SPECS` 一列

讀端形狀抄的是同一支檔案已經示範過的 `aimAssistMobPenalty()`：
`activeGamepadFeel()` 每次呼叫都 `Configs.tryGet(GAMEPAD_DOC_ID)`，
和 `CameraRig` 讀 `config.camera@1` 同一條路 ⇒ **存檔 → 玩家重整分頁就生效**，
⛔ 不必重建 client 映像。`mapGamepadFrame` 維持**純函式**（手感由系統層在 poll
當下注入 `ctx.feel`，和既有的 `abilityRangeMult` 同一個形狀）。

## ⭐ 最重要的一個發現：稽核列的第五格是**空的**

issue #520 的證據列了五格，其中一格是 `GROUND_CAST_MAX = 6`。
**它今天對手把一格都不影響** —— GH#512（本版稍早，commit `4a7c1443`）已經把手把的
地面型夾限換成 `padCastReach()`（從技能自己的 `range` × 出貨 `abilityRange` 推導），
那個常數現在只剩 `input/TouchInput.ts` 的 tap / drag-aim 在用。

⇒ 把它放進「手把手感」會是一格**存了但手把上什麼都不會發生**的欄位
（第一·五守則：卡片上不可以有「說了但不會發生」的字）。所以這一版**刻意不收它**，
理由逐字寫進 `config.ts` 的 schema 檔頭與後台頁的 intro。
觸控要調的話，它該長在觸控自己的文件上，⛔ 不是借住這一份。

⚠️ 也就是說 issue #520 的「五格」與這一版的「五格」**不是同一組**：
我用 `longPressMs`（原本也是寫死的 `GAMEPAD_LONG_PRESS_MS = 400`，
而長按門檻正是 owner 最可能想調的手感之一）補上第五格。

## 守衛與突變

`apps/client/src/input/gamepadFeelConfig.test.ts`（101 行，實作 313 行）：

1. **三住處逐格一致** + 出貨文件被 `zConfigDoc`（collection union）收下
   + 反向對照（換掉 tag 要被拒 —— 少了它，壞掉的 union 也會全綠，失敗形態 ④）
2. **承重**：餵一組**非出貨**的手感，五條路（兩個前導距離／搜敵半徑／死區／長按門檻）
   真的都跟著動。⛔ 斷言不抄出貨數值，全部從 `DEFAULT_GAMEPAD_FEEL` 推導
   （測試的探針值取「出貨值與測試值的正中間」，所以 owner 哪天調了出貨值，
   這條測試不會用錯誤的訊息紅）
3. **承重**：`GamepadSystem.poll()` 真的把生效中的手感交給純 mapping
   —— 那一行刪掉會**靜靜退回出貨值**（`ctx.feel` 的 fallback 是出貨值，
   所以那是一條可以無聲刪掉的接線）

**突變紀錄**（一批一條，挑最承重的）：
`mapGamepadFrame` 的 `const feel = ctx.feel ?? DEFAULT_GAMEPAD_FEEL;`
→ 改成 `const feel = DEFAULT_GAMEPAD_FEEL;`（＝後台的值到不了純 mapping）
⇒ **2 / 3 條紅**（承重那兩條都紅，drift 那條照樣綠 —— 這正是它們分工的證明）。
改回。
