## 這把尺怎麼量（⛔ 為什麼不是 grep）

票文自己量到：拿 config id 的 camelCase 去 grep 高估 4 倍。掃描器走三層，每一層都是 AST／checker：

| 層 | 做什麼 | 抓到什麼 |
|---|---|---|
| ① 讀取點 | production 原始碼（`packages/shared/src` · `apps/game-server/src` · `apps/client/src` · `apps/content-api/src`，排除 `*.test.*`／`__fixtures__`／`testkit`）裡每一個 `X.enabled`／`X["enabled"]`／`const {enabled} = X` 的**讀**（寫入不算）| 296 個 |
| ② 歸屬 `originsOf` | 從 `X` 往回追資料流：屬性鏈 · 變數初始值與賦值 · 解構（含 `...rest`）· **參數 → 呼叫點實引數**（沿回傳值往下追時 context-sensitive，`Env` 綁那一次呼叫的引數）· 類別成員初始值與**所有** `obj.member = …` · 函式回傳值 · 物件字面值屬性（含 spread、`Object.freeze/assign`）· 三元／`??`／`||` · 陣列 callback 元素／`Object.values/entries`。終點三種：型別上 `schema: "config.x@1"` 字面值 · **直接**引數的查表鍵（`Configs.tryGet(TAUNT_DOC_ID)`、`find(c => c.schema === …)`、`configDoc("x", …)`，常數解開）· 同函式的 `d.schema === …` 守衛 | 96 格裡 95 格歸得到（差的 1 格 `commsWheel` 正是缺陷本身）|
| ③ 活性 | 讀取點所在的頂層宣告，要從出貨入口（game-server `cluster/main.ts`／`index.ts`、client `main.tsx`、content-api `index.ts`）沿「值位置的識別字參照 ＋ 模組載入（type-only import 會 elide）」走得到 | 1,339 檔裡 **128 檔走不到**（見附錄）—— #1035 當時的 `apCoefficient.ts` 就是這一種 |
| 中繼 | `enabled: typeof r.enabled === "boolean" ? r.enabled : DEFAULT` 這種**抄進政策物件**的讀不算消費（第二個住處，不是決策）；下游 `if (!rules.enabled)` 才算，而②會沿物件字面值把它追回 config | 只抄不讀的開關仍是 0 |

**誠實列出看不到的：** Go 消費端（用豁免＋證據檔）· `return d.enabled` 以回傳值中繼會被算成消費（偏綠）· 沒綁 `Env` 的參數退回「所有呼叫點聯集」，聯集 > 3 份 config 就當追不到（偏紅，寧可讓人來看）· 深度上限 32 · `GGD_ENABLED_TRACE=<file>:<line>` 可印單一讀取點的歸屬軌跡（debug 用；trace 時不讀 memo）。

**開發中抓到的量尺陷阱（都修了）：** ⓐ 查表鍵一開始掃整棵引數子樹 ⇒ `wallBlockRulesFromDoc(Configs.tryGet(X))` 在外層就停，把 `wallBlock.enabled` 記成 `enabled`（改成只認直接引數）ⓑ 撞深度上限的空結果進了 memo，毒到較淺的查詢（`mobWaves.boss.king.enabled` 因此假紅；改成截斷結果不快取）ⓒ `Object.freeze({...})` 擋住回傳值追蹤（taunt／icon-upload 假紅）ⓓ `...rest` 解構被當成屬性名（weather 路徑多一段）ⓔ `typeof x.enabled === "boolean" ? …` 的條件位置被當成決策（normalizer 全部變假消費端）。
