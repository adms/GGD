# GH#545 — 結算三個 3D model 靠太開

> owner 2026-08-22（逐字）:「勝利結算三個3d model 角色**靠在一起不要分那麼開**」

---

## 1. 量到的根因 ——「分那麼開」不是誰調錯一個數字

`styleOverlayCanvas` / `styleCrown` 把每一格的中心算成

```ts
const centre = ((slot + 0.5) / n) * 100;   // 三個人 ⇒ 永遠 16.7% / 50% / 83.3%
```

＝ 三張卡把**整個視窗寬度**均分。而**卡片寬度**是 `min(Xvh, Yvw)`，在寬螢幕上
由**高度**決定。**兩者的單位不同**，所以同一份設定在不同長寬比下疏密完全不一樣：

| 視窗 | 卡片寬 | 間距（中心到中心） | **相隔幾個卡片寬** |
|---|---:|---:|---:|
| 1920×1080（16:9 桌機） | ≈10.8vw | 33.3vw | **≈3.1** |
| 1440×900（16:10） | ≈12.1vw | 33.3vw | ≈2.8 |
| 2560×1080（21:9） | ≈8.1vw | 33.3vw | **≈4.1** |
| 390×844（直式手機） | 29.3vw | 33.3vw | ≈1.1 |

⇒ ⭐ **owner 在桌機上看到的正是那個 3.1–4.1。** 手機上它一直都是「靠在一起」的 ——
所以這不是一個被調錯的數字，是一個**單位不一致的形狀**。

⚠️ 這同時解釋了為什麼修法不可以只是「把 16.7 改成 33」：那樣在直式視窗上三張卡會**疊成一堆**。

## 2. 做了什麼（全部在檔案柵欄內）

### `apps/client/src/render/RoundWinnerStage.ts`

| 新增 | 是什麼 |
|---|---|
| `podiumSlotCentrePct(slot, total, spacing)` | 純函式。`pitch = (100 / n) * spacing`，中心對稱外推。⭐ **`spacing === 1` 與 2026-08-22 之前逐字同解** —— 它同時是「一鍵回到舊畫面」的那一格 |
| `podiumSpacing(cfg)` | 政策 → 倍率。缺席回退保險絲、超界夾回 `[PODIUM_SPACING_MIN, PODIUM_SPACING_MAX]` |
| `PODIUM_SPACING_MIN / MAX / FALLBACK` | `0.2` / `1.5` / **`0.5`** |
| `styleOverlayCanvas` 的 vw 上限 | `Math.min(88 / n, ((100 / n) * spacing) * 0.94)`；高度上限同比例 `× 96/88`。**`spacing === 1` 時 `94/n > 88/n` ⇒ `min()` 選 `88/n` ⇒ 尺寸逐位元不變** |

⭐ **為什麼 vw 上限要跟著間距收**：那是「調緊 ⇒ 在直式視窗上疊成一堆」的唯一防線。
桌機上 vh 上限贏，所以桌機的卡片大小**完全沒被動到** —— 只有站位靠攏。

`showTeam` 每一次都重算 `spacing`（和 `podiumSlotOrder` 同一個理由：人數沒變但政策變了的那一回合圖層是重用的）。

兩條 `it()`，全部走**出貨的 `showTeam`**（headless 注入假件），⛔ 不掃字串、⛔ 不釘數字：

   ⭐ 基準線**從函式自己推導**，⛔ 不抄 `16.667`。
2. **它是一格政策**：同一個 harness 換 `podiumSpacing` 1 → 0.4，兩側卡片與**皇冠**一起靠攏（冠的 `left` 逐字等於自己那張卡）；**而且** `min(…vh, Yvw)` 裡的 `Y`（寬與高）隨間距變小 —— 那是「調緊 ⇒ 直式視窗上疊成一堆」的防線。

⇒ **2 條全紅**（`expected 33.333 to be less than 33.333`）。已用 `Edit` 改回，⛔ 不是 `git checkout`。
