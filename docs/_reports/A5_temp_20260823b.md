# A5 · LAG 監控整合成一支（`__ggdDiag()`）

> owner 2026-08-23 逐字：「想一個機制系統專門找、監控 LAG 縮小找 root cause 的試錯時間，
> **之前應該有做類似功能請整合起來**」

## 他說對了：東西已經有四份，只是互不相通

| 既有的 | 看得到 | ⛔ 看不到 |
|---|---|---|
| `render/lifecycleLedger`（448 行） | 逐回合 × 逐類別普查、最老活幾秒、`suspects()` | 每一幀的成本 |
| `perfBus` | fps / workMs / ping / jitter / 六格健康計數器 | rAF **外面**發生的事 |
| `ui/PerfOverlay.healthWarnings()` | 六格計數器非零時畫在藥丸旁 | 數字**為什麼**變壞 |
| `render/AdaptiveQuality` | 降級階梯 | ⚠️ **只**讀那一條 rAF 的 `workMs` |

⇒ 沒有新開第五個系統：`perf/diag.ts` **沒有自己的狀態、沒有自己的計時器、沒有自己的緩衝區**，
它把四份拉到同一張紙上。唯一真的新量測是 `perf/longTasks.ts`（下面②），
因為它量的東西**沒有任何既有儀表拿得到**。

## 做了什麼

### 1. 一個入口 `__ggdDiag()` —— 五節，純文字，貼進 issue 就是完整現場
`apps/client/src/perf/diag.ts`。`__ggdDiagReset()` 把兩支被動量表歸零（「重現一次再量」）。
`__ggdLifecycle()` **留著**（它是第⑤節），⛔ 不打斷既有肌肉記憶。

```
① 每幀預算   wall = rAF 工作 + 上限刻意閒置 + ⭐ unaccounted
② 主執行緒被誰佔住   longtask（近 10s）+ 凍結長度（⛔ 沒有夾）
③ 網路   ping / jitter / 距上一張快照 / 取樣數
④ 場上有多少東西   ⭐ 左邊是儀表上的數字，右邊是真的
⑤ 累積   lifecycleLedger.report() 逐回合 × 逐類別
```

### 2. ⭐ `unaccountedMs` —— ⛔ 不可以藏的那個差額

```
wallMs = workMs + capSleepMs + unaccountedMs
```

第三段裝的正是 owner 在追的東西：瀏覽器合成、forced reflow、GC、shader 編譯、React reconcile。
⚠️ **在此之前它從來沒有出現在任何一個畫面上**，而 `AdaptiveQuality` 只讀 `workMs`
⇒ **這一段再大，畫質階梯也不會降**（它以為機器很閒）。
⇒ 「fps 儀表很好看卻很卡」第一次有了可以指名的解釋。

⛔ **負值照樣印**：負代表兩個滾動視窗（adaptive 的窗 vs 送出去的幀的窗）不同步 ——
那本身是訊號，`Math.max(0, …)` 掉等於把矛盾藏起來。
⚠️ 刻意用 `1000/avgFps` 而不是 `perfBus.frameMs`：後者是**最後一幀**的瞬時間隔，
而 `workMs` 是滾動平均，混算會讓差額每 250 ms 跳一次。

### 3. `PerformanceObserver('longtask')` + 凍結長度（`perf/longTasks.ts`，唯一的新檔）
- `buffered: true` ⇒ 掛上去**之前**的 longtask 也拿得到（開場那一波 shader 編譯不會消失）
- ⛔ 零幀成本：passive observer，⛔ 不輪詢、⛔ 不掛 rAF
- ⛔ Safari / Firefox 沒有這個介面 ⇒ `supported: false`，畫面印「不支援」、**⛔ 不是 0**
- 環狀緩衝 64 筆（⛔ 一個沒有上限的登記表就是下一個洩漏）

### 4. ⚠️ 三條量到的儀表謊言，全部處理

| 謊 | 現在 |
|---|---|
| `minFps` 永遠 ≥ 10（`FrameDelta` 把 dt 夾在 `[1,100]`）⇒ 300ms 卡頓與 2 秒凍結都寫 10 fps | ⭐ **誠實替代品**：4 Hz 取樣計時器**自己晚了多久**（⛔ 沒有夾）。撞到地板時 `minFpsIsFloored` 會在①當場說「上面那個數字是假的」。⛔ 沒有動 `FrameDelta` —— 夾是**對的**（同一個 dt 餵給預測與動畫） |
| `drawCount = scene.meshes.length`（含 disabled／池子裡的），⛔ 不是 draw call | `lifecycleLedger.sceneTruth()` 並排印 `meshesEnabled` 與 `getActiveMeshes()`（上一幀真的畫的）。面板標籤改成誠實的 `ent / mesh / psys` |
| `particleCount` = **系統數**，⛔ 不是活粒子數 | `sceneTruth()` 加總 `getActiveCount()` 印真的顆數 |

⛔ **沒有覆寫 `perfBus` 那兩格**（它們有自己的消費端與守衛）—— 而是把「儀表上的數字 vs 真的」
印在同一行，差額一眼看得到。讀不到回 **-1**，⛔ 不是 0。

### 5. 擋不掉的那一半
`diagWarnings()` 接在既有 `healthWarnings()` 前面，畫在**永遠可用**的 fps 藥丸旁 ——
⛔ 不受 `showPerfOverlay` 管（那一格出貨預設 false）。
門檻刻意訂高（凍結 ≥400ms／長任務 ≥250ms/s／幀外開銷 > 迴圈成本且 ≥8ms）：
⭐ **一個一直亮著的警報等於沒有警報**（同 `suspects()` 的第三個條件）。

## ⭐ 最重要的一個發現（突變驗證當場抓到的）

把 `PerfOverlay` 的 `perfWatch.note(nowMs, SAMPLE_MS)` 拿掉之後，**兩條**測試紅了 ——
第二條不在預期內：`longTasks()` 在 `idle`（還沒有人打過點）時回 **`supported: true` + 全 0**。
⇒ ⛔ 那正是這一支存在要防的那種謊：「量不到」與「很順」在 0 上長得一模一樣，
而且它**只在接線斷掉時**才會出現 —— 也就是最需要它說實話的那一刻。
修法：`longTasks()` 讀的時候自己 `start()`（冪等），⛔ 不依賴有沒有人打點。

## 開關（owner 常設：「留後台開關可以簡易 rollback」）

⭐ **沒有新增任何 config 欄位** —— 整個診斷掛在**既有的**
`vfx-cleanup.lifecycleLedgerEnabled`（已經三個住處齊全）底下：
關掉 ⇒ 第④⑤節熄燈，報告開頭當場印一行「⚠️ lifecycleLedgerEnabled=false」。
①②③（純讀 perfBus + 兩支零成本被動量表）永遠可用，因為它們**沒有成本可以省**。
⚠️ 這是刻意的取捨：多一格死欄位＝第一·五守則的「說了但不會發生的字」。
