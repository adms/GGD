## ① GH#660 —— 「淡出飛上天的粒子」的殘留

### 根因（量出來的，⛔ 不是猜的）

GH#569 已經立了「fade out 尾段一律最多佔 0.5 秒」這條常設規定，而 owner 又看到同一件事。
原因是**「尾段」的定義漏掉了一半**：

| | |
|---|---|
| `fadeOut.ts` 的「尾段」 | **最後一個還看得見（alpha > 0）的關鍵格** → 它後面第一個歸零的關鍵格 |
| `fx.fam.dissipate.*`（＝「施法時飛上天的粒子」那一族）的 alpha | `0.75 → 0.75 → 0.315 → 0`（4 格） |
| ⇒ 量到的尾段 | **0.443 秒** ⇒ **在 0.5 以下 ⇒ 那道閘一次都沒有叫過** |
| ⇒ 玩家看到的 | 從 α 開始掉那一刻起算的 **0.886 秒**（整族壽命 1.107 秒） |

⭐ 中間多一格「半亮」就把淡出**切成兩段**，於是舊定義只量到最後一段。

### 修法：一格上限 + 同一支夾子（⛔ 不是第二套規則）

- **新窗口** `dissipateWindow(doc)`：**最後一個還在峰值 alpha 的關鍵格** → **同一個歸零的關鍵格**。
  ⭐ 兩個窗口**同時結束**（共用 `windowFrom()`），所以兩個上限可以直接比誰嚴。
- **新上限** `config.vfx-cleanup@1.vfxDissipateMaxSec`，**出貨 0.5**
  （＝ owner 在 GH#569 說的那個秒數，⛔ 不是我另外挑的數字）。
- `clampFadeOutTail(doc, maxSec, dissipateMaxSec = maxSec)` —— **第三個參數預設等於第二個**是刻意的：
  沒有傳它的呼叫端（`W3xEmitterRig` 算「效果什麼時候被回收」的那一支，在本 lane 柵欄外）
  拿到的壽命與 `toParticleSystem` 真的建出來的粒子壽命**一致**，⛔ 不會出現
  「粒子 0.72 秒死光而發射器再賴 0.4 秒」那種看不見的殘留。
- 夾在**唯一的解析入口** `toParticleSystem()`，⛔ 不改 585 份文件（第〇·四守則）。
- ⭐ **只夾非常駐**（`opts.persistent` / `doc.ambient`）—— GH#660 原話點名「持續 5 秒的光環
  ⛔ 那不該被砍」，而「常駐」早就是程式裡的一格旗標（`markVfxPersistent` 讀的正是它）
  ⇒ 判準是**已經存在的資料**，⛔ 不是一張會腐爛的豁免名單。
- ⚠️ **夾到就印一行**（`[vfx] 收尾夾子: <id> 1.107s → 0.721s`），每份文件只印一次。
  fail-open 沒錯，**靜默**才是缺陷。

### 影響面（量到的）

| | |
|---|---|
| 出貨 vfx 文件 | 585 份 |
| 舊閘（尾段 > 0.5）會夾的 | 88 份 |
| ⭐ 新閘（收尾全長 > 0.5，非常駐）會夾的 | **173 份**，壽命中位數縮 **25%** |
| 最兇的幾份 | `fx.w3x.particle.sephboom.p01` 8.0s → 0.66s · `lasercannonfinalred.p07` 5.0s → 0.55s · `godie-blackhole1-p0` 3.5s → 0.5s |
| dissipate 那一族 | 1.107s → **0.721s**（身體 0.221 ＋ 上限 0.5） |

⚠️ **為什麼是 0.721 不是 0.5**：owner 的規定是「**收尾**最多 0.5 秒」，⛔ 不是「整支特效 0.5 秒」——
身體（還在最亮的那一段）**秒數不動**，砍身體就是砍特效。
⭐ 而走 `VfxSystem.play()` 的那條路上還疊著 `oneShotMaxLifeSec`（0.6），比較嚴的贏。

### 止血閥

`vfxDissipateMaxSec` 拉到上界 **8**（＝出貨文件裡最長的那一份）⇒ 這道夾子實際上不會叫
＝ 一鍵回到這一版之前的畫面。⛔ 不必改程式、不必重新 build client。

## ② GH#654 —— 天氣：下雨

### 現況（先量再做）

`content/config/weather.json` + `config.weather@1` **已經出貨**（GH#610 第二批）：
濕地面 · 積水 · 雷擊補光 · **霧的兩層**（`scene.fog` ＋ 飄過去的霧片）。
⇒ 這一批缺的**只有降水**，所以做法是**在既有機制上加一層**，⛔ 不是開第二套天氣系統。

### 一個機制 ＋ 一張表

- `WeatherWeights` 加一格 `rain`；`WEATHER_KIND_WEIGHTS` 補一欄：
  `rain: 1` · `storm: 1` · 其餘 **0**（含兩個 `indoor-*`）。
  ⭐ `indoor-damp`（洞窟滲水）**地面濕、有積水，而天上一滴都不掉** —— owner 的
  「有些場景是室內，請不要下雨」抱怨的是**天上掉水**，⛔ 不是地上有水。
- ⭐ 「**哪一張圖下雨**」**沒有新的住處**：仍然是 `arenas` 那一格級別。
  ⇒ ⛔ 不可能「天氣說晴朗、天上在下雨」。
- 六格新純量（全部 `.optional()`，防線上舊 override 被 Zod 退回 ⇒ 2026-08-02 骨架事故的形狀）：
  `rainEnabled`(**false**) · `rainDropsAtFull`(1200) · `rainFallSpeed`(22) ·
  `rainTiltDeg`(12) · `rainStreak`(9) · `rainAlpha`(0.22)。
- 客戶端**一個**系統：`apps/client/src/vfx/WeatherRainFx.ts`
  （純函式 `rainPlan()` ＋ `buildRain()`），`ArenaScene` 一行接線。

### ⭐ 出貨 = 關

新功能，⛔ 不是修復 ⇒ **不套**第〇·六守則的「優先權大的更新後都是預設啟動」。
owner 打開 `rainEnabled` 之前，畫面與上一版**逐像素相同**（守衛①就在驗這件事）。

### GH#654 明文要求先量的兩件事

1. **效能進降級階梯**：`rainPlan()` 把滿載滴數 **乘上** `particleBudgetScale(…particleDensity)`
   —— 與 `VfxSystem` / `AmbientVfx` **同一顆**旋鈕。降到 0 ⇒ 這一層不建（守衛④）。
   ⇒ ⛔ 不是「開了就永遠在」（#614）。
2. **⛔ 不遮住玩家看得見的資訊**：`rainAlpha` 上界 **0.6**（玩法界線，理由與霧的兩格同源
   —— 雨落在相機與英雄之間），而出貨值 0.22 **刻意離上界很遠**（裝飾⛔ 不是遮蔽）。

### 兩個實作決定（我挑的，都留了開關）

| 決定 | 理由 |
|---|---|
| GPU 粒子，CPU 是**退路** | GH#654 逐字「⛔ 不要 CPU 粒子」。`GPUParticleSystem.IsSupported` 為真走 GPU；⚠️ NullEngine 沒有 WebGL2 transform feedback ⇒ 測試量到的是 CPU 那條路，兩條共用同一個 `IParticleSystem` 與同一份 `rainPlan()` |
| **風向不開後台格** | 從場地 id 推導（`fogBankSeed` + `fogHash01`）⇒ 同一張圖每次進來風向一致，兩張圖不會同向。多一格只會多一個沒有人會調的旋鈕 |
| **雨標成常駐** | ⏳ GH#570 的兜底掃描出貨掃**整個 scene** ⇒ 不標的話 5 秒後雨就停了，⛔ 而畫面上只會看到「雨下一下就停」 |
| 生命週期綁在 emitter mesh 上 | `disposeArena()` 收 root 的那一刻雨跟著死 ⇒ `ArenaHandles` ⛔ 不必多開一格（同 `buildFogBanks` 把 observer 綁在 `mesh.onDispose` 的理由） |
