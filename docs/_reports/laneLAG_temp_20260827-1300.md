## 1. 為什麼在此之前沒有人拿得到數字 —— 量尺**當場就會說謊**

前兩輪都寫了「headless 量不到 frame time」。這一輪用**真瀏覽器**
（Claude Browser pane · **Apple M5 Max / ANGLE Metal / WebGL 2.0**）跑，
⛔ 但它**不是**直接就能量：

| 陷阱 | 量到的 | 如果沒發現會怎樣 |
|---|---|---|
| ⭐ **分頁是 `hidden`** | `requestAnimationFrame` **12 秒 0 幀**；一次 screenshot 剛好逼出 **1 幀** | 每一段的環形緩衝都是空的 ⇒ 報告印一組**分母 0** 的漂亮數字 |
| ⭐ **canvas 背後緩衝不跟著 CSS 走** | 視窗縮到 640×400 之後，backing store **仍然是 2560×1600** | A/B 會得到「降解析度沒有用」這個**相反**的結論 |

⇒ ⭐ 兩個都正是 CLAUDE.md 記過的形狀（「canvas 背後緩衝 300×150」「量尺自己會說謊」）。

**解法（⛔ 全部住在 `/private/tmp/lag/wt` 這個丟棄式 worktree，repo 一個位元組都沒動）：**

1. **MessageChannel rAF pump** —— 背景分頁裡 Chrome **不節流** self-post 的 message
   ⇒ 拿它當 vsync。它在**兩幀之間**跑、⛔ 不在 callback 裡 ⇒ ⭐ 逐段歸屬仍然誠實，
   ⚠️ 只有 wall-clock / `unaccounted` 被它灌大。
2. **`?cs=<秒>`** —— vs-bot 選角出貨值是 **320 秒**而 bot 不會提前鎖定
   ⇒ 每量一次空等 5 分鐘。只改**建房參數**，⛔ 不碰任何逐幀成本。
3. **`window.dispatchEvent(new Event('resize'))`** —— 逼 Babylon 真的重配 backing store。

⭐ **量尺自證每一次都印出來**：燒 4 ms → `draw` 量到 **4.00 ms**、其餘段最大 **0.00 ms**
（**兩個方向**都驗）。⛔ 自證沒過的話底下每一格作廢。

## 2. ⛔⛔ 擋路的那個東西：**HEAD 進不了遊戲**（GH#760 的當日回歸）

### 量到的

真瀏覽器 · localhost · HEAD：點「Play offline vs bots」之後
**永遠停在「Connecting to match…」**，而伺服器那邊房間是好的
（`rooms.active=1` · `sim.ticks` 一直在跑）。同時 `GameApp.collectEntities`
**每一幀**擲 `TypeError: Cannot read properties of undefined (reading 'forEach')`。

### 根因（逐行）

`48089294`（**今天 06:56**，GH#760 步驟 2）把 `MatchState.entities` 標成 view-gated：

```ts
view()(MatchState.prototype, "entities");     // packages/shared/src/protocol/schema.ts:994
```

那一格的檔頭已經寫對了一半 ——「⛔ 沒有 `client.view` 的客戶端一個實體都收不到」。
⭐ **而它沒寫的那一半才會咬人**：**有 view、但 view 裡一個實體都沒有的時候，
Colyseus 根本不送這一格** ⇒ 客戶端讀到 **`undefined`**（⛔ 不是 `size === 0` 的空 map）。

⚠️ 而那正好就是**選人畫面**。實測（183 份連續快照）：`champSelect / noEntities`，
⭐ 一份都沒有例外。逐欄位量過，**只有 view-gated 的那一格缺席**：

```
phase champSelect · entities undefined · seats _MapSchema(size 0) · duels _ArraySchema(len 0)
```

⇒ ⭐ **「空的非 view 集合會上線、空的 view-gated 集合不會」** —— 這就是 #760 改變的東西。

### 它造成的兩件事

| 位置 | 症狀 |
|---|---|
| `GameApp.onStatePatch` 的閘 `if (!state?.seats \|\| !state.entities) return` | ⭐ **整份快照被丟掉** ⇒ `syncHudFromState` 一次都沒跑 ⇒ `connected` 永遠 false ⇒ **進不了選人畫面 ⇒ 打不了遊戲** |
| `GameApp.collectEntities` · `frameBusProjection`（3 處） | **每一幀**擲 `TypeError` ⇒ `renderFrame` 死在第 4 步 ⇒ 後面的 views/camera/vfx/anchors/**draw** 全部不跑 |

⚠️ **它是死結**：離開 champSelect 要玩家鎖定英雄 → 鎖定要選人 UI → 選人 UI 要
`connected` → `connected` 要 `syncHudFromState` → 而它被那一行擋著。

### ⚠️ 用詞紀律 —— 我量到的**只有**這個環境

⭐ 量到的是「**localhost · HEAD · offline vs bots** 這條路死結」。
⛔ 我**沒有**量線上（禁令：不碰 ggd.adms.ai）、⛔ 也沒有量 platform 的 seat-reservation 那條路。
⚠️ ⭐ 但 `champSelect` 是**兩條路共用**的階段，而缺席與流程無關、只與「view 裡有沒有實體」有關
⇒ **強烈懷疑它是全流程的**。⛔ 這一句是推論，⛔ 不是量到的。

### 修在哪（⭐ 客戶端，⛔ 不是把 `view()` 拿掉）

「空的 view-gated 集合不上線」是 **Colyseus 的編碼事實**，⛔ 不是伺服器忘了指派 view
（`MatchRoom.onJoin` 已經 `zoneViews.onJoin(client)` 了）。
⇒ ⭐ 會**再次**發生的是「客戶端假設它一定在」，所以閘要立在客戶端這一側。

**落地**（全部在柵欄內）：

- 🆕 `apps/client/src/net/viewGatedEntities.ts` —— `entitiesOf()` / `entitiesDelivered()`，
  ⭐ 讀那一格的**唯一**入口（⛔ 不讓 `?? {}` 散落成第二個住處）。
- `GameApp.ts` —— 閘改成 `if (!state?.seats) return;`（`seats` **沒有** view tag），
  **20 處** raw read 全部走 `entitiesOf()`。
- `game/frameBusProjection.ts` —— 3 處同上。
- ➕ 順帶：`duelViews` 的 `state.duels.length` → `state.duels?.length ?? 0`。
  ⚠️ 這一個是**既有的**（第一份快照抵達前 `renderFrame` 就在跑），
  在此之前被 `collectEntities` 擋在前面所以看不到；修完上面那些之後它變成新的第一個。
  實測每次進場**必定** 4 次。

### 驗收（⭐ 螢幕上量到的，⛔ 不是「應該會好」）

| | 修之前 | 修之後 |
|---|---|---|
| 點 Play offline vs bots | ⛔ 永遠「Connecting to match…」 | ⭐ `connected:true` · `phase:champSelect` · **12 seats** |

## 3. ⭐ #614 的正題：逐段歸屬

**環境**：M5 Max · 1280×800 · dpr 2 ⇒ backing store **2560×1600 = 4.10 MP** ·
新手競技場（`arena.skeleton`，**最輕的一張**）· offline vs bots · fps cap 60 ·
畫質 L0（adaptive 有在跑，`resolutionScale=1`，⛔ 沒有降級）。

### 第一回合 combat（分母 **3,194 幀**，視窗 180）

```
逐段 p50 合計 3.50ms   （wall 16.9ms = rAF 工作 3.5ms + 上限閒置 13.2ms + unaccounted 0.2ms）
fps 59 (min 53) · 上限 60

draw     p50  2.70ms · p95  3.30ms · max   7.40ms · 77%
camera   p50  0.40ms · p95  0.70ms · max  17.30ms · 11%
vfx      p50  0.30ms · p95  0.50ms · max   0.80ms ·  9%
views    p50  0.10ms · p95  0.20ms · max   2.20ms ·  3%
round    p50  0.00ms · p95  0.00ms · max   0.10ms ·  0%
drain    p50  0.00ms · p95  0.40ms · max   1.60ms ·  0%
predict  p50  0.00ms · p95  0.10ms · max   0.20ms ·  0%
anchors  p50  0.00ms · p95  0.10ms · max   0.20ms ·  0%
—— 迴圈外面（住在 unaccounted）——
domAnchors p50 0.30ms · p95 0.40ms · max 0.60ms
```

場上：`scene.meshes` 635（enabled 394，**上一幀真的畫 77**）·
粒子系統 154 / **活粒子 2,673 顆** · mat 256 · tex 325 · 實體 6。

### ⭐ 兩個直接的結論

**① 兩個被推理關掉的嫌疑犯，數學上救不了 lag。**

| #614 的嫌疑犯 | 它住在哪一段 | 那一段的 p50 佔比 |
|---|---|---|
| ⚡ `castArcs`（爆散弧帶） | `vfx` | **9%**（0.30 ms） |
| 🌍 `world-cues point.mobSpawn` | `drain` → `vfx` | **0%**（drain p50 0.00 ms） |

⇒ ⭐ 就算把 `vfx` **整段砍到 0**，一幀也只從 3.50 → 3.20 ms。
⛔ 這與票上「關掉之後還是 lag」完全一致 —— **它們從來就不是兇手**。

**② `draw` 那 77% 是什麼？做了 A/B（⭐ 兩個方向）**

| 解析度 | 像素 | `draw` p50 |
|---|---:|---:|
| 1280×800 @dpr2 | **4.10 MP** | **2.70 ms** |
| 640×400 @dpr2 | **1.02 MP** | **1.60 ms** |

⇒ 少掉 3.08 MP 只省下 **1.10 ms**（≈ **0.36 ms/MP**），⭐ 而 **1.24 ms 是不隨像素動的固定成本**。

⇒ ⭐ **`draw` ≈ 46% 填充率 + 54% 固定（draw call / state change）**。
77 個 mesh 吃掉 1.24 ms ⇒ **≈ 16 µs / draw**，⭐ 那是**送指令的 JS 成本**，⛔ 不是 GPU。

⚠️ ⭐ **兩條槓桿都要**：`resolutionScale`（已經是 adaptive 的旋鈕）治得了填充那一半，
⛔ 治不了另一半 —— 另一半要**減少 draw call**（合批 / instancing），
⭐ 而那正好就是 **#382 的方向**（那條 lane 已經量到 12 份 prop 共用同一張 1024² 貼圖）。

### 跨回合累積（順帶量到，對到 owner「到第七回合就很難動作」那條線）

`__ggdLifecycle` 逐回合 live 數：

| kind | R1 | R2 | R3 |
|---|---:|---:|---:|
| `geo:all` | 172 | 344 | **394** |
| `mesh:…` | 1 | 161 | **193** |
| `mat:…` | 0 | 97 | **110** |
| `tex:?` | 11 | 32 | **51** |
| `skel:…` | 6 | 20 | **37** |

⭐ **單調在長**（最老的活了 217 秒）。
⚠️ ⭐ **但到 R3 為止它還沒有變成 frame time**：`draw` p50 2.70 → 2.80 ms、合計仍是 3.50 ms。
⇒ ⛔ **不要**把「物件在長」直接當成「所以才 lag」——這一份量測**證明不了**那條因果。
⭐ 唯一跟著變壞的是**凍結**：R1 `75.7 ms × 1 / 241 取樣` → R3 `102.8 ms × 4 / 906 取樣`。
