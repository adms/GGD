## #605 —— `spawnModelFx` 整族沒有聲音通道 ✅ 落地

> owner 2026-08-23：「**也別忘了動地剁，跟相關的音效要播出來**」

### 做了什麼（⭐ 補一格解決整族，⛔ 不是逐支接線）

| 層 | 檔 | 內容 |

| 型別 | `sim/effects/variants/spawnModelFx.ts` | 同兩格（`EffectDef` 是手寫聯集，⛔ 不從 Zod 推導） |

| 客戶端 | `audio/vfxSound.ts` | `modelFxCues()` ＋ 落點音的**絕對時間**登記表（`update()` 回收、`reset()` 清空） |

### ⭐ 我挑了什麼（owner 的常設指令：自己判斷、留後台開關）

| 爭議 | 我挑的 | 為什麼 |
|---|---|---|
| `onTouch` 要不要有聲音 | ⛔ **沒有 `touchSoundKey`** | `onTouch` 是逐段取樣班表：最多 24 取樣 × 12 具 = **一次施放幾百發**，那是音爆不是音效。「打到人的那一聲」已經有住處（傷害事件走**特效命中**那一層） |
| `onArrive` 要不要有聲音 | ✅ **有** | owner 的「動地剁」就是**落點**那一聲 |
| 一具一發 vs 一次施放一發 | **一次施放一發** | radial×12 十二具同時落地 ⇒ 十二發同時響 |
| 落點時間怎麼算 | 取整組實例**走最久**的那一個 | 出貨內容上與「第一個」相同；長短不一時，聲音對得上畫面最後發生的事 |
| 聲音掛在哪一層程式 | **`vfxSoundCues`**，⛔ **不是** `VfxSystem` 的 `case "modelFxSpawn"` | 那個 case 第一行是 `if (!this.modelFx) break;`（一個**算繪**前提）—— 掛在它後面 = 模型檔沒進來連聲音也一起消失 |

**後台那一格叫 `config.audio-map@1.modelFxSound`**（`content/config/audio-map.json`）：
`enabled: false` ⇒ 整族逐位元回到 GH#605 之前；`arrive: false` ⇒ 只留施放音。
出貨值 `{ enabled: true, arrive: true }` ——「開」是我挑的那一邊，因為 owner 的話是「音效要播出來」。

### 守衛

`apps/client/src/audio/modelFxSound.test.ts` —— 出貨的 `audio-map.json` ＋ 出貨的 38-03 技能文件
（key **從內容讀出來**，⛔ 不抄字面值）→ 真的 `VfxSoundLayer` → 真的 `vfxSoundCues`/`vfxLoopPushes`
→ 真的 `SpatialSfxQueue.flush` → 斷言落在 `playSfx` 收到的 key 上（⭐ 讀最終物件）。
含「還沒到時間不可以響」與「到期後登記表歸零」兩格回收斷言，＋ 開關兩檔的反向對照。

### ⚠️ 順帶發現：`modelFxSpawn` 的 **payload 契約對不上**（⛔ 不是這條 lane 修的）

sim 送 `{ caster, modelKey, path, speed, x, z, zone, instances[] }`；
`VfxSystem.ts:2016` 讀 `ev.data.spec`（`ModelFxMotionSpec`）＋ `y` / `facingRad` / `target` / `arriveVfxKey`
—— **全 repo 沒有任何地方寫過這五格**。⇒ 那個 case 第一次取值就 `undefined` 而 `break`。

- `eventFanout.ts` 的檔頭**自己**寫著這種故障：「An event that arrives with the wrong shape is
  worse than one that never arrives, because the handler silently no-ops and the feature still
  looks "done"」。
- ⇒ #605 票裡「畫面**有**、只是無聲」這個前提**存疑**：畫面那一半可能也是空的。
- ⛔ 沒有當場修：兩邊是**兩種設計**（sim 送逐實例算好的方向；客戶端的 rig 從 spec ＋ facing
  自己重算），而 `facingRad` 需要 `atan2`（`sim/**` 禁止三角函式）。
  對齊它要動 `render/modelFxPath.ts` / `modelFxRig.ts`（柵欄外），且是一張**獨立的票**。
- ⭐ 這條 lane 的音效**不受影響**：它刻意走 `vfxSoundCues`，⛔ 不經過那個 case。

## #603 —— EX 魔法陣從出生就掛著 ✅ 落地

> owner 2026-08-23：「**EX 技學習到時**，底下魔法陣記得要顯示跟 JASS 一樣」

### 根因（⛔ 不是「機制沒做」）

`zPersistentVfx` 的表**逐字**寫著：`when` 缺席 = `GetUnitAbilityLevel(u,'A0xx') > 0`
（「這支技能**在身上／已解鎖**就掛著」）。而客戶端把「缺席」實作成**恆真** ——
於是魔法陣從出生就在腳下。原作是 `set udg_EX_Mode = true` **之後**才 attach。

### 修法：⛔ 零個新的 schema 欄位

`SeatState.abilityRanks` 與 `SeatState.exRank` **本來就在線上**（`snapshot.ts:374`）。
⇒ ⛔ 沒有動 `protocol/schema.ts`（`defineTypes` 是 APPEND-ONLY，加一格不可逆），
⛔ 也沒有在客戶端重寫條件求值器（帶 `when` 的那一批仍由
`persistentVfxClientCoverage.test.ts` 擋著 —— **那個決定是對的，我沒有推翻它**）。

- `render/views/persistentVfx.ts` 新增純函式 `persistentVfxKeysFor(doc, resolveAbility, learned)`：
  EX → `exRank > 0`；Q/W/E/R → `abilityRanks[i] > 0`；**天生技恆真**（等級 1 起自動擁有）。
- `GameApp.persistentVfxFor(key, seatId)` 變成三行轉接器。
- ⭐ **兩條算繪路都接了**：`syncAmbient`（粒子/緞帶）與 `formAttachmentFor`（**glb 掛件**，
  魔法陣其實走這一條）。⛔ 只改一條 = 粒子等解鎖、模型從出生就掛著。
- `learned === null`（seat 還沒同步／小怪 `seatId === -1`）⇒ **fail-closed**：
  原作是「解鎖之後才 attach」，所以「還不知道」的正解是「還沒有」。

### 守衛

`render/views/persistentVfxTiming.test.ts` —— 夾具是**出貨的**
`content/champions/godie-h020.json` ＋ `content/abilities/godie-h020.ex.json`。
驗的是**時機**：`exRank 0` ⇒ `liveKeys` 空且 port 一次都沒被呼叫；學到 ⇒ 出現；
退回 0 ⇒ 句柄 `cancelled === true` **且**帳本忘掉它（⛔ 不是 alpha=0）。

### ⛔ 沒有做後台開關

owner 的原話就是這個行為本身（「EX 技學習到時」），⛔ 沒有第二個候選可挑 ⇒ 沒有爭議要 rollback。
另外 `content/config/ambient-vfx.json` 在柵欄外，而新增一份 config 會動到
`apps/admin/src/store.ts` ＋ `ui/App.tsx`（已知的共用檔）—— 併行時那是撞車。

> owner 2026-08-23：「技能說明記得改，不然之前都是寫未實作」

### 量到的（修前 / 修後）

| | 被印「天生被動 · 效果尚未移植（目前無作用）」 |
|---|---|
| **修前** | **5 格** —— `godie-h020.passive`（04-00 翔封界 `flight`）· `godie-hjai.passive`（同，鏡射）· `godie-e002.passive`（20-00 銀色甲胄 `block`）· `godie-e008.passive`（21-00 灼眼 `vision`）· `godie-hapm.passive`（52-00 十二道試煉，**真的空**） |
| **修後** | **1 格** —— 只剩 `godie-hapm.passive`（它連 `passive` 區塊都沒有） |

⇒ ⭐ **4 格謊話全部消失，而唯一真的空的那一格仍然誠實。**

### 修法：判準從 **schema 推導**

`passiveRankGrantsSomething()` 原本手寫三格（`modifiers`/`hooks`/`auras`），
而 `zAbilityPassiveRank` 早就長到 13 格（`SOURCE_GRANT_SHAPE` 展開的
`flight`/`vision`/`block`/`deathWard`/`critStrike`/`attributes`/`damageTypeOverride`/
`penetration`/`typeStreakImmunity`/`immobile`/`primaryAttribute`）。

```
PASSIVE_RANK_PAYLOAD_KEYS = Object.keys(zAbilityPassiveRank.shape) − PASSIVE_RANK_GATES
PASSIVE_RANK_GATES        = { whileForm, whileStatus }        ← 唯一手寫的一半
```

⭐ 推導**方向**是刻意挑的：「欄位**預設**是酬載，扣掉列名的閘」⇒
**新增一種酬載自動被算進去**（正是這張票的病）；新增一個**閘**忘了登記會往另一個方向錯，
而那個方向由守衛的第二條斷言擋住。

### 守衛（⭐ 兩個方向，`ui/passiveSlotHonesty.test.ts`）

它問的是**兩個名詞的關係**，⛔ 不是重述判準自己：
「UI 說這一格有沒有效果」vs「**sim 真的會不會掛上一份 `ModifierSource`**」
（後者逐條照 `sim/abilities/abilityPassives.ts::rankBlock` 的空值測試，含出貨的 `hasSourceGrant`）。

① 有酬載的**一格都不可以**被標未實作 ② 真的空的**仍然**要被標未實作
（②另含一個「只有閘的 rank 區塊」的合成夾具 —— 出貨樹上今天沒有這一種，
少了它「判準退化成一律放行」會逐位元不被察覺）。

### 突變驗證（⭐ 這一批的那一條，兩個方向都做了）

| # | 突變 | 結果 |
|---|---|---|
| ① | `PASSIVE_RANK_GATES` 加入 `"flight"`（＝從推導清單裡拿掉 flight） | 🔴 紅，訊息**指名** `godie-h020.passive 04-00 翔封界` / `godie-hjai.passive 04-00 翔封界`，並印出判準看得到的酬載清單 |
| ② | `passiveRankGrantsSomething` 改成 `return true` | 🔴 紅（「形態閘／狀態閘是**閘**，⛔ 不是酬載」） |
