# E4 —— 1000 隻殭屍會不會來不及算？用 Go 重寫值不值得？

> owner 2026-08-23（逐字）：
> 「四閘 wall 297.8 秒⋯**不是很久嗎？用 GO 寫跑 benchmark 看看會不會比較好？
>  包括後端處理地圖物件的時候，避免像是有 1000 個殭屍在地圖上，
>  後端來不及計算的問題**」

⭐ **兩個答案，先講：**

| 題 | 答案 |
|---|---|
| **① 1000 隻殭屍撐得住嗎？** | ⛔ **雲端撐不住**（一間房 42–56 ms/tick vs 預算 33.3 ms）。本機撐得住 |
| **② 用 Go 重寫值不值得？** | ⛔ **不值得。** 同一個演算法下 Go 只快 **1.05×**（＝沒有差）。⭐ 真正的槓桿是**換資料結構**：留在 TS 就有 **3.4×** 與 **80×** |

⚠️ ⭐ 這與 A3 那張票的結論**是同一個形狀**：那次也是先假設「Python 慢」，
量完發現是一行 O(F×N) 掃描，修掉之後 Python 自己快 11.4× 而 Go 反而慢 8%。
**這一次的答案一樣：慢的是演算法，⛔ 不是語言。**

⚠️ owner 問題裡的「四閘 wall 297.8 秒」是**測試閘的 wall-clock**，
⛔ 與 sim 的 tick 預算是兩件事 —— 這份報告只回答**後端來不及計算**那一半。

## 1. ① 曲線：實體數 → ms/tick

⭐ 全部量到的（`WARM=200 TICKS=300`，一間房，穩態）：

| 實體 | 小怪 | **本機 P50** | **本機 P99** | 雲端 ×3 P50（估） | 雲端 ×4 P50（估） |
|---:|---:|---:|---:|---:|---:|
| 100（≈ 出貨尖峰 112） | 88 | **0.552** | 2.951 | 1.7 | 2.2 |
| 250 | 238 | **1.486** | 2.227 | 4.5 | 5.9 |
| 500 | 488 | **4.567** | 5.644 | 13.7 | 18.3 |
| **1000 ← owner 問的** | 988 | **13.967** | **18.373** | ⛔ **41.9** | ⛔ **55.9** |

**曲線形狀**：500→1000 實體翻倍，P50 ×3.06、P99 ×3.26 ⇒ 約 **N^1.6～1.7**。
⚠️ 100→250 只有 N^1.1 —— ⭐ **二次項要到 250 實體以上才發威**，
所以「出貨尖峰 112 沒事」⛔ 不能外推成「1000 也沒事」。

### ⇒ 撞破 33.3 ms 的點

| 情境 | P50 撞破 | P99 撞破 |
|---|---:|---:|
| 本機 | ~1,700 實體 | ~1,400 |
| **雲端 ×3（估）** | **~870** | **~740** |
| **雲端 ×4（估）** | **~730** | **~630** |

⭐ **結論①：1000 隻殭屍在雲端那台上，一間房就會吃掉 1.3–1.7 個 tick 預算。**
⚠️ 而且要看 **P99 不是平均** —— 玩家感覺到的是那一格卡頓，⛔ 不是平均值。
⚠️ 再乘上房數：Colyseus 一個 process 是**單一 event loop**，
`DEFAULT_MAX_ROOMS = 50` ⇒ 兩間房同時打 1000 隻就已經爆了。

## 3. ② 熱點一：空間雜湊 —— 語言 vs 演算法

**方法**（⭐ 這是這份報告唯一有意義的地方）：
從**出貨的 SimWorld** 上錄下一段**真的** op-trace（warm 200 tick 之後錄 5 tick），
四個實作**重播同一段 trace**，而且**每一筆查詢的回傳陣列都要與出貨 TS 當場的答案逐位元相同**。

```
testdata/trace-n1000.jsonl.gz   5,000 次 insert · 5,056 次 query · 每次平均命中 24.2 個
testdata/trace-n100.jsonl.gz      500 次 insert ·   558 次 query · 每次平均命中 10.7 個
```

⛔ 一個比較快但答案不一樣的實作，量到的數字沒有意義 ——
所以 `TestBothImplsReproduceShippedResults` 是這包唯一承重的守衛。

### ⭐ 2×2：N=1000，ms/tick

| | **TS** | **Go** | Go / TS |
|---|---:|---:|---:|
| **出貨的演算法**（map + set + sort） | 3.03 – 3.18 | **3.04** | ⭐ **1.05×（＝沒有差）** |
| **換資料佈局**（flat array + generation stamp） | **0.88 – 0.93** | **0.49** | 1.88× |
| 同語言的演算法收益 | ⭐ **3.4×** | 6.2× | |

**N=100 的同一組**（⚠️ ⭐ 這一格更說明問題）：

| | TS | Go |
|---|---:|---:|
| 出貨的演算法 | **0.0845** | 0.118 ← ⛔ **Go 反而慢 40%** |
| 換資料佈局 | 0.0352 | 0.0209 |

⭐ **在出貨的實際規模（112 實體）上，逐條移植的 Go 比 TS 慢。**
理由是 V8 的 `Map` 在小尺寸上比 Go 的 `map` 快，而這個演算法整段就是在打 map。

### ⚠️ 為什麼「換佈局」贏這麼多 —— 配置次數

Go 的 `-benchmem` 直接指出來（每 5 tick）：

| | B/op | allocs/op |
|---|---:|---:|
| 逐條移植 | 5,147,982 | **44,439**（≈ 8,888 次／tick） |
| 換佈局 | 187,745 | **608**（≈ 122 次／tick） |

⇒ ⭐ **出貨的 `queryAABB` 每一次呼叫都配一個 `Set`、一個展開陣列、一次帶 closure 的 `sort`**，
而 `queryCircle` 每次再配兩個 `{x,z}`。GC 的 3.15% 就是它們的帳單。

⚠️ 附註：原生 arm64 的 Go 是 2.18 / 0.43（比 Rosetta 快 ~1.4×），
⛔ 但這台沒有 arm64 的 node 可以配對，所以**表裡一律用同條件的那一組**。

## 4. ② 熱點二：小怪選敵掃描 —— ⭐ 這裡才是最大的一筆

`MobSystem.ts:209` 的形狀：**每一隻小怪走一遍整張 `world.team`**。

```
1000 隻殭屍 × 1,024 筆 team = 每 tick 一百萬次迭代
其中 999,976 次的工作是：讀一個欄位 → 發現同隊 → continue
```

⭐ 真正要找的只有 **12 位英雄**。⇒ 這是一條 **O(N²)，而分子是常數**。

| N=1000，ms/tick | TS | Go |
|---|---:|---:|
| **出貨的形狀**（走整張 `Map`） | **2.98 – 3.09** | —— |
| 走整張表但攤平成陣列 | 0.6 – 1.5（⚠️ 抖） | 0.433 |
| ⭐ **只走「敵對可選目標」索引** | **0.038** | 0.030 |

⇒ ⭐ **同樣的答案，TS 自己就快 80×。** 換 Go 只再省 0.008 ms（＝雜訊）。

⚠️ 那份索引是 **O(1) 維護**的（spawn / death / 陣營轉換各動一次），
⛔ 不是一個新的每 tick 掃描。⛔ 這包**沒有**實作它 —— 這是 benchmark，⛔ 不是出貨補丁。

### ⚠️⚠️ 做這一格時抓到的自己的錯（留著，因為它是失敗形態④）

第一版的測試夾具**沒有誘餌**：兩個 zone 在地圖上相距 80 格，
所以「跨 zone 的英雄」永遠比同 zone 的遠 ⇒ ⭐ **把 zone 判斷整條刪掉，答案一模一樣**。
突變跑出來是**綠的**。⇒ 現在夾具裡有一批**貼在小怪臉上、但 zone 標成另一區**的敵方單位，
同一個突變才會紅（`n=100 mob 57: all=3 indexed=15`）。

## 5. ⭐ 結論：⛔ 不要用 Go 重寫

### 5a. 逐條回答 owner 的問題

| 問 | 答 |
|---|---|
| 「用 GO 寫會不會比較好？」 | ⛔ **不會。** 同演算法 1.05×，而在出貨規模（112 實體）上**還更慢** |
| 「1000 個殭屍後端來不及計算？」 | ⭐ **雲端目前確實來不及**（42–56 ms vs 33.3）。⛔ 但原因是**兩條可修的演算法**，⛔ 不是 TypeScript |

### 5b. 修完之後的推估（⚠️ 標成推估，⛔ 不是量到的）

| | N=1000 現況 | 換資料結構之後 |
|---|---:|---:|
| 空間雜湊 | 3.0（隔離量）～6.4（profile 佔比） | 0.9 ～ 2.0 |
| 小怪選敵 | 3.0 | 0.04 |
| **sim 全部** | **13.97** | ⭐ **≈ 6.5 – 8.8** |
| 雲端 ×3（估） | 41.9 ⛔ | **19.5 – 26.4** ✅ |
| 雲端 ×4（估） | 55.9 ⛔ | 26 – 35 ⚠️ 邊緣 |

⇒ ⭐ **兩條 TS 的資料結構修改，就足以讓 1000 隻殭屍在雲端進到預算內**（×3 情境），
而它們**不需要換語言、不需要重寫 sim、不需要拆掉 client/server 共用的那份 TS**。

### 5c. ⛔ 那 Go 什麼時候才值得？

⭐ **等這兩條修完之後再問**。修完之後 Go 的邊際收益只剩 ~0.45 ms／tick（≈ 5%），
而代價是：sim 不再與 client 共用一份程式碼、`purity.test.ts` 那一整套決定性守衛要重寫、
420 支技能的 JSON 引擎要跟著搬。⇒ ⛔ **這個交換在現在的數字下不成立。**

⚠️ **這份量測沒有涵蓋的**（⛔ 不要把結論外推到這些）：
snapshot / Colyseus encode（前一份報告量過）· 客戶端渲染 ·
50 間房的多工 · 以及 sim 剩下的 39%（那 39% 沒有單一熱點，是攤平的）。

### 突變紀錄（三條，⭐ 兩條**第一次是綠的** —— 留著因為那本身是結論）

| 突變 | 結果 |

## 7. 建議開的票（⛔ 這條 lane 不自己修 —— 第零守則⑧）

| # | 是什麼 | 大小 | 不修會怎樣 |
|---|---|---|---|
| 1 | `SpatialHash` 換 flat-array + generation stamp 佈局（TS） | 中（要處理「回傳值是共用緩衝」對現有呼叫端的影響） | 1000 隻時每 tick 多燒 2–5 ms |
| 2 | `world` 加一份「非 MONSTER_TEAM 可選目標」索引，`MobSystem` 改走它 | 小 | 1000 隻時每 tick 多燒 3 ms（**80× 的浪費**） |
| 3 | `queryCircle` 加一條純量入口（⛔ 不配 `{x,z}` 物件） | 很小 | profile 上白佔 10.3% |

⚠️ 第 1 條有一個**真的陷阱**：出貨的 `queryAABB` 回傳的是**新陣列**，
換成共用緩衝之後，任何「把結果留到下一次查詢之後才用」的呼叫端會靜默拿到錯的東西。
⇒ 那條票要先 `grep` 所有呼叫端，⛔ 不可以直接換掉。
