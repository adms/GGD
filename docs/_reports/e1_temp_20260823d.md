# lane E1 —— 三選一卡片「選完前閃爍」的根因（2026-08-23）

> owner 2026-08-23 逐字：「**隨機三選一卡片選完前的閃爍 請找到根因修正**」
> （同一件事的前一則）「剛進商店 介面有些部分會**黑閃爍** **選完隨機三選一又回復正常**」

⚠️ 這份報告裡凡是沒有 `檔:行` 或 `量到` 的句子都是**推測**（第三守則）。

---

## 1. ⭐ 量到的（⛔ 不是照單全收上一輪的嫌疑）

用 `React.Profiler` 數三選一子樹的 commit 次數，驅動的是**出貨的**
`syncHudFromState()`（⛔ 不是手刻 store 寫入），內容是**真的出貨道具 id**
（走最重的那條 `ItemCardBody` 卡面）：

| 量什麼 | 修好前 | 修好後 |
|---|---:|---:|
| 20 張快照（只有 `mana` 在動，**牌一張都沒變**）→ commit 次數 | **20** | **0** |
| 同 20 張快照 → `MutationObserver` 記到的 **DOM mutation** | **0** | 0 |
| 節點身分（`[role="dialog"]`）是否被換掉 | 否 | 否 |
| `innerHTML` 是否有變 | 否 | 否 |
| 每次重跑的 `actualDuration`（jsdom） | 0.2–3.6 ms（中位 ≈0.7 ms） | — |

⇒ ⭐ **「~30 Hz 重繪」這個嫌疑是真的**（實際是 SNAPSHOT_HZ，20 張快照 20 次 commit），
而且它的**開／關時機與 owner 那半句話逐字吻合**：沒有 offer 時選擇器回**同一個 `null`**
（`Object.is` 相等）⇒ 這條 churn **只存在於「卡片出現到選完」這一段**，
選完的那一刻整條消失。⛔ 沒有第二個機制有這個時序。

## 2. ⛔ 但同一次量測也證明：**它自己畫不出「黑閃」**

**0 個 DOM mutation** ⇒ 這 20 次重跑**沒有寫任何一個位元組到 DOM**
⇒ 沒有 style 改寫、沒有節點替換、沒有 `@keyframes` 重啟、**沒有任何 paint invalidation**。
⭐ 螢幕上逐位元相同。

⇒ 它剩下的唯一成本是**主執行緒 JS**（≈0.7 ms × 20 Hz ≈ **1.4 %**）。
那**對得上**上一輪列的第 ①-4 條路（「主執行緒塞住 raster 來不及」），
⛔ **但 1.4 % 不足以塞住任何東西。**

⭐ **結論（誠實版）**：這是一個**真缺陷**，是「選完就正常」這條線上唯一一個
時序完全吻合的機制，也把 ①-4 從嫌疑名單上劃掉了 —— ⛔ **但我沒有量到它就是那個黑閃。**
⛔ 不要把 #618 當成關掉了。

## 3. 修了什麼 —— ⭐ 修在**來源**，⛔ 不是修在那個面板上

`apps/client/src/net/RoomStore.ts`

```
+ const offersCache = new Map<number, { key: string; view: OfferView[] }>();
+ function stableOffers(seatId, next) { 內容一樣就回上一次那一個陣列 }
  offers: stableOffers(ss.seatId, ss.offers.map(…))
  resetHudStore(): offersCache.clear()
```

**為什麼修來源**：這個檔的檔頭逐字承諾「Every write is change-guarded so snapshot
patches that don't alter HUD-visible values cause **zero re-renders**」——
`seats` 那道 change-guard 只保護**整個陣列**（快取鍵含 `cooldowns`/`mana`/
`statusRemainTicks`，中場每張都在動），巢狀在裡面的 `offers` 於是每張換一次身分。
⇒ ⭐ 修在來源，**任何未來訂 `offers` 的消費端都免疫**，而「這份 offer 有沒有變」
只有一個住處（第〇·四）。
⛔ 我**沒有**動 `AugmentDraftPanel.tsx` 一個字元 —— 它的選擇器本來就是對的寫法。
⛔ 我**也沒有**動 `IntermissionStage.tsx`（它兩個選擇器早就防好了）。

⚠️ **`resetHudStore()` 要清快取**：不清的話下一場「同一個座位、同一組牌」會拿到
**上一場**那個陣列（同型於 `ownerMatchId` 那條）。

## 4. ➡️ 沿著「選完就回復正常」找到的**下一個**（⛔ 我沒有改，柵欄外／需要瀏覽器）

那一刻只有**三件事**同時開關，而 ①②已被上一輪與本輪排除，剩下**一個**：

⭐ **焦點遮罩（focus scrim）—— 一張蓋滿全螢幕的半透明層，剛好蓋在中場的 WebGL canvas 上。**

| | |
|---|---|
| 誰 | `AugmentDraftPanel.tsx:88-105`：`position:absolute; inset:0`、`background: rgba(6,9,16,0.62)`（`intermissionLayout.ts:125`）、`animation: ggdFocusIn 200ms`、`pointerEvents:"auto"` |
| 疊在誰上面 | 中場 canvas 走 portal 到 `document.body`、`INTERMISSION_Z.stage = 7`；scrim 在 `#hud-root`（z 10）裡 ⇒ **它一定蓋在那張 canvas 上** |
| 為什麼可疑 | 它**存在的區間 = owner 描述的區間**（卡片出現 → 選完）。一個帶 opacity 動畫的全螢幕合成層壓在 WebGL canvas 上，會讓那張 canvas 掉出「直接合成」快路徑 ⇒ 任何一幀來不及就是**沒呈現**；而上一輪已證明「沒呈現」在此之前長得就是**黑** |
| ⛔ 為什麼我沒動它 | ① 拿掉／改薄它會**取消 P2 那個刻意的設計**（`intermissionLayout.ts` 用約 20 行散文論證它為什麼要吃點擊）② 我**沒有瀏覽器可以量**，⛔ 不猜第三輪（`ggd-give-owner-a-measuring-tool`） |
| ⭐ 怎麼在 10 秒內量到 | 商店裡 offer 還在時開 console 看 `perfBus.renderLoopErrors` / fps 藥丸旁的 ⚠️（`85966763` 今天剛把 `webglcontextlost` 接上去）；同時把 scrim 的 `background` 暫時改成 `transparent` 看黑閃會不會消失 |

⚠️ 另外請主 session 順手問 owner 一句（上一輪也問過、還沒有答案）：
**「是選完就不閃，還是進商店幾秒後就不閃？」** —— 前者是因果，後者只是時間標記。
