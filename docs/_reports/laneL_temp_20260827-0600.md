## 二、#760 步驟 2 —— 做了什麼、為什麼安全

### 剔除規則
一個連線的可見 zone 集合：

| 情況 | 送什麼 |
|---|---|
| 算不出他的 zone（還沒坐下 / 純觀眾 / replay 觀眾） | **全部**（安全預設，與客戶端 L3 的 `VisibleZones.end()` 同一個 fail-safe） |
| 自己的每一場決鬥都還在打 | **只有自己的 zone** ← ⭐ 剔除真正發生的那一格（一場比賽的大部分時間） |
| 自己那一場已經分出勝負 | 自己的 zone ∪ **全部還活著的** zone（超集合，⛔ 不猜他會挑哪一區） |
| `zone < 0` 的實體 | 一律送（與 L3 的 `has()` 同一條規則） |

### 為什麼這是客戶端可見集合的**超集合**（⛔ 不必改客戶端一行）
1. `GameApp.refreshVisibleZones` = 自己的 zone ∪ `spectateZoneByPlayer`
2. `spectateZoneByPlayer` 只由 `spectateGoTo` 寫，它第一行是 `mayGoTo(zone, frameBus.spectateOffer)`
3. offer 來自 `render/spectateFocus.pickSpectateZone`，**第一行**是 `if (!ownDuelDecided(ownZone, duels)) return null;`

⇒ 自己的決鬥未決之前，客戶端**結構上**不可能渲染別區。
⇒ 被剔除的位元組正是 L3（`apps/client/src/net/zoneVisibility.ts` 的 `ingestZonedTransforms`）本來就會丟掉的那些。
⇒ 票上兩個 Known risks（插值瞬移、觀戰看到空競技場）**結構上不會發生**。

### ⚠️ 這一輪最貴的一個發現（第三守則的形狀）
第一版寫成 `entities: { map: EntityState, view: true }` —— **`defineTypes()` 會靜默丟掉 `view`**（那個寫法只有新的宣告式 `schema()` API 認得，`annotations.js:390-397` 在 `schema()` 函式裡）。
⇒ 共用編碼照樣送出全部實體，測試「剔除了」那一條紅在 `expected 42 to be less than 42`，而**沒有任何東西告訴我 tag 沒被套上**。
⇒ 正解 `view()(MatchState.prototype, "entities")`。已寫進 `schema.ts` 的宣告註解，⛔ 不讓下一個人再踩。

### ⚠️ 第二個發現（決定了 ReplayRoom 那一段）
`ChangeTree` 把 view-tagged 欄位的異動放進**另一個 changeset**（`filteredChanges`），而 `SchemaSerializer.applyPatches` 對 `client.view == null` 的客戶端送的是 `encoder.encode(it)`（只走 `root.changes`）。
⇒ ⛔ **沒有 view 的客戶端一個實體都收不到**（⛔ 不是「收到全部」）。守衛第一條的最後一行就在釘這件事。
