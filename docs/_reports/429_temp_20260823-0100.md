# 🚨 每回合越來越 lag —— 客戶端那一半（lane: vfx / 2026-08-22）

owner:「戰鬥進到**第二回合**變得非常 lag，之後**每回合越來越嚴重**，直到整個地圖無回應」

⚠️ 這一份只涵蓋**客戶端**（`apps/client/src/vfx/**` + `render/modelFxRig.ts` +
`render/roundFxRegistry.ts`）。sim 那一半由另一條 lane 查。

---

## ⭐ 結論：客戶端有**一個**無界成長，就是 2026-08-22 新接的 `ModelFxRig`

方法是**量**，⛔ 不是讀程式碼推論：拿**出貨的組裝點** `createRoundFx()` 建一整套場景型
FX，用**出貨的** `RoundVfxLifecycle.sync(phase)` 驅動回合邊界，跑 8 個回合，每個邊界之後
量 Babylon 場景的每幀成本代理量。

每回合餵的事件：`vfxSpawn` · `hitImpact` · `modelFxSpawn` · `screenFlash` · `floatingText` ·
`vfxArc`，加上 **GameApp 每一幀**都會做的 `ambient.attach(id, modelKey, root, extras)`
（extras 每次都是**新陣列**），最後 30 秒商店時間 + 英雄下場。
每回合換一批 modelKey / doc id —— ⛔ 不是造假：英雄升級解鎖 R/EX、第 3 回合起殭屍加入、
每回合換地圖（#145）。

（peak 與 boundary-after 兩種取樣都量了，兩者的成長率一樣。）

### 這一欄的成長軸是「**這場比賽看過幾個不同的 modelKey**」

把探針改成每回合重用同一批 modelKey（`FIXED_KEYS=1`）→ 8 個回合全部是 **72，一個都沒長**。

### 根因：`maxPooledPerModel` **看起來**是上界，但它不是

`ModelFxRig` 的 free-list 是 `Map<modelKey, ModelFxNodes[]>`，每個 key 上限 12。
`resetForRound()` 把活著的實例**收回池子**，⛔ 但從來沒有人修剪那些池子，
`pool` 的 **key 數本身也沒有上界**。3 個新 key/回合 × 12 × 2 節點（root + axis）= 72。

⭐ 這是 **GH#270 逐字記過的同一句話**，換一層再犯一次 ——
`VfxSystem.resetForRound()` 的註解自己就寫著：

> per-key 上限**只有在 key 的數量有上界時**才構成上界

⚠️ 而且在出貨路徑上每一個閒置節點底下掛的是 `instantiateModelsToScene()` 的 glb 實例
（真的 mesh + 材質），⛔ 不是探針裡的空節點 —— 探針的 72 是**下界**。

## 修法（兩道閘，都在 `render/modelFxRig.ts`）

| | 做什麼 |
|---|---|
| ① `release()` 加 `maxPooledTotal`（出貨 48） | free-list 的**全域**上界。⛔ 沒有它，12 × 無界 key = 無界 |
| ② `trimPoolTo(cap)`，由 `VfxSystem.resetForRound()` 呼叫 | 回合邊界把**所有** free-list 加起來修剪到 `cap`，並把空的 free-list 從 Map 除名 |

⭐ `cap` 走**既有**的 `ringCapForRoundBoundary(vfxCleanupPolicy())`，
⛔ 沒有新增 config 欄位（那要動 `schema/config/**`，在柵欄外）。
理由是既有先例：`arcs.trimTo(ringCapForRoundBoundary(policy))` 的註解說「電弧的網格
free-list 走**同一格政策** —— 它和預告圈是同一種東西」。模型特效的閒置池化節點
（每個帶著一份 glb 實例）逐字是同一種東西。

出貨政策 `purgeSharedPoolsOnRoundEnd: true` ⇒ cap = 0 ⇒ 回合邊界**整個還回去**
（owner 已經表態要「省記憶體」而不是「下一回合第一次施法少一次配置」）。
`enabled: false` ⇒ `Infinity` ⇒ 逐位元回到今天的行為（止血閥，第一守則）。

順手（1 行）：`acquire()` 的 `serial` 從 `born.length` 改成單調計數器 ——
回收會把 `born.length` 縮回去，於是兩個同時活著的節點會拿到**同一個名字**，
而守衛正是照名字在場景上數的。

### 修之後

同一支探針，8 個回合：`modelfx-*` = **0 / 0 / 0 / 0 / 0 / 0 / 0 / 0**，其餘各欄不變。

## ⚠️ 順手發現、⛔ 沒有修（第零守則⑧，請主 session 決定要不要開票）

1. **`ScreenFxLayer.setShakeSink()` 是一條死線** ——
   `VfxSystem.installShakeSink()` → `screenFx.setShakeSink(fn)` 只寫進 `this.shakeSink`，
   而 `shake()` 讀的是 `this.opts.addShake?.(…)`。`ScreenFxLayer` 在 `VfxSystem` 的建構子裡
   是 `new ScreenFxLayer()`（⛔ 沒有 opts），所以**相機震動一次都不會發生**。
   典型的失敗形態③：整條接線可以刪掉而測試全綠。修法是 1 行（`shake()` 改讀 `this.shakeSink ?? this.opts.addShake`）。
2. **`ModelFxRig.dispose()` 會 dispose 它**不擁有**的 `AssetContainer`** ——
   `loadContainer` 出貨接的是 `AssetManager.load()`，而那是一份 **per-Scene 的共用快取**
   （檔頭：「every consumer instantiates from that container」）。目前只在離開比賽時發生，
   與 scene 銷毀同時，所以看不出來；⛔ 但只要有第二個消費者共用同一份 glb 就會踩到。
3. **`containers` map 在一場比賽裡只增不減** —— 一個 modelKey 一份 AssetContainer，
   回合邊界不碰。⚠️ 因為它與 AssetManager 共用同一個物件，這一層**不應該**自己收，
   要收也是收 AssetManager 那一層（見上一條）。
