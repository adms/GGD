#### R2 ⛔ 出貨預設下，8 階降級階梯**只有 1 個旋鈕真的會動**

**C**（`render/QualityController.ts::compute` + `settings/types.ts::DEFAULT_GRAPHICS`）

出貨值：`qualityPreset: "high"`（⛔ 不是 `"auto"`）＋ `dynamicResolution: true`。
`compute()` 走的是 `else if (g.dynamicResolution)` 那一支：

```ts
resolutionScale = fixedPresetResolution(g.resolutionScale, rung.resolutionScale);
// ⛔ particleDensity / shadows / drawDistance 一格都不動
```

| 階梯上的旋鈕 | 出貨預設下會不會動 |
|---|---|
| `resolutionScale` | ✅ 但只在 **1.0 → 0.85** 之間（`FIXED_PRESET_RES_FLOOR`）⇒ 像素數最多降 **28%** |
| `particleDensity` (1.0→0.6→0.3) | ⛔ **永遠 1.0** |
| `shadows` | ⛔ **永遠 on** |
| `drawDistance` (140→55) | ⛔ **永遠 140** |
| `airScatter` / `weather` 四格 | ✅（它們讀 `adaptive.level`） |

⇒ ⭐ **機器再怎麼吃力，粒子、陰影、繪製距離都不會退讓。**
⚠️ 而且因為 R1，`adaptive.level` 讀的是一個**只涵蓋 1/10 成本**的訊號 ——
它連 0.85 那一階都不一定會踩。

#### R3 ⛔ 每幀**至少 3 次強制回流（forced synchronous layout）**，而且是「寫完再讀」的最壞順序

**C**（逐行）

| 位置 | 讀什麼 | 這一幀在它之前寫過什麼 |
|---|---|---|
| `GameApp.ts:1963-1964`（每個 viewport） | `canvas.clientWidth` / `clientHeight` | 上一條 rAF 的 DOM 寫入 ＋ React 在 microtask 裡的重繪 |
| `GameApp.ts:1935`（結算凍結時） | 同上 | 同上 |

⭐ `clientWidth` 是 **layout-flushing property**：瀏覽器必須把整份文件的 layout 算完才回答。
⇒ 一次代價正比於**整個 HUD 的 DOM 規模**（`HudRoot` 掛 **47 個元件**，⭐M：`grep`），
⛔ 不是正比於「我改了幾個節點」。

⚠️ `WorldAnchorLayer` 的那一次是最貴的，因為它在**同一個 callback 裡先寫後讀**
⇒ 100% 命中 forced reflow，⛔ 沒有任何批次可言。

#### R4 ⛔ `WorldAnchorLayer` 每幀對每一條血條做 **4 次 `querySelector`**

**C**（`WorldAnchorLayer.tsx:254-262`）

```ts
for (const [id, anchor] of frameBus.champions) {      // 12 位英雄
  const hp       = node.querySelector('[data-role="hp"]');
  const mana     = node.querySelector('[data-role="mana"]');
  const castWrap = node.querySelector('[data-role="cast-wrap"]');

```

⇒ 12 × 4 = **48 次屬性選擇器查詢／幀** ＝ 60 fps 下 **2,880 次／秒**。
⭐ 這個檔的檔頭自己寫著「no createElement, no remove(), **no Map churn** in the frame loop」——
⛔ 它把節點池化做對了，卻在池化的節點上每幀重新**查**它的四個子節點。
修法是建節點時把四個 ref 存進一個 struct（`makeChampionNode` 已經是唯一建點處）。

#### R7 ⚠️ 每回合**新建一個 WebGL context ＋ 一整條後製管線**（中場市集）

dispose(false,TRUE):        textures 不變 (net 0)  且 src.albedoTexture 仍然活著

## 3. ⭐⭐ 為什麼「試錯時間」這麼長 —— **儀表自己在說謊，四處**

⭐ owner 要的是「**縮小找 root cause 的試錯時間**」。
⇒ 先看：現在的儀表為什麼幫不上忙。

| # | 謊 | 證據 | 後果 |
|---|---|---|---|
| **①** | `workMs` 自稱「這一幀的成本」 | R1：只量 10 條 rAF 裡的 1 條 | ⭐ **「工作 4 ms」與「20 fps」可以同時為真** ⇒ 每一次查 lag 都從一個假的起點開始 |
| **②** | `minFps` 永遠 ≥ 10 | `FrameDelta.take()` 把 dt **夾在 [1, 100] ms**（`frameCap.ts:FRAME_DELTA_MAX_MS`），而 `FrameRateMeter.sample(dtMs)` 吃的就是夾過的值 | ⭐ **一次 300 ms 卡頓與一次 2 秒凍結在面板上長得一模一樣**（都寫 10 fps）。而 owner 的原話是「直到整個地圖無回應」 |
| **③** | `drawCount` 這個名字 | `Renderer.stats()` 回的是 `scene.meshes.length` —— **場上一共有幾顆 mesh**（含 disabled / 池子裡的），⛔ 不是 draw call、⛔ 不是 active mesh | 池子越大這個數字越大，而它與這一幀畫了什麼**沒有關係** |
| **④** | `particleCount` 這個名字 | 回的是 `scene.particleSystems.length` —— **系統數**，⛔ 不是活粒子數 | GH#270 owner 自己量的是「144 個發射器 / **2,819 顆活粒子**」——⭐ 那兩個數字**只有診斷面板有**，主面板沒有 |

⭐ 再加上：**整個面板掛在 `network.showPerfOverlay` 底下，而出貨預設是 `false`**
（`settings/types.ts:290`）⇒ owner 平常看到的只有一顆 fps 藥丸。

⇒ ⭐⭐ **這就是為什麼上一輪只能交出「推理出來的嫌疑犯」。**

## 4. ⭐⭐ 機制：**幀預算解剖器**（Frame Budget Profiler）

> 目標逐字：「**想一個機制系統專門找、監控 LAG 縮小找 root cause 的試錯時間**」
> ⇒ 它必須能回答一句話：「**這一幀的時間花在哪？**」

### 4.0 設計約束（先寫死，免得做成第二個會說謊的儀表）

| | |
|---|---|
| **① 涵蓋全部 rAF** | ⛔ 不可以再做一個只量 `GameApp` 的東西（那正是 R1） |
| **② 一定要有「其他/未歸屬」那一格** | ⭐ 各段加起來 < 整幀 ⇒ **差額要印出來**，⛔ 不可以藏起來（否則它會像 `workMs` 一樣讓人查錯方向） |
| **③ 自己不可以是 lag** | 關掉時 `mark()` 只有一個布林測試；開著時要能量**自己的**開銷並印出來 |
| **④ owner 不開 console** | ⇒ 走 `network.*` 設定開關 + 畫面上的面板，與 `showVfxDebug` 同形（那是這個 repo 已經驗證過的形狀） |
| **⑤ 一鍵帶走** | 一個鍵把最近 N 秒的資料變成一段可以貼進 issue 的文字 |

### 4.1 檔案與欄位（逐檔、逐格）

#### ① `apps/client/src/perf/frameProfiler.ts`（新）

```ts
export const PHASES = [
  "drain", "predict", "views", "ambient", "cameras", "sfx",
  "vfx", "anchors", "render", "hud",            // ← 固定索引，⛔ 不是字串 map
] as const;

let on = false;                                  // ← 關掉時整支模組是零成本
const acc = new Float64Array(PHASES.length);     // ⛔ 不配置、⛔ 不 GC
let open = -1, openAt = 0;

export function phase(i: number): void {         // 開一段（自動關上一段）
  if (!on) return;
  const t = performance.now();
  if (open >= 0) acc[open] += t - openAt;
  open = i; openAt = t;
}
export function endPhases(): void { if (on && open >= 0) { acc[open] += performance.now() - openAt; open = -1; } }
```

⭐ **為什麼是索引不是字串**：字串 map 每幀查 10 次 = 每幀 10 次 hash；
`Float64Array` + 常數索引是一次陣列寫。⛔ 這不是潔癖，這是約束③。

**落點**（`GameApp.renderFrame` 現成的分段註解就是段界，⛔ 不用重新設計）：
`// 1) drain` → `phase(P.drain)`；`// 3) local prediction` → `phase(P.predict)`；
`// 4) entity views` → `phase(P.views)`；`syncAmbient` → `phase(P.ambient)`；
`// 5) cameras` → `phase(P.cameras)`；`// 5b) FLUSH THE COMBAT SOUND FIELD` → `phase(P.sfx)`；
`// 6) vfx` → `phase(P.vfx)`；`updateFrameBus` → `phase(P.anchors)`；
`this.renderer.render()` → `phase(P.render)`；然後 `endPhases()`。
⇒ **10 次 `performance.now()`／幀**。⭐ 量得到（見 4.4「它自己準不準」）。

#### ② `apps/client/src/perf/rafSentinels.ts`（新）⭐ **這是最關鍵的一支**

```
啟動時註冊兩條**自我重排**的 rAF：
  head — callback 的**第一行**就 re-register  ⇒ 下一幀排在最前面
  tail — callback 的**最後一行**才 re-register ⇒ 下一幀排在最後面
```

rAF callback 依**註冊順序**執行，而「這一幀註冊的」會被排進**下一幀**的隊尾。
⇒ head 在自己 callback 的**第一行**重排 ⇒ 下一幀它排在最前；
tail 在自己 callback 的**最後一行**重排，而它這一幀本來就跑在最後
⇒ 它重排的時刻晚於這一幀所有其他 loop 的重排 ⇒ 下一幀它仍然排在最後。**這是歸納不變式，⛔ 不是巧合。**

⚠️ 兩個要寫進註解的邊界（⛔ 不可以靜默）：
· repo 裡的 loop 有兩種寫法 —— **第一行**重排（`GameApp.ts:1628`、`WorldAnchorLayer.tsx:240`、
  `AbilityBar.tsx:332`、`Minimap.tsx:480`）與**最後一行**重排（`mobHealthBar.tsx:127`）。
  ⭐ 上面那個不變式對**兩種**都成立，⛔ 但只有在 tail 是「最後一行重排」時成立。
· 一個**中途掛載**的元件（回合切換時的面板）第一幀會排在 tail 後面
  ⇒ 那一幀的 `otherRafMs` 少算一次。⭐ ⇒ 面板要印 `sentinelSkew` 計數，⛔ 不要假裝沒有。

```
frameTotalMs = tailStart - headStart          // ⭐ 這一幀「全部 rAF 」的主執行緒時間
otherRafMs   = frameTotalMs - workMs - Σphase(hud 以外)  // ⭐ R1 那 9 條的總和
```

⇒ ⭐ **這一格就是本報告 R1 的量尺**，⛔ 而它今天不存在。

#### ③ `apps/client/src/perf/longTasks.ts`（新）

```ts
new PerformanceObserver(list => { for (const e of list.getEntries()) { longTaskMs += e.duration; longTasks++; } })
  .observe({ type: "longtask", buffered: true });
```
⭐ 它抓得到**任何 in-frame 計時器抓不到的東西**：GC 暫停、React reconcile、
forced reflow（R3）、shader 編譯、貼圖上傳。⛔ 零額外開銷（瀏覽器原生）。
⚠️ Safari 不支援 ⇒ 面板要印「不支援」，⛔ 不可以印 0（那與「沒有 long task」長得一樣）。

#### ④ `apps/client/src/perf/resourceCensus.ts`（新）—— **1 Hz，⛔ 不是每幀**

```
meshes / activeMeshes(scene.getActiveMeshes().length) / drawCalls /
materials / textures ⭐ / particleSystems / activeParticles(Σ getActiveCount) /
transformNodes / animationGroups / domNodes(document.getElementsByTagName('*').length) /
jsHeapMB(performance.memory?.usedJSHeapSize)
```
⭐ **`textures` 這一格就是 R8 / R9 / GH#561 的量尺** ——

#### ⑤ `apps/client/src/perf/roundTimeline.ts`（新）—— ⭐ 「越玩越 lag」的直接證據

⇒ ⭐ **「越玩越 lag」會直接顯示成一條單調上升的欄。** ⛔ 不用再猜是哪一種資源。

### 4.4 ⭐ 「它自己準不準」怎麼驗（⛔ 不可以只靠設計說得通）
