## ① GH#700 —— 出貨的雨在真瀏覽器上一定擲例外（T0）

### 量到的根因（複驗成立）

Babylon 7.54 的 `GPUParticleSystem` 把**平台實作**放在另一個模組：
`gpuParticleSystem.js:739` 用 `GetClass("BABYLON.WebGL2ParticleSystem")` 查全域註冊表，
查不到就 **擲** `The WebGL2ParticleSystem class is not available!`。
而全 repo **零** `import ".../webgl2ParticleSystem"`（唯一提到它的是 S7 audition 的動態 import）。

⭐ **一個在探針上量到、S7 報告沒寫的細節**：
`this._scene.particleSystems.push(this)` 發生在 `gpuParticleSystem.js:726`，
也就是**平台檢查（732）之前** ⇒ 一顆**建構失敗的殘骸**仍然留在 `scene.particleSystems` 裡，
名字一模一樣。⛔ 所以「場上找得到一顆同名的 GPU 粒子系統」對這個缺陷**結構性失明**
（我的第一版守衛就是這樣寫的，突變當場抓到它是綠的 —— 見下）。

### 改了什麼

| 檔 | 改動 |
|---|---|
| `apps/client/src/vfx/WeatherRainFx.ts` | ① 補 `import "@babylonjs/core/Particles/webgl2ParticleSystem"`（side-effect，⛔ 檔頭已註明不可當無用 import 刪掉）② 檔頭那句「NullEngine ⇒ 測試量到 CPU 路」原本只是**散文**，現在寫明它正是這個缺陷能出貨的原因，並指向新守衛 |
| `apps/client/src/render/ArenaScene.ts` | `buildRain` 的裸呼叫 → `buildRainSafely()`：**fail-open**（吞例外、地圖照建）＋ **fail-loud**（`console.error` 一行指名天氣降水）＋ **latch**（`rainPlatformFailed`，⛔ 不再重試、⛔ 不洗版） |

⚠️ 客戶端只建 WebGL `Engine`（⛔ 無 WebGPU，`grep` 過）⇒ 只需要註冊 WebGL2 那一個平台。
哪天真接了 WebGPU，`supportComputeShaders` 會要 `ComputeShaderParticleSystem` —— 那條路今天
由同一個 fail-open 接住**並且會喊**（而且守衛②量的就是那條）。

### 守衛 `apps/client/src/render/weatherRainGpuPath.test.ts`（新）

⭐ **重點：它把 `engine.getCaps().supportTransformFeedbacks` 打開**，逼 NullEngine 走
**出貨那條 GPU 路** —— 這就是「守衛不能只在 NullEngine 的預設能力上跑」的具體樣子。
兩條都走出貨的 `buildArena`，⛔ 不自己 new 粒子系統；下雨的 seed 是**搜出來的**（出貨機率 0.3），
⛔ 不抄字面值。

- ① transform feedback ⇒ 雨是 `GPUParticleSystem` **且 `isStarted()` 且 `emitRate>0` 且沒有人被 fail-open 接住**
- ② `supportComputeShaders`（那個類別全 repo 沒人 import ⇒ **真的**建構失敗）⇒ 地圖照建 ＋ `console.error` **恰好一次** ＋ 第二次 build **不再喊**

**突變（2026-08-25）**：拿掉那行 import ⇒ ①②**都紅**。
⚠️ 而**第一版的①在同一次突變下是綠的**（就是上面那顆殘骸）—— 突變測試當場付清成本，已把它寫進守衛檔頭。

## ② GH#701 —— floatingText 零渲染消費端

### 先查了「傷害數字走哪一條」（GH#701 明文的 known risk）

`ui/combatText` + `frameBus.combatText`（固定池）+ `ui/WorldAnchorLayer` 的 rAF 逐格 patch DOM。
⇒ ⭐ **共用那一層**，⛔ 沒有造第二套：同一個 rAF、同一顆容器、同一套 pooled-node 紀律、
同一支字體（`COMBAT_TEXT_FONT`）與同一份外框配方（`combatTextShadow`）。
⛔ 但**不走** `combatTextCss` —— 它每一格都綁在「誰打誰、打多少」，而浮字沒有類別也沒有數字
（`FloatingTextFx` 檔頭早就寫過：硬塞要在 `CombatTextCategory` 上開一個「其他」分支）。

### 為什麼是一份登錄表，不是在 `GameApp` 加一行

HUD 是 React、特效是 Babylon，兩邊**沒有共同的父**（`GameApp` 建 `VfxSystem`，`HudRoot` 掛
`WorldAnchorLayer`）。要嘛在 `GameApp.ts` 加一行接線（第〇·六守則點名的「一行接線」病，
而且那個檔是 lane 互撞重災區），要嘛讓那一層**自己報到**。
⇒ `FloatingTextFx` 建構＝`liveLayers.add(this)`、`dispose()`＝離開；
`export const floatingTextLayers: ReadonlySet<FloatingTextFx>`。
⭐ 副作用：`VfxSystem.ts` / `GameApp.ts` **一個字都沒動**（都在別的 lane 手上）。

### 改了什麼

| 檔 | 改動 |
|---|---|
| `apps/client/src/vfx/FloatingTextFx.ts` | 登錄表（建構報到／dispose 離開）＋ 檔頭寫下這個缺陷的形狀 |
| `apps/client/src/ui/WorldAnchorLayer.tsx` | 新增「技能浮字」段：`frameBus.project(x, y+lift, z)` → 按需長出的 `<div data-role="floating-text">` 池（⛔ 不預配 200 顆）、`slot:gen` 當快取 key、`combatTextLane` 分道、卸載時 `remove()`。純函式 `floatingTextCss()` 匯出給守衛逐格讀 |
| `packages/shared/src/sim/stuckEscape.ts:173` · `sim/combat/hitstopHold.ts:398` | ⭐ **兩句說謊的註解**（「客戶端 `FloatingTextFx` 真的在畫」）改掉，寫下它假在哪、誰補的、閘在哪（第三守則） |

### 守衛 `apps/client/src/ui/floatingTextRenders.test.ts`（新）

jsdom + `createRoot` 掛**出貨的** `<WorldAnchorLayer/>`，餵**出貨的** `FloatingTextFx`
（⛔ 不自己造 entry —— 那是形態⑤），rAF 換成手動步進（⛔ 不睡 16ms）。
量：帶「脫困」的節點**恰好一顆** · `display:block` · `opacity>0` · `font-size>0` ·
`color === rgb(150,230,255)`（技能寫的顏色） · `transform` 真的擺到座標上 · 有描邊 ·
**到期回收後被藏起來**。
**突變**：`node.textContent = e.text` → `""` ⇒ 紅（找不到帶字的節點）。
