# L5 —— 內容樹只載入一次

**日期** 2026-08-23 · **柵欄** `packages/shared/src/content/`

---

## 一句話

`packages/shared/src/content/` 底下每一支「⛔ 不是在驗打包器/索引/版控」的測試，
現在都從 **`content/bundle.json` 一次讀完**（`__fixtures__/shippedContent.ts`），
⛔ 不再各自 `readdir` + `readFileSync` 1,727 次。
bundle 與磁碟對不上時它**自動退回逐檔讀** —— 慢，但同一份資料。

## ⛔⛔ 先講最重要的一件事：**省下來的是 ~3 秒，⛔ 不是 144 秒**

計畫書寫的「省 ~144 秒」是**估錯的**，而我把它量出來了。
估法是「content-loading 測試平均 4,022 ms vs 非載入的 1,987 ms ⇒ 差額 × 72 支」。
⚠️ **那 2 秒的差額不是 I/O。** 逐項量到：

| 一支 content 測試的時間花在哪 | |
|---|---:|
| vite `transform` + 模組 `collect`（zod schema 圖、registries…） | **絕大部分** |
| `ContentLoader.load()` 的 **zod parse** 1,712 份文件 | ~74 ms |
| **檔案 I/O**（1,727 次 `readFile`）← ⭐ **只有這一段是這次改掉的** | **~126 ms** |

⇒ ⭐ **每支測試檔省 ~140 ms**，⛔ 不是 ~2,000 ms。
22 支 × 140 ms ≈ **3.1 秒**的測試時間（全套測試時間約 360 秒）。

⚠️ 真正的大頭是 `collect`（基準線量到 **321.66 秒**，比 `tests` 的 359 秒只少一點）——
那是模組載入/轉譯，**這次的改動一點都碰不到它**。下一個 144 秒住在那裡。

## 量到的（⛔ 不是估的）

### ① 根因：`ContentLoader` + `FsContentSource` = 1,727 次 `readFile`

出貨樹是 **1,712 份文件 / 14 個集合**。一次載入要讀
`manifest.json` + 14 份 `_index.json` + 1,712 份文件。
`packages/shared` 裡打這一行的測試檔有 **66 支**（另有 50+ 支自己抄了一份
`readdirSync` 版的 `docs(collection)` helper）。

| 路徑（`tsx` 直接量，⛔ 不含 vitest 的 transform） | 冷（第一次） | 暖 |
|---|---:|---:|
| `ContentLoader` + `FsContentSource` | 347 ms | 200 ms |
| `ContentLoader` + 本檔的 bundle 來源 | 115 ms | 74 ms |

裸 I/O：全樹 `readdir`+`readFile`+`JSON.parse` 冷 190 ms / 暖 62 ms；
單一 `bundle.json`（2.47 MB）46 ms / 38 ms。
逐集合（暖）：`abilities` 421 份 42 ms · `vfx` 643 份 18 ms · `champions` 71 份 5.7 ms。

⇒ ⭐ **只讀 `champions` 的測試改讀 bundle 會變慢**（5.7 ms → 38 ms）。
所以我**沒有**把 `docs(collection)` helper 全部換掉，只換了本來就已經在載入 bundle
的那幾支（parse 已經付過了）。

### ② ⚠️ 「整套只 parse 一次」做不到 —— 而且是量出來的

vitest 2.1.9 預設 `pool: forks` + `isolate: true`。三支探針測試各印 `process.pid`
與 `globalThis` 上的旗標：

```
PROBE-A pid 34697 seen undefined
PROBE-B pid 34698 seen undefined      ← 三個不同 pid，globalThis 不共用
PROBE-C pid 34699 seen undefined
--no-isolate --maxForks=1 之後: pid 35280 / seen a / seen b
```

⇒ 省的是「**每一個測試檔行程的第一次**」，⛔ 不是「整套只做一次」。
⛔ 我沒有去動 `isolate`：那會讓 `sim/content/registry.ts` 的 module-level singleton
跨檔共用，是另一個等級的風險，⛔ 也不在這條 lane 的柵欄裡。

### ③ A/B：**同一份程式碼、同一分鐘、同一台機器**

⚠️ 這台機器上同時有別條 lane 在跑，`time` 的 wall-clock **完全不可信**
（基準線那一輪 1314% CPU，改完那一輪只有 1157%，控制組的 465 支未改動測試
自己就慢了 **+19.2%**）。⇒ ⛔ 不要用「改前 68.6 s / 改後 85.8 s」下任何結論，
那量到的是隔壁 lane。

⭐ 所以 A/B 用**同一份程式碼**做：把 `content/bundle.json` 的 **mtime** 推回 1970
就會逼出 fallback（＝**舊行為**，逐檔讀），還原就是新行為。四輪交替：

| 輪 | TREE（舊，逐檔讀） | BUNDLE（新） |
|---|---:|---:|
| 1 | wall 8.09 s / tests 26.40 s | wall 8.10 s / tests **24.03 s** |
| 2 | wall 8.34 s / tests 27.51 s | wall 7.93 s / tests **24.26 s** |
| 3 | wall 8.74 s / tests 29.26 s | wall 8.53 s / tests **25.21 s** |
| 4 | wall 8.92 s / tests 29.25 s | wall 8.37 s / tests **26.00 s** |
| **平均** | **28.10 s** | **24.88 s（−11.4%）** |

（23 支檔＝22 支改動 + 新閘。`tests` 是 vitest 自己報的測試執行時間總和。）

⇒ **−3.2 秒**，每支 ~140 ms —— 與 ① 的「fs 200 ms vs bundle 74 ms」對得起來。
wall-clock 只動 ~3%，因為它被 `transform`/`collect` 蓋住（見上）。

## 做了什麼

### 新檔 `packages/shared/src/content/__fixtures__/shippedContent.ts`

| 匯出 | 用途 |
|---|---|
| `shippedContentSource(rootDir?)` | `new FsContentSource(dir)` 的 **drop-in**；`dir` 不是出貨那棵樹時原封不動退回 `FsContentSource` |
| `shippedDocs<T>(collection)` | 一個集合的每一份文件，依**檔名**排序（＝ `readdirSync().sort()` 的順序） |
| `shippedDocFiles<T>(collection)` | 同上，帶 `{ file, doc }` |
| `shippedDocMap<T>(collection)` | `id → doc` |
| `shippedBundleIsFresh()` | 這個行程走的是 bundle 還是檔案樹 |

### ⭐ fail-**slow**，兩段，⛔ 不是 fail-open

`icons.test.ts` 的檔頭記著一條真的限制：「索引只有主 session 會跑 `content:build`
重建，測試在重建前後都必須是綠的」。而併行 lane ⛔ 禁止自己跑 `content:build`
⇒ **一個剛編過 `content/` 的 lane 手上的 bundle 一定是舊的**。

1. **mtime 掃描**（1,712 次 `statSync`，11 ms，⛔ 不讀內容）→ 列出**嫌疑名單**
2. ⭐ 嫌疑的那幾份**真的讀出來比 `hashDoc`**（＝ bundle 自己記在 `entry.hash` 的那個）

全部對得上 → 走 bundle；有一份對不上（或嫌疑 > 32 份）→ **退回逐檔讀**。

⚠️ **第 2 段不是多餘的，它是踩出來的**：第一版只有 mtime，而量測跑到一半
另一條 lane 的產生器把 `config/ability-vfx-bindings.json` 與 `config/combo-strikes.json`
**原樣重寫**（`git status` 乾淨、位元組一個都沒變），mtime 卻往前跳
⇒ 純 mtime 把 bundle 判成過期，**整批測試永遠走慢路，而且從外面完全看不出來**
（我自己就先量到一組「沒有任何改善」的假數字）。

⚠️ 這與 CLAUDE.md 罵的 fail-open **不同型**：那一種退回的是**別的語意**
（骨架英雄／沒錄到影），這一種退回的是**同一份資料的另一條讀法**。

### ⛔ 誰沒動（判準：驗打包器/索引/版控 → 讀樹；驗內容本身 → 讀 bundle）

- `shippedBundleIsCurrent.test.ts` —— 它的工作就是抓「bundle 過期」
- `shippedBundleHasTrackedSources.test.ts` —— 抓「來源沒進版控」
- `bundle.test.ts` —— 在 `cpSync` 的 temp 樹上重建打包器
- `loader.test.ts` / `buildIndexesValidates.test.ts` —— 被測的就是 loader 與 build 腳本本身

### 改了 22 支

18 支換 `new FsContentSource(X)` → `shippedContentSource(X)`；
4 支（`abilityMirror` · `championFormsResolve` · `championFormVisibility` ·
`championFormGoku`）把自己抄的 `docs(collection)` helper 換成 `shippedDocs*`
（第〇·七守則的「融合重複」—— 同一段 8 行程式碼在 repo 裡有 20 份以上的複本）。

⚠️ **唯一的語意差別**：bundle 是用 `stableStringify` 序列化的，所以從 bundle 讀回來的
文件**鍵是排序過的**（`-0` 也會變 `0`）。內容定址系統從第一天起就把兩者當同一份
（`hashDoc` 也走 `stableStringify`），瀏覽器端拿到的正是排序過的那一份。
⛔ 但依賴**作者寫的鍵序**的測試（例：`Object.keys()[0]` 當「第一個欄位」）不可以改用。

## ⭐ 下一個真的有 144 秒的地方：`collect`

基準線 491 支測試檔：`collect` **321.7 s** / `tests` **359.4 s** / `prepare` **117.7 s**。
`collect` 是**模組轉譯與載入**，⛔ 這次一個位元組都沒動到它。
可以查的方向（都還沒量）：
`src/content/schema/` 那 68 個檔的 import 圖有多深、
`registries.ts` 是不是每一支 sim 測試都被迫拉進整套 zod schema、
`--no-isolate` 對 registry singleton 的真實風險有多大。
