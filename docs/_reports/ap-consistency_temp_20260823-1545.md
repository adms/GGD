**⭐ 一句話結論：owner 是對的。推導鏈裡一個 AP 項都沒有，而那個缺口在 LV30 是 1.68×、LV99 是 2.67×。**
**⭐ 但缺口的方向是「打得比設計承諾更痛」，⛔ 不是「打不死」—— 把 AP 算進去之後，
三個錨點（LV30 / LV50 / LV99）全部從 ❌❌ 變成 ✅✅✅。**

⚠️ 全部數字走**真的** stat pipeline（`ContentLoader` → `registerAll` → 真 `SimWorld` →
`spawnChampion({level})` → `world.stats.get(id).final`），母體 = 出貨的 **49 位對戰可選英雄**
（`packages/shared/testkit/balancePopulation.ts`）。傷害那一欄有一組是真的丟進

## 0. 先說清楚：AP 一共走**兩條**路進傷害，⛔ 不是一條

| 路 | 算式 | 住哪 | 是不是系統倍率 |
|---|---|---|---|
| **① 加法**（技能自己的係數） | `flat + AP × coeff` | 技能 JSON 的 `amount.ratios[{stat:"ap"}]` | ⛔ 不是（是內容） |
| **② 乘法**（全域，每一支技能都吃） | `× (1 + AP × 0.005)` | `content/config/ap-damage-scaling.json` | ⛔ 不是（自己一份 config） |

⇒ **一發技能的實際傷害 = `(flat + AP × coeff) × (1 + AP × rate)`**。
消費端逐字驗過（⛔ 不是掃註解）：
`packages/shared/src/sim/combat/damage.ts:991` —— `pkt.amount *= apDamageMult(world, pkt.source, pkt.origin)`，
掛在**傷害佇列**排空那一行，緊貼全域倍率、在 `mitigate()` 之前；
`apps/game-server/src/match/MatchController.ts:1170` 把出貨 config 灌進 world。
出貨 `scope: "ability"` ⇒ 只有 `origin` 以 `ability:` 開頭的封包吃，普攻/火圈/守衛塔不吃。

⭐ **關鍵：② 這一層與技能自己有沒有 AP 係數無關。** 所以就算一支技能的 `coeff = 0`（出貨 31.2%
的級距節點是這樣），它仍然吃到 `(1 + AP×0.005)` —— **推導鏈漏掉的主要就是這一層**。

## 3. 缺口在哪一行程式：`anchorFloorFrom()` 的分子沒有 AP 項

// packages/shared/src/content/damageTiers.ts
export function anchorFloorFrom(baseHp: number, bonus: number): number {
  const step = tierStep();
  const raw = (baseHp + bonus) / KILL_CASTS_REF;   // ← ⛔ 一發的傷害被當成「就是級距本身」

## 5. ⭐ owner 問的第二半：「每等級 +1 AP」今天真的生效嗎？

**✅ 生效，而且它是 AP 成長的最大單一來源。** 逐條驗過（⛔ 不是讀註解）：

| 環節 | 位置 | 狀態 |
|---|---|---|
| 出貨值 | `content/config/per-level-bonus.json` → `{"ap":{"amount":1,"appliesTo":"all"}}` | ✅ |
| Zod + `DEFAULT_*` | `schema/config/perLevelBonus.ts` · `sim/baseBonus.ts::DEFAULT_PER_LEVEL_BONUS` | ✅ |
| 灌進 world | `MatchController.ts:1102` `this.world.perLevelBonus = perLevelBonusFromDoc(...)` | ✅ |
| 進管線 | `stats/statPipeline.ts:271-272` 把 `perLevelBonus` + `level` 傳給 `finalizeStat` | ✅ |
| 真的加上去 | `sim/baseBonus.ts::finalizeStat` → `perLevelBonusFor(...)`（env 倍率**之後**、clamp **之前**） | ✅ |
| **行為驗證**（⛔ 不是掃程式） | 同一份母體把 `world.perLevelBonus` 換成 `{}` 重量：LV30 AP **135.3 → 106.3**、LV99 **333.6 → 235.6** | ✅ |

⇒ **這一格在 LV30 值 21.4% 的 AP、LV99 值 29.4% 的 AP，換算成技能傷害是 LV30 +9.5%。**

### 5.1 `appliesTo: "all"` 是什麼意思 / `primaryAttribute`（M5）有沒有分支

- `appliesTo` 三態：`all`（每一位都給）／`primary`（只給主屬性是該屬性的）／`nonPrimary`（只給不是的）。
- `perLevelBonusFor()`（`sim/baseBonus.ts:78`）的第一行是
  `if (e.appliesTo !== "all") { …讀 primary… }` ——
  ⭐ **出貨是 `"all"`，所以 `primary` 這個參數今天根本沒被讀到**。
- M5 的第十一格授予（`SourceGrantFields.primaryAttribute` → `statPipeline.ts::sourcePrimaryAttribute`）
  確實接上了 `finalizeStat({ primaryAttr })`，⭐ 但它**只在 `appliesTo` 不是 `"all"` 時才有作用**。
  ⇒ **今天它對每級 +1 AP 是逐位元 no-op。**
- 出貨內容裡填 `primaryAttribute` 的文件數：**0**（唯一命中的 `content/editor-target-profile.json`
  是編輯器契約的欄位清單，不是一份會掛上身的來源）。
- 出貨母體的主屬性分佈：STR 24 / AGI 28 / INT 19（71 張卡）——
  ⭐ 所以哪天把 `appliesTo` 改成 `nonPrimary`，會有 52 位吃到、19 位吃不到。

### 5.2 ⚠️ 這一格**沒有後台頁**（第一守則的三個住處只有兩個）

`apps/admin/src/configDocCoverage.ts:120` 把 `per-level-bonus` 明列在**已知缺口**表裡，
理由是它的 `perLevel` 是 `z.record`（鍵不固定），通用表單引擎畫不出來。
⇒ ⭐ **owner 今天要改「每等級 +1 AP」這一格，只能改 `content/config/per-level-bonus.json`
再部署（`--content-only`），⛔ 後台上點不到。**（`ap-damage-scaling` 三個住處齊全，後台有頁。）

## 7. ⭐ 缺口的形狀：**先擴大、後收斂**（⛔ 既不是常數也不是線性）

分子（血量）對等級是**一次**的（`HP = 931.6·lv + 6,760`），
分母（傷害 `(flat + AP·c)(1 + AP·r)`）對等級是**二次**的（AP 對等級一次）。
⇒ 「幾發打死」= 一次 ÷ 二次 ⇒ **有一個頂點，過了頂點就開始下降**。掃 LV1..400：

| 情境 | 頂點 | 頂點值 | LV99 | LV200 |
|---|---:|---:|---:|---:|
| 極大 `coeff=0` | LV400+ | 28.37 | 18.55 | 24.04 |
| 極大 `coeff=0.6` | **LV337** | 21.26 | 16.86 | 20.35 |
| 小 `coeff=0.6` | **LV169** | 56.11 | 52.99 | 55.77 |

⇒ ⭐ **在遊戲的等級範圍（1–99）內，AP 追不上血量 —— 但它不是發散的，
它是一條「還在爬坡、頂點在 LV169–400」的曲線。** 等級上限 99 落在坡上，
所以玩家經驗到的仍然是「越高等越難一發解決」，⛔ 但幅度只有不算 AP 時的一半。
