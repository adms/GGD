# A1 · `pnpm ship` —— 自動分級出貨（2026-08-23b）

> owner 2026-08-23 逐字：「或是其他**輕量級動態線上上架方式 (hotfix, patch) 設計與建議**，
> 並且要**能自動化判斷執行**」＋「最後記得**全部規則轉成自動化指令避免疏漏忘記**」

## 做了什麼

一支 `pnpm ship`：**路徑集合 → 分級 → 只跑該跑的閘 → 版號 → push → release note → 部署 → 煙霧**。

| 檔 | 是什麼 |
|---|---|
| `scripts/ship.sh` | 入口（＝部署協定六步的程式版）。`pnpm ship` |
| `tools/deploy-timing/pipeline.mjs` | 編排。⭐ 分級走既有的 `run.mjs tier`、閘走既有的 `parallel-gates/ship.mjs`，⛔ 兩者都不重寫 |
| `tools/deploy-timing/shipPlan.mjs` | **純函式**那一半：`gatePlan()`（哪幾支閘）· `gateArgs()`（翻成旗標）· `deploySteps()`（每一步） |
| `tools/deploy-timing/shipPlan.test.mjs` | 守衛（75 行）。餵**真實歷史 commit** 的路徑集合 |
| `tools/deploy-timing/tiers.json` | 加 `gatePlan` / `deploy` / 每個 plan 的 `rebuild`+`ssh`（機器可讀） |
| `tools/parallel-gates/ship.mjs` | 加 `--suites` / `--no-typecheck` / `--list`；並加入一支被漏掉的閘 |

## ⭐ 最重要的設計決定：**級別⛔ 不決定跑哪些閘**

owner 的說法把兩件事綁在一起（「T1（只有 client）⇒ 跑 client 那半的閘」），但實際的
`tiers.json` 裡 `apps/client` 是 **T3**（client bundle 烘在 `ggd-edge` 映像裡），
而 T0/T1 是**後台旋鈕／overlay**這條完全不同的路。⇒ 我把它拆成**兩個各自讀同一份路徑集合**的問題：

| 問題 | 誰答 | 判準 |
|---|---|---|
| 要不要重建映像？ | `classify()` + `downgrade()`（既有） | 路徑 → `tiers.json` |
| 這次可能弄壞誰？ | `gatePlan()`（新） | 路徑 → 誰讀得到它 |

⛔ 用級別推閘會漏：一次 `content/` ＋ `tools/` 的改動是 **T2（不重建映像）**，
而它照樣讓 36 支產生器閘全部過期。

**實測（`--plan-only`，真實歷史區間）：**

| 區間 | 級別 | 重建 | 閘 |
|---|---|---|---|
| `v0.25.6..v0.25.7`（142 檔） | T3 | ✅ | 全跑 |
| `85a995fc`（純 docs 一檔） | NOOP | ⛔ | 序列段 ＋ `skills:check` ＋ **只有** `packages/shared`；⛔ 不 typecheck |
| 認不得線上版本 | T3 | ✅ | **全跑**（fail-closed） |

## 🐛 最重要的一個發現：`tier` 在這個 repo 上**等於沒用**（已修）

`git diff --name-only` 預設把非 ASCII 路徑印成 **C 風格跳脫＋雙引號**：

```
"docs/\346\212\200\350\203\275\347\267\250\350\274\257\345\231\250…​.md"
```

那條字串**對不到 `tiers.json` 任何一條規則**（第一個字元是 `"`，連 `docs/` 前綴都不是）
⇒ fail-closed 落 **T3**。方向是安全的，⛔ 但後果是**一次純文件改動也會被判成「完整重建 191s」**——
而 `docs/技能標記機制與效果規則.md` 這一族 CJK 檔名遍佈全樹。
量到：`v0.25.6..v0.25.7` 的 142 個檔裡有 1 條因此變成 unknown。
修法：`git -c core.quotepath=false`（`run.mjs` 與 `pipeline.mjs` 各一處）。

**第二個發現**：`tools/deploy-timing/tier.test.mjs` **沒有被任何閘跑到** ——
`pnpm test` 是 `pnpm -r`（逐 workspace package），而 `tools/deploy-timing/` 不是 package；
`ship:check` 的 `packagesWithVitest()` 只掃 `apps/` 與 `packages/`。
⇒ 一支決定「哪些閘可以不跑」的程式**自己沒有閘**。已加入 `ship.mjs` 的並行段。

## ⛔ 沒有削弱任何既有的閘

- `pnpm ship:check` **不帶旗標的行為逐字不變**（守衛：`gateArgs` 對全跑的計畫回 `[]`）。
- `skills:check` 的 36 支**從不打折**，`packages/shared` 的 vitest **永遠跑**
  （`src/ops/` 那一族讀 `scripts/`、`CLAUDE.md`、`apps/admin/`、`docs/`）。
- fail-closed 三個入口：路徑對不到規則 ⇒ 全跑；`alwaysSuites` 指到不存在的包 ⇒ 全跑；
  `--suites` 認不得的名字 ⇒ **exit 2**（⛔ 不靜默略過）。
- **閘紅了 ⇒ 後面一步都不做**（⛔ 不是「先 tag 起來再說」）。

## 🔒 mutating 的那幾步**預設只印不跑**

`release:tag` / `push` / `gh:release` / `deploy` / `smoke` 五步預設印出**逐字可複製的指令**，
`--execute` 才真的跑（而且缺 `--tag` 或 `--notes` 就 exit 2）。
併行 lane 的硬規則：⛔ 不自己 push / gh 寫入 / 部署。
⚠️ `smoke` 雖然對 host 唯讀，仍標成 mutating —— 它是一條**打到正式站**的 ssh。

## 突變驗證（一批一條，挑最承重的）

`shipPlan.mjs` 的 `forceAll = unknown.length > 0 || missing.length > 0` → 拿掉 `unknown` 那一半
⇒ 「沒被規則吃到的路徑 ⇒ T3 **而且**閘全跑」當場紅（改回）。

## 用法

```bash
pnpm ship --stamp "v0.25.7-3-gabc1234"   # ⭐ 起點＝線上右下角的版本徽章
pnpm ship --plan-only                     # 只印計畫，⛔ 一個閘都不跑
pnpm ship --execute --tag "說明" --notes docs/_release/<檔>.md
```

⚠️ 起點是**線上正在服務的那個 commit**，⛔ 不是「我這次改了什麼」（2026-08-02 那次事故的形狀）。
