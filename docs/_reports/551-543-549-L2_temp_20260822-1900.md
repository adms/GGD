## 二、⭐ 最重要的一個發現：介面**逐字對上了**，只有兩處語意要主 session 拍板

L1 已經把四個 variant 落進 `packages/shared/src/sim/effects/variants/`（`spawnModelFx.ts`
`screenFlash.ts` `screenShake.ts` `floatingText.ts`）。我逐欄比對過，**欄位名一個字都沒有差**：

| kind | 欄位 | 對上？ |
|---|---|---|
| `spawnModelFx` | `shape` `modelKey` `path` `speed` `distance` `count` `spinDegPerSec` `scale` `lifeSec` | ✅ 全對 |
| `screenFlash` | `colorRgb` `peakAlpha` `durationSec` `applyTo` | ✅ 全對 |
| `screenShake` | `amplitude` `durationSec` `applyTo` | ✅ 全對 |
| `floatingText` | `text` `colorRgb` `sizeScale` `riseSpeed` `durationSec` `applyTo` | ✅ 全對 |

⭐ 而且 L1 的 `distance` 在 `orbit` 時被定義成**環半徑**（⛔ 不是走多遠）——
`modelFxPath.ts` 的 `orbit` 分支正是這樣讀的（切線速度 ÷ 半徑 → 角速度）。這一條如果兩邊
各自猜，出來的畫面會是「環的大小對、轉速差一個量級」，而**沒有任何測試會紅**。

### ⚠️ 兩處要拍板（都不擋出貨，但現在不決定日後會變成兩份真相）

1. **`toTarget` 同時給了 `distance`**。L1 的註解寫「`toTarget` 省略 = 走到目標身上」，
   ⛔ 沒說給了要怎麼辦。我實作成 `span = min(到目標的距離, distance)` ——
   ⭐ 理由：一支指定型技能不應該飛過頭。如果引擎側解成「一律走 `distance`」，
   兩邊會在「目標很近」時錯開。**建議把我這一條寫進 L1 的註解**（一句話，⛔ 不必改碼）。
2. **`floatingText.applyTo` 只有 `"self" | "victim"`**（⛔ 沒有 `"all"`），
   而 `screenFlash` / `screenShake` 有三個值。`screenFx.ts` 的 `ScreenFxAudience`
   是三值型別；`FloatingTextFx` 本身⛔ 不讀 `applyTo`（由呼叫端過濾），所以現在不衝突。
   ⚠️ 但外部編輯器會看到兩個不一樣的下拉 —— 要嘛統一成三值，要嘛在契約文件寫明為什麼不同。

## 三、⛔ 還沒有的那一段：**sim → client 的傳輸**

`packages/shared/src/sim/effects/effectRegistry.ts` 目前缺這四個 handler（tsc 紅，見第六節），
所以「這一發特效怎麼從權威側送到我的瀏覽器」這條線**還不存在**。

⭐ 這三個 kind 與既有 effect 有一個結構差異，值得主 session 在接線前先決定：
**它們沒有一格是 sim 狀態**。`spinDegPerSec` / `scale` / `colorRgb` / `sizeScale` /
`riseSpeed` 全部 L1 自己標了「純視覺，⛔ sim 不讀它」。⇒ 它們要走的是**特效廣播**那條路
（同 `spawnVfx` 的下行事件），⛔ 不是 `EntityState` 的 schema 欄位 ——
`defineTypes` 是 append-only 而且 `ENTITY_FLAG` 只剩 11 格，用掉任何一格在這裡都是浪費。

我這一側的三個入口函式已經是「拿到一包參數就演」的形狀，⛔ 不需要任何 sim 型別：

```ts
modelFxRig.spawn(spec, { origin, facingRad, target }, onArriveFx?)   // 回傳實際生了幾個
screenFxLayer.flash(spec, { isCaster, isVictim })                    // 回傳有沒有畫
screenFxLayer.shake(spec, { isCaster, isVictim })                    // 回傳有沒有送到相機
floatingTextFx.spawn({ text, x, y, z, colorRgb?, sizeScale?, riseSpeed?, durationSec? })
```

⚠️ **`{{i}}` 佔位符沒有人做**。約定寫「由發射端代入」，而 L1 的 `floatingText.ts` 只宣告
`text: string`。⛔ 我這一側刻意**不**做代入（第〇·四守則：一個模板兩個代入點 = 兩份會漂的真相）。
⇒ 這是一個**真的洞**：現在寫 `"{{i}}Hit"` 的技能會在畫面上印出字面的 `{{i}}Hit`。
建議實作點在 L1 的 handler（它才知道自己是第幾段）。

## 七、幾個刻意的決定（⛔ 都寫在檔頭裡，這裡只列標題）

- **閃爍是一個 DOM overlay，⛔ 不是 PostProcess** ——
  `vfx/CombatPostFx` 的檔頭記著上一次在螢幕空間做位移的代價：68° 俯角下只有地板有高頻細節，
  於是玩家看到的是「地板在震」（owner 原話：「為什麼開始戰鬥 地板總是會有莫名的震動波紋曲線」）。
  純色 overlay 沒有這個問題，而且在 mobile/low 品質層照樣在（post-process 在那一層是關掉的，
  而「不知道發生什麼事情」在低階機上更嚴重）。
- **震動走既有的 `CameraRig.addShake`，⛔ 不另開一條** —— 那裡已經有預配置的 impulse 池、
  最弱者被搶佔、三次方收尾、與品質層/reduced-motion 相乘的 `shakeScale`。
- **一個 div，多發在數學上合成** —— 克勞德一次七刀 = 一秒七次 `createElement` + 七次 layout。
  合成規則是「取最亮的一發當色相、alpha 相加後夾上界」，⛔ 不是平均（平均把紅+綠變成髒黃）。
- **`FloatingTextFx` 不是 `ui/combatText`** —— 後者的每一格語意都綁在「誰打誰、打多少」上
  （類別／陣營關係／傷害學派／admission 優先序／RO 拋物線）。把技能作者寫的一句話塞進去，
  要在 `CombatTextCategory` 開一個「其他」分支然後讓 `combatTextStyle` 的七格各開例外
  —— 那正是第〇·五守則說的「為某支技能寫一個 if」。
- **`modelFxRig` ⛔ 不算傷害** —— `onArrive`/`onTouch` 的 `EffectDef[]` 在權威側解算。
  我只收一個 `onArriveFx(落點)` 的視覺回呼。客戶端自己解算命中 = 失敗形態⑤。
- **free-list 有上界** —— 滿了就**真的 dispose** 並從 `born` 除名。
  ⛔ 只是「不放回池子」會留下沒有人指得到的孤兒，一場 20 分鐘的比賽積出幾百個（#131 的慢動作版）。
