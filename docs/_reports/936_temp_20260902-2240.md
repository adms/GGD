## 1. 先量到的三件事（⛔ 都不是推測）

### ① 票文把 `ratios` 的住處指錯了

| 票文說 | 實際（grep 出來的） |
|---|---|
| `packages/shared/src/content/schema/effects/_shared.ts` | ⛔ 那裡沒有 `ratios` |
| `packages/shared/src/sim/effects/dynamicTerms.ts` 算 `coeff × stat` | ⛔ 那個檔算的是 `resourcePct` / 距離項，**碰不到 `ratios`** |

⭐ 真住處：
- Zod：`packages/shared/src/content/schema/common.ts::zScaling`（**只有這一份**，`.strict()`）
- sim：`packages/shared/src/sim/effects/effect.ts::resolveScaling`（`for (const r of sc.ratios ?? [])` 那一行）

⚠️ 連帶：**#929（真傷不吃 AP 乘數）與這張票不衝突** —— 票文寫「同一個檔案區域（`dynamicTerms.ts`）⇒ ⛔ 不要同時開兩條 lane」，
而這張票**一行都沒碰** `dynamicTerms.ts`。兩條 lane 其實可以並行。

### ② ⭐⭐ 最重要的發現：`common.ts` ↔ `condition.ts` 是一條**會炸的 import 迴圈**

`ratios[].when` 要 `zEffectCondition`，而 `condition.ts` 反過來要 `common.ts` 的 `zRef`，
且它在**模組本體**就呼叫 `zRef(...)`。實測（探針，⛔ 不是推理）：

```
TypeError: zRef is not a function
  ❯ packages/shared/src/content/schema/condition.ts:192:15
```

⚠️ **而且第一版的修法（`export * from "./ref"` 門面）也不夠** —— 又量到第二個事實：
> vite/vitest 的 SSR transform 把 **import 全部提到最前面**，卻把 `export {}` 的
> `defineProperty` 留在**模組本體** ⇒ 迴圈回來的那一刻 `common.zRef` 還沒被定義。

⭐ **真 ESM 的 indirect binding 撐得住這件事，⛔ 而我們跑的不是真 ESM** ——
也就是說「re-export 沒有 TDZ」這個**正確的 ESM 知識**在這裡會給出**錯的結論**。

⇒ ⭐ 正解不是「讓迴圈活下來」，是**把迴圈拿掉**：
`zId`/`zRef` 一族搬進新的葉模組 `schema/ref.ts`，**`condition.ts` 直接 import 它**
⇒ `common → condition → ref` 變成一條**單向鏈**。
`common.ts` 仍 re-export 那五個名字當**門面**，所以全 repo 既有 import 端**一個都不用改**
（含 `tools/skill-spec/gen_spec.ts:71` 那條寫死路徑的 —— ⭐ 這正是 `zScaling` **不能搬家**的原因）。

### ③ 量尺自己先出過一次錯（⭐ 校準救的）

第一次跑 vitest 時 `zod` 解析不到 ⇒ 看起來像我的改動炸了。
⭐ **跑了一次 baseline 才發現探針本身是壞的**（worktree 缺 workspace 的 `node_modules` symlink）。
⇒ 修法：把主 repo 的 `packages/shared/node_modules`、`apps/editor/node_modules` symlink 進 worktree
（**⛔ 未進版控，只是本機**）。

### ⭐ 三條路的語意（刻意，⛔ 不是疏忽）

| `when` | `holds`（求值器） | 結果 |
|---|---|---|
| 缺席 | 有／沒有都一樣 | ⭐ **計入，而且一次都不問** ⇒ 今天出貨的 208 個 AP 節點**逐位元不變**、**零 rng draw** |
| 有 | 有 | 問它，`true` 才計入 |
| 有 | ⛔ 沒有 | ⭐ **不計入（fail-CLOSED）** |

⚠️ 最後一列是**決定**：這一格存在的理由就是「一個有條件的加成被當成常駐在發放」。
fail-OPEN 會**逐字重現這張票要修的缺陷**而且看起來完全正常；
fail-closed 讓「沒接線」長得跟「條件沒成立」一樣 —— ⭐ 而那也是預覽路徑
（`apps/editor` 沒有 world 可問）唯一誠實的答案：「**保證拿得到的那一份**」。

### ⭐ 為什麼求值器是**傳進來的函式**，⛔ 不是在 `resolveScaling` 裡呼叫 `evaluateCondition`

`resolveScaling` 至今是**純函式**（輸入全在參數上、不碰 world），而
`evaluateCondition(world, cond, ctx)` 要 `SimWorld` **而且會消耗 `world.rng`**。
⇒ 用跟既有 `attrs: AttrLookup` **完全一樣的形狀**（第零守則⑨：同型的東西用同一個模板）。

### ⚠️⚠️ ⭐ 尚未接線：**今天 sim 裡沒有任何呼叫點會傳 `holds`**

用詞紀律（CLAUDE.md）：**鏈路已接上到 resolver，⛔ 未接到 handler。**
⇒ 今天若有內容寫了 `ratios[].when`，sim 一律走 **fail-closed**（那一項不計入）。

**接線只需要一個地方**，而且**不在我的柵欄裡**：

- 9 個 sim 呼叫點（`damage.ts` / `damageArea.ts` / `damageLine.ts` / `dot.ts` /
  `chainLightning.ts` / `heal.ts` / `shield.ts` / `spendMana.ts` / `effectCommon.ts`）
  各多傳一個參數；
- ⭐ **或者更好**：在 `effects/effectCommon.ts` 加一支
  `casterCond(ctx) = (cond) => evaluateCondition(ctx.world, cond, {self: ctx.caster, target: ctx.targets[0]})`
  —— 跟既有的 `casterAttrs(ctx)` **完全同一個形狀**，9 個呼叫點各加一個引數。

⚠️ 接線時要一起決定的一件事：`dot.ts` 是**每個 tick** 呼叫一次 `resolveScaling`
⇒ 條件會**逐 tick 重評**（多半是對的：狀態掉了就不該再吃係數），
⛔ 但 `when` 裡若有 `chance` 葉會**每 tick 抽一次籤**。
