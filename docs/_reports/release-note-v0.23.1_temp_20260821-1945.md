⚠️ **這正是 2026-08-19「我猜你掉了超多」的那個形態**：帳本是**追著時間跑**的，
起草 release note 的那一刻它**一定**落後於最新的訊息。
⇒ ⭐ **起草 note 之前必須先跑一次 `msgledger:check`，紅了要補**，
⛔ 不可以假設「帳本是完整的所以直接抄」。

### ⚠️ 一個容易騙過人的細節（第三守則）

```bash
pnpm msgledger:check 2>&1 | tail -25; echo "EXIT=$?"
#   → 印出 EXIT=0，而真正的離開碼是 1（ELIFECYCLE）
```

`$?` 拿到的是 **`tail`** 的離開碼。真正的訊號是輸出裡的 `ELIFECYCLE Command failed with exit code 1`。
⇒ CLAUDE.md「硬性技術約束」裡記的三種變形，這次踩到第 1 種。

## 4 · 65 列是怎麼算出來的（⭐ 計算基礎，⛔ 不是估的）

```
帳本 83 列 = 52 原文(M) + 31 裁決回寫(R)
補撈        +2 原文(M)
------------------------------------------
            54 M + 31 R = 85

配對規則：每一列 R 併進「它之前 ≤3 分鐘、尚未被配對的最近一列 M」
  → 20 列 R 被併進 M            （例：12:28 M ↔ 12:29 R）
  → 11 列 R 找不到 M，自成一列   （owner 原話包在更長訊息裡或被打斷）
------------------------------------------
最終列數 = 54 + 11 = 65        ✅ 65 + 20 = 85 = 83 + 2   零遺漏
```
