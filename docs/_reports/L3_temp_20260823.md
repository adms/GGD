## 這一段做了什麼（前一段 `f98fc92b` 已經把帳本本身落地）

`f98fc92b` 落地的是**場景普查**：mesh / material / texture / particleSystem /
transformNode / geometry 逐類數，⛔ 不需要任何呼叫端記得任何事。
⭐ 但它同時開了一條 `gauge(kind, read)` 給「場景看不見的東西」（free-list 池、
Map 快取、per-entity 狀態表）—— 而那條路**一個呼叫端都沒有**。

⚠️ 那正是**失敗形態⑧**（消費端存在，但它消費不到）：`take()` 裡有
`for (const [kind, read] of this.gauges)`、tsc 綠、測試綠，而那個迴圈**永遠跑 0 次**。
第七回合真正在長的那一族（每一格掛著一個活 view 的 `Map`）從頭到尾不在帳本上。

## 做的兩件事

### ① `gaugeContainers(prefix, bag)` —— 接線成本＝**一行**（owner 的必要條件 1）

`Map` / `Set` 有 `size`、陣列有 `length`，這個 repo 裡幾乎每一個會長大的東西都是
這兩種之一 ⇒ 呼叫端**不寫任何讀取函式**，把容器本身交出來就好：

```ts
lifecycleLedger.gaugeContainers("view", { champions: this.champions, /* … */ });
```

⭐ **⛔ 沒有 `release()`**：讀的是容器**當下**的大小 ——「忘了從 Map 刪掉」這件事
**本身**就是被量的東西，⛔ 不是一個要記得配對的呼叫（那個形狀會把我們正在追的
缺陷原封不動再造一次：忘了 release 跟真的洩漏在帳本上長得一模一樣）。

⭐ 容器一律 **`WeakRef`**：一個被丟掉的 registry / 已 dispose 的場景快取，⛔ 不可以
因為登記表拿著它而活下來 —— 否則這支偵測器**自己就是下一個洩漏**。物件走了那一格
自動退場。量表數也吃 `MAX_KINDS`（64）上限，溢位**數出來**印在 `report()` 尾巴。

### ② 接四個已知重災區（示範，其餘留給後續）

| 接線點 | 量到什麼 | 為什麼場景普查看不到它 |
|---|---|---|
| `render/EntityViewRegistry`（建構子一行，14 格） | `champions` / `projectiles` / 三個 pool / `lastPos` / `speedEma` / `culled` / `occluded` / `tinted` / `builtForm` … | 它們裝的是 **view 物件與 per-entity 狀態**，⛔ 不是 mesh |

| `vfx/GroundDecalPool` | `decals` · `textures` | ⭐ **對照組** —— 它有硬上限，長到頂就該平掉 ⇒ 警報第三條件會讓它熄燈 |
| `render/groundTextureCache` | 每個 Scene 的快取筆數 | 貼圖**刻意**跨回合留著（GH#536），所以 `scene.textures` 分不出「正常暖機」與「每回合又新建一組」；**筆數**分得出來 |
