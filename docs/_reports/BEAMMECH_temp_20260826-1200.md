## 1. 五題的答案

### Q1 `spawnModelFx.scale` 是純量還是三軸？ → ⛔ **純量。不能。**

| 位置 | 證據 |
|---|---|
| schema | `packages/shared/src/content/schema/effects/spawnModelFx.ts:178` —— `scale: z.number().positive().max(MODEL_FX_MAX_SCALE).optional()` |
| 線路型別 | `packages/shared/src/sim/effects/spawnModelFx.ts:126` —— `scale?: number` |
| sim 轉發 | 同檔 `:352` —— `...(e.scale !== undefined ? { scale: e.scale } : {})` |
| 客戶端 | `apps/client/src/render/modelFxRig.ts:460` —— `root.scaling.setAll((doc.scale ?? 1) * (ev.scale ?? 1))` ⭐ **`setAll` ＝ 等向，結構上表達不了非等向** |

**JASS 全域普查**（`war3map.j`，paren-aware 解析 35 個 `SetUnitScalePercent`）：

| | 個數 | 佔比 |
|---|---:|---:|
| 等向（x=y=z） | 22 | 63% |
| ⭐ **非等向** | **13** | **37%** |

非等向的 13 個分三族：

| 族 | 例 | 行 | GGD 對應的軸 |
|---|---|---|---|
| **Z 拉長**（x=y<z） | `200,200,400`（h007 龜派 dummy）· `180,180,300`（h01V 天神烈破） | 26791 · 36049 | WC3 是 **Z-up** ⇒ 這是「柱子變高 2×」 |
| **Z 壓扁**（x=y>z） | `250,250,50` · `100+2n,同,100` · `50+5n,同,50` | 49915 · 49652 · 49890 | 扁盤／衝擊環 |
| **X 拉長**（面向軸） | `500,100,100` · `100+50×lvl,100,100`(h01V) · `WoodLevel×150+200,300,300` … | 31029 · 36051 · 47942 ＋4 | 沿**面向**拉長 |

⚠️⚠️ **軸對應要換算，⛔ 不可以照抄 `(200,200,400)`**：

- WC3：**Z-up**、`+X` 是面向。
- GGD：Babylon **Y-up**；`modelFxAxisCorrection()`（`apps/client/src/render/modelFxPath.ts:72-79`）
  把 `model@1.fxLongAxis` 宣告的那一軸**轉到 `+Z`（行進軸）**。
- `imported.netherstrike` / `w3x.stock.revivehuman` 兩份都是 `fxLongAxis: "y"`
  （`content/models/*.json`）＝ 轉檔後的 glb-Y ＝ **WC3 的 Z（垂直）**。

⇒ ⭐ **WC3 的 Z 拉長 ＝ GGD 的行進軸拉長**（那正是 owner 要的「90 度橫放的 beam」）。
`(200,200,400)` 在 GGD 是「等向 2.0 ＋ **沿行進軸再 ×2**」。
⇒ ⛔ 而 **X 拉長那一族在 GGD 是「橫向」**，⛔ 不是行進軸 —— 一格「長軸倍率」表達不了它。

**⭐ 掛哪個節點（Babylon 合成順序，⛔ 不是猜的）**

節點樹是 `root`（位置 ＋ `rotation.set(0, yaw, roll)`，`:585`）→ `axis`（`axisEuler`，`:461`）→ 幾何。
Babylon 的 local matrix 是 `S·R·T`，子節點先算 ⇒ 頂點順序是
`S_axis · R_axis · S_root · R_root`。

⇒ **`root.scaling` 作用在「已經橫放好」的座標系**：`+Z` ＝ 行進軸 ＝ 長軸、`+X` 橫向、`+Y` 上。
⇒ 而 `roll`（`spinDegPerSec`）也繞 `Z` ⇒ **Z-only 拉伸與 roll 可交換**，翻滾不會把光束甩歪。
⛔ 掛在 `axis` 上就變成「模型自己的座標系」，逐模型意義不同（fxLongAxis 一改語意就跑掉）。

### Q2 同點疊多具不同模型：現在要寫幾個節點？ → ⭐ **N 個節點，而那是對的。⛔ 不要開 `layers[]`。**

- **今天可行**：兩個 `spawnModelFx` 節點，各自帶 `preset` ＋ 自己的 `modelKey`。
  `sim/effects/spawnModelFx.ts` 每次 `apply()` 發一則 `modelFxSpawn`；

  `modelFxRig.ts:456` 的 pool key 是 `poolKeyOf(ev.modelKey, look)` ⇒ 兩層互不干擾、決定性不變。
- **成本**：每層 = 1 事件 + 1 glb 容器 + 1 pool key + `count` 具實例。
  預算 `DEFAULT_MAX_LIVE = 48`（`modelFxRig.ts:286`）。`count:1` 時 2–3 層 = 2–3 具，⛔ 不是問題；
  `count:6` 時 3 層 = 18 具就開始吃預算（⇒ 又一個 `count:6` 應該回到 1 的理由）。
- ⛔ **不建議「一個節點多層」**：這一族只有 2 層，而兩層**連 modelKey / clip / clipTimeScale /
  scale / anchor 都不同** —— 第零守則⑨ 的判準是「第二個東西跟第一個**只差參數**才抽模板」，
  這裡不是。開 `layers[]` 會讓「一具模型的演出」有兩個住處（第〇·五守則）。

⭐⭐ **真正的阻塞是素材，⛔ 不是機制**：

## 2. ⭐⭐ 五題之外的一個發現 —— 它比五題都貴

### `scale` 住在**家族模板**裡，使「大小正確」**結構上不可能**

原作的渲染大小是**兩個乘數**：w3u 單位型別的 `usca` × runtime 的 `SetUnitScalePercent`。
`tools/w3x-import/out/vfx-census/MODEL_USAGE.json` 的 `params.scale` 逐筆量到：

| dummy | .mdl | w3u `scale` | JASS % (rank1–4) | **積** |
|---|---|---:|---|---:|
| `h00S` 勝利劍（20-03） | ReviveHuman | **0.2** | 265–310% | **0.53–0.62** |
| `h00X` 勝利劍黑化 | NetherStrike | **0.2** | 265–310% | 0.53–0.62 |
| `h007` 特效龜派（09-04） | ReviveHuman | **1.25** | 265–310% | **3.31–3.88** |
| `h008` 特效三號（共有第二層） | FragDriller | **2.0** | 365–410% | 7.3–8.2 |
| `h01V` 天神烈破 | ReviveHuman | **3.0** | X 150–300% | — |
| `h01P` 野戰電子砲（59-04） | Awaken | 1.0 | 150–240% | 1.5–2.4 |

⭐ **同一份 `ReviveHuman.mdl` 被三個 dummy 用，w3u 基底是 0.2 / 1.25 / 3.0 —— 15 倍的差距。**
而 GGD 的 `content/models/w3x.stock.revivehuman.json` 只有**一格** `scale: 0.101`
（那是「這份 glb 換算成世界單位」，正確地住在模型上），
⇒ 那 15 倍的 per-dummy-type 差異**必須**住在**節點**的 `scale` 上。

**而出貨 7 個節點有 6 個吃同一個家族預設 `2.5`**（只有 08-03 覆寫 4.5、59-04 覆寫 count）：

```
godie-e002.e / e00l.e (20-03)  → {modelKey: revivehuman, tint:[1,.39,.39]}    ← scale 從模板拿 2.5
godie-o00x.r / ogrh.r (09-04)  → {modelKey: revivehuman}                       ← scale 從模板拿 2.5
godie-n01c.e / nbbc.e (08-03)  → {scale: 4.5}
godie-e00r.r        (59-04)    → {count: 1}                                    ← scale 從模板拿 2.5
```

⇒ 20-03 與 09-04 的**忠實比例是 1 : 6.3**，而今天兩支拿到**同一個數字**。

⭐ 這正好解釋 owner 2026-08-23 的那句「**避免出現很小顏色又不對的氣功砲**」——
而 `scale` 只要還住在家族模板的 `default` 裡，它就**結構上**對不了：
它是一個 **per-dummy-type** 的量，⛔ 不是 per-family 的量。
（與 `modelKey` 逐字同一個道理 —— `modelFxStagingContract.test.ts` ⑤ 已經為 `modelKey`
立過這條規矩：「它是**身分**不是幾何」。`scale` 的 w3u 那一半也是身分。）

### 順帶：一個**閘的洞**

`schema/effects/spawnModelFx.ts` 的 refine 表對**帶 `preset` 的節點整批跳過**跨欄位檢查
（`:327` 的 `const fromPreset = e.preset !== undefined`，`:338/:348/:356/:395/:408/:415/:422` 七處）。
⇒ **模板自己**產出一組互斥／惰性的組合時，⛔ 沒有任何東西會紅
（例：`count` 回到 1 之後 `spacing:2` 就是「有設但沒有人讀」，而那正是這張表整篇在擋的形狀）。
⇒ 建議 APPLY／GATE lane：把 refine 對**解析後**的節點再跑一次（`resolveModelFxPreset()` 之後），
或在 `templates` 的守衛裡驗「解析後的節點自己過得了 refine」。

### 最小改動的具體形狀

**P1 逐階 `scale`** —— ⭐ 復用既有機制，⛔ 不發明第二種寫法
```
schema/effects/spawnModelFx.ts:178
  scale: zRankScalar(z.number().positive().max(MODEL_FX_MAX_SCALE)).optional()
sim/effects/spawnModelFx.ts:352
  const sc = rankScalar(e.scale, ctx.rank);
  ...(sc !== undefined ? { scale: sc } : {})
```
線路型別 `ModelFxSpawnEvent.scale?: number` **不變**、客戶端 **零改動**。
⭐ 一鍵 rollback ＝ 內容寫回純量（`number` 仍然合法，語意逐位元不變）。
