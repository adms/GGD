`skills:sync 裁剪: ⛔ 不知道這一次改了哪些路徑 ⇒ 全跑` —— 當天 5 次跑 `ship:check`，
裁剪 **0 次生效**。A4 做好的裁剪引擎（`syncPlan.mjs`）一直待機，因為沒有人記得帶
`--sync-base`。一個要人記得帶旗標才生效的裁剪，等於沒有（元規則：閘不是判準）。

## 修法（只動 `tools/parallel-gates/ship.mjs` ＋ 守衛）
序列段的 base **預設 `origin/main`**（＝上一次 push ＝上一次部署——這個 repo 的
部署協定就是 push 後遠端 `git pull`，remote 是 github.com，⛔ 不是正式站主機）。

fail-closed **不減反加，五道全部往「全跑」倒**：
1. ⭐ 新增：`git fetch` 失敗/逾時（`GGD_SYNC_FETCH_TIMEOUT_MS`，預設 10s）⇒ 全跑
2. ⭐ 新增：`origin/main` 有本地沒有的 commit（有別的東西先 push 了），或落後本地超過
   `GGD_SYNC_BASE_MAX_BEHIND`（預設 100）⇒ 全跑**並印原因**
3. `origin/main` 解析不到 ⇒ 全跑
4. 計畫 `full`（路徑對不到輸入表）⇒ 全跑（原樣保留）
5. 算計畫擲例外 ⇒ 全跑（原樣保留）

⚠️ 明確給了 `--sync-base`／`--sync-paths`／`GGD_DEPLOYED_REF` 時**不碰網路**；
`--no-sync` 也不 fetch（`shipPlan.test.mjs` 的 `--list` 消費者因此不受影響——
它逐行 parse stdout，所以裁剪決定在 `--list` 模式印到 **stderr**）。
⛔ 沒有削弱任何閘的判準：只裁「跑不跑」，每一支的指令與判準逐字不動。
