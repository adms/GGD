### ⭐ 為什麼是「同一張表的兩種鍵」而不是第二套機制（第〇·五守則）

`formVisualFor` 早就是三個旋鈕的**共同上游**：
顏色 → `championTintFor` · 大小 → `modelOverrideFor` · 掛件 → GameApp 的 `formAttachmentFor`。
⇒ 狀態只要餵進**那一行**，三樣同時活過來。⛔ 沒有第二處要接，也沒有第二份規則。

### ⛔ 兩張表命中時是**取代**，不是相乘

遷移期同一對會兩邊都有（形態還在、狀態也掛上了）。相乘 = 同一個外觀套兩次
（Saber 的青白會變成青青白白）。⇒ 只要任何一格狀態外觀命中，形態那一份整份讓位。
於是**「遷移中」與「退場後」畫面逐位元相同** —— 那正是這條規則要買的東西。

### ⛔ 沒有動 `content/`

⭐ 兩個新欄位都有 Zod `.default()`，所以出貨的 `content/config/form-visuals.json`
**一個位元組都沒改**（實測 `safeParse` 綠、`statuses = {}`、`statusStrength = 1`）。
⇒ ⛔ 不需要 `content:build`、不會讓 `shippedBundleIsCurrent` 過期（併行鎖）。

### ④-1 `apps/client/src/GameApp.ts` —— **M1 的最後一根接線**（另一條 lane 佔用中）

⚠️ 少了這一段，`statusIdsForSeat` 恆 `undefined` ⇒ M1 在客戶端是**死的**（失敗形態③）。

模組層先加一個常數（避免每幀配一個空陣列）：

```ts
/** ⭐ M1（GH#599）—— 沒有狀態時共用的空清單，⛔ 不要每幀 new 一個。 */
const EMPTY_STATUS_IDS: readonly string[] = [];
```

然後在 `this.championBody = championBodyHooks({` 的 `championIdForSeat` **下一行**插入：

```ts
      // ⭐ M1（GH#599）—— 變身外觀掛在**狀態**上的那一半。座位的 statusIds 是
      // 全座位都送的（net/snapshot.ts 的座位迴圈跑 ctl.seats 全部，而
      // MatchState.seats 沒有任何 Colyseus filter），所以這一行不需要任何新的
      // 線路欄位、不需要新的 ENTITY_FLAG bit、也不需要動 apps/game-server/**。
      statusIdsForSeat: (seatId) =>
        seatId === undefined
          ? EMPTY_STATUS_IDS
          : (hudStore.getState().seats.find((s) => s.seatId === seatId)?.statusIds ??
            EMPTY_STATUS_IDS),
```

（`hudStore` 已經 import 過了；`championIdForSeat` 用的就是同一份表。）
