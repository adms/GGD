## 1. ⭐ 最重要的一個發現

> **`ui/PadCursor` 少了 `pointer-events: none`，整個功能會「看起來完全正常」而一個按鈕都按不到。**

游標本身是一顆掛在 `document.body` 上的 div。`document.elementFromPoint(x, y)`
回傳的是**最上層有 pointer-events 的元素** —— 如果游標自己吃 pointer events，
那麼**每一次** A 都會打到那張 22px 的箭頭貼紙。畫面上：箭頭跟著搖桿滑順地移動，
hover 效果不亮，按下去沒反應。⛔ 這是失敗形態②（算出來了但沒送到）的變種：
每一個零件都對，只有它們的組合是空的。

⇒ 那一行在 `ui/PadCursor.ts` 裡被標成**承重**並附了理由，⛔ 不是一行普通的樣式。

第二個同型的坑（也已經關掉）：**`el.click()` 的 `clientX/clientY` 是 0**。
這個 repo 有一整族讀座標的接收端（拖曳、tooltip 定位、canvas 熱區），
用 `click()` 的話它們會全部以為玩家點在螢幕左上角 —— 「點得到但點錯地方」
比點不到更難查。⇒ 派的是整串 `pointerdown → mousedown → pointerup → mouseup → click`，
每一個都帶座標。

## 2. 做了什麼

### ① `apps/client/src/input/padCursor.ts`（新，純核心，264 行）

沒有 DOM 也能跑的那一半。三個純函式 + 設定解析：

| 匯出 | 做什麼 |
|---|---|
| `padCursorNextMode(prev, opts)` | ⭐ **THE GATE**。三條規則，順序有意義 |
| `stepPadCursor(pos, axes, dtMs, t, viewport)` | 一幀之後游標在哪（死區重正規化 + 加速曲線 + 夾在畫面內） |
| `padCursorHome(viewport)` | 開啟時放螢幕正中央（⛔ 不是 0,0） |
| `resolvePadCursorTuning(doc)` / `padCursorTuning()` | 設定 → 手感，超界**回報**不靜默吞 |

⭐ **「戰鬥中自動停用」整個住在一個判準裡**，⛔ 這裡不重判一次「現在算不算戰鬥」：

```ts
if (!opts.enabled) return false;
if (!opts.menuOwnsPad) return false;   // ⭐ 承重：來自 padFocusNav.focusNavActive()
if (opts.togglePressed) return !prev;
if (opts.backPressed && prev) return false;
```

`menuOwnsPad` 就是 `padHudFocusActive({screen, phase, hasScope, hudFocusMode})` 的答案 ——
螢幕／階段／有沒有 modal 三件事**已經**有唯一的住處，游標只是讀它。
⇒ 那條規則哪天改了，游標跟著改，⛔ 不會有第二份會分岔的定義。

⚠️ **兩個場合，兩個模型**（票上點名的）落地方式就是這一行：
選單場合 → 焦點導覽為主 + 游標為輔；戰鬥中 → 游標**不存在**，
英雄照舊走「直接操控 + 軟鎖定」（`AimResolver` / `padCastReach`），
⛔ 不是拿游標去點地板。

### ② `apps/client/src/ui/PadCursor.ts`（新，瀏覽器那一半，135 行）

⛔ **刻意不是 React 元件**（`ui/PadKeyboard.tsx` 是）：游標每一幀都動，
一個每幀 `setState` 的元件會讓 React 在選單裡跑滿 60fps 的 reconcile，
而它畫的東西是**一個 `transform`**。

| 匯出 | |
|---|---|
| `showPadCursor` / `hidePadCursor` / `isPadCursorVisible` | 掛/收那顆 div |
| `padCursorHit(at)` | `elementFromPoint`（游標自己因 `pointer-events:none` 不會被打到） |
| `syncPadCursor(at)` | 移動 + hover：`mousemove` 每幀派，`mouseover`/`mouseout` **只在換人時**派 |
| `padCursorPress(target, at)` | 整串帶座標的滑鼠事件 + `focus()` |

⚠️ `mouseover` 每幀派會讓「進來就播音效」的接收端在游標靜止時每秒響 60 次 ——
所以是換人才派。

### ③ `apps/client/src/ui/PadFocusNav.tsx`（改，接線）

⛔ **沒有第二套 pad loop**（那會是第三套）。每一幀由既有的迴圈叫進來：

- 手把拔掉 → 收游標（留著一支不會動的箭頭會蓋在真的滑鼠游標旁邊）
- `backEdge` 在 `prevBack` 被覆寫**之前**取，游標模式與 HUD 焦點模式**共用同一次**
- 進入模式：`padCursorHome()` + `clearPadFocus()`（游標接手了，焦點環留著會有兩個「我在這裡」）
  + `prevCursorA = true`（切換鍵按下的那一幀 A 可能也按著，⛔ 不要當成一次點擊）
- 模式中：`stepPadCursor` → `syncPadCursor` → A 邊緣 → `padCursorHit` → 按下去
- 模式中 `nav.reset(); return;` —— 左搖桿在移動指標，⛔ 不可以同時把焦點也走掉
- ⭐ 游標打到文字欄位時走的是**同一個** `shouldOpenPadKeyboard` 決定（#503），
  ⛔ 不是第二份判斷 —— 游標點進帳號欄一樣要能打字

另外把 activate 分支的小鍵盤改成吃 `keyboardEnabled`：關掉時 A 落回 `cur.click()`
（＝ #503 之前的行為），⛔ 不是「按了沒反應」。

### ④ 守衛（2 支，共 **78 行** —— 體驗層 80 行上限之內）

| 檔 | 驗什麼 |
|---|---|
| `input/padCursor.test.ts`（42 行） | 戰鬥中一律關（承重）· 推搖桿會動/死區不動/長幀不甩出畫面 · 超界會回報 |
| `input/padKeyboard.test.ts`（36 行，jsdom） | ⭐ 按鍵**真的寫進** `<input>.value` 且派得出 `input` 事件 |

⛔ 沒有任何一條斷言抄出貨數值（速度/曲線/死區全部從 `SHIPPED_PAD_CURSOR` 推導）。
⛔ 不開對抗輪（體驗層）。

## 4. ⚠️ 需要主 session 接線

### (a) `config.gamepad@1` 加五格（Zod + `content/config/gamepad.json` + admin）

⛔ 這條 lane **沒有碰** `packages/shared`、`content/`、`apps/admin`（柵欄外，
而且動 `content/` 會逼出 `content:build`＝全域鎖）。

⭐ **接上去之後 `input/padCursor.ts` 一行都不用改** —— `resolvePadCursorTuning()`
走的是欄位表（`PAD_CURSOR_FIELDS`）而不是一份手抄的鍵名清單，五個鍵一落進 JSON
就會被讀到。今天讀不到就用 `SHIPPED_PAD_CURSOR`。

| 欄位 | 型別 | 下界 | 上界 | 出貨值 | 標籤（後台） |
|---|---|---:|---:|---:|---|
| `cursorEnabled` | boolean | — | — | `true` | 選單裡要不要提供「以左搖桿移動虛擬游標」這條退路（戰鬥中一律停用） |
| `keyboardEnabled` | boolean | — | — | `true` | 焦點停在文字欄位上按 A 時要不要浮出螢幕小鍵盤 |
| `cursorSpeed` | number | `100` | `4000` | `1100` | 搖桿推到底時虛擬游標的速度（每秒像素） |
| `cursorAccel` | number | `1` | `4` | `1.8` | 虛擬游標的加速曲線指數（1=線性；越大代表輕推越慢、推到底一樣快，好瞄準小按鈕） |
| `cursorToggleButton` | int | `0` | `19` | `10` | 用哪一顆手把鍵切進／切出虛擬游標（標準對應：10=左搖桿按下 L3、11=R3、2=X） |

⚠️ **`deadzone` 刻意不是第六格** —— 票上點名的「死區」**今天已經是** `config.gamepad@1.deadzone`
（#520 落地），而 `padCursor` 直接讀它。死區描述的是**這支搖桿的漂移量**（硬體性質），
⛔ 不是「選單裡」與「戰鬥中」兩種偏好；替游標再開一格 `cursorDeadzone` 就是
同一個數字的第二個住處（第〇·四守則），而兩份一定會分岔。
`SHIPPED_PAD_CURSOR.deadzone` 從 `DEFAULT_GAMEPAD_FEEL_POLICY.deadzone` 推導，
⛔ 沒有手打一份 `0.15`。

⚠️ 每一格都有**上界**（第一守則）：`cursorSpeed` 打成 11000 會讓游標一撥就飛到
螢幕另一邊，`cursorToggleButton` 打成 80 會讓那顆鍵永遠讀不到 `pressed` ——
兩個在畫面上都跟「功能沒做」一模一樣。

分組建議：與既有五格同一張表（「🎮 手把」），新五格排在既有五格之後。

### (b) `ui/ControlLegend.tsx` 要多一列（⛔ 柵欄外）

畫面上的操作說明卡目前**沒有**「L3＝虛擬游標」這一列。
⚠️ 這是第一·五守則的**鏡像**：卡片上不可以有說了不會發生的字，
而**做得到卻沒有說**同樣是缺陷 —— 沒有人會去按一顆說明卡沒提過的鍵，
所以整條退路等於不存在。

建議文案：`L3　虛擬游標（選單）`，只在選單場合顯示。

### (c) `ui/hud/padHudFocus.ts` 的 override seam 至今**零呼叫端**

`applyPadHudFocusOverride` / `PAD_HUD_FOCUS_FIELDS` 全 repo 只有它自己的測試在用
（#508 出貨時 admin 那一格沒接）。⇒ 那五格今天**後台調不到**。
和上面 (a) 是同一次接線，建議一起做。
