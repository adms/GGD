## 1. 換算來源（⛔ 一個字面值都沒有第二個住處）

公式與係數的**唯一住處**是 `tools/ap-conversion/knobs.json` 的 `$formula`：

```
apPct = max(minPct, round_halfUp( coeff × apPerAttrPoint × 100 ÷ stepPct ) × stepPct)
       = max(10,   round_halfUp( coeff × 0.25 × 100 ÷ 10 ) × 10)
```

⭐ 本輪的四個數字**全部是用出貨的那支函式算出來的**
（`apply.pct_for()` / `apply.rewrite_description()`），⛔ 不是我手算再抄進去：

| 乘數 | → AP% | 出處 |
|---|---:|---|
| `智慧*6` | **150%** | `godie-i02t` 傷害 |
| `智慧*9` | **230%** | `godie-i03b` |
| `智慧×4` | **100%** | `tpl-random-barrage` 引用的 42-04（與 42-04 卡面現況逐字一致） |
| `力量×1` | **30%** | `godie-i018`（⛔ **沒有落地**，只是算給 owner 看） |

⚠️ 改寫用的是**產生器自己的** `rewrite_description()` 逐字輸出
（含 `(智慧*6)` → `(150% [AP])` 的「外層括號要保留」那條規則），
所以將來 `claims.json` 的語料真的擴到 `content/items/**` 時，
`apconv:build` 重跑的結果與今天磁碟上的**逐位元組相同** —— ⛔ 不會多出一個假的 diff。

### 2.1 為什麼 `tpl-random-barrage` 不是「換算」而是「修一句過期的引用」

那份模板**一格傷害酬載都沒有**（`gen.damage_amounts()` 回 0 筆），
那串字描述的是 42-04 的**欄位由來**。但 42-04（`godie-n003.r` / `godie-n01g.r`）
今天的卡面逐字寫著「一次 **100% [AP]** 點傷害」⇒
讀模板的人會回去 42-04 找 `智慧×4` 而**找不到**。
⇒ 它不是效果宣稱，是**一句指向不存在數字的引用**，所以修法是改字不是換公式。

### 2.2 被取代的原文另存在哪（第一·五守則）

⛔ 不是丟給 git history —— 改數值的人在同一個表單裡就看得到。

⚠️ 誠實記一筆（兩件都適用）：這兩份文件**一格效果酬載都沒有**
（`godie-i02t` 完全沒有 `passive`／主動效果；`godie-i03b` 只有三條屬性 `modifiers`）。
⇒ 卡面這些數字**今天在場上都不會發生**。那是另一條缺口（道具主動技能尚未實作），

## 3. ⭐ 要 owner 裁決的兩件（兩種都算好了，⛔ 我沒有挑）

### 3.1 `godie-i02t` 盾甲天書 —— **治療那一半跟不跟著換？**

| | 卡面會長這樣 |
|---|---|
| **A（今天出貨的）** | 對範圍內敵方傷害 **(222+150% [AP])**，回復友軍血量 **(222+智慧\*6)** |
| **B（治療也換）** | 對範圍內敵方傷害 **(222+150% [AP])**，回復友軍血量 **(222+150% [AP])** |

- **選 A 的理由**：owner 2026-08-21 的原話是「原本有屬性額外**傷害**的部分」——
  「回復友軍血量」不是傷害。把它一起換是一次 owner 沒有要求的**機制**變更
  （治療從此吃法強成長）。
- **選 B 的理由**：原作把兩半寫成**同一個數字**（`222+智慧*6` 逐字重複兩次），
  拆開之後這件道具會變成**一半新制一半舊制**；而如果 owner 要的系統性結果是
  「三圍不再直接餵**任何**酬載」，那 A 就是漏網之魚。

⇒ 出貨先做 A，並把它登記成 `exemptions.json` 的 `NEEDS_RULING`（⛔ 不是漏掉）。

### 3.2 `godie-i018` 朗基努斯之槍 —— **on-hit 讀「總力量」算不算屬性額外傷害？**

| | 資料會長這樣 |
|---|---|
| **A（今天出貨的）** | `amount.attrRatios: [{attr:"str", basis:"total", coeff:1}]`，卡面「等同 **(總力量)** 之閃電傷害」 |
| **B（換算）** | `amount.ratios: [{stat:"ap", coeff:0.3}]`，卡面「等同 **30% [AP]** 之閃電傷害」 |

- **選 A 的理由**：它是**基準式**（`basis: "total"`，含裝備加成，對應原作
  `GetHeroStatBJ(…, true)`），⛔ 不是裁決管的那種「乘數幾倍屬性」。
  換掉會把「**堆力量 → 這把槍變強**」整條流派拆掉，而那是這件神器的識別特徵本身。
  ⚠️ 而且它的**觸發機率**也讀三圍（`chanceFrom: agi/total`）——
  只換傷害不換機率，這件道具會剩下一半的三圍耦合。
- **選 B 的理由**：「等同總力量」在數學上就是 `力量×1`，而 `力量×1 → 30% [AP]`
  是同一條公式定義得出來的。

⚠️ **成本不對稱**：選 B 是一次真的平衡變更（實測 lv10 約 53 點總力量 → 換成
30% [AP] 之後傷害改由法強決定，而這是一件**沒有法強加成**的物理向神器）。
⇒ 我不替 owner 挑。
