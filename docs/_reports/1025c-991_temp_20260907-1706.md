## ① 上一條 lane 刻意沒做 C 的那個擋點 —— ⭐ 它是對的，而這是它的解

> 「熱套用時知道哪幾個 id 是新加的，⛔ **重啟後那資訊就沒了** ⇒
>  半套會變成『重啟前只進社群房、重啟後跑進官方房』。」

⇒ ⭐ **出身（provenance）在「發布」那一次寫入就記下來**，⛔ 不是在 shard 推導。

| 層 | 做了什麼 |
|---|---|
| **記** | `Overlay.Community map[string]bool`（`collection/id` → true），**與內容同一個 mutex、同一次原子寫入、同一個 generation** |
| **服務** | `GET /api/v1/content-overlay/community` —— ⭐ 逐欄位等於 `GET /curation/whitelist`（`{version,updatedAt,champions[],items[],abilities[]}`） |
| **公告** | ⛔ **沒有第二種通知機制**：這份清單**就是**覆蓋層的一部分，所以 `commit()` 既有的 `chan:content` / `content-overlay` 公告已經涵蓋它 |
| **取快照** | shard 在**開房那一刻**（`MatchRoom.buildMatch`），⭐ 抄白名單那條路（TTL 快取 · 不可變快照 · fail-safe） |
| **套用** | ⭐ **一刀切在白名單上** —— 選角／隨機池／bot／商店／掉落／EX 全部走同一個 `Whitelist` seam，⛔ 不是六個 if |

### ⭐ 為什麼住在覆蓋層裡而不是另開一個 store

⛔ 另一個 store ＝ 兩個寫入端 ⇒「這份文件在覆蓋層裡」與「它是社群來的」可以漂。
⭐ 住在同一份文件裡，兩件事**在同一個位元組層級的寫入裡一起成立或一起不成立**。
（`Bases` 已經是同一個形狀的先例，它的檔頭寫著同一個理由。）

### ⭐ 出身是**平台自己的判斷**，⛔ 不是投稿者的宣稱

`Material.Origin` 由 `handlers.go` 的 submit **按角色**填（一律 `player`，只有帶編輯器
憑證的才是 `ai-editor`），而 `normalizeMaterial` 把包裡自稱的一律覆蓋。
⇒ ⭐ `submissionPublisher()` 讀的是平台的判斷。

### ⭐ 三條「出身跟著內容走」的邊（每一條都補了，⛔ 不是只有 happy path）

| 動作 | 出身 | ⛔ 漏掉會怎樣 |
|---|---|---|
| `PutDocFrom(community=true)`（發布） | ✅ 記上 | —— |
| `PutDoc`（**admin 編輯**一份社群英雄） | ⭐ **保留** | 營運改個錯字＝作者換人 |
| `DeleteDoc` / `RevertDoc` | ⭐ **清掉** | 清單長出「指到不存在的內容」的 id（白名單踩過的那個病） |
| `RestoreAll` / `RestoreDoc`（GH#326 版本回滾） | ⭐ **跟著那一版回捲** | ⛔ 回滾後社群英雄**變成官方內容** ⇒ 下一場出現在官方房，而回滾看起來完全成功 |

## ② `contentPool` 的四個住處

⚠️ ⭐ **兩格東西，⛔ 不要混為一談**（我刻意沒有把「預設池」再做成第二格設定 ——
那會是一個零消費端的裝飾）：

| | 是什麼 | 誰轉 |
|---|---|---|
| `roomSettings.contentPool` | **這一間房**用哪一份內容池（`official` / `community`） | 房主，每一間房 |
| `config.ugc@1.communityRoomOnly` | ⭐ 「社群內容」這個分類**生不生效** | owner，一鍵 rollback |

`communityRoomOnly = false` ≡「每一間房都是社群房」，⇒ ⭐ 一格布林就表達得完，
⛔ 不必再開一格 `defaultContentPool`。

| 住處 | 檔：行 |
|---|---|
| **① 出貨值** | `content/config/ugc.json:12` —— `"communityRoomOnly": true` |
| **② Zod ＋ DEFAULT** | `packages/shared/src/content/schema/config/ugc.ts:176`（`z.boolean().describe(...)`）· `:226`（`DEFAULT_UGC.communityRoomOnly`）· `:242`（`UgcPolicyResolved`）· `:264`（`resolveUgc`） |
| **③ admin** | `apps/admin/src/configForms/specs/ugc.ts`（`derivedFields` 自動長出那一格；`consumer` / `effect` 兩段散文逐格更新） |
| **④ ⭐ 消費端** | `apps/game-server/src/curation/communityContent.ts:267` 的 `communityRoomOnly()`，由 **`apps/game-server/src/rooms/MatchRoom.ts:626`** 讀（`buildMatch`），套用在 **`:629`** 的 `applyContentPool(...)` |

`contentPool` 本身（房間設定那一格）住 `packages/shared/src/roomSettings.ts`：
`ROOM_CONTENT_POOLS` / `ContentPool` / `DEFAULT_CONTENT_POOL`（＝`official`）＋
`ROOM_ENUM_SETTING_VALUES` 一張表（⭐ 加第二格 enum 房間設定時只加一列，
`sanitizeRoomSettings` 一個字都不用改）。

⚠️ ⭐ 它**刻意不在** `ROOM_SETTING_KEYS` 裡：那張表的每一格都是「有上下界的數字」，
而客戶端的開房表單就是照它產生**數字輸入框**的（`RoomListPanel.tsx`）——
混進一格 enum ＝ 表單長出「請輸入 official–community 之間的數字」。

**Go 那一層**（透明轉送，⛔ 不驗）：`apps/platform/internal/room/room.go` 的
`MatchSettings.ContentPool *string` ＋ `merge` ＋ `redisFields` ＋ `matchSettingsFromRedis`
（新增 `parseOptString`：⭐ 空字串讀成**缺席**，⛔ 不是「房主設了空字串」）。
⇒ 今天 `POST /api/v1/rooms` 帶 `"contentPool":"community"` 就開得出社群房。

## ③ 開關清單與我挑的預設

| 開關 | 我挑的預設 | 理由 |
|---|---|---|
| ⭐ `config.ugc@1.**communityRoomOnly**` | **true**（社群內容只進社群房） | 票文驗收逐字「社群內容**預設只在社群房**出現；官方房**選不到**」⇒ 第〇·六守則「優先權大的更新後預設啟動」 |
| ⭐ `roomSettings.**contentPool**` 缺席時 | **`official`** | 同上。⚠️ 缺席 ≠ 重設：不認得的值**被拒絕**並記進 `rejected`，⛔ 不靜默換成預設（靜默換掉 ⇒ 房主開了社群房卻拿到官方內容，而畫面完全正常） |

## ⑥ GH#991（非編輯器那一半）—— 做了什麼、⭐ 以及一個推翻票文的發現

### ⭐⭐ 發現：**提交端點今天就存在，而票文（與那支閘）在找另一條不存在的路**

| 票文／閘說的 | ⭐ 逐行複驗的結果 |
|---|---|
| 「content-api 的 proposals 端點沒有身分檢查」 | ✅ 成立，⛔ **但那不是玩家投稿的路** |
| `ugcGateIsArmed.test.ts`：「`apps/` 底下**零個** UGC 提交路由」 | ⛔ **它掃的是 `ugc/(proposals\|submissions)` 這個路徑樣式** —— 而真的那條叫 **`POST /api/v1/submissions`**（`submissions/handlers.go:125`），掛在 `auth.Middleware` 後面、有 `ui-cues.playerContent.submit` 當開關、有 digest 重算、有待審深度上限 |

⇒ ⭐ 這是 CLAUDE.md 記過的形狀：**「我查的那條路上沒有」≠「它不存在」**。
⚠️ 那支閘因此是**結構上瞎的**：它對真正的那條路永遠回「零命中 ⇒ 沒有洞」，
⭐ 而它的 `calibrate()` 只證明了掃描器對 `ai-review/promote` 找得到 ——
⛔ 證明不了它的**路徑樣式**對得上真實世界。
⛔ 我**沒有改它**（`packages/shared/src/ops/**` 是柵欄）⇒ ⭐ **留給主 session 開票**：
把 `UGC_SUBMIT_PATHS` 改成掃真正那條，或改問「submit handler 有沒有綁齊那幾格」。

### ⭐ 真正的缺口是「那四格 config **零個執行期呼叫端**」—— 補上了

（CLAUDE.md 記過 #1035：三個住處齊全、後台看得到、驗收全綠，而沒有一行 production 讀它，活了 4 天。）

| 格 | 消費端（檔：行） |
|---|---|
| `enabled` | `apps/platform/internal/server/playercontent.go` 的 `ugcSubmissionPolicy()` → `apps/platform/internal/submissions/handlers.go:164-169`（403 `UGC_DISABLED`） |
| `maxBytes` | 同上 → `handlers.go:175`（`MaxBytesReader`，⭐ 讀取上限跟著生效值走）＋ `submissions.go:241`（`normalizeMaterial`） |
| `maxPendingPerPlayer` | 同上 → `submissions.go` 的 `Submit()`（`effectiveMaxPending()`） |
| `quotaPerPlayerPerDay` | 同上 → `Submit()`（**今天送過幾份**，UTC 日界；⭐ 改稿也算 —— 配額擋的正是磨佇列） |
| `requireAuth` | ⚠️ ⭐ **誠實地說：今天沒有獨立呼叫端** —— 那條路線本來就掛在 `auth.Middleware` 後面（匿名根本進不來）⇒ 它是一格**宣告**。已寫進 admin 的 `consumer` 散文，⛔ 沒有假裝它有消費端 |

⭐ **政策只能更緊**：`SubmitPolicy.effectiveMaxBytes()` / `effectiveMaxPending()` 取
`min(政策, 二進位檔常數)`。⛔ 後台調不出一個比映像能承受的更大的數字，
⭐ 而拒絕訊息會說出**真正生效的那個數字**（投稿者看不到後台）。

⚠️ ⭐ 順手修了一個**指錯方向的錯誤訊息**：`MaxBytesReader` 在半路切斷 ⇒ decoder 看到
截斷的 JSON ⇒ 原本回「submission body is not valid JSON」——
⭐ 那會讓投稿者去檢查一份**完全合法**的檔案。現在 `errors.As(&http.MaxBytesError)` 分開回答。

⚠️ 出貨行為**沒有變**：`ugc.enabled` 出貨 false，而 `ui-cues.playerContent.submit`
出貨也是 false ⇒ 兩格 AND，這條路今天本來就關著。
