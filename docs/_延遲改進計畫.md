## 二、「延遲」其實是四種故障，修法完全不同

上一版最大的錯是**只針對甲**，而甲最貴、風險最高、最不可能是真兇。

| | 故障 | 手感 | 修法 | 目前證據 |
|---|---|---|---|---|
| **甲** | RTT + 沒有預測 | 鈍但**平順** | 樂觀預測 | 無 |
| **乙** | **伺服器丟 tick** | 一頓一頓、忽快忽慢 | 降低每 tick 成本 | **史前科**（見下） |
| **丙** | 每個客戶端收到全世界 | 尖峰卡 | 剔除 | **已確認結構** |
| **丁** | **客戶端每幀工作** | 全程掉幀、**手機主場** | 減少單位成本 | **已確認結構** |

### 乙的證據：#46 的「修法」會把症狀變成現在這樣

`match/tickLoop.ts` 檔頭：sim 中途停止 tick，**三次獨立目擊**。
修法是 `MAX_CATCHUP_TICKS = 5` 的 clamp + **丟掉超過的整個 tick 債**（`:85-88`）。
→ **那個 clamp 把「凍結」轉換成「無聲的變慢」。**

而 `plan.dropped` 為 true 時**唯一的輸出是一行 `console.warn`**
（`rooms/MatchRoom.ts:519-523`）。沒有計數、沒有指標、沒有 UI。
**如果伺服器每分鐘在丟 tick，我們現在完全不會知道。**

→ **最快的第一步不是寫程式，是讀線上日誌**找 `sim fell behind real-time`。一條指令。

### 丙的證據：零剔除

`net/snapshot.ts:189` 是 `for (const [id, t] of world.transform)` ——
**全世界每一個實體、送給每一個客戶端、每一次快照。**
而 `#67` 已確立「小地圖只顯示玩家自己那一區」——**玩家只跟自己那半場互動，卻在收兩區的資料。**
客戶端也照單全收：`GameApp.ts:965-976` 對每個實體都 `interp.push()`，不分 zone。

### 丁的證據：階梯管不到最貴的兩樣

`render/AdaptiveQuality.ts:29-38` 的降級順序是**解析度 → 粒子 → 陰影 → 繪製距離**。
它**碰不到模型面數，也碰不到實體數量**，而且是**由實際幀成本驅動的事後補救**——幀掉了才降級。

**而 #115 的 LOD 缺口不是「變體不存在」，是「產生出來了但執行期不去載」**：
實測 164 個資產裡 **83 個已經有 `-mid` / `-small`（51%）**，
`imported/`（英雄本體）129 個裡就有 **55 個**。
**檔案就躺在 `content/assets/models/` 裡沒人讀。**
→ 手機上**最便宜的一個大收益**：不用產生任何東西，只要接上載入路徑。

  `net/TimeSync.ts:37` 的 `renderTick(nowMs, delayMs = INTERP_DELAY_MS)` **延遲本來就是參數**；

## 七、資產優化到底有沒有用？

- **3D 模型**：只影響丁，但**丁在手機上是主場**，而且階梯管不到模型面數 → **1-3 是最便宜的大收益**

- **特效**：**這一項是真的** —— 洩漏的粒子/mesh 不回收 → 每幀成本**單調成長** →
  症狀是「**越打越鈍**」。owner 已親眼看到殘留。#262 在做，**它同時是延遲題**
