# 體素特徵生成 — 實作規格

> owner 2026-07-27 指示:體素要的是**特徵生成**。角色是一個直立矩形,從頭到腳的
> 色塊條碼就是那個角色的特徵主視覺顏色。範例(航海王三人):
> 香吉士 = 黃髮／膚／黑西裝／黑鞋;魯夫 = 草帽褐＋**紅帽帶**／膚／紅背心／藍短褲／
> **膚色小腿**／涼鞋;索隆 = 綠髮／膚／白襯衫／**黑腹卷**／深綠褲。
> 多拉A夢 = 藍頭＋黑眼＋紅鼻＋白臉＋紅項圈＋黃鈴鐺＋白肚＋藍腿＋白腳。
>
> 約束:**後台自動產出,但貼圖在地端生成。**

---

## 0. 先講一件會決定整個方向的事

**現有 #231 生成器的設計目標,跟 owner 要的是反的。**

`packages/shared/src/content/voxelSkin/generate.ts` 的成功標準是**「沒有兩個長一樣」**,
靠 hash + 關鍵字規則達成。它的檔頭明寫**刻意拒絕**取樣英雄圖示,理由是量到:

> 141 個圖示檔只有 **87 個不同 byte-hash**,**24 組重複**;一張圖同時是兩隻皮卡丘
> 和曹操孟德。取樣它會 **CLONE looks, not separate them**。

owner 要的是**「像不像本人」**。這兩個標準會打架 —— **兩個綠頭髮的角色,本來就該長得像。**

**所以這份規格不是改良現有生成器,是加一層權威壓在它上面**,只管我們知道「本人長什麼樣」
的那些角色;其餘 w3x 原創單位(沒有「本人」可比對的),現有 hash 生成器仍然是最好的答案,
一行都不刪。

### 兩個關鍵的既有事實

**① atlas 已經是逐面繪製。** `types.ts` 定義 `SkinPart = head | torso | armL | armR | legs`
× `BoxFace = front | back | right | left | top | bottom`,每個組合有自己的 `AtlasRect`。
→ **條碼的「部位內部垂直分帶」是在既有 rect 裡畫橫條,不需要改 UV 佈局。**

**② 臉部特徵已經有家。** `EyeStyle` / `MouthStyle` / `FaceMark` 已存在且畫在 head 的
front 面。→ **多拉A夢的黑眼＋紅鼻不需要新機制**,只需要把顏色接到條碼的臉部槽。

**③ 現有 `VoxelPalette` 是 7 個扁平槽**(`skin hair outfitPrimary outfitSecondary metal eye accent`)。
owner 的條碼是**有序帶堆疊 + 佔比**。這是 **schema 變更,不是換值** —— 必須誠實面對。

## 2. 特徵模型 —— 條碼是什麼

### 2.1 兩種帶

從三張範例圖讀出來的結構,分兩種,**兩種都是特徵**:

- **主帶**(12–28%):黃髮 / 紅背心 / 藍短褲 / 深綠褲
- **細帶**(1–5%):魯夫的**紅帽帶**、黑帽緣、索隆的**黑腹卷**、多拉A夢的**黃鈴鐺**

⚠️ **細帶不可當雜訊丟掉。魯夫拿掉紅帽帶,就只是「一頂褐色帽子」。**
辨識度有一半在細條上,任何「小於 N% 就併掉」的簡化都會殺死角色。

### 2.2 十一槽解剖表

| # | key | 槽位 | 典型佔比 | 歸屬部位 | 範例 |
|--:|---|---|--:|---|---|
| 1 | `hair` | 頭髮 / 帽 | 12–20% | head | 香吉士黃 · 索隆綠 · 魯夫草帽褐 · 多拉A夢藍 |
| 2 | `hatBand` | 帽帶 / 髮飾細條 | 2–4% | head | **魯夫紅帶** |
| 3 | `hatBrim` | 帽緣 / 瀏海細條 | 1–3% | head | 魯夫黑緣 |
| 4 | `face` | 臉 / 膚 | 8–14% | head | 三個都有 |
| 5 | `collar` | 頸 / 領 | 2–5% | torso | **多拉A夢紅項圈** |
| 6 | `chestTrim` | 胸飾細條 | 2–4% | torso | **多拉A夢黃鈴鐺** |
| 7 | `top` | 上衣軀幹 | 18–26% | torso | 紅背心 / 白襯衫 / 黑西裝 |
| 8 | `waist` | 腰 / 腹卷 | 3–8% | torso | **索隆黑腹卷** |
| 9 | `pants` | 下身 | 18–28% | legs | 藍短褲 / 深綠褲 / 黑西褲 |
| 10 | `shin` | 小腿(裸露) | 0–12% | legs | **魯夫膚色小腿**(香吉士沒有) |
| 11 | `shoe` | 鞋 / 腳 | 3–8% | legs | 涼鞋褐 / 黑皮鞋 |

每槽皆可缺席(`null`)。存在的槽,佔比正規化總和 = 1.0。

### 2.3 兩條結構規則

**① 同色相鄰帶不可合併。**
範例圖裡香吉士的黑西裝是**兩塊、中間留一條髮絲線** —— 那是上衣和褲子,只是同色。
合併它們會毀掉體素骨架的**髖關節**,人偶不能動。

> **色帶是外觀,分節是結構,兩者不可互相吃掉。**
> 實作上:`top` 與 `pants` 永遠是兩個獨立槽,即使 hex 相同。

**② 條碼是 1-D,臉不是。**
多拉A夢的**黑眼 + 紅鼻**不是環繞全身的帶,是**貼在頭部正面**的圖案。所以兩層:

- **底層**:條碼 → 環繞全身(6 面都畫)
- **面層**:眼 / 鼻 / 嘴 / 印記 → 只畫 head 的 `front`(既有機制)

### 2.4 手臂怎麼辦

`armL` / `armR` 不在條碼裡(條碼是**中軸剖面**)。規則:

```
sleeve = "long"  → 整支手臂 = top 色
sleeve = "short" → 上半 = top 色, 下半 = face 色(膚)
sleeve = "none"  → 整支 = face 色(膚)
```

索隆長袖、香吉士長袖、魯夫無袖。`sleeve` 是條碼規格的第 12 個欄位,不是帶。

## 3. 條碼從哪來 —— 四層權威

| 層 | 來源 | 權威 | 誰產生 |
|---|---|---|---|
| **L0** | **後台人工填表**(11 槽色票 + 佔比) | **最高** | owner |
| L1 | 從參考圖自動抽 | 助手,永遠可被 L0 覆寫 | 地端 `voxel:extract` |
| L2 | 從名字/描述的顏色詞抽 | 弱 | 純函式 |
| L3 | **現有 #231 hash 生成器** | 保底,保證不重複 | 既有程式碼 |

現有的四層 hash 鏈(L1 override / L2 keyword / L3 element / L4 hash)**整條降級成本表的 L3**。
`generate.ts` 一行都不刪。

> **理由**:115 位英雄裡真正「大家認得的名角」是少數。其餘 w3x 原創單位根本沒有「本人」
> 可比對,hash 生成器對它們仍是最好的答案。強行對它們套條碼只會產生更爛的結果。

## 4. 從圖抽色帶 —— 演算法與**它會怎麼壞**

### 4.1 演算法

1. **去背** — 取四角像素眾數當背景色,從邊緣 flood-fill(容差 ΔE ≤ 8)
2. **求 bbox**,高度正規化到 100 列
3. **每列取眾數色** —— **不是平均**
   > 平均會把紅+藍變成紫,而**紫色在角色身上根本不存在**。這是這步唯一會犯的致命錯。
4. **相鄰列 ΔE < 12 併段** → raw runs
5. **raw runs 對齊到 11 槽** —— 用 §2.2 的佔比先驗做匈牙利式最小成本指派
6. **量化**到既有 `palette.ts` 的調色盤(保留 `Tone` 表)

### 4.2 故障表 —— 先寫下來,否則會安靜地出貨爛泥

| 故障 | 症狀 | 守衛 | 裁決 |
|---|---|---|---|
| w3x 圖示有黑外框 | 首/末帶變成框色 | 先裁外框;首末帶若 ΔE(框色) < 10 就丟棄 | 自動修 |
| 背景非單色 | 整條變背景色 | 去背後前景像素 < 40% | **FAIL** |
| 反鋸齒混色 | 帶色是不存在的中間色 | 取眾數 + ΔE 併段 | 自動修 |
| 角色沒填滿畫框 | 佔比先驗全錯 | bbox 高 < 60% 畫框 | **SUSPECT** |
| **全部帶顏色都差不多** | 一根泥巴柱 | **帶間最大 ΔE < 25** | **FAIL** |
| **圖示重複** | 24 組拿到一模一樣的條碼 | 條碼 hash 撞號 | **DUPLICATE** → 強制人工 |
| 帶數過少 | 只抽出 2–3 帶 | 有效帶 < 4 | **SUSPECT** |

⚠️ **最後兩條不是假想。** `generate.ts` 已量過「141 檔 / 87 個不同 hash / 24 組重複」——
**DUPLICATE 保證會發生**,守衛不是防禦性編程,是已知需求。

### 4.3 裁決三值 + 一值

`PASS` / `SUSPECT` / `FAIL` / `DUPLICATE` —— 與 `scan_ability_effects.py` 同一個形狀。
後台只讓 owner 看 **SUSPECT + FAIL + DUPLICATE**;PASS 的摺疊起來。

## 5. 後台做什麼 / 地端做什麼

owner 的約束:**貼圖在地端生成**。切點:

### 5.1 後台(server)—— 只碰 JSON,一個像素都不碰

- **條碼編輯器**:11 槽 × (顏色 + 佔比) + `sleeve` + 臉部三槽
- **預覽 = 純 CSS 疊色塊** —— 長得跟 owner 給的範例圖一模一樣
  > 這是整個設計最好的一點:**後台不需要任何圖形函式庫就能所見即所得**,
  > 因為條碼的視覺表示**就是**一疊 `<div style="height:N%;background:#hex">`。
- **裁決表**:批次抽取的結果,只顯示需要人看的那幾筆,勾選核准
- 核准 → 寫進耐久 overlay(與 #189 同一條路)

### 5.2 地端(local)

```bash
pnpm voxel:extract   # 讀參考圖 → 條碼草稿 + 裁決表   (讀圖必須在地端)
pnpm voxel:build     # 讀已核准條碼 → PNG + glb        (產貼圖必須在地端)
```

`build` 走既有管線:`voxel/texture.ts` 出 atlas → `pngWrite.ts` → `glbWrite.ts`,
產物落 `content/assets/`,再由既有 `pnpm content:build` 收進 bundle。

### 5.3 契約

> **條碼規格 JSON 是唯一契約。後台永遠不產生像素,地端永遠不決定顏色。**

這條界線讓兩邊各自演進而不互相破壞,也讓「後台自動產出」與「貼圖地端生成」兩個
看似衝突的要求同時成立。

## 6. 資料結構(要加進 `voxelSkin/types.ts`)

```ts
/** 一條帶。null 代表這個槽在這個角色身上不存在。 */
export interface BarcodeBand {
  /** '#rrggbb' */
  hex: string;
  /** 佔全身高的比例,0..1。存在的帶總和必須 = 1.0(±0.001) */
  frac: number;
}

export type BarcodeSlot =
  | "hair" | "hatBand" | "hatBrim" | "face"
  | "collar" | "chestTrim" | "top" | "waist"
  | "pants" | "shin" | "shoe";

export interface VoxelBarcode {
  v: 1;
  championId: string;
  /** 十一槽,缺席為 null。順序固定,不可重排(它就是解剖順序)。 */
  bands: Readonly<Record<BarcodeSlot, BarcodeBand | null>>;
  sleeve: "long" | "short" | "none";
  /** 臉部三槽的顏色;款式沿用既有 EyeStyle/MouthStyle/FaceMark */
  faceColors: { eye: string; nose: string | null; mouth: string };
  /** 這條碼是誰決定的 —— 稽核用,不可省略 */
  source: "manual" | "extracted" | "keyword" | "generated";
  /** extracted 才有 */
  extraction?: {
    refImage: string;
    verdict: "PASS" | "SUSPECT" | "FAIL" | "DUPLICATE";
    reasons: string[];
    maxPairwiseDeltaE: number;
    foregroundRatio: number;
  };
}
```

**`source` 欄位是強制的。** 沒有它,三個月後沒人知道某個難看的角色是 owner 親自指定的
還是抽取器出的包 —— 而這兩者的處理方式完全相反。

## 7. 條碼 → 3D

```
bands 1–4  (hair/hatBand/hatBrim/face)      → head  的 6 面,垂直分帶
bands 5–8  (collar/chestTrim/top/waist)     → torso 的 6 面,垂直分帶
bands 9–11 (pants/shin/shoe)                → legs  的 6 面,垂直分帶
sleeve                                      → armL/armR 的分帶規則(§2.4)
faceColors                                  → head.front 的既有 decal 機制
```

每個部位內部,把該部位的帶按 `frac` 正規化到該部位的 `AtlasRect` 高度,畫橫條。
**實作點:`voxelSkin/paint.ts`**,它現在畫的是 style 驅動的形狀,要加一條
「若有 barcode 則先鋪底帶」的路徑;既有 style 繪製留在上層(帽子輪廓、圖騰等)。

## 8. 驗收 —— 怎麼不變成「做了但玩家拿不到」

這一節是 v0.9.1 的教訓直接套用。這個 repo 的頭號故障是「做了但玩家拿不到」,
已知**七種**形狀,其中兩種是 v0.9.1 才抓到的(源碼掃描 / 屬性掃描)。

| | 斷言 | 判定 |
|---|---|---|
| ❌ | `barcode.bands` 有 11 個 key | 證明不了任何像素 |
| ❌ | 後台表單有 11 個 `<input>` | 證明不了**存出去的內容** |
| ❌ | `expect(src).toMatch(/paintBarcode/)` | **源碼掃描** —— 證明那行被打進檔案,不證明它跑過 |
| ❌ | 讀 `aria-label` 或 `data-*` 確認顏色 | **屬性掃描** —— 屬性不是像素 |
| ✅ | **產出的 PNG,每一帶中心點取像素 === 規格 hex** | 貼圖是產物,只有像素能作證 |
| ✅ | 後台預覽讀回**實際 inline background-color**,且套 CSS 隱形黑名單 | |
| ✅ | 普查:每個白名單英雄都有條碼,且**沒有一個 maxPairwiseΔE < 25** | 泥巴柱普查 |
| ✅ | **同色相鄰帶仍是兩個槽**(香吉士 top === pants 但 `bands.top !== bands.pants` 物件) | 護住髖關節 |

### 必跑的變異(每個都要紅)

1. `texture.ts` 的帶色全部寫死成第一帶 → 像素斷言必紅
2. `paint.ts` 的 barcode 路徑加 `if (false)` → 像素斷言必紅
3. 把 `top` 與 `pants` 在同色時合併 → 結構斷言必紅
4. 抽取器的 `maxPairwiseDeltaE` 守衛改成永遠回傳 999 → 泥巴柱普查必紅
5. 後台存檔時改送出貨預設值而非使用者編輯 → 存檔內容斷言必紅

> 第 5 條是 v0.9.1 ⑤ 的原始缺陷(`M2 payload 改由 shippedForm() 生`),
> 已知會發生,不是假想。

## 11. 這份規格**沒有**解決的事(誠實記錄)

- **側面輪廓**。條碼是中軸剖面,對「有大側影特徵」的角色(超大翅膀、背後巨劍)
  沒有表達力。那些走既有 `motifs`(head/shoulder/back),與條碼正交。
- **漸層與圖案**。條碼是純色帶。條紋衫、格子裙、迷彩無法表達。目前判斷:
  體素尺度下這些本來就會糊掉,**不做**;若日後要,是在帶上加 `pattern` 欄位。
- **抽取器的通用正確性**。§4.2 的守衛只擋**列舉出來的**故障。這個類別無界
  (半透明、陰影、多角色同框……),守衛表會隨遇到的案例成長,不會一次到位。
