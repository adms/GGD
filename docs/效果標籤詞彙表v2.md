## 怎麼讀這份表

### 狀態只有三個記號

| 記號 | 意思 | 編輯器該怎麼呈現 |
|---|---|---|
| **✅** | 引擎裡就是這個原語，今天可用 | 正常選項 |
| **🧩** | 由現成原語**組合**而成，出貨成一個具名預設（preset） | 正常選項，展開後可以逐格微調 |
| **🔨** | 要動程式，[補完計畫](ability補完計畫.md)裡有它的批次 | ⛔ **標成「開發中」並禁止選取**，不要讓它看起來可用 |
| **💤** | owner 2026-08-04 裁決**這一輪不做**，保留在表上當參考 | ⛔ 不出現在下拉選單，只出現在文件 |

⛔ **「🔨 未完成的 token 出現在可選的下拉選單裡」是這個專案已經發生過的缺陷**
（`onLevelUp` 今天就是：後台選得到、sim 裡零個發射點）。
編輯器的狀態記號不是裝飾，是防止作者寫出啞卡的閘。

### 「能不能用」是兩欄，不是一欄

v1 最大的錯是把這兩件事混成一個 ✅：

- **原語在不在** —— 引擎有沒有這個機制
- **誰寫得出來** —— 這個機制的授權格開在哪幾種文件上

【格擋】的原語**完全存在**（`combat/block.ts` 是完整實作），但它的授權格
**只開在道具上** —— 技能、天生技、三選一增益卡都寫不出來。
v1 把它標成 ✅，於是一張寫了格擋的增益卡會安靜地什麼都不做。

所以層 5 有一張[授權矩陣](#授權矩陣)，而每一列都標了它的授權格。

### 每一列都有殭屍欄

| 記號 | 意思 |
|---|---|
| **🧟✅** | 對殭屍生效 |
| **🧟❌** | 對殭屍**靜默無效**，沒有任何錯誤訊息 |
| **🧟🔨** | 今天無效，[補完計畫 A3](ability補完計畫.md#a3--殭屍-statscomp--statuscomp) 之後生效 |

**為什麼這一欄要升格**：第 3 場之後殭屍波開始，場上**大多數敵人是殭屍**。
一個標著 ✅ 而 🧟❌ 的效果，在半個遊戲裡是不存在的。
v1 把這件事寫在一格註解裡，於是它讀起來像註腳，實際上它決定卡片值不值得做。

⚠️ **owner 2026-08-04 已裁決給殭屍建 StatsComp 與 StatusComp**（推翻同日上午的「不作」）。
所以本表的 🧟❌ 大多會在 A3 之後變成 ✅ —— 但**在 A3 出貨之前，🧟❌ 就是 🧟❌**。

## 四層，不是五層

> owner 2026-08-04：「**[層 3 觸發時機] [層 4 條件] 這兩個不是很像嗎？
> 應該說是同一個池子裡，只是放在觸發、還是判斷條件而已，不應該是分開兩種放。
> （層 3、4 保留但選項共用）**」

**這個觀察是對的，而且它有一個乾淨的形式：**

> **一個謂詞有兩種讀法。**
> 問「**現在成不成立？**」＝ 條件（level）。
> 問「**什麼時候變成成立？**」＝ 觸發（edge）。
>
> 同一個謂詞「血量低於 35%」，當條件時是「只有他殘血才算數」，
> 當觸發時是「他血量**掉破** 35% 的那一刻」。
> **兩個欄位保留（`HookDef.on` 與 `HookDef.condition`），但選項來自同一個池子。**

所以本表是四層：

| 層 | 是什麼 | 引擎欄位 | 例 |
|---|---|---|---|
| **1 · 效果種類** | 原子動作 —— 發生了什麼 | `EffectDef.kind` | `damage` / `dot` / `leap` / `shield` |
| **2 · 狀態軸** | 掛在身上的持續性修改 | `applyStatus` 的具名欄位 | `stun` / `root` / `moveSpeedMult` |
| **3＋4 · 謂詞池** | 什麼時候 / 什麼情況 | `HookDef.on` ∪ `HookDef.condition` | 擊殺時 · 血量低於 X% · 這一發是暴擊 |
| **5 · 授權格** | 哪一種文件宣告得了哪一種能力 | 各 schema 的欄位 | 卡片今天只有 `modifiers` + `hooks` |

**具體例子**：`【暈眩】` 和 `【焚身】` 看起來同類，在引擎裡分屬不同層 ——
- `【焚身】` 是**層 1** 的 `dot`（一個效果種類）
- `【暈眩】` 是**層 2** 的 `stun`（`applyStatus` 上的一個布林）

所以「給我一個暈眩效果」在引擎裡不存在。正確寫法是
**「發一個 `applyStatus`，把 `stun` 這一軸打開」**。

# 結構事實（不是標籤，但會撞到的牆）

這七條會讓上面整批 ✅ 在某些情境落空。**編輯器要把它們變成畫面上的提示，不是文件裡的小字。**

### ① 殭屍身上吃不到 `applyStatus` / `applyBuff` / `grantAttribute`

`packages/shared/src/sim/mobs.ts` 只建 `transform` / `health` / `nav` / `team` / `mob`
（＋ boss 的 `flight`），**從不建 StatusComp 也不建 StatsComp**。後果逐條可驗：

- `applyStatus.ts:22` `const st = world.status.get(target); if (!st) continue;` → **靜默跳過**
- `statPipeline.ts:233` `attachSource` `const sc = world.stats.get(id); if (!sc) return;` → **靜默跳過**

所以【暈眩】【定身】【減速】【詛咒】【暴走】【破甲】【破魔】【虛弱】【易傷】【凋零】
【重創】【冷凍】【石化】對整波殭屍**一律零效果，而且沒有任何錯誤訊息**。

相對地走自己 store 的四個是有效的，**那就是要抄的形狀**：
`taunt`(`world.taunt`) · `knockback`(`world.knockdown`) · `invulnerable`(`world.invulnerable`) ·
`dot`(`world.dot`，只要有 HealthComp)。

⭐ **owner 2026-08-04 裁決：建 StatusComp + StatsComp，但輸出那一段不做。**

實作分三段，**只做前兩段**：

| 段 | 做什麼 | 做不做 | 之後這些標籤在殭屍身上 |
|---|---|---|---|
| A3a | `mobs.ts` 加一行 `world.status.set(id, {effects: []})` | ✅ **已出貨 v0.9.39** | 【暈眩】【定身】【減速】【詛咒】【暴走】【沉默】【恐懼】【睡眠】【標記】→ 🧟✅ |
| A3b | 給殭屍 StatsComp | ⛔ **owner 第二輪裁決：不做** | 【破甲】【破魔】【破防】【易傷】**永久 🧟❌** |
| A3c | 讓殭屍的**輸出**讀 StatsComp | ⛔ **不做** | 【虛弱】【凋零】**永久 🧟❌** |

⚠️ **A3b 比原本估的貴，這是砍掉它的原因**：`stats/statPipeline.recomputeStats`
第一句是 `if (!sc || (!champ && !sm)) return;`，而且下一行 `Champions.get(sc.championId)`
—— 殭屍兩者都沒有，所以給它一個 StatsComp 之後管線會**直接跳過它**。
那不是「惰性建立就好」，是要教屬性管線認識**第三種身體**。

⛔ **編輯器要把 A3c 的後果寫在畫面上**：作者選了「降低攻擊力」類的 debuff 時，
要提示「**這個效果對殭屍無效**」。否則會做出一張在殭屍回合半殘的卡。

⚠️ **A3b 有一個必須擋的靜默陷阱**：`MovementSystem.ts:179` 是
`world.stats.get(id)?.final[Stat.MoveSpeed] || (world.mob.has(id) ? mobSpeed : BASE_MOVE_SPEED)`
—— 用的是 `||`。殭屍一旦有 StatsComp 而 `MoveSpeed` 非零，`mobProfile` 的三段速度
（一般／特殊／殭屍王，#262 特地分開的）會被**完全繞過且無錯誤**。

> ⚠️ **v1 這一段有一處錯**：它寫「全 repo 只有兩處建 StatsComp」。
> 實際是**三處** —— `spawnChampion.ts:70` · `summons.ts:181` · **`auraCarrier.ts:286`**。
> 第三處是靈氣載體，A3 要一起考慮。

### ② 火圈不走傷害佇列，所以所有 hook 對它一次都不發

`sim/fireRing.ts:1172` 與 `systems/FireRingSystem.ts:98` 都是 `hp.hp -= dmg` **直接扣血**
＋ 發一個 `fireRingDamage` 事件，**完全不進 `world.damageQueue`**。

後果三條：`onDamageTaken` / `onDamageDealt` 對火圈不發、`invulnerable.blocksTrueDamage`
對它無效（該檔檔頭 ⑤ 自承）、任何「受傷時」的卡片在火圈裡不動作。

⛔ **owner 2026-08-04（第二輪）裁決：A1 不做。這三條因此是永久事實，不是待補的缺口：**

1. **任何寫「受傷時 / 造成傷害時」的卡片，在火圈裡不會觸發。**
   → 卡片文案不可以承諾「站在火圈裡也會⋯」這一類行為。
2. **`invulnerable.blocksTrueDamage` 對火圈永遠無效**
   （`FireRingSystem.ts` 檔頭 ⑤ 自承的那個 bug 不修了）——
   所以「免疫真傷」的卡片在火圈裡**不會保護玩家**，文案要避開。
3. 未來的易傷／反彈也看不到火圈。

⚠️ 編輯器應該在作者選 `onDamageTaken` / `onDamageDealt` 時，
把這件事寫在欄位說明裡 —— 否則它是一個「卡上寫了、火圈裡沒有」的靜默落差。

### ③ `ENTITY_FLAG` 的位元用完了 —— CLAUDE.md 那句是過期的

`protocol/schema.ts:942` 是 `export const ENTITY_FLAG_FREE_BITS = [] as const;`，
第 938 行註解逐字「THE BUDGET IS NOW EXHAUSTED — ZERO BITS LEFT」，
而 `formFlags.test.ts:125` 有一條 `expect(ENTITY_FLAG_FREE_BITS).toEqual([])` 在守。

- **好消息**：`statusIds` + `statusRemainTicks` 兩條平行陣列已經在線上（`schema.ts:137/146`），
  **逐座位只送自己的** → 任何新的 status 文件會自動出現在自己的 HUD 上帶名字與倒數、**零接線**。
- **壞消息**：任何「**別人也看得到**」的狀態（敵人身上的破甲光環、隊友的冰凍外觀、
  頭上的標記）今天**沒有頻道**。

⭐ **owner 2026-08-04 裁決：開頻道（「yes」）。**
→ 「別人也看得到的狀態」**變成做得到的**，編輯器可以開放這一類設計。

⚠️ 但它是全計畫**唯一不可逆的一步**，所以有排程約束：
**所有要上線的欄位合併成一次 `defineTypes` 追加**，排在最後
（見 [E2](ability補完計畫.md#e2--wire-頻道)）。
編輯器實作時：**不要自己偷加 wire 欄位**，把需求登記到那張表上。

⚠️ 澄清一個常見誤讀：`ENTITY_FLAG_FREE_BITS = []` 說的是**旗標位元**用完了，
**不是**「不能再加欄位」。`EntityState` 追加一格 `float32` / `uint16` 是合法路徑。

### ④ 形狀烘進 kind 名字，沒有共用的 `shape` 欄位

`spawnProjectile` 是**真的**把形狀與效果分開了（projectile doc 管 speed/range/hitRadius/pierce，
`onHit` 才是效果），而 `damage` / `damageArea` / `damageLine` **把形狀烘進 kind 名字**。

後果可以數：同一個「圓形 AoE 傷害」有兩條寫法且射程換算待遇不同；
`heal` / `applyStatus` / `knockback` / `shield` **沒有** Area 或 Line 版本（24 個 kind 逐一對過），
「範圍治療」「範圍暈眩」今天要靠 `tpl-proxy-fanout 範圍逐一施法` 繞。

⚠️ **每加一個新 kind 就多欠一組 Area/Line/Cone 版本 —— 這個債會相乘。**

⭐ **owner 2026-08-04 裁決：「新 kind 一律帶 `shape`」。**

→ **這是編輯器要遵守的硬約束**：本輪新增的每一個 effect kind 都帶
`shape: single | circle | line | cone`（＋ circle/cone 的 `radius`、line 的 `length`/`width`）。
既有 `damage` / `damageArea` / `damageLine` **原封不動**，零文件改動。

→ 實際效果：`dispel{shape:"circle", radius}` 就是**範圍淨化**（天生牙那一件直接用得上），
不用再發明第二個 kind。編輯器的形狀選擇器**對新 kind 一律出現，對舊三個不出現**。

# 編輯器必須做的七件事

不做這七件，作者會做出「卡上寫了、遊戲裡沒有」的東西 —— 那是 `CLAUDE.md`
列出的**失敗形態 ②**（做了但玩家拿不到），這個專案已經踩過很多次。

### 1 · 🔨 與 💤 的 token 不可以看起來可用

下拉裡出現一個選得到但零發射點的事件，就是今天 `onLevelUp` 的狀態。
**標成「開發中」並禁止選取**，或乾脆不出現。

### 2 · 每一格都要顯示「對殭屍生效嗎」

不是小字，是圖示。作者選了 `enemyChampion` 當觸發對象時，
編輯器應該當場提示「**這個觸發在殭屍身上不會發動，而第 3 場之後場上大多是殭屍**」。

### 3 · 觸發與條件共用一個下拉，但要按「觸／判／封」三欄過濾

選了不帶封包的事件（`onKill` / `onInterval` / `onLevelUp`）之後，
所有帶 **封** 的謂詞要灰掉。⛔ **這個檢查今天已經存在於載入期**
（`effect.ts:1198` 的 refine）—— 編輯器的工作是把它提前到編輯當下，
不是重寫一份會漂移的第二套規則。

### 4 · 每一個「A 還是 B」都要是欄位，不是註解

`CLAUDE.md` 第一守則。編輯器上每一格參數都要能存進 `content/`，
而 `content/` 是 **live bind-mount** —— 改一次不用重建映像。

### 5 · 說明文字要寫「它影響什麼」，不是複述欄位名

而且**語意改了，舊文案就是謊話，必須一起改**。

### 6 · 數值欄位要有上界，不是只有下界

`validateField` 在 2026-07-29 之前只檢查 `min`，所以 50 打成 500 會過後台、
在下游才被拒或被靜默夾掉。

### 7 · 一個新欄位要同時落在三個地方

1. `content/config/*.json` —— 出貨值
2. `packages/shared/src/content/schema/config.ts` —— Zod schema（**上下界都要**）+ `DEFAULT_*`
3. `apps/admin/src/*.ts` —— `SHIPPED_*` + 欄位 union + 順序 + 標籤 + 分組 + `configFromForm`

⚠️ 如果那個欄位也走 Go 平台，`apps/platform/internal/*` 的鏡射**一定要一起改** ——
key 不在 Go 那份，平台會把它從它服務的每一張表丟掉，後台看不到也改不了。

| `internalCooldownScope` | `source`（預設）\| `perAbilitySlot` | 冷卻的作用域 |
| `chance` | 0 ~ 1 | 機率（省略＝必定） |
| `chanceFrom` | `{attr: str\|agi\|int, basis: base\|total, coeff, min, max}` | 機率由屬性推導（朗基努斯之槍那種「敏捷越高機率越高」） |
| `condition` | `zEffectCondition`（E-5） | 什麼情況才算數 |
| `target` | `self` \| `event` \| `allies` | 效果打在誰身上 |
| `victim` | `champion\|mob\|any\|enemyChampion\|allyChampion\|enemy` | 事件對象要是哪一種 |
| `damageSource` | `any\|basic\|nonBasic\|ability\|other` | 這一發傷害的來源要是哪一種 |

⛔ **順序是硬約束**：`victim` / `damageSource` / `condition` 這三道閘必須在
`internalCooldown` 與 `chance` **之前**。插到骰子後面會讓被擋掉的一發也抽籤，
**每一份既有錄影的亂數流整條位移**。

## E-5 · 條件樹（`HookDef.condition`）—— 今天只有 3 種葉子
