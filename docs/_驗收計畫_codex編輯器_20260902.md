# 驗收計畫：Codex 特效編輯器（2026-09-02）

> ⭐ **驗收標準不是「八招好不好看」** —— owner 2026-09-01 逐字：
> 「**八個驗收技能特效是用來驗收編輯器是否能做出對應技能，不是直接套用回去遊戲主程式中**，

## 1. 契約對帳（⭐ 機器，零人力，幾分鐘）

**分母（量到的）**：`ggd-editor-coverage.json` `_total` = **5,137 格**

| 類 | 數 | ⭐ 驗什麼 |
|---|---:|---|
| `required` | **5,137** | 編輯器**暴露了幾格**？未暴露的逐格列名 |
| `notRequired` | **15** | ⛔ 引擎今天做不到 ⇒ ⭐ **編輯器做出控制項就是紅**（做出來的內容上線是死的）|
| `ownerOnly` | **39** | ⭐ 可唯讀顯示，⛔ **做成可調控制項就是紅** |

⭐⭐ **⛔ 只從一頭掃會結構上失明**（本 repo 的綠燈假象⑫）——**兩頭都要走**：

| 方向 | 問題 | ⛔ 漏掉什麼 |
|---|---|---|
| 契約 → 編輯器 | 每一格**被暴露**了嗎？ | 漏掉「編輯器有而契約沒有」的 |
| ⭐ 編輯器 → 契約 | 每一個控制項**在契約裡查得到**嗎？ | ⭐ 查不到 ＝ **編輯器自己猜了一個欄位** ⇒ 它產的 JSON 會被引擎拒絕 |

**指令**
```bash
pnpm editorcov:build          # 先把契約重生成（⛔ 對舊契約驗＝驗了一個過期的分母）
pnpm caps:export              # runtime-capabilities 同步
# 然後由編輯器側輸出一份「我暴露了哪些欄位」的清單，兩邊做集合差
```

## 2. ⭐⭐ 往返驗證（**最重要的一層**，機器）

⭐ **這是唯一問「兩個名詞的關係」的一層**，其餘各層問的都是名詞。

```
編輯器產出的 JSON
   → 出貨的 ContentLoader（嚴格 Zod）
   → 出貨的 sim（真的跑一場）
   → 斷言「機制真的發生了」
```

| ⛔ 不夠 | ⭐ 要有 |
|---|---|
| 「JSON 通過 schema」 | schema 過**不代表**引擎會做那件事（本 repo 的失敗形態⑧：case 存在但第一行讀零寫入端的欄位就 break） |
| 「編輯器預覽看起來對」 | 預覽是**編輯器自己畫的**，⛔ 不是遊戲畫的 |
| 「檔案存得下來」 | 出貨的 bundle 要**真的載得進去**（2026-08-02 的事故就是這一格） |

**⭐ 驗收條件**：把六（八）招的編輯器輸出丟進 `pnpm content:build` ＋ 跑真的 sim ⇒
每一招**列名的機制**逐條被觀測到（傷害有發、狀態有掛、模型有生成事件）。

⚠️ ⭐ **量尺要雙向校準**（`calibrate()`）：
先拿一份**已知會動**的技能量到「有」，再拿一份**已知壞掉**的量到「沒有」。
⛔ 只驗「應該有」那一邊的量尺，會在它最該說話的時候沉默。

## 3. ⚠️ `partial` 那 30 個 —— ⭐ 最危險的一格

**量到的**：`ggd-runtime-capabilities.json` 宣告 **supported 16 · ⭐ partial 30 · unsupported 15**

⇒ ⭐⭐ **半數的能力是「一半能用」** —— 而編輯器最容易在這裡騙人：
控制項有、拖得動、存得下去，⛔ **而引擎只做了其中一半**。

**⭐ 每一個 partial 要問兩題：**
1. 編輯器有沒有**告訴使用者哪一半不能用**？（⛔ 沉默 ＝ 使用者會做出上線即死的內容）
2. 那個「不能用的一半」在往返驗證（第 2 層）裡**會不會紅**？

⛔ 若兩題都是否 ⇒ ⭐ **那不是編輯器的缺陷，是契約說謊** ⇒ 回頭修 `caps:export` 的宣告。
