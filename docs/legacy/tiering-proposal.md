# 五級分帶提案 —— 英雄屬性 / AoE 範圍 / 技能 CD 與 MP

> 產生於 2026-08-11。三條線的量測 + 一輪複驗合併。
> ⛔ 本文件**沒有動過任何 `content/` 檔案**。所有「要改什麼」都是提案。

---

## 一、三句話

1. **量到什麼**：用出貨的 `championStatBase()` 把 119 份英雄文件重算到 lv10，八項屬性**全部都有分布可以分帶**；AoE 那 29 支「全場命中」是**誤報**（實際 3.0–9.41，遠小於決鬥區半徑 24），但另有 **2 支**裸 `radius` 技能真的蓋滿全場；技能成本方面 owner 要求的「單體 vs 範圍差 2~4 倍」在出貨資料裡**四個指標全部不成立**（實測 1.00–1.50 倍），而且 **MP 現在根本不是成本**（93.7% 的技能在自己冷卻轉完前就回滿魔）。
2. **哪些可以直接做**：攻擊距離與移動速度是**純 `baseStats`**，改了不牽連任何其他屬性 —— 這兩項可以直接落地。AoE 四級制、以及 25 支 T0 硬傷裡的「宣告範圍但引擎打不到別人」也都是明確的修正。
3. **哪些需要你拍板**：⚠️ **有一題必須先答，否則後面所有數字都沒有意義** —— 你指定的五格數值（1.5/3/5/7/10 等）是**填進卡片的值**，還是**玩家實際打得到的值**？出貨的倍率鏈會讓兩者差 1.67 倍（攻擊距離）到 4 倍多 650（生命）。其餘決策集中在第五節三張清單。

## 二、量測基礎（先講清楚數字打哪來）

### 2.1 戰力公式 —— 任務書給的版本是錯的

任務書寫「戰力 = `baseStats` + `growth` × (等級−1)」。出貨的法則是**三層**
（`packages/shared/src/sim/stats/attributes.ts`）：

```
stat(L) = baseStats + attr(L)·coefficient + growth·(L−1)
```

漏掉中間那一項，正好製造出「魔抗只有 4 種相異值、AP 全部是 0」的錯覺 ——
AP 的 `baseStats.ap` 確實全部是 0，因為 **AP 100% 來自智慧**。補回去之後：

| 項目 | 只看 baseStats | 出貨公式（116 位） |
|---|---:|---:|
| 魔抗 | 4 | **71** |
| AP | 1 | **70** |
| 生命 | 40 | 74 |
| 攻速 | 15 | 90 |
| 防禦 | 27 | 80 |
| AD | 60 | 84 |

➡️ **任務書「魔抗與 AP 沒有分布可以分帶」這一條被推翻。** 八項全部可以分帶。
（真正分不了帶的東西是另一回事，見第四節。）

### 2.2 母體：119 列 / 116 位

`docs/engine-tiers.json` 有 **119 列**，但界線只由 **116 位真英雄**長出。
排除 3 份：`sela`、`thorne`（內容載入失敗時的骨架替身）、`godie-zombiex`（小怪側喪標麥可）——
`attributes.source = authored`，不是被設計出來的英雄。三份仍保留在表裡並標 `inDistribution: false`。

⚠️ **本文件所有計數一律以 116 為分母**，並在每處標明。
（⚠️ 上一版報告的正文引 119、交付的 JSON 用 116，兩邊對不起來 —— 已修正。）

⚠️ `hero.coupling` 的同帶率（AP↔魔抗 72.3%、生命↔AD 46.2%、攻速↔防禦 24.4%）
是用 **119** 算的，混進了三位骨架替身。**未以 116 重算** —— 方向可信，小數點請勿引用。

### 2.3 界線用 Jenks 自然斷點，不是等分位

攻擊距離 116 位裡有 **76 位並列在 1.6**（65.5%）。等分位的四個切點算出來是
`1.6 / 1.6 / 1.6 / 7.3` —— 三個相同，前三帶是空的。改用 Jenks 自然斷點
（一維最小類內平方差 DP 精確解，無隨機、可重現），界線落在資料自己的縫隙上。
兩種切點都輸出到 JSON，`quintileDegenerate` 旗標標出哪幾項會塌。

### 2.4 ⚠️ 卡面值 ≠ 玩家吃到的值

出貨 `content/config/combat-env.json` 有九個非 1 的倍率會落在這八項上，
`content/config/base-bonus` 再加基礎加成（在所有倍率**之後**）：

| 項目 | 倍率鏈 | 額外 |
|---|---|---|
| 攻擊距離 | `attackRange` ×0.6 | **再 × 體型倍率**（見下） |
| 生命 | `maxHealth` ×4.0 | **+650**（倍率之後） |
| 魔抗 | `defense` ×1.0 × `magicResistMult` ×0.2 | — |
| 移動速度 | 近戰 ×0.8 / 遠程 ×0.6 | — |
| 攻速 / 防禦 / AD / AP | ×1.0（中性） | — |

**所以「極大 = 10」寫進 `baseStats.range`，玩家實際攻擊距離是 6.0**
（決鬥區半徑 24 的 25%）。

### 2.5 ⚠️ 體型 → 射程：第 10 個倍率，上一版漏了

`finalizeStat`（`packages/shared/src/sim/baseBonus.ts:233-236`）對 `Stat.AttackRange`
**額外乘一個 `rangeScale`**，而出貨的 sim 真的餵它
（`packages/shared/src/sim/stats/statPipeline.ts:196`）：

```ts
rangeScale: attackRangeScaleFactor(def.bodyScale, world.bodyScaleRules)
```

`content/config/body-scale.json` 是 `enabled: true`，斷點表 `1→1.0 / 2→1.2 / 3→1.3`
（中間線性內插，兩端夾住不外推 —— 所以 `bodyScale < 1` 的 8 位倍率仍是 1.0）。

### 3.2 AoE 範圍四級

#### ⛔ 先講結論：GH#310 是誤報

`expand.ts:318` 對 `unit: "wc3u"` 的 slot 一律套 `toLen()` = **×11/600**，
而 `tpl-instant-blast` / `tpl-proxy-cast` / `tpl-ground-nova` 的 `radius` slot
**全部宣告 `"unit": "wc3u"`** —— 換算本來就有做。

實跑 `expand()` 對全部 29 支：**29/29** 的輸出與文件既有的 `radius` 欄位吻合到小數兩位
（513.5→9.41、500→9.17、327→6.00、163.5→3.00）。再跑 `registerAll()` + `Abilities.get()`，
`AbilityDef.radius` = 9.41 / 9.17 / 6.00。**實際生效半徑 3.0–9.41，全部遠小於決鬥區的 24。**

誤報來自量尺自己：`tools/engine-atlas/atlas.ts:281` 對整個 `AbilityDef` 做 `walk()`
收集所有叫 `radius` 的數字再取 `Math.max`，而 `mergeExpansion` **刻意保留**
`def.template.params` —— 於是 max 挑中了作者填的**未換算輸入** 513.5。
（失敗形態⑤：被測的不是出貨的那個。）

➡️ **四級制本身仍然值得做，但它是「設計統一」，不是「修 bug」，優先序應該重排。**

#### ⚠️ 但真的有 2 支蓋滿全場（都是裸 `radius`，不是模板）

| 技能 | 英雄 | radius | 說明 |
|---|---|---:|---|
| `godie-o00k.passive`「86-00 裝可愛」| 皮卡娘 | **29.33** | = 1600 × 11/600。換算是對的，但原作 1600 就是近乎全圖的嘲諷 |
| `godie-efur.r`「13-04 龍星群」| 揍敵客桀諾 | **24** | 出貨描述自己寫「半徑 24.0 單位 —— 那是一整個決鬥區的半徑，講白了就是全場」 |

⚠️ 上一版只找到第一支，因為普查用嚴格 `> 24` 過濾，**剛好等於 24 的被濾掉了**
（跟 `atlas.ts` 犯的是同一種錯：過濾條件把要找的東西排除掉）。
`godie-efur` **不在** `roster.json` 的 `retiredChampions`（那裡只有 `godie-e00u`、`godie-u01f`），
且 task #212「開放英雄名單 +2：賈修、揍敵客」已完成 —— **是活的英雄**。

## 四、⚠️ 如實標出：哪些地方分布撐不起五帶

任務書預期的兩項（魔抗、AP）**其實可以分帶** —— 那個預期來自一個漏了三圍的公式。
但**確實有東西撐不起五帶**，只是位置不同。以下逐條，不粉飾。

### 4.1 英雄屬性：11 格薄帶（<5 人）

那一格的值是由一兩位英雄的現值決定的，**不是分布給的**。
你對攻擊距離就是直接指定的 —— 這幾格同理，**請直接指定**：

| 項目 | 薄帶 | 人數 |
|---|---|---:|
| 攻速 | 極大 | **1** |
| 移速 | 極小 / 極大 | 3 / 4 |
| 生命 | 極大 | 3 |
| 防禦 | 極小 / 極大 | 2 / 4 |
| 魔抗 | 極小 / 大 / 極大 | **1 / 2 / 1** |
| AD | 極小 | 1 |
| AP | 極小 / 極大 | 1 / 1 |

### 4.2 魔抗與 AP：可以分帶，但五格不是自然的形狀

| | 相異值(116) | 小帶吃掉 | 薄帶數 | 變動中位 |
|---|---:|---:|---:|---:|
| 魔抗 | 71 | **81 / 116 = 69.8%** | 3 格 | 6.4% |
| AP | 70 | **76 / 116 = 65.5%** | 2 格 | 5.3% |

➡️ 誠實的說法：**這兩項有分布，但它是「一大坨 + 幾個孤點」，不是五個群。**
硬切五帶的結果是「小」變成背景值、另外三格各住 1–2 人。
**建議這兩項用設計指定，不要從分布推導。**

### 4.3 攻擊距離：等分位會整個塌掉（已改用 Jenks）

76/116 並列在 1.6 → 等分位四切點 `1.6 / 1.6 / 1.6 / 7.3`，前三帶全空。
這正是舊版 `tiers.ts` 的作法。**已改 Jenks，但你要知道界線是被迫遷就這個並列。**

### 4.4 CD/MP：5 格的最上緣是發明的，不是百分位

`tierMethod.cutPoints` 宣告的是兩步（百分位 → 吸附刻度），
但 `tiers.js:13` 有**沒被寫進文件的第三步**：

```js
for (let i=1;i<cuts.length;i++)
  if (cuts[i] <= cuts[i-1]) cuts[i] = nice[nice.indexOf(cuts[i-1])+1] ?? cuts[i-1]+1;
```

兩條百分位撞在一起時，它把後面那條**往上推到手寫階梯的下一格**。
60 的「最近刻度」是 60 不是 70；120 的最近刻度是 120 不是 125。

| 群·指標 | 原始百分位 | 實際切點 | 退化程度 |
|---|---|---|---|
| 範圍 冷卻第1階 | `[25,40,60,**60**]` | `[25,40,60,70]` | 單一值 60 橫跨百分位 59–92 |
| 範圍 冷卻滿階 | `[27,40,60,**60**]` | `[25,40,60,70]` | 單一值 60 橫跨 58–91 |
| 自身 冷卻第1階 | `[12,45,60,**60**]` | `[12,45,60,70]` | 單一值 60 橫跨 43–90（**108/231 = 46.8%**）|
| 自身 冷卻滿階 | `[12,45,60,**60**]` | `[12,45,60,70]` | 單一值 60 橫跨 42–89 |
| 自身 MP滿階 | `[60,120,**120**,300]` | `[60,120,**125**,300]` | 「中」帶 = `[120,125)`，**裡面只有 120 這一個值**（50 支）|

➡️ **那四格冷卻的分布最多只撐得起四帶，第五帶是補出來的。**
切在 60 與 70 之間本身合理（值都疊在 60，沒有別的地方可切）——
**壞的是把它講成百分位。**
⚠️ 特別是自身冷卻：**46.8% 的技能全部是同一個 60 秒**，拿它當調校基準會誤導。
