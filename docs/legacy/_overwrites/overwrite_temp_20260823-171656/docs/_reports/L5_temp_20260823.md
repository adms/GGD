# L5 —— 內容樹只載入一次

**日期** 2026-08-23 · **柵欄** `packages/shared/src/content/`

---

## 一句話

`packages/shared/src/content/` 底下每一支「⛔ 不是在驗打包器/索引/版控」的測試，
現在都從 **`content/bundle.json` 一次讀完**（`__fixtures__/shippedContent.ts`），
⛔ 不再各自 `readdir` + `readFileSync` 1,727 次。
**bundle 過期時它自己退回逐檔讀** —— 慢，但逐位元組相同。

---

## 量到的（⛔ 不是估的）

### ① 根因：`ContentLoader` + `FsContentSource` = 1,727 次 `readFile`

出貨樹是 **1,712 份文件 / 14 個集合**。`FsContentSource` 一次載入要讀
`manifest.json` + 14 份 `_index.json` + 1,712 份文件。

`packages/shared` 裡打這一行的測試檔有 **66 支**（另有 50+ 支自己抄了一份
`readdirSync` 版的 `docs(collection)` helper）。

| 路徑 | 冷（每個行程的第一次） | 暖 |
|---|---:|---:|
| `ContentLoader` + `FsContentSource` | 347 ms | 200 ms |
| `ContentLoader` + bundle 來源 | 115 ms | 74 ms |

裸 I/O（⛔ 不含 zod）：全樹 `readdir`+`readFile`+`JSON.parse` 冷 190 ms / 暖 62 ms，
單一 `bundle.json`（2.47 MB）46 ms / 38 ms。

### ② ⚠️ 「整套只 parse 一次」做不到 —— 而且是量出來的

vitest 2.1.9 預設 `pool: forks` + `isolate: true`。實測探針（三支測試檔各印
`process.pid` 與 `globalThis` 上的旗標）：

```
PROBE-A pid 34697 seen undefined
PROBE-B pid 34698 seen undefined
PROBE-C pid 34699 seen undefined      ← 三個不同 pid，globalThis 不共用
```

加上 `--no-isolate --maxForks=1` 之後才變成 `pid 35280 / seen a / seen b`。

⇒ ⭐ **省的是「每一個測試檔行程的第一次」那一份**，⛔ 不是「整套只做一次」。
⛔ 我沒有去動 `isolate`：那會讓 `sim/content/registry.ts` 的 module-level
singleton 跨檔共用，是另一個等級的風險，⛔ 不在這條 lane 的柵欄裡。

## 做了什麼

### 新檔 `packages/shared/src/content/__fixtures__/shippedContent.ts`

| 匯出 | 用途 |
|---|---|
| `shippedContentSource(rootDir?)` | `new FsContentSource(dir)` 的 **drop-in** —— `dir` 不是出貨那棵樹時原封不動退回 `FsContentSource` |
| `shippedDocs<T>(collection)` | 一個集合的每一份文件，依**檔名**排序（＝ `readdirSync().sort()` 的順序） |
| `shippedDocFiles<T>(collection)` | 同上，帶 `{ file, doc }` |
| `shippedDocMap<T>(collection)` | `id → doc` |
| `shippedBundleIsFresh()` | 這個行程走的是 bundle 還是檔案樹 |

### ⭐ fail-**slow**，⛔ 不是 fail-open

`icons.test.ts` 的檔頭記著一條真的限制：「索引只有主 session 會跑 `content:build`
重建，測試在重建前後都必須是綠的」。而併行 lane 的規則 ⛔ 禁止 lane 自己跑
`content:build` ⇒ **一個剛編過 `content/` 的 lane 手上的 bundle 一定是舊的**。

⇒ 夾具先做一次 **11 ms 的 mtime 掃描**（1,712 次 `statSync`，⛔ 不讀內容）：

- bundle 比**每一份**來源都新 → 走 bundle（快）
- 有任何一份來源比 bundle 新 → **自動退回逐檔讀**（慢，但**逐位元組相同**）

⚠️ 這與 CLAUDE.md 罵的 fail-open **不同型**：那一種退回的是**別的語意**
（骨架英雄／沒錄到影），這一種退回的是**同一份資料的另一條讀法**。
唯一會漂的東西是 wall-clock。

### ⛔ 三支永遠留在檔案樹上

判準（owner 2026-08-23）：**驗打包器/索引/版控 → 讀樹；驗內容本身 → 讀 bundle。**

- `shippedBundleIsCurrent.test.ts` —— 它的工作就是抓「bundle 過期」
- `shippedBundleHasTrackedSources.test.ts` —— 抓「來源沒進版控」
- `bundle.test.ts` —— 在 `cpSync` 的 temp 樹上重建打包器

另外 `loader.test.ts` 與 `buildIndexesValidates.test.ts` 也沒動：
前者被測的就是 `ContentLoader`／`FsContentSource` 本身，後者跑的是 build 腳本。

## 閘與突變

新閘 `packages/shared/src/content/__fixtures__/shippedContent.test.ts`（52 行）：
**bundle 那條路與檔案樹那條路，每一個集合逐份相同（id · 順序 · 內容）**。

⚠️ 比對用 `stableStringify` ⛔ 不是 `JSON.stringify`：bundle 是用它序列化的，
所以 bundle 裡的文件**鍵是排序過的**，磁碟上的是作者寫的順序（`-0` 也會變 `0`）。
內容定址系統從第一天起就把兩者當同一份（`hashDoc` 也走 `stableStringify`），
瀏覽器端拿到的也正是排序過的那一份。
⛔ 但如果某支測試真的依賴**作者寫的鍵序**（例：`Object.keys()[0]` 當「第一個欄位」），
它就不可以改用這一支。

**突變紀錄（真的跑過）**

| # | 改壞什麼 | 結果 |
|---|---|---|
| ① | `docsFromBundle` 排序鍵 `` `${a.id}.json` `` → `a.id` | 🔴 紅，訊息指名 `projectiles[3]: imported.bolt.arcane ≠ imported.bolt.json` 等 6 處 |
| ② | 把 `content/bundle.json` 的 mtime 退回 1970（模擬 lane 剛編過內容沒 build） | ✅ **全綠** —— 夾具自動退回逐檔讀（fail-slow 生效）。mtime 已還原 |

## ⭐ 還沒做的：柵欄外的 **44 支**，一行 sed

同一個換法在 `packages/shared/src/sim/` 與 `src/ops/` 底下還有 **44 支**測試檔
（`new FsContentSource(CONTENT_DIR|CONTENT)`），⛔ 不在這條 lane 的柵欄裡。
以本批量到的 **−46%** 推算，它們合計約 **115 秒**的測試時間，可望再省 **~50 秒**。

換法完全機械（三步，⛔ 不改任何斷言）：

```
new FsContentSource(CONTENT_DIR)  →  shippedContentSource(CONTENT_DIR)
- import { FsContentSource } from "…/node/FsContentSource";
+ import { shippedContentSource } from "…/content/__fixtures__/shippedContent";
```

⛔ **三支要跳過**：`sim/content/requirement.test.ts`、`sim/effects/incomingReflect.test.ts`、
`sim/effects/itemCooldownEnv.test.ts` —— 它們的參數是 `dir`（temp 樹）。
⭐ 其實就算換了也不會壞（`shippedContentSource(dir)` 對非出貨樹會退回 `FsContentSource`），
但那三支換了**一點也不會變快**，純粹是 churn。
