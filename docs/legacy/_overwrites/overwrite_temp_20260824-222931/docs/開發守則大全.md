# 開發守則大全 —— 可轉移的工程紀律十五章

> 這份文件是一個實際專案（多人併行 AI 工作流、內容驅動的線上服務）兩個月踩坑的沉澱，
> **重新編寫成不綁定任何專案的通用守則**。每一條背後都有真實事故，
> 以匿名化的「案例」框呈現，數字都是量到的。
> **用法**：逐章讀「原則」決定採不採用；附錄 A 是可直接勾選的採用清單。
> 各章一律四段：**原則 → 為什麼 → 怎麼落地 → 反例**。

## 用詞約定

| 詞 | 意思 |
|---|---|
| **判準** | 一句「要記得問自己⋯」的規則。靠人在當下想起來才生效 |
| **閘** | 一個數字門檻、一行指令、一條會紅的測試、或一個會擋下動作的 hook。不靠記憶生效 |
| **住處** | 一份知識（數字、決策、綁定）被寫下來的位置。「第二個住處」= 同一份知識的副本 |
| **守衛** | 保護某個功能的自動化測試：改壞實作它就紅 |
| **突變驗證** | 把實作關鍵那行改壞 → 確認守衛紅 → 改回來，證明守衛不是裝飾品 |
| **lane** | 一條併行的工作流（人或 AI agent），與其他 lane 共用同一個 repo |
| **owner** | 擁有產品決策權的人。工程師（或 AI）是執行者，不是決策者 |
| **靈魂層 / 體驗層** | 核心行為（使用者依賴的機制）/ 周邊（後台頁、工具、文案、接線） |

## 第 1 章 元規則：閘不是判準

> 這一章是整份文件的骨架。後面十四章的每一條，最終都要問同一個問題：
> **「它是一個閘，還是一句散文？」**

### 原則

任何想寫成「要記得⋯」的規則，先問：**它能不能變成一個數字、一行指令、
或一條會紅的測試？** 能，就做成那個；不能，才允許寫成散文——而且要有自知之明：
散文遲早失效。

閘有強度階梯，能上就往上：

| 強度 | 形狀 | 例 |
|---:|---|---|
| 5 | **會擋下動作的 hook**（動作發生前跑） | 覆蓋檔案前自動留底的 pre-write hook |
| 4 | **會紅的測試**（CI / commit 前必跑） | 「文件裡那句話與程式碼比對」的守衛 |
| 3 | **唯一入口的指令**（把多步序列封進腳本） | 部署只有一條指令，腳本自驗後置條件 |
| 2 | **一行自檢指令** | commit 前算「實作行數 / 測試行數」的 awk |
| 1 | **數字門檻** | 「context 用量 ≥ 95% 就存快照」 |
| 0 | 散文（「要記得⋯」） | ——遲早失效 |

### 為什麼

來源專案的規則文件誠實記錄了**五次「判準失效」**：規則寫得清清楚楚、
寫的人自己踩、踩的當下他「知道」那條規則。原因很簡單：
**出事的當下沒有人在讀散文，只有閘在跑。**

同一份文件裡，同一個解法的形狀出現了至少四次（部署序列、版號規則、
內容驗證時機、測試預算）——四次都是「散文失效 → 換成數字/指令/測試 → 從此不再犯」。
這不是巧合，是規律。

### 怎麼落地

1. 每次要在團隊文件裡寫「要記得⋯」「注意⋯」「不要忘了⋯」時，停下來，
   照上面的階梯找一個更高強度的形狀。
2. 閘要在**動作發生的當下**響。寫在 schema 裡但只在下游某條測試才跑的驗證，
   等於在離現場十公里的地方裝警報器——響的時候第一行錯誤指向別的地方，害人反向追。
3. 閘不可以被放寬。一條被放寬成模糊比對的逐位元組檢查，等於沒有閘
   （典型元兇：產生物裡帶時間戳，逼得 `--check` 只能模糊比對——解法是拿掉時間戳）。
4. 會擋人的閘要想清楚擋不擋得起：**一個常誤擋的 hook 會被人關掉，而被關掉的閘
   等於沒有閘。** 備份類寧可「只留底、永不擋」；「沒有任何合法情境」的動作才硬擋。

### 反例

> **案例（散文失效兩次才變成 hook）**：「覆蓋／刪除之前先備份」寫成規則之後，
> 同一個人先用 `git checkout <檔>` 一次洗掉三條併行 lane 的成果，
> 幾天後又用 `cat >` 洗掉一份唯一副本的文件（救不回來）。兩次他都「知道」規則。
> 之後它變成 pre-write hook，在動作前自動留底——從此不必靠任何人記得。

> **案例（規則只寫了一半）**：版號規則寫了「同一天只 bump patch」，
> 漏寫「跨天要 bump minor」——結果十天打了 45 個 patch 沒翻頁。
> 修法不是把散文補齊，是把版號算術封進發版腳本，並配一條守衛。

## 第 2 章 值只有一個住處

### 原則

任何**算得出來的數字**（由公式、級距表、共用設定推導的值），
只能住在**一個地方**（共用表／設定檔），在**載入時**解析——
⛔ 不烘進每一份使用它的文件、文案、產生物。

判準一句話：**同一個數字有沒有第二個住處？** 有，就錯了。

### 為什麼

烘出去的那一份**必然過期**，而且成本是 O(N)：N 份文件 × 每次公式改動
= 一次完整的重新產生鏈。

> **案例（一行公式改動 ≈ 一小時）**：某次把一個係數從公式裡拿掉，實際引爆：
> 199 個「級別與算好的值都寫進去」的節點要重寫、兩支批次腳本、
> 12 支下游產生器過期、4 份測試基準線重轉、說明文案全部重推。
> 它本來應該是「改一個數字、跑一次測試」。

### 怎麼落地

新增任何「有級距／有公式」的欄位時，照這個順序：

1. **表住共用設定目錄**（級距表、冷卻表、成長曲線⋯）。
2. **文件只寫級別名**（`"damageTier": "極大"`），不寫算好的值。
3. **解析在載入時**（一個 `resolveTier()` 家族），⛔ 不是在產生器裡先算好塞進去。
4. **面向使用者的說明用佔位符**（「造成 {{dmg}} 點傷害」），渲染時代入——
   寫死的「造成 6000 點」在級距改動的那一刻變成謊話。
5. **加一條守衛**：同一個節點不可以同時有級別與算好的值。
6. **例外要帶理由進豁免表**：真的不屬於任何級距的值（一次性的、逐字匯入的）
   可以留字面值，但要寫下「為什麼它不該有級別」——一個能被反駁的理由，
   不是「還沒收」。

### 反例

| 形狀 | 判定 |
|---|---|
| `{"damageTier": "極大"}`，值在載入時從表解析 | ⭐ 對 |
| `{"damageTier": "極大", "flat": 6000}` | ⛔ 錯：`flat` 是第二個住處，公式一改它就是謊話 |

第 5 章的「三個住處」不是這條的例外：那三個住處存的是**同一格欄位在三層系統
（出貨值／schema 預設／後台介面）的接線**，彼此之間有 drift 守衛互相盯著——
有守衛盯的鏡像是接線，沒守衛盯的副本才是第二個住處。

## 第 3 章 內容＝資料、程式＝機制

### 原則

系統裡的「一項內容」（一個商品、一支技能、一種報表、一類通知）**不是一段程式，
是一組模板參數**。程式只提供**機制**（一種效果、一個 hook 事件、一個條件葉），
內容用資料把機制組起來並填參數。

判準：**如果我在為「某一項內容」寫 if，我就越線了。** 那個 if 該是一個
可組合的條件葉，而那項內容該在資料裡引用它。

推論：**N 個同型項目 = K 個模板 + 一張表，不是 N 輪實作。**

### 為什麼

1. 為單一內容寫的 if 會複製 N 份、各自腐爛；抽成機制之後它是一格下拉選單。
2. 批次成本差一個數量級：一批 90 項內容逐項做是 90 輪；先盤點「每個缺的機制
   擋住幾項」再按擋住數做機制，實測 3 輪解決 21 項。
3. 「到處改改改」是反面標記：diff 散落 10 個檔各改兩行、而那 10 處在做同一件事
   = 漏了一次抽象。

### 怎麼落地

1. 接到一批同型需求，⛔ 不要逐項實作。順序是：
   **盤點**（每項需求對照引擎現況，數出每個缺口擋住幾項）→
   **排序**（按擋住的數量做機制，不是按項目順序做項目）→
   **實作機制**（含守衛與突變驗證），內容由資料側產出。
2. 「引擎支援哪些機制」的清單必須**從出貨註冊表推導**，⛔ 不可以手寫。
   對外契約（給外部編輯器、給下游團隊）尤其如此——對方看不到你的程式碼，
   沒有辦法發現你在說謊。守衛要關**兩個方向**：宣告不支援但其實有（對方白白繞路）、
   宣告支援但其實沒有（對方做出上線就是死的內容）。
3. 寫第二個東西時發現它跟第一個只差「參數」——**停手，先抽模板。**

### 反例

> **案例（手寫能力表說謊兩次）**：一份手寫的「引擎能力表」，檔頭自己記錄了
> 它撒過兩次謊：一個能力寫 false 但引擎早就有了、另一個能力整列漏掉。
> 結論被它自己寫成一句話：「一個被散文守著的 flag 活過了散文的保存期限，
> 而**沒有任何東西變紅**。」

> **案例（六個 if vs 一個條件葉）**：某批內容有六項架在同一個機制
> （「對帶有 X 狀態的目標追加 Y」）上。寫成六個 if 是六份各自腐爛的程式；
> 寫成一個條件葉是資料裡的一格選單，第七項免費。

## 第 4 章 衝突優先序階梯，與「被取代的知識要另存」

### 原則

當多個資訊來源對同一件事各說各話（新設計 vs 舊系統實際行為 vs 舊文件），
**預先立好一座優先序階梯**，衝突時照梯子裁決，不要每次現場吵。
通用形狀（重製／遷移類專案）：

| 層 | 來源 | 為什麼排在這 |
|---:|---|---|
| 1 | **owner 的新版設計** | 這是設計。重製不是移植，設計贏過考古 |
| 2 | 設計的機器可讀翻譯（結構化資料） | 它與第 1 層打架＝翻譯錯了，改翻譯 |
| 3 | 舊系統的**實際行為**（程式碼／執行結果） | 程式不會說謊，所以排在舊文案前 |
| 4 | 舊系統的文案／說明 | 與第 3 層打架時可能是刻意的隱藏行為 → 問 owner |
| 5 | 舊系統的原始設定值 | 最低——很多欄位根本沒被讀 |

兩條配套：

- **同一份文件內部**也會自相矛盾：**內文 > 標籤**（而且要回頭把標籤改成符合內文，
  不是留著兩個打架的來源）；**引述／對白不是規格**——任何自動讀規格找機制的東西
  （正則、LLM、編輯器建議）要先剝掉整段引號內容，否則台詞裡的「35 秒後」
  會被讀成一支有 35 秒時序的功能。
- ⛔ **被取代的知識要另存，不可以無聲消失。** 高層級贏了，低層級的值另存進
  一份「被取代紀錄」。**測試可以跟著設計走，知識不可以無聲消失。**

### 為什麼

沒有階梯，每一次衝突都是一次升級到 owner 的中斷；有階梯，多數衝突可以自動裁決。
而「另存」是階梯能被信任的前提：人們敢讓高層級贏，是因為知道輸的那邊沒有被銷毀——
哪天設計被推翻，考古成本是零。

### 怎麼落地

1. 專案開工第一週就把階梯寫下來，請 owner 簽字。
2. 遇到衝突，兩條路，看能不能停：**可以停** → 列一張表（哪一項 · 哪兩層打架 ·
   各自說什麼 · 照階梯的結論）拿去確認；**不能停**（大批次、owner 不在）→
   照階梯做下去，**把選擇做成一格可回捲的開關**，高層級贏的結果**預設 on**——
   開關存在是為了回頭，不是為了觀望。
3. **測試只做預設啟動的那一邊。** 開關關掉的舊行為不測（它是逃生口，不是功能）；
   預設值本身改變時才測新的預設。一個開關兩條路 = 兩倍測試，而第二條路不值。

### 反例

> **案例（對白被讀成機制）**：三支功能的說明裡帶著角色台詞，
> 自動掃描把「在 35 秒後宣布勝利吧」讀成一支有 35 秒延遲的功能。
> 修法不是「跳過行首是引號的行」（漏掉行中引述），是剝掉**整段**引號內容。

## 第 5 章 可調優先於寫死

### 原則

所有功能以**後台可調**（開關、數值、參數）為預設形狀。
**寫死才需要理由；可調不需要。**「決策點」也算——如果寫程式時心裡出現
「這裡要選 A 還是 B」，那就是一個決策點，它該是一格開關，預設值選 owner 明說的那個。
⛔ 不要在註解裡辯護你選了哪個——那個註解本身就是「這裡本來該是欄位」的證據。

### 為什麼

1. **改一個寫死的值 = 一次完整部署**（build、測試、重啟）；
   改一格後台欄位 = 存檔生效。
2. **owner 會反覆推翻自己的數值**（實測同一個係數兩個月內改了四次）。
   每一次寫死等於預付一次部署成本。
3. **執行者常常猜錯。** 把選擇權留在後台，猜錯的成本從一次 PR 降到一格下拉選單。
4. 「拿去問 owner」也是一種「挑一個」：它把選擇權還給 owner，
   卻沒把**改變的成本**降下來——他下次想改還要再問一次。
   順序永遠是：先問「這能不能是一個欄位？」，不能才升級成裁決。

### 怎麼落地

1. 一格欄位要**同時**落在三個住處，缺一就要有 drift 守衛變紅：
   ① 出貨設定檔（版本控制內） ② schema ＋程式預設值 ③ 後台介面
   （欄位、標籤、分組、驗證）。
2. **欄位要有上界，不是只有下界**——50 打成 500 要在輸入的當下被擋，
   不是在下游被靜默夾掉。
3. 說明文字寫「**它影響什麼**」，不是複述欄位名。
4. **語意改了，舊文案就是謊話**：一格欄位的語意變更後，`grep` 一遍所有描述它的
   字串（實測一句過期描述同時住在四個檔）。
5. 後台 override 會蓋掉設定檔——改設定前先查線上有沒有存過 override，
   否則部署成功但使用者那一場沒變。
6. ⛔ **「可調」不等於「執行者可以自己轉」。** 有一族欄位屬於 owner（倍率、定價）：
   把欄位做出來是執行者的工作，**行使它不是**。判準：這次改動引用得到 owner 的
   哪一句原話？引用不到 → 不要動；要動就列成選項拿給他（列了就真的不要自己挑）。
   閘：一份「owner 旋鈕帳本」記每一格的出貨值＋逐字原話，一條守衛比對帳本與實際設定。
7. owner 不在、工作又不能停時：**自己判斷，但留一格一鍵回捲的開關**，
   預設＝自己挑的那個，回報時逐條說「我挑了什麼、那一格叫什麼」。
   沒有開關的自作主張只是自作主張——挑錯的成本必須是「他改一格選單」，不是一次部署。

### 反例

> **案例（寫死的決策點把功能鎖死）**：兩個寫死常數相乘
> （回合門檻 × 每回合節奏）讓一條高價內容路線**永遠開不了**，
> 而後台一個都改不到。
> **案例（逐項 map 漏一列）**：逐項寫死的價格表，上架新項目忘了補一列
> = 那一項免費送——兩次。

## 第 6 章 「說了但不會發生」是最危險的綠燈

### 原則

**介面上不可以有「說了但不會發生」的字。** schema 收得下、後台存得起來、
畫面印著那句話、build 全綠、全套測試全綠——而系統裡什麼都不發生：
這是最危險的失敗形態，因為**每一個零件都是對的，只有它們的組合是空的**，
沒有任何既有守衛會紅。

### 為什麼

> **案例（25 處空宣稱通過三千多條測試）**：三件新內容身上有 25 處
> 「宣告了一個修飾效果，但在出貨設定下它逐位元等於不存在」的組合
> （上限已被夾死所以提升上限是空話；乘法修飾掛在基數為 0 的屬性上，0×任何東西=0）。
> 全部通過 build 與 3,594 條測試。

### 怎麼落地

1. **修法是替換，不是刪掉效果留著描述**——那樣介面還在說謊，只是更難查。
   三條出路照順序試：① 換成做得到的等效機制 ② 把描述改成只講真的會發生的事
   （當做不到的那一半本來就影響不到任何人時）③ 升級成 owner 的決定
   （需要改平衡資料或新機制時，⛔ 不要自己挑數字）。
2. 加一條**組合層守衛**：掃全部出貨內容，只問一件事——
   「這條宣稱在出貨設定下，有沒有可能改變任何一個可觀察的結果？」
   ⭐ 守衛的白名單要**從出貨設定推導**，不抄字面值——設定哪天開了空間，
   守衛自動放行，不必改測試。
3. **改完描述要逐句回頭對照資料**，⛔ 不可以憑印象寫——實測改寫描述時
   順手多寫了一句該內容根本沒有的效果。
4. **撞到字數上限時：另存全文＋留指標，⛔ 不是壓縮取代。** 實測直接截斷塞回去，
   無聲少了 254 字而一切全綠。這與第 4 章「被取代的知識另存」是同一條規矩。

### 反例

反例就是「為什麼」那個案例本身。值得記住它的結構：
**單元測試驗零件、schema 驗形狀、都不驗「組合是否為空」**——
所以這一類守衛必須存在於組合層，而且必須以出貨設定為基準。

## 第 7 章 守衛驗機制不驗數字；突變驗證；八種失敗形態

### 原則

- 一條測試如果把實作關鍵那行刪掉還是綠的，它就不是守衛。
  **每條新守衛都要做突變驗證**（改壞→確認紅→改回來），紀錄寫進 commit。
- 守衛驗「**機制會不會發生**」（倍率有沒有被乘進去、事件會不會停止），
  ⛔ 不驗「**數字是多少**」（倍率是 3 還是 4）。
- 要斷言數字就**從設定推導**，⛔ 不抄字面值。

### 為什麼

出貨數值已經有帶 drift 守衛的住處（第 5 章）。測試裡再抄一份就是**第四個住處，
而它沒有守衛**——所以它一定過期，而且**用錯誤的訊息紅**：
實測一條紅著喊「BOSS 的延長機制壞了」的測試，真相只是回合長度被調過，查了半小時。
數值本來就是 owner 每週在改的東西；寫死在測試裡等於替一個預期會變的東西上鎖。

### 怎麼落地——八種「做了但使用者拿不到」的失敗形態

寫測試時逐條對照，八種都真的發生過：

| # | 形態 | 匿名化案例 |
|---|---|---|
| ① | 算出來了但畫在畫面外／被上游吃掉 | 三種尺寸的單位在畫面上同一個高度（正規化吃掉了縮放） |
| ② | 算出來了但從沒送到消費端 | 狀態位沒人寫進快照；請求被靜默截斷但介面回報請求值 |
| ③ | 從渲染樹刪掉而測試全綠 | 一行展開運算子刪掉，功能整個撤銷，3,563 條測試全綠 |
| ④ | 斷言方向跟缺陷無關 | 對正確與壞掉的實作都會過的斷言 |
| ⑤ | 被測的不是出貨的那個 | 測試自己手寫了出貨路徑從不寫的欄位 |
| ⑥ | 掃原始碼字串代替跑行為 | `grep` 有沒有那個函式名，代替真的跑註冊表 |
| ⑦ | 掃屬性代替掃行為 | 「三個 kind 解析出三個 key」≠「畫面上真的不一樣大」 |
| ⑧ | **消費端存在，但它消費不到** | 事件有 case、路由放行、型別檢查綠——而 case 第一行讀一個**零寫入端**的欄位然後 return |

形態⑧值得單獨講：實測**一天中五次**，根因是事件匯流排的 payload 沒有型別，
消費端想讀任何欄位就非強制轉型不可，每一個轉型都是一個靜默的洞。
四種常見守衛對它結構性失明：grep 有沒有 case／型別可指派性（結構指派兩個方向都放行）
／測試自己造 payload 餵消費端（形態⑤：量的是虛構通道）／掃檔案有沒有提到欄位名。
**兩層修法**：驗證跑真的東西（載入出貨內容 → 跑出貨產生端 → 真事件 → 餵真消費端）；
根治是讓契約變成型別檢查的紅（payload 型別住 emit 站旁邊，收發兩端 import 同一個）。

其餘落地要點：

1. 突變驗證只做**一條承重的線**（拿掉它整批功能就消失的那條），不是每個分支各一條。
2. 只有靈魂層做突變；體驗層一條薄守衛；純數值調整 0 行測試（見第 10 章的預算表）。
3. **斷言要讀最終物件**：實作若 clone 之後再指回去，對原始物件寫的斷言永遠過。
4. 「不重要的功能」一條薄守衛就夠，**不開對抗性複驗迴圈**——
   對抗迴圈沒有收斂條件（停止條件是「已知的洞關了」，不是「沒人想得出新的」）。

### 反例

> **案例（守衛與缺陷同向）**：一條「瞄準優先序」的測試，對正確的實作與
> 壞掉的實作都會過——它斷言的方向跟缺陷無關（形態④）。突變驗證十秒就能抓到它。

## 第 8 章 使用者看得到才算做完

### 原則

**「鏈路接上了」不等於「做完了」。** 對使用者看得到的功能，
在終端證據（真的像素、真的聲音、真的回應）存在之前：

- ✅ 只准說：「**鏈路已接上，⛔ 未驗收**」
- ⛔ 不准說：「做完」「已修」「已上線」
- release note 與關票註解裡的「已修」**必須帶證據指標**（守衛測試名或驗收報告路徑）
  ——引用不到就不是「已修」，是編的。

### 為什麼——五層根因（只修最上層必然復發）

> **案例（「已修」寫進 release note，而它當時就是假的）**：一個視覺功能
> 事件有送、白名單放行、頂點在動——而畫面上零像素（形狀住在 alpha 通道且兩緣是 0）。
> 四條守衛全綠。owner 得自己開產品才發現，他的原話：「我不想當你的人肉測試機。」

| 層 | 問題 |
|---|---|
| ① 缺陷本身 | 資料的某個組合使輸出全透明 |
| ② 守衛為什麼沒抓到 | 四條全在**中間節點**。根因：測試環境畫不出像素 ⇒ 寫的是「方便驗的東西」，不是「驗收標準」 |
| ③ 為什麼回報「做完」 | **「做完」這個詞沒有證據標準**——它被用成「我的工作鏈完成」（commit＋綠燈），不是「使用者看得到的結果被證明」 |
| ④ 第一版防線為什麼防不住 | 見下面「四個洞」 |
| ⑤ 為什麼會有②③ | 沒有任何東西**區分**「鏈路接通」與「使用者可見」這兩種宣稱——它們在回報裡長得一模一樣。**兩種東西長得一樣就會被混用** |

### 怎麼落地——第一版防線的四個洞，逐洞一個補法

| 洞 | 為什麼防不住 | 補法 |
|---|---|---|
| a. 路徑柵欄 | 上游造成的不可見不會碰到被監控的目錄 ⇒ 閘綠 | **出貨態掃描**：不看 diff，掃全部出貨資產的靜態可判不變量 |
| b. 標記是自我宣告 | 閘 grep 的是標記字串，不是斷言內容 ⇒ 空殼測試貼標記就過 | 帶標記的測試**必須含可見性斷言詞彙**，否則閘紅並指名該檔 |
| c. diff 閘看不到已出貨的壞 | 沒有 diff 碰它就永遠不紅 | 同 a：掃描驗**現在出貨的狀態**，不是這次改了什麼 |
| d. **量尺自己會說謊** | 同一輪兩個量測錯誤得到相反結論 | **校準寫成程式**：量尺先量一個已知亮的 control，量不到 ⇒ 這台量尺的一切結論作廢；掃描器內建 sentinel（自造一份必失敗的輸入，斷言抓得到） |

關鍵洞見：**很多「要真環境才驗得到」的失敗，其實是靜態可判的。**
（UV 全同一點、出生透明度 0、加法混色疊全黑——四種都不用渲染就判得出來。）
headless 測試環境不是藉口，是「沒把驗收標準翻成可判的不變量」。

「百分百防範」的誠實答案：**單一一支閘做不到**——用五層彼此獨立的防線疊起來
（diff 閘、出貨態掃描、族群專項守衛、帶校準的真渲染抽查、用詞紀律），
讓同一個缺陷要同時穿過五個洞才能再發生。

### 反例

反例就是③那一層：release note 裡一句沒有證據指標的「已修」。
它與第 15 章「宣稱要有出處」同構——**宣稱引用不到出處，那個宣稱就是編的。**

## 第 9 章 非結構化資產的驗收：HITL 分層漏斗

### 原則

視覺、音效、動畫這類**機器判不了語意**的資產，驗收用分層漏斗：
機器篩掉判得了的，**有邏輯地**把剩下的送人類批次審查。
**兩個極端都是錯的**：全機器（機器根本不會問「這像不像閃電」）
與全人工（owner 變成人肉測試機）。

### 為什麼

機器與人各有一段擅長的：靜態不變量（透明度 0、零長度音檔、斷掉的引用）
機器一秒判完、永不疲勞；「這聲音配這個動作對嗎」只有人答得了。
把人力花在機器判得了的東西上是浪費；把機器判不了的東西全綠放行是說謊。

### 怎麼落地

| Tier | 誰驗 | 驗什麼 | 結果 |
|---|---|---|---|
| 0 硬性不變量 | 機器（build 閘） | 靜態可判的「必不可見／必無聲」 | 自動擋下，不進人類佇列 |
| 1 可量測界線 | 機器（閘） | 時長、預算、音量範圍 | 界內自動過；超界擋下或降級 |
| 1.5 初審 | AI 看圖／聽聲 | 接觸表逐格看：明顯空白／破圖 → 自動 fail | 縮小人類佇列；⛔ 不得當高風險項的終審 |
| 2 HITL | 人類（批次審查頁） | 語意題：「像不像」「配不配」「讀不讀得出來」 | 一頁網頁、逐格 ✅/❌/備註、鍵盤快捷 |

**什麼進 HITL（邏輯篩選，不是全部）**：新資產／內容 hash 變了（舊核准自動過期）·
首次接線 · 機器信心低 · 風險加權（被引用次數 × 使用頻率）· 從未被人審過的。

**三個把人力變成一次性的乘數**：
1. **感知基準線**：人類核准一次 ⇒ 存下決定性種子的參考影格 ⇒ 之後每版重渲染
   做感知比對，漂移超閾值才重新進佇列——**人審一次，機器守永遠**。
2. **A/B 並排**：有原作／舊版可比的，審查頁左右並排——機器判不了相似度，
   但機器可以把並排擺好，這是加速人審最便宜的一招。
3. **接觸表進 release note**：每版自動渲染「引用最多的前 N 個資產」成一張圖——
   owner 十秒掃完，不必進產品。

⚠️ pending 數量可以進部署檢查的**警示行**，但硬擋要是一格可調且**預設不擋**——
部署不可以被「人不在」卡死。

### 反例

> **案例（全機器的極端）**：一個視覺資產壞了幾週，所有機器閘全綠——
> 因為機器沒有任何一層在問語意題，而人類從來沒被安排看過它。
> **案例（全人工的極端）**：每個資產都等 owner 開產品親眼看
> = 驗收吞吐量被一個人的時間上限鎖死，而他的原話是「我不想當你的人肉測試機」。

## 第 10 章 成本紀律：預設不查、預設不測、預設不派人

### 原則

驗證與探查不是免費的美德，是要編預算的成本。預設值一律是「不做」，
做要有理由——而理由要量得出來。

### 為什麼

> **案例（預算被完整用反）**：實測某天 25 個 commit 的行數統計：
> 測試/實作比最高的四項全是體驗層（最高 **17.5×**：11 行接線配 192 行測試），
> 最低的兩項全是靈魂層（核心機制只有 **0.6×**）。同倉庫測試檔數量超過原始檔。
> 規則早就寫了六份文件、owner 講過三次——全是判準，沒有一條是閘。

### 怎麼落地

**① 測試預算分層（硬上限，不是建議）**

| 層 | 測試上限 | 突變 |
|---|---|---|
| 靈魂層（核心行為） | 測試行數 ≤ 實作行數 | 一條承重的線 |
| 體驗層（後台／工具／文案／接線） | ≤ 實作行數，且 ≤ 80 行 | 接線類做一次，其餘不做 |
| 純數值調整 | **0 行**（住處＋drift 守衛已經在守） | 不做 |

commit 前一行自檢（超標砍測試，不是砍實作）：

```bash
git diff --cached --numstat | awk '{if($3~/\.test\./)t+=$1+$2; else i+=$1+$2} \
  END{printf "實作 %d / 測試 %d = %.1f×\n", i, t, t/(i?i:1)}'
```

**② 跑測試的節奏（攢起來一次跑）**：一批工作 vitest ≤ 3 次
（全部寫完一次／修完紅一次／突變一次）、typecheck 1 次（開工前「確認環境」那次是純浪費）、
突變一批一條、全套只在 commit 前跑一次。

**③ 紅了之後批次撈錯，⛔ 不是「跑一次→修一個→再跑一次」**：
① 一次撈全部（幾個閘同一個指令跑完寫進 log，一次讀完）
② 歸因到根因（N 個紅是不是同一個？產生鏈上游動了，下游全會紅）
③ 改在來源，一次驗。
判準：**如果我要打的指令跟上一次一模一樣，我就做錯了。**
重跑同一個閘只有一種合法情況：改完全部之後的那一次確認。
實測反例：14 輪 × 每輪讀第一行錯誤 ≈ 50 分鐘，而全部的紅只有 1 個根因。

**④ 長工超時要看**：任何指令／工作流超過 5 分鐘沒新輸出 → 去看
（CPU 0% = 掛了：kill、單獨重跑）；同一個閘紅第三次 → 停，那是迴圈不是壞運氣，
找結構性根因。閘跑的時候⛔ 不動任何檔——mid-run 改動 = 下一輪的紅。

**⑤ 一天一版**：一次發版 = 一次全套驗證＋一次部署。實測一天發 5 版 = 5 倍成本。

**⑥ 不排版次，直接開幹**：把工作標成「大工程、排下一版」不是規劃，是丟棄——
session 的 context 撐不到下一版。唯一合法的分批理由是「同時跑會撞車」，
而分出來的每一批都要在同一天做完。

**⑦ 順手發現的缺陷開票，不當場修**：錯的不是修，是替 owner 決定了「先修它」——
排序是他的權力。配套回收閥：**部署前把這一輪順手開的票整理成一張表拿給他勾**
（是什麼·多嚴重·修起來多大·不修使用者會遇到什麼），否則開票就變成把缺陷埋進票堆。

**⑧ 預設不派 subagent**：只有 owner 明說、或真的要平行讀大量檔案**而且**答案會
改變接下來做什麼，才派。「現在狀態如何」一律自己答。實測反例：為了回答「做完了嗎」
派了 19 個 agent、245 萬 token，產出是五次查詢就能列的一張表。

### 反例

見「為什麼」的案例。根因不是不知道規則——是那些規則全是判準。
本章的每一條都配了數字或指令，就是為了這個。

## 第 11 章 併行多 lane 的紀律

### 原則

多條 lane 共用同一個 repo 時，**隔離單位是檔案，共用的東西
（index、HEAD、stash、全域產物）一律當成不屬於任何一條 lane**。

### 為什麼

git 的 index、HEAD、stash 是**全 repo 共用**的。兩條 lane 各自「正確」的操作，
交錯起來就是事故——而且多半不報錯。

### 怎麼落地

1. **柵欄用檔案級，⛔ 不是目錄級**——「四張票都動同一個目錄」而串行，
   實測它們動的是不同檔案，白白損失平行度。但**逐檔列名是必要的**，
   不能只說「你可以動那個目錄」。
2. **commit 的唯一正解（踩了四次才定案）**：

   ```bash
   # ⛔ 全程不 stage —— 連 git add 都不要
   printf '%s\n' "$MSG" > /tmp/msg.txt
   git commit -F /tmp/msg.txt -- <逐檔列名>
   ```

   為什麼連 `git add` 都不行：`add` 與 `commit` 之間哪怕幾十秒，
   別的 lane 的裸 `commit` 就會把你 stage 的檔一起掃走。
   反方向同理：**pathspec 只擋得住「我把別人的送上車」，
   擋不住「別人把我的送上車」**——`commit -- pathspec` 一步到位就沒有那個視窗。
   實測：`git add -- <我的 6 個檔>` 之後打了一個裸 `git commit`，提交了 332 個檔。
3. ⛔ **併行時禁 `--amend`**：它動的是 HEAD，而 HEAD 在併行時不屬於任何 lane
   ——實測 amend 到了別人幾秒前的 commit。pathspec 保護不了它。要修剪就再 commit 一次。
4. ⛔ **禁共用 stash**：平行 lane 跑 `git stash` 會互相倒進對方的樹。
5. ⛔ **`git checkout <檔>` / `restore <檔>` 是不可逆刪除**：它退回整個檔案，
   連同**別條 lane 在同檔上所有未 commit 的東西**。要還原一行就用編輯器改回那一行。
   判準：**一個動詞影響到我沒有逐一看過的位元組，就是越線**
   （`git add -A`、`checkout <檔>`、`stash`、裸 `commit` 同屬此類）。
6. **全域鎖**：會寫共用產物的指令（聚合產生器、bundle 重建）同一時間只能一條 lane 跑；
   多 lane 併行時全部禁跑，由主 session 最後統一跑一次（唯讀的 `--check` 隨便跑）。
7. **產生器的產物不准手改**——下一次重生成把它打回來，那個「又紅了」看起來像新的錯，
   還會造成「閘每跑一次就把修好的東西刪一次」的無限迴圈。做成會擋的 hook，
   擁有者表**從產生器實際寫的檔量出來**，不手寫。正確動作：改來源、重生成、
   驗「重生成之後改動還在」——那才是「修好了」的定義。
8. **agent 的報告：摘要 ≤500 字＋完整報告寫成檔案**。細節不是砍掉，是換住處。
9. **⛔ 不要用兩階段（計畫 agent → 實作 agent）**，除非後段需要的東西前段產生了
   而後段查不到。實測慢 3 倍：後段不信任長報告、還是會自己再查一遍。並行度用滿。

### 反例

> **案例（lane 落在下架的文件上）**：A lane 下架的資料文件正好是 B lane 的落點——
> 兩邊各自全綠，而成果沒人用得到。柵欄只隔了「寫」，沒隔「彼此的前提」；
> 唯一叫的是一條跨 lane 的對帳守衛。跨 lane 的前提也要有閘。

## 第 12 章 fail-open 可以，靜默不行

### 原則

「失敗時退回安全值」常常是對的設計（不讓首次載入被內容擋住、
壞掉的錄影不可以弄壞一場服務）。**錯的從來不是 fail-open，是靜默**：
選擇 fail-open 的同時，必須有一個**會回非零、或畫面上擋不掉**的東西說出來。
一行沒有人讀的 log 不算。

判準：寫「失敗時退回 X」的當下，同時問——**「誰會知道它退回了？」**

### 為什麼

> **案例一**：內容驗證失敗 → 註冊骨架資料讓系統照開。內容全毀那天，
> 網站正常打開、登入正常、版本徽章正常——唯一的訊號是一行 console warn。
> 結果選擇畫面整個空的、沒有人能進場，而所有健康檢查是綠的。
> **案例二**：錄影模組故意非同步開檔（壞掉的錄影不能弄壞服務）——
> 整段時間一場都沒錄到，而 `/healthz` 說 ok。

兩個都是對的設計。錯的是沒有任何東西 fail-loud。

### 怎麼落地

1. 每一處 fail-open 配一個 fail-loud 出口：健康端點的一格欄位、
   啟動時的自我檢查、部署後置條件的一項。
2. **健康檢查要驗真的能力，不是驗設定**：「能不能寫錄影」的檢查是
   **開機真的建一個檔再刪掉**，不是讀一格「錄影目錄」設定。
3. 退回路徑要在監控上與正常路徑**長得不一樣**——「壞掉跟正常長得一模一樣」
   就是這一章要消滅的唯一敵人。

### 反例

反例是一個常見的錯誤修法：把 fail-open 改成 fail-closed（驗證失敗就整個不啟動）。
那只是把「靜默的壞」換成「大聲的癱瘓」——首次載入被擋、服務起不來。
正解永遠是 **fail-open ＋ fail-loud**，兩個一起。

## 第 13 章 註解會說謊，去驗證

### 原則

看到「已驗證」「measured」「see xxx.test.ts」「這個檔只有⋯」這類宣稱，
**先確認那個檔案真的存在、那條測試真的在跑、那個數字現在還對**。
宣稱要有出處；重要的宣稱要有守衛盯著它。

### 為什麼

> **案例一**：檔頭寫「見 xxx.test.ts，它從真實物件把數字讀回來」——那個檔案不存在。
> **案例二**：註解、抽取器、測試、文件**四層自洽地一起錯**
> （抽取器讀不到某資料來源，一個 10 秒的值被吃掉，還有一條測試把這個 bug 釘住）。
> **案例三**：規則文件寫「那顆碟只有作業系統、從頭到尾 11%」——實測它 65%、
> 只剩 33G，而且快滿的正是它。一個被散文守著的數字活過了保存期限，沒有任何東西變紅。

### 怎麼落地

1. **文件裡的關鍵數字，讓守衛去讀那一行**：一條測試真的解析文件裡的那句話、
   與程式碼裡的常數比對——文件再說謊就會紅。
2. 「規則寫在 schema 裡」不算數——要問「**那條規則在編輯發生的當下跑不跑**」。
3. **紅燈出現在合併之後，不代表合併造成它**——先去更早的 commit 重跑再歸因。
4. 自己寫註解時：能寫成守衛的宣稱就寫成守衛；寫不成的，附上日期與量測方法，
   讓下一個人有機會反駁它。

### 反例

四層自洽地一起錯（案例二）是最深的形狀：**交叉驗證失效，因為四層抄的是同一個源頭。**
對抗它的唯一方法是讓其中一層直接觸碰真實（真的跑、真的讀、真的量），
而不是互相引用。

## 第 14 章 部署協定：後置條件要驗「關係」，不驗「名詞」

### 原則

部署是**兩個獨立版本化的東西相遇的那一刻**（程式映像 × 內容資料、
服務 × schema、新版 × 線上狀態）。後置條件如果只分別檢查每一半（「名詞」），
在相容性故障面前**必然全綠**——要驗的是兩半之間的「關係」。

### 為什麼

> **案例（四項後置條件全綠而網站不能玩）**：內容與程式分開部署
> （內容是 live bind-mount，映像只在完整部署時重建）。四個新 schema tag
> 不在已部署映像的驗證 union 裡 → 內容整份載入失敗 → fail-open 退回骨架。
> 四項後置條件：內容檔的項目數✅、白名單數✅、映像版本戳✅、帳號數✅——
> **每一項驗一個名詞，沒有一項驗「這個映像能解析這份內容」**。那是配對的性質，
> 不可能由分別檢查每一半得到。

### 怎麼落地

1. **加後置條件時問：它驗的是一個名詞，還是兩個名詞的關係？**
   關係型的例子：讀服務**自己的**載入結果（映像裡的驗證器真的跑過 bind-mount 上的
   內容之後得到的登錄表）——靜態檔案伺服器會很樂意把一份解析不了的資料送出去，
   登錄表不會。
2. **部署指令只有一條**，封進腳本，腳本自驗後置條件並在失敗時回非零。
   ⛔ 不要憑記憶重打多步序列——實測把地雷寫成清單是不夠的，
   同一個人幾小時後踩中了自己清單裡的兩條。散文治不了「憑記憶重新推導一個五步序列」。
3. **煙霧測試讀「唯一的破綻」**：fail-open 系統壞掉時表面一切正常，
   唯一訊號常常是啟動 log 的一行（「載入了 N 項 via bundle」vs「falling back」）。
   ⚠️ 用全新分頁——console 緩衝跨導覽保留，舊的失敗訊息會疊在新的成功訊息上面，
   看起來像還沒修好。
4. **來源與產物都要進版控**：build 讀的是工作區，未 commit 的來源檔會被烘進
   已 commit 的產物——repo 裡出現「產物有、schema 不認、來源不存在」的組合，
   而部署走 `git pull`，線上拿到的正是它。守衛比對 `git ls-files`：
   **出貨的是 git，不是你這台機器的工作區。**
5. **資源閘要量對的那顆碟**：容器引擎報的資料目錄會說謊（實測兩次）。修法不是
   換一個寫死的路徑（那是下一次說謊），是把每一個會寫位元組的路徑都量一遍，
   **取最緊的那一顆**並指名它。閘放在 pull 之前——空間不夠時線上那版一個位元組都不動。
6. **診斷相容性故障最快的一招**：把線上正在服務的那份資料抓下來，
   用**候選版本的驗證器**逐份驗——幾十秒把「我猜部署會修好」變成部署前量到的事實。
7. ⛔ 部署指令不要接 `| head`——管道提早關閉 → SIGPIPE → 遠端腳本半路死掉留下殘骸
   （實測 80GB 快取塞爆磁碟、整站 502）。要看輸出就重導到檔案；腳本 `trap '' HUP PIPE`。
8. ⛔ 永遠不在正式站上測試；也不要為了「驗證」請 owner 自己打一場——那是把成本轉嫁。
   留下來的驗證是**機械的、幾秒鐘有答案、而且會因為這次改動而變**的那些。

### 反例

見「為什麼」的案例。它的結構值得背下來：**配對性質不可能由分別檢查每一半得到**——
這句話同時解釋了為什麼單元測試抓不到第 6 章（組合是空的）與第 7 章形態⑧
（收發兩端各自正確）。

## 第 15 章 開票規格（摘要）

> 完整規格見 `docs/開票守則.md`。這裡只收與其他各章咬合的骨架。

### 原則

**票（issue）是跨 session 的唯一長期記憶**——context 會斷、對話會被壓縮、
人會換班，只有票留下來。所以票的品質規則不是文書禮儀，是記憶的完整性協定：

1. **owner 說的話一律 `> 引言` ＋日期，逐字，不改寫。**
   沒有引言格式的句子，下一輪讀到時**預設是執行者的推測**，不是需求。
2. **收到裁決的當下就寫進票**（一行指令完成，同時落票與當日帳本兩個住處）。
   升級問題**之前**先查「他答過了嗎」。
3. 出貨數值的每一次改動，要能逐項引用到 owner 的一句原話；
   引用不到 ⇒ 它是執行者加的 ⇒ 不可以寫進 release note 的「owner 的裁決」那一節。
4. 票裡寫了「等你勾選」就真的不要自己挑。

### 為什麼

> **案例（自己的推測變成他的需求）**：owner 只說了「這個值太高了，給我三個方案」。
> 「3.5 發」這個目標是執行者自己挑的——他把它寫進票裡，幾小時後（context 斷過一輪）
> 回來讀，**分不出哪一句是 owner 說的**，於是把自己的推測當成需求引用、
> 寫進 release note、追著它調數值。owner 看到的是一個他從沒提過的數字被當成需求在追。
> 根因：**票裡兩種東西長得一樣**（他的原話與我的推測都是一段中文）。

> **案例（同一題問了三遍）**：同一個問題 owner 回答了三次以上，
> 而答案就逐字寫在執行者自己的帳本裡。根因不是「不知道要記」，
> 是**記錄的成本高於當下的注意力**——所以修法是把記錄壓到一行指令，跳過它就沒有藉口。

### 怎麼落地

- 一張票一件事；標題可搜尋；owner 原話用引言塊；執行者的分析明確標「推測／提案」。
- 「逐字」是硬要求：owner 的四個字原話可能帶著「不要新增第二個欄位」的資訊，
  摘要會弄丟它。
- release note 帶一張「逐句對票」表：從 session 紀錄**撈出** owner 期間的每一則訊息
  逐句對到票號——⛔ 不可以憑印象重寫（實測憑印象漏掉整條線，owner 當場抓到）。
  這張表同時是兩件事：對 owner 是「我沒有漏掉你說的話」的證據，
  對下一輪是唯一還讀得到的完整需求清單。

### 反例

見「為什麼」的兩個案例。它們與第 8 章的用詞紀律是同一個病：
**兩種不同權威等級的句子長得一樣，就會被混用**——修法永遠是給它們不同的格式。
