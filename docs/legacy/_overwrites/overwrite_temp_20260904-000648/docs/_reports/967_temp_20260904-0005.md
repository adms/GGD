## 二、「⭐ 有沒有可能根本不需要 cwebp？」（lane 指派要求逐條回答）

⛔ **結論：不換。留 `cwebp`，裝進映像。** 四條可以被反駁的理由：

1. ⭐ **repo 裡今天零個 JS/WASM 影像編碼器**（`sharp` / `jimp` / `@jsquash` 在全部
   `package.json` 上**零命中**）⇒ 換編碼器 ＝ **新增一個相依**，
   而 `libwebp-tools` 是 **一個 apk 套件**。
2. ⭐ **1,039 支出貨 webp 是 `cwebp -q 90 -resize 128 128` 的產物**（更正 A）。
   換編碼器 ⇒ 新舊 icon 的位元組來自兩支不同的編碼器 ⇒ ⛔ 一個**沒有守衛**的視覺漂移。
3. ⭐ **成本量過了**：runtime stage ＋`libwebp-tools` 的映像增量是
   **695,916 B ≈ 680 KiB（+1.2%）**（見四）—— ⛔ 「省一個相依」省不到值得換的量。
4. ⭐ **第一·四守則（有就用）**：`cwebp` 是既有工具鏈，
   ⛔ 而「自己生成／換一套」是第三階，要先說得出前兩階為什麼不行 —— 說不出來。

⚠️ ⭐ 反過來說，**如果哪天真的換成純 JS 編碼器**：本 lane 加的守衛會**自己紅**並說
「⛔ 掃不到任何 `execFileSync("<bin>")` ⇒ 要嘛轉檔搬家了，要嘛換了編碼器（那就刪掉這條閘）」
—— ⛔ 它不會靜靜地繼續綠。

## 三、做了什麼

### ① `docker/content-api.Dockerfile` runtime stage

```dockerfile
RUN apk add --no-cache tini libwebp-tools \
 && cwebp -version > /dev/null
```

⭐ **第二行是刻意的，⛔ 不是裝飾**：票文 Scope ② 要一條「⛔ 不可以靜默 fail-open」的自檢，
而 `/health` 那一格在**本 lane 的柵欄外**（更正 B）。
⇒ ⭐ 把 fail-loud 做在**更早、更硬**的一層：**套件改名／上游拿掉 ⇒ `docker build` 當場回非零**，
⛔ 不是等到第一次轉檔才 ENOENT，⛔ 也不是一行沒有人讀的 log。

⚠️ ⭐ 而它**比 `/health` 那一格早**：`/health` 只在服務跑起來之後才說話，
build 時的 `cwebp -version` 讓一個裝不起來的映像**根本產不出來**。
⭐ 兩者不衝突 —— `/health` 那一格仍然值得做（見七）。

### ② 守衛 `packages/shared/src/ops/contentApiCwebpInRuntimeStage.test.ts`（4 條）

⭐ **需求是推導的，⛔ 不是手寫「要裝 libwebp-tools」**：
從 icon 轉檔那條路的**出貨原始碼**（`tools/icon-gen` ＋ `packages/shared/src/content/icons`
＋ `apps/content-api/src`，⛔ 不含測試檔）掃 `execFileSync("<bin>")`，
再要求 runtime stage 裝得起那個 bin。

| 條 | 驗什麼 |
|---|---|
| 1 | ⭐ 推導**非空**（⛔ 一個推導出空集合的閘 ＝ 永遠會綠的閘，CLAUDE.md ⑨） |
| 2 | ⭐⭐ 出貨 Dockerfile 的 **runtime stage**（最後一個 `FROM` 之後）帶得起它們 ＋ 有 fail-loud 自證 |
| 3 | ⚠️ **sentinel**：合成一份「裝在 build stage」的 Dockerfile 餵進**同一支檢查器** ⇒ 必須抓到 |
| 4 | ⚠️ **sentinel**：「只裝不跑」（沒有 `cwebp -version`）⇒ 必須紅 |

⭐ **兩個方向都走**（CLAUDE.md ⑫）：
① bin → 套件（每一支被執行的外部程式都要有人裝，⛔ 表裡沒有的 bin 也要紅，不是靜默略過）
② 套件 → bin（`APK_PACKAGE_FOR` 裡**沒有人要**的列也要紅 ⇒ ⛔ 不讓那張表變墳場）。

⚠️ ⭐ **為什麼這條閘只讀檔案、⛔ 不跑 `docker build`**：前例 `composeLogCap.test.ts`
逐字寫過同一個理由 ——「CI 上不一定有 docker，而一條**環境不對就跳過**的閘等於沒有閘」。
⇒ 「`libwebp-tools` 真的提供 `cwebp`」那一半交給 **Dockerfile 自己**（`cwebp -version` 回非零）。

### ③ 突變驗證（一次，⭐ 用 `scripts/edit-or-die.py`，⛔ 不是 `python3 -c "…replace…"`）

把 `libwebp-tools` 從 runtime stage **搬到 build stage** ⇒ 守衛**紅**，訊息逐字：

> ⛔ `libwebp-tools`（提供 `cwebp`，`tools/icon-gen/convert-webp.mjs` 要用）裝在**前面的 stage**，
> 而 runtime stage（`FROM node:22-alpine`）沒有 —— ⭐ 裝錯 stage 等於沒裝

⭐ **它指名了 stage** ⇒ ⛔ 一個只 `grep libwebp-tools` 的閘會被這個突變騙過去（票文 Test 節點名的那個要求）。
還原後 `diff` 對原檔 **零差異**。

## 四、映像大小（⭐ 量過的，⛔ 不是「幾乎沒變」）

| 量法 | 數字 |
|---|---|
| ⭐ **映像增量**（同一顆 `node:22-alpine`，只差這一行；`docker image inspect .Size`） | **58,141,991 → 58,837,907 B** ＝ **+695,916 B ≈ 680 KiB（+1.2%）** |
| apk 自報 installed size | `libwebp-tools-1.6.0-r0` **395 KiB** ＋ 相依 `libwebp-1.6.0-r0` **385 KiB** ＝ **780 KiB** |

⚠️ 兩個數字不相等是正常的（apk 報的是解壓後檔案大小，映像層另有壓縮與 metadata）——
⭐ 兩者同一個量級，互相對得起來。

## 五、容器內驗證（AC#1）

```
$ docker run --rm node:22-alpine sh -c 'apk add --no-cache tini libwebp-tools && cwebp -version && which cwebp'
1.6.0
/usr/bin/cwebp
```

⭐ 驗的是**出貨 runtime stage 的那一層**（同一顆 base image、同一行 `apk add`），
⛔ **不是**完整 `docker compose --profile dev up`（那要跑 `pnpm install --frozen-lockfile`
的整棵相依樹）—— 票文 Test 節自己寫著「⛔ **不做**容器整合測試」，第零守則⑦ 同向。
