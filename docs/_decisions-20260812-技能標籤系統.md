## 1 · ⏸ 還沒決定的三件事

### 決策 1 · 互斥的**仲裁規則**放哪

| | 現況 | 提案 |
|---|---|---|
| 規則住在 | **進來的那一份效果**上（`exclusiveOnExisting`） | **互斥軸**上 |
| 後果 | A 寫 `replace`、B 寫 `reject` 兩邊都合法 → **誰贏取決於施放順序** | 同軸只有一條規則，結果與順序無關 |

**我的建議：放在軸上。**
⚠️ 這是**行為變更**（今天的順序相依會消失），所以要你點頭。
⭐ 但今天的實際風險是 0：`exclusiveGroup` 在 **2,035 份出貨內容裡採用率是 0** ——
機制做好了、schema 收得下、測試綠的，**沒有一份內容在用**。
⇒ 現在改沒有既有內容會被影響，晚改就會有。

### 決策 2 · **互斥軸的清單**是推導還是手寫

- **推導**（我的建議）—— 第〇·五守則：對外能力清單 ⛔ 不可以手寫。
  同一個 repo 已經有一份手寫的 `SIM_CAPABILITIES`，它的檔頭自己記錄了它撒過兩次謊。
- **手寫** —— 便宜一輪，但外部編輯器看不到我們的 registry，**沒辦法發現我們在說謊**。

成本差：推導要多做一支導出器（≈一輪）。

### 決策 3 · 順序：先做 18 個低風險標籤，還是先做交互模型

⭐ **我的建議：先做 18 個。** 23 個 blocked 按**交互風險**重切（不是按 group）：

| | 幾個 | 風險 | 可以現在做嗎 |
|---|---:|---|---|
| **事件標籤**（升級時／回合勝負／購買道具／進入範圍時…） | 13 | **零** —— 兩個事件同時發生不會打架 | ✅ |
| **條件標籤**（對 BOSS／靜止 N 秒／附近敵人達 N 人…） | 5 | **零** —— 條件是純查詢，不寫狀態 | ✅ |
| **【每回合只發動一次】** | 1 | ⚠️ 它**不是事件**，是掛在別的事件上的節流器 | → 做成每個 hook 的**一格欄位** |
| **效果標籤**（牆／環繞衛星／魔力耗盡／韌性） | 4 | **高** —— 見第 2 節，owner 已裁 | 見下 |

**＝ 23 個裡 18 個交互風險是零**，可以照第零守則⑨ 用
「一個發射介面 + 18 格參數表」批次做，⛔ 不必等交互模型。

## 3 · 交互模型的形狀（決策 1/2 通過後才動）

⛔ **配對表是死路**：139 個標籤 = **9,591 對**；做完 23 個 blocked = 162 個 = **13,041 對**，
而且每加一個新標籤要新填 ~160 格。那是第零守則⑨要擋的 N 輪。

⭐ 改成**三根軸，交互用算的** —— 新增一個標籤的成本從「填 160 格」變成「填 3 格」：

| 軸 | 回答什麼 | 現況 |
|---|---|---|
| **通道** channel | 兩份同時在 → 怎麼合併（相加／相乘／取最大／只留一份） | 半有：`ModOp.Flat`/`PercentAdd`/`PercentMult` 已經是通道，但**標籤層看不到** |
| **互斥軸** axis | 能不能同時存在、同軸誰贏 | 有原語但是**自由字串**（打錯字＝互斥靜默消失，沒有東西會叫），且仲裁規則位置錯（決策 1） |
| **管線階段** stage | 誰先算 → 決定 A 影不影響 B | ⚠️ 第三類交互。實例：manifest 自己的 notes 寫【破甲】【破防】【破魔】是「**屬性無效、但狀態掛得上而且條件查得到**」—— 既不是互斥也不是疊加 |

### 三道閘（成本低，現在下都會綠 ＝「趁門還關著先上鎖」）

1. `exclusiveGroup` / `stackKey` 改成**登錄表 enum** → 打錯字在 `content:build` 就紅
2. **跨文件同 `stackKey` 但數值不同 → 紅**（今天 **0** 個，鎖在 0）
   ⚠️ 這個危險是真的：`applyBuff.ts:69-71` 自己的註解寫「同 key 第二發沿用**第一份**的
   modifiers」⇒ 兩支技能共用一個 key，**第二支的數值會被靜默丟掉**
3. `ggd-tag-interactions@1` 導出檔 + **兩個方向**的守衛（宣告有其實沒有／宣告沒有其實有）
