## ⭐⭐ 頭條：每個戰鬥場景省 **26.7 – 48.0 MB**

KayKit 的 `dungeon_texture`（**一張 15.4 KB 的 1024² PNG**）被內嵌進
**12 份出貨 prop**，而預算工具**各算 5.33 MB**。

Babylon **有** URL 去重（命中就完全不上傳），⛔ 但 glTF 載入器餵的 URL 是
`data:${rootUrl}${fileName}#image${index}` ⇒ ⭐ **結構上命中不了**。

⚠️ 而接下來發生的事才是重點：
**預算工具把這個缺陷寫進成本模型 → 用一句像物理定律的註解守著 → 棘輪再把高估收成「已接受」→ 一路長到 20 筆。**

| | 量到的 |
|---|---|
| 每個戰鬥場景省下的 VRAM | **26.7 – 48.0 MB**（分母 13 個 scene 列） |
| 第一回合貼圖上傳次數 | **9–26 → 5–18**（每場省 1–9 次 1024² 上傳） |
| 48 MB 閘 | 13 筆越界 ⇒ **11 筆回到閘內**（`combat-skeleton` 54.0 → **27.4**） |

⇒ ⛔ 而 #382 票上提的「地標 scenery 換分母」**一筆都修不到** ——
分母只影響 6 筆 model 列，越界的 13 筆**全是 scene 列**。建議撤掉那條驗收條件。

剩兩筆是**真債**要你勾：`combat-heavens-arena` 52.9 MB（單件 16 MB 的 2048² 旗幟）·
`champ-select` 81 MB（1,061 張 UI 圖示，與模型無關）。

## ⭐ 一把只驗過**單邊**的尺，不算自證過

那條 lane 的第一版量尺量 `getLoadedTexturesCache().length` ——
⛔ 而 `NullEngine._releaseTexture(texture) { }` **是空的**，清單永遠不變短
⇒ ⭐ 「去重生效」與「沒生效」**量起來一模一樣**。

⚠️ ⭐ **而校準當時是綠的** —— 它只驗了「應該多」那一邊。

⇒ 已寫進守則：`calibrate()` 要驗**兩個方向**。
> 一把單邊校準的尺會**在它最需要說話的時候沉默**：
> 它證明得了「東西在」，⛔ 證明不了「東西不在」——
> ⭐ 而效能/可見性這一族，缺陷通常長成後者。
