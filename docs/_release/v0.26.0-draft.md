### ⭐ 客戶端／伺服器移動速度**終於一致**（#616）

> owner：「客戶端移動還是**非常不順 常常有回溯**的部分 是不是**移動速度客戶端跟伺服器端
>  其實不匹配**？」+「尤其是**後來新地圖大小有變化** 可能是移動量測的公式有落差」

⭐ **他問對了，而且不匹配的地方比一處多。** 伺服器的移速是一條**鏈**
（`fixed("moveSpeed")` → `byAttackType(近戰 ×0.8 / 遠程 ×0.6)`），而客戶端的影子
**只乘了第一格** ⇒ 影子比本體快 **25%（近戰）／67%（遠程）** ⇒ 每一次校正都是一次回溯。

⇒ 抽出 `predictedStats.ts` 讓兩邊走**同一支** `finalizeStat`，⛔ 而不是客戶端再抄一份公式。
守衛 `moveSpeedParity.test.ts` 對近戰與遠程各驗一次（含一條「兩個倍率真的不同」的對照組）。

⚠️ **地圖大小那一半量過了 —— ⛔ 不是原因。** 但同一輪對帳又挖出**另外五層**只在
伺服器套用的東西，一併修掉（見 #616）。

### 🐌 「到第七回合就很難動作」找到元兇了（#620）

> owner：「這版改完還是LAG 一定有地方有問題, **到第七回合就很難動作**」

⭐ **第七回合這個數字不是巧合**：`mobWaves.schedule` 在 R7 跳到每區 30 隻 × 2 區
= **60 隻同時活著**（R3–R5 是 30、R6 是 40）。

⛔ 而那 60 條血條**每一幀都在重跑整棵 React** —— `sameSpecs` 比的是螢幕座標與血量，
而那三樣**每一幀都在變**。檔頭逐字寫著「只有在這一幀的規格真的變了才 setState」，
⚠️ 那句話對**移動中**的目標從來就是假的。

⇒ 拆兩層：React 只管「誰在場」，位置與血量改由 rAF **直寫 DOM**（`transform`，
⛔ 不是 `left/top`，後者每一條都逼一次 layout）。
守衛用 `React.Profiler` **數 commit 次數** —— ⛔ 只看 DOM 抓不到這個缺陷。

### 🔵 地上那一堆亮藍色圈圈（#617）

> owner：「地上常出現**一堆亮藍色往外擴散的圈圈特效** 應該不是 w3x 原始特效⋯
>  **我感覺是硬加的 太亮太搶眼不好看**」
> ＋「散開**速度感要夠快**、**半透明淡出更快衰減**，這樣才會有**力量感**，
>  目前**太慢存活時間也太長**（0.8秒內，根據**傷害五級距越大速度越快**）」

⭐ **他兩件都說對了**：它是一顆烘在 TS 裡的 `CreateTorus`，⛔ 不是任何一份 vfx 文件、
⛔ 不在任何 w3x 綁定表 ⇒ **結構上不可能有原作對應**；而 `disableLighting` + emissive
⇒ 不吃場景光，在哪都一樣刺眼；而它**每一次魔法傷害各一發**。

| 後台格 | 出貨 | 治什麼 |
|---|---|---|
| `impactRingAlpha` | 0.35 | 太亮太搶眼 |
| `impactRingRadius` | 1 | ⛔ **不縮**（力量感需要射程） |
| `impactRingLife` | 0.55 | 太慢 · 存活太長 |
| `impactRingFadePow` | 3 | 半透明淡出更快衰減 |
| `impactRingMaxLifeSec` | 0.8 | ⛔ 硬天花板（逐字「0.8秒內」） |
| `impactRingTierSpeed` | 1.8 | 五級距越大越快 |

⇒ 240ms → 極小 **132ms** / 極大 **73ms**；擴散 **1.8〜3.3 倍快**。全部轉回 1 = 回到今天之前。

⛔ 這裡最容易做錯的一步是**把環縮小** —— 擴散速度 = 半徑 ÷ 壽命，縮半徑會**再慢一次**。

## 🚨 部署風險（⛔ 這一項比上面全部都重要）

### 磁碟閘在看一顆**不會滿的碟**（#618）

```
DockerRootDir = /data/docker  →  /data (sdb)   剩 291G   ⇐ 閘量的是這顆
/var/lib/containerd = 57G     →  /    (sda1)   剩  33G   ⇐ 會滿的是這顆（已用 65%）
```

Docker 29 用 **containerd image store** ⇒ 位元組住 `/var/lib/containerd`。
⇒ 閘**每一次都綠**。⚠️ 這正是 2026-08-16 那次 **502** 的形狀 —— **同一支腳本、第二次**。

⇒ 修法是**不要猜**：把每一個 docker 會寫的路徑都量一遍，取**最緊的那一顆**。

## 🧮 平衡：AP 自洽複驗（#616）—— ⛔ 我推翻我自己三個結論

> owner：「你的公式有算上 **AP加成額外技能傷害**嗎，以及**每等級+1AP的基礎提升**，
>  如果沒有你不是真的自洽，而**這些都不是系統倍率**」

派了一輪對抗複驗。量測全部重現得出來，**但兩個「最重要的一格」站不住**：

1. ⛔ 「三個錨點的 ❌ 是漏算 AP」—— **我選錯了參考級距**。出貨主流是**小（500，77%）**
   不是極小（200，8.3%），而**一個 AP 項都不算**，三個錨點就已經全部 ✅。
2. ⛔ 「缺口先擴大後收斂，頂點在 LV169」—— `levelCap = 99`，而我掃到 LV400。
   逐級實測：**在玩家碰得到的整個範圍內是單調擴大的，沒有收斂**。
3. ⛔ 「41.7%/3.0%/14× 是舊 config 算的」—— 四種組合都跑過，**沒有一種重現得出來**。

⚠️ 而 owner 那句「這些都不是系統倍率」**只對三分之二**：AP 的**量**本身有
`intToAbilityPower` 撐著（LV30 佔 **53%**）⇒ 把 AP 直接帶進推導鏈 = 把系統倍率帶進去。

🆕 順帶挖到三個**沒有閘**的缺口：`echoloop:check` 38 格只看得見 **2 格**（`baseHp`
是從文件正則讀出來的常數，換 env 不重算）· `owner-knobs.json` 只覆蓋 **12/38** ·
**相稱性只有下限沒有上限**（83.9% 的節點不遵守級距梯子，最大 2.5×）。
